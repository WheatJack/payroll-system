# 后端架构评审 01

> 评审对象：`docs/详细设计.md` v0.1（2026-11-26）、`db/schema-mysql.sql`、`pom.xml`、`src/main/resources/application.yml`、`src/main/java/com/insbean/payroll/` 骨架
> 评审角色：后端架构师
> 前提：C1–C10 视为已确认，不质疑前提本身；只在前提内部找漏洞。
> 分级：**P0** = 设计与数据模型层面的错误，不解决就按现在的结构开工，会写出"静默算错钱"的代码；**P1** = MVP 上线前必须补齐；**P2** = 可排期。

## 结论摘要

| 级别 | 条数 | 主要落在 |
|---|---|---|
| P0 | 8 | 唯一键与幂等实现冲突（L3 被绕过）、期间状态机无守卫、`compiled_by` 缺失、生成事务边界、导入幂等、区间重叠、重跑覆盖手工数据、domain 边界不可强制 |
| P1 | 12 | 合计语义、记录级并发、汇总一致性、API 缺口、字典可变性、导入落库边界、计薪资格、主体归属校验、密钥生命周期、数据范围机制、期间生命周期、主体上下文 |
| P2 | 10 | 文档内部矛盾、种子数据、审计噪声、历史数据范围、认证、导出、冗余字段、精度、工龄口径、软删除与唯一索引 |

一句话：**数据模型的分寸感是好的（金额字符串、`active_key` NULL 技巧、按主体拆期间都站得住），但"哪些不变量由数据库兜底"这条原则只在可写成唯一索引的地方被执行，其余地方（区间、状态、职责分离、主体归属）退化成了文字承诺，而编排放大量依赖这些没有兜底的不变量。**

# 一、P0（不解决不能开工）

## P0-1 L3 唯一索引 + `ON DUPLICATE KEY UPDATE` 会把其他主体的记录静默改写

**问题**
§4.2 规定批量生成用 `INSERT ... ON DUPLICATE KEY UPDATE` 保证幂等；而 `pay_record` 的唯一键是 `uk_emp_ym_active (employee_id, period_ym, active_key)`。这个键的冲突有两种含义完全相反的原因：

1. 同一期间重跑（期望：更新本期自己那条）；
2. **另一主体本月已有该员工的记录**（期望：报错，拒绝写入）。

`ON DUPLICATE KEY UPDATE` 不区分这两者。命中第 2 种时，它会把上海那条记录的 `company_id / period_id / dept_id / emp_name` 改成北京的，把上海工资表里的这个人"搬走"。唯一键仍然只有一条，全程没有异常，L3 防线被"幂等实现"自己绕过。

**为什么是问题**
这是目前设计里唯一一条能**同时**让"重复发放校验失效"和"跨主体数据被篡改"的路径，触发点是最常用的「生成」按钮，且结果不可观测：没有错误行，没有异常日志，只有一份金额对不上但条数正常的工资表。财务要等到与上月对比时才会发现。

**位置**
`docs/详细设计.md` §4.2 配套第 1 条（"批量生成幂等"）；`db/schema-mysql.sql:283`（`uk_emp_ym_active`）、`:284`（`idx_period_emp` 目前是非唯一索引）；`common/GlobalExceptionHandler.java:39`（只识别 `uk_emp_ym_active` 一个键名）。

**修复建议**

1. 把 `idx_period_emp (period_id, employee_id)` 升级为 `UNIQUE KEY uk_period_emp (period_id, employee_id)`。本期重跑的幂等冲突由它承担，`ON DUPLICATE KEY UPDATE` 从此只可能命中本期自己的行。
2. `uk_emp_ym_active` 退化为**纯跨主体守卫，不参与 upsert**。写入单条记录的正确顺序：
   ```sql
   SELECT id, period_id, company_id FROM pay_record
    WHERE employee_id = ? AND period_ym = ? AND deleted = 0;
   -- 命中且 period_id = 本期  -> UPDATE（重跑）
   -- 命中且 period_id <> 本期 -> 该员工记为失败，回查 company 名，报"已在『XX分公司』发放"
   -- 未命中                    -> INSERT（由 uk_emp_ym_active 兜住真正并发）
   ```
   2000 人规模下一次 `IN (...)` 预查即可，不要逐条查。
3. `GlobalExceptionHandler` 增加 `uk_period_emp` 分支；两条错误文案必须可区分："本期该员工已存在（请使用重跑）" vs "该员工本月已在其他主体发放"。
4. 不要用"在 ODKU 里写 `IF(period_id=VALUES(...), id, 故意制造冲突)`"这类技巧，可读性和可移植性都会崩。

## P0-2 「编制人 ≠ 锁定人」没有任何字段支撑，C4 的内控规则无法落地

**问题**
§4.6 与 §4.7(3) 都把"编制人 ≠ 锁定人"列为**代码硬校验**。但 `pay_period` 只有 `created_by`（建期间的人，可能是系统或代办）和 `updated_by`（最后一次写，锁定动作本身就会覆盖它）。没有任何字段记录"谁编制了本期工资表"。

**为什么是问题**
C4 把审批挪到系统外，系统内就只剩这一条职责分离保障。不实现 = 同一个人可以自己编、自己锁，C4 的补偿设计整体失效；而事后审计回答不了"这一期是谁编制的"，`unlock` 追责时也找不到对象。这不是可选的加分项，是 C4 写进设计里的硬约束。

**位置**
§4.6 末尾 C4 段；§4.7(3) 第一条；`db/schema-mysql.sql:209-228`（`pay_period` 无 `compiled_by`）；§5.3 `POST /periods/{id}/lock`。

**修复建议**

1. `pay_period` 增加 `compiled_by BIGINT NULL`、`compiled_at DATETIME NULL`。
2. 写入时机：generate、import commit、记录明细编辑、单条重算，**任何一次产生或修改本期核算数据的操作**，若 `compiled_by IS NULL` 则置为当前用户；若已有值且不是当前用户，**不覆盖**（记住首位编制人）。锁定/解锁不得修改这两列。
3. 锁定时把校验下推到 SQL，而不是只在 service 里 if 一下：
   ```sql
   UPDATE pay_period
      SET status='LOCKED', locked_by=?, locked_at=NOW()
    WHERE id=? AND status='EDITING'
      AND (compiled_by IS NULL OR compiled_by <> ?);
   ```
   `affected = 0` 时再查一次当前行，区分"状态不是 EDITING"和"你不能锁定自己编制的一期"，给出不同文案。
4. 多人编制时语义要定：推荐"锁定人不得等于首位编制人"；若业务要求"不得等于任一编制人"，需要 `pay_period_operator(period_id, user_id, role)` 明细表，成本更高，须业务确认后再建。
5. 补 `GET /periods/{id}` 详情接口，返回 `compiled_by/compiled_at/locked_by/locked_at/unlock_reason`（当前 §5.3 完全没有期间详情接口，前端拿不到这些字段）。

## P0-3 期间状态机只有一句"校验状态并加行锁"，没有方案；分批提交与行锁在结构上互相矛盾

**问题**
§4.6 只写了"所有写接口进入前校验期间状态并加行锁，不能只靠前端禁用"，没有说明：谁拿锁、锁持有多久、分批提交之间锁是否还在。而 §6 要求生成/导入"分批提交（500 条/批），不用单一大事务"。两者放在一起，三种可能的实现全部有洞：

| 可能的实现 | 后果 |
|---|---|
| 每批一个事务、各自 `SELECT ... FOR UPDATE` | 第 1 批提交即释放锁；窗口期内别人可以开始第二次生成、或把期间锁定。后续批次会写进已锁定期间 |
| 整个生成持有一个大事务以独占期间行 | 直接违反 §6 的分批要求；2000 人 × ~10 项在单事务里长时间持有期间行锁，且回滚代价巨大 |
| 只在入口 `SELECT` 一次状态，不加锁 | 两人同时点生成都能通过校验，两次生成交错执行，最终金额取决于批次交错顺序，不报任何错 |

**为什么是问题**
这是整个系统的写路径地基。守卫不成立，"锁定后不可写"就是纸面承诺；而 §4.6 自己声明"锁定是数据库层面的约束"，实际连"哪个 SQL 语句"都没写，实现者一定会选第 3 种（最省事）。

**位置**
§4.6「锁定是数据库层面的约束」段；§6 事务行；§5.3 全部写接口；`db/schema-mysql.sql:221`（`version` 声明为乐观锁，但全文没有任何接口使用它）。

**修复建议**（按操作时长分成两类，不要用同一种锁）

1. **短事务**（锁定、解锁、单条编辑、单批导入提交）：事务内**第一条**语句执行
   ```sql
   SELECT status, version, generation_token FROM pay_period WHERE id = ? FOR UPDATE;
   ```
   校验 `status` 后写数据，提交即释放。必须写成 `FOR UPDATE`，必须与后续写同一个 `@Transactional` 同一个连接，不能是 `@Transactional(readOnly=true)` 之外的预检。这才是"加行锁"的正确落法。
2. **长任务**（生成）：不要在数据库事务里持锁，改用**期间租赁**：
   ```sql
   ALTER TABLE pay_period
     ADD generation_token CHAR(36) NULL,
     ADD generation_at    DATETIME NULL;
   ```
   获取：
   ```sql
   UPDATE pay_period SET generation_token=?, generation_at=NOW()
    WHERE id=? AND status IN ('DRAFT','EDITING')
      AND (generation_token IS NULL OR generation_at < NOW() - INTERVAL 30 MINUTE);
   ```
   `affected=1` 才算拿到。每批开始前用 `WHERE generation_token=?` 续租并**重新校验 status**；正常/异常/超时都释放。
3. **锁定必须拒租**：`POST /periods/{id}/lock` 的 WHERE 要加 `AND generation_token IS NULL`。否则"生成到一半被锁定，剩余批次继续往 LOCKED 期间写"——这是分批提交引入的、单事务方案里根本不存在的新竞态，必须显式处理。
4. `version` 与 `FOR UPDATE` 二选一，不要都留着不用。推荐短事务用行锁，`version` 只保留给"期间列表并发展示"或直接删掉。
5. 把守卫收敛成唯一入口：`period` / `run` / `record` / `importjob` 四个模块的**所有**写操作都必须先调用同一个 `PeriodGuard.requireEditable(periodId)`（内部就是第 1 条的 `FOR UPDATE`），并加一条 ArchUnit 规则禁止绕过。少一条写路径，锁定就是纸糊的。

## P0-4 生成是分批提交，但没有 `run_id`、没有失败恢复、异步线程失控

**问题**
§4.3 ⑦「分批 upsert，每 500 条 flush」、§5.3 `/generate` 异步返回 runId、`pay_run` 有 `emp_failed / error_msg`，但是：

- `pay_record` 没有 `run_id`；
- `pay_run` 失败后没有任何恢复/补偿协议；
- `@EnableAsync` 且未定义执行器，Spring Boot 默认 `applicationTaskExecutor` 的 `maxSize=Integer.MAX_VALUE`、队列无界，并发生成既不排队也不拒绝。

**为什么是问题**（三条可复现的后果）

1. 第 7 批失败：前 6 批（3000 条）已提交，期间已进入 `EDITING`，而 §4.6 只在 `DRAFT` 允许删除，且 `pay_period` 根本没有 `deleted` 列（见 P1-11）。于是既删不掉、也没有 `run_id` 能定位"哪些行是这次失败任务写的"，清理只能靠人工 SQL。
2. 进程重启（内网单机部署，发布、断电、OOM 都会发生）：`pay_run` 永远停在 `RUNNING`，如果按 P0-3 实现了租赁，则期间被租 30 分钟；用户看到"生成中"，再点一次被拒，除了等没有出路。当前没有任何启动补偿。
3. 三个人同时点三个主体的生成 = 三个无上限长任务共用 Hikari 的 20 个连接，且互相不知道对方存在。

**位置**
§4.3 ⑦；§5.3 `POST /periods/{id}/generate`、`GET /runs/{runId}`；`PayrollApplication.java:8`；`db/schema-mysql.sql:230-247`（`pay_run`）、`:249-288`（`pay_record` 无 `run_id`）。

**修复建议**

1. `pay_record` 增加 `last_run_id BIGINT NULL` + `KEY idx_last_run (last_run_id)`。它一次解决三件事：失败清理（按 run 定位）、批次溯源、`pay_run.emp_success/emp_failed` 由它 `COUNT` 派生（递增计数在崩溃时必然错）。
2. 生成改为**三阶段**，用阶段划分消解"分批提交 vs 整体原子"的矛盾：
   - **预校验（只读）**：批量加载在职员工、档案、字典，算出全部"预期失败"清单（跨主体冲突、档案缺失、资格不符），写入 `pay_run_error`（见 P1-4）；此时不写一条 `pay_record`。
   - **分批写入**：只写通过预校验的员工，每批 500 条**要么全成要么整批回滚并中止本次 run**。因为预期失败已在阶段 1 剔除，批次里再出现员工级失败只可能是真异常，中止是正确反应。
   - **收尾**：写 run 终态、刷新期间统计（P1-3）、释放租赁。
3. 明确"重跑契约"：本次 run 失败时已写入的行**保留**，用户可再次生成——因为幂等键是 `uk_period_emp`（P0-1），重跑是 UPDATE 而不是新增。这条契约必须写进设计，它是分批提交可以被接受的前提。
4. 启动补偿（`ApplicationRunner`）：
   ```sql
   UPDATE pay_run SET status='FAILED', error_msg='进程重启中断', finished_at=NOW() WHERE status='RUNNING';
   UPDATE pay_period SET generation_token=NULL WHERE generation_token IS NOT NULL;  -- 单实例部署可全清
   ```
5. 定义专用 `ThreadPoolTaskExecutor`（core=1, max=2, queue=20，拒绝时抛 `BizException("当前有核算任务在执行")`），不要复用默认执行器。
6. `@Async` 拿不到 `SecurityContextHolder`（默认 `MODE_THREADLOCAL`）。当期主体范围、操作人必须在**派发前**解析好并作为参数传入异步方法；否则审计记录的 operator 会是空或串人。或者注册 `DelegatingSecurityContextAsyncTaskExecutor`。

## P0-5 导入幂等是"先查 hash 再提交"，存在 TOCTOU；`APPEND` 模式与 C2/C3 直接冲突

**问题 A：幂等判定有竞态**
§4.5：「上传 → 计算 hash → 命中已提交批次则直接拒绝」。`pay_import_batch.file_hash` 只有普通索引 `idx_file_hash`（`schema:330`）。两人几乎同时提交同一文件：双方都查不到"已提交"批次，双方都提交成功。`UPSERT` 模式侥幸幂等，`APPEND` 模式把每个人的金额加两遍。

**问题 B：`APPEND` 在语义上就是系统内补发**
`import_mode` 提供 `APPEND`（有则累加）。但 C2 明确变动项导入的是**工资金额**（绝对数，不是增量），C3 明确不做补发/扣回。对绝对金额做"累加"，等价于"再发一次"，这既是 C3 禁止的补发，也绕开了 L1（文件内重复）与 L2/L3（每人每月一条）的全部防线——因为累加发生在一条已存在的合法记录上，唯一索引永远不会被触发。

**为什么是问题**
导入是财务每月的日常动作，重复提交/交错提交是现实中最常见的操作失误。`APPEND` 给了这个失误一个"不报错、金额翻倍"的出口，而且事后只能靠人工逐行核对修正（C3 下没有补回机制）。

**位置**
§4.5 导入模式与幂等两段；`db/schema-mysql.sql:318`（`file_hash`）、`:320`（`import_mode`）、`:330`（`idx_file_hash` 非唯一）。

**修复建议**

1. 改为**以插入批次行为幂等第一步**，不再"先查后插"：
   ```sql
   UNIQUE KEY uk_period_file (period_id, biz_type, file_hash)   -- 替换 idx_file_hash
   ```
   范围必须是 `(period_id, biz_type, file_hash)` 而非全局 `file_hash`：同一份文件合法地导进不同期间、或在 FIXED/VARIABLE 两种模板下各用一次是合理的。`POST /import/validate` 第一条 SQL 就是插批次行（`status=VALIDATING`）；撞键即返回"该文件已提交或正在处理"。
2. MVP **删除 `APPEND`**，只保留 `UPSERT`（默认）。若保留 `INSERT_ONLY`，其"跳过"必须在回显中逐行列出"该员工该科目已有值 X，本次值 Y，已跳过"，否则用户会默认生效。
3. 更符合 C2 的做法是把提交做成**差异确认**：预校验回显对每个变化单元格展示 `原值 → 新值`，用户确认后 UPSERT，并在审计中逐条记录 item 级变更（见 P1-2）。金额是绝对数，这个模型天然幂等、天然可审。
4. `pay_import_batch` 补 `committed_by`（提交人；提交时刻用已有的 `finished_at`）：预校验人与提交人可能不是同一个人（§4.5 的流程本身就分了两个动作）。

## P0-6 薪酬档案区间不重叠没有真正的兜底；并发调薪会产生两个开口区间

**问题**
§4.1 写「区间不重叠由应用层校验 + `uk(employee_id, effective_from)` 兜底」。但该唯一键只能阻止两条**起止日期完全相同**的区间。MySQL 8 没有 exclusion constraint，`[2025-01-01, 2025-12-31]` 与 `[2025-06-01, NULL]` 的重叠它完全拦不住。所以这不是"兜底"，只是"同一生效日不能两条"。

并发路径（调薪 = 读当前开口区间 → 截断 `effective_to` → 插入新区间）：
```
A、B 同时读到 [2025-01-01, NULL]
A 截断为 2025-06-30，插入 [2025-07-01, NULL]
B 用同一条旧行截断为 2025-05-31，插入 [2025-06-01, NULL]
=> 两条 effective_to IS NULL 的区间
```
§4.1 的取数规则 `effective_from <= 末日 AND (effective_to IS NULL OR effective_to >= 末日)` 此时返回**两行**。若实现用 `LIMIT 1` 或"取 id 最小的"，2025-07 以后会静默取到 06-01 那条，基本工资错误。

**为什么是问题**
§4.1 自己强调"基本工资是加班费、经济补偿金的法定计算基数"。基数静默取错，等于后续所有法定金额都错，而且没有任何异常可以追溯。更糟的是设计文档把它标成了"已兜底"，评审者/测试者不会再检查这里。

**位置**
§4.1「取数规则」与「区间不重叠由…兜底」；`db/schema-mysql.sql:163`（`uk_emp_effective`）；§5.1 `PUT /comp-profiles/{id}`。

**修复建议**（用系统自己已经在用的 NULL 技巧，不要引入新机制）

1. 封住"每人最多一个开口区间"：
   ```sql
   open_key BIGINT AS (IF(effective_to IS NULL AND deleted = 0, employee_id, NULL)) STORED,
   UNIQUE KEY uk_emp_open (open_key)
   ```
   插入新开口区间前必须先截断旧区间——顺序颠倒会直接撞唯一键，这正是想要的效果。这个写法和 `pay_record.active_key` 是同一个模式，团队已经理解。
2. 更彻底（推荐长期方向）：不存 `effective_to`，只存 `effective_from`，区间由 `ORDER BY effective_from` 后 `LEAD()` 推导。无重叠、无空洞由构造保证，不需要任何校验。代价是取数 SQL 变复杂。
3. 无论是否改表，写入事务内必须 `SELECT ... FROM emp_comp_profile WHERE employee_id = ? ORDER BY effective_from FOR UPDATE`，把同一员工的调薪串行化。
4. 取数改为**断言恰好一行**：查到 0 行或 ≥2 行都抛出带 `employee_id` + 期间的错误。静默取错比报错危险一个数量级。
5. 保留 `uk(employee_id, effective_from)` 作为"同一天不能两条"的补充，但文档里不要把它描述成"兜底不重叠"。

## P0-7 重跑生成会覆盖人工编辑：`source` 的合并语义没有定义

**问题**
§4.6 允许 `EDITING` 状态下再次"生成"，§4.3 生成写 FIXED（来自档案）与 COMPUTED（重算）。但全文没有说明：重新生成时已存在的 IMPORT/MANUAL 明细（绩效、加班、扣款）是否保留？记录级 `gross_amount / deduction_amount / net_amount` 是否重算？

**为什么是问题**
两种最自然的实现都错，且都不报错：

- **先删明细再重建**：一次重跑抹掉全公司手工录入的绩效奖金。用户唯一的线索是"金额变了"。
- **只 upsert FIXED/COMPUTED、不动其他、也不重算合计**：`gross/deduction/net` 停留在旧值，与明细不符，直接违反 §4.4 金额铁律，并一路带进锁定、汇总、年报。

**位置**
§4.3 ②–⑦；§4.6 `EDITING` 允许生成；`db/schema-mysql.sql:300`（`pay_record_item.source`）。

**修复建议**

1. 把合并规则写死进设计并落到代码：生成只允许改写 `source IN ('FIXED','COMPUTED')` 的明细；`source IN ('IMPORT','MANUAL')` **一律不动**。
2. 金额合计只能有一个实现。建一个 `RecordTotalizer.recompute(recordId)`，由**生成收尾、明细编辑、导入提交、单条重算**四个入口统一调用，重算并回写 `gross/deduction/net`。§4.4 的"合计 = 明细加总"如果有第二处实现，迟早分叉。
3. 生成时若本期已存在 IMPORT/MANUAL 明细，run 结果要明确回显"N 条手工/导入明细已保留"，并在 UI 给出前后差异，不要静默。
4. 若业务真正想要的是"重跑 = 全部推倒重来"，那是另一个动作：单开 `POST /periods/{id}/reset`（见 P1-4），语义与"生成"分开。一个接口不要承担两种意图。

## P0-8 `domain` 层"不依赖 Spring"目前只是一句注释，没有任何强制手段；计算契约也未定义

**问题**
§2.1 声明"`domain` 包不依赖 Spring 容器，可脱离数据库直接单元测试；这是核算正确性能被验证的前提"。但：

- 只有**一个 Maven 模块**，`domain.payroll` 只是一个包名，编译期没有任何东西阻止它 `import com.baomidou.mybatisplus.*` 或 `org.springframework.*`；
- `common` 包里混着 Spring-free 的 `Result/BizException` 与 Spring AOP 的"审计切面、权限注解"，所以 `domain` 连 `common` 都不能依赖，而这个边界没写；
- `ItemCalculator` 只有一句话"每个 COMPUTED 科目一个实现"，没有签名、没有输入类型、没有输出类型、没有"谁负责算合计"。

**为什么是问题**
架构评审的第一问不是"分层图好不好看"，而是"约束能不能被执行"。现状下：开发者写第一个计算器时最省事的路径就是 `@Autowired PayItemMapper` 然后直接查字典——一次破例之后，边界就不存在了。而"可脱离数据库测试"正是这套设计用来证明"钱算得对"的唯一手段，丢了它，剩下的只有端到端对账。

具体后果：`domain` 一旦依赖 MP 实体，所有单元测试都要构造 `EmpEmployee`（带 `@TableName`、逻辑删除字段），实体改一次字段所有用例陪跑；"纯函数"再也没法用 property-based 测试批量验证。

**位置**
§2.1「关键约束」；§2.2 包结构（`common` 与 `domain.payroll` 的依赖关系未定义）；§4.3「计算策略接口」；`pom.xml`（单模块）。

**修复建议**

1. **拆 `common`**：`common` 只放 Spring-free 的东西（`Result`、`BizException`、金额工具）；把审计切面、权限注解、`@RestControllerAdvice` 移到 `web` / `security`。否则 `domain` 无法复用任何 common 类型。
2. **定义计算契约**（`domain.payroll.model`，全部是无注解 record）：
   ```java
   record PeriodContext(String periodYm, LocalDate periodEnd, BigDecimal hpd)
   record EmployeeSnapshot(long employeeId, String empNo, long companyId, long deptId,
                           LocalDate hireDate, LocalDate workStartDate, int status)
   record ProfileSegment(LocalDate from, LocalDate to, BigDecimal baseSalary,
                         Map<String, BigDecimal> fixedItems)
   record ItemDef(String code, String name, Category category, Direction direction,
                  boolean includeInGross, int scale, int sortNo)
   record PayLine(String itemCode, Direction direction, BigDecimal amount, Source source, int scale)
   record CalcInput(PeriodContext period, EmployeeSnapshot emp, ProfileSegment profile,
                    List<ItemDef> dictionary, List<PayLine> importedLines)
   record CalcOutput(List<PayLine> lines, BigDecimal gross, BigDecimal deduction,
                     BigDecimal net, List<CalcWarning> warnings)
   ```
   `domain` 只依赖 JDK；字典、`hpd`、期间末日全部**作为输入传入**，内部禁止 `LocalDate.now()`、禁止读库、禁止读配置。
3. **强制手段二选一**（推荐第 1 个）：
   - ArchUnit 测试（一个文件，成本最低）：
     ```java
     noClasses().that().resideInAPackage("..domain.payroll..")
       .should().dependOnClassesThat()
       .resideInAnyPackage("org.springframework..", "com.baomidou..", "jakarta..");
     ```
   - 或多模块 Maven（`payroll-domain` 的 pom 不引 Spring/MyBatis），编译期强制。2000 人单体，多模块收益不大，ArchUnit 足够。
4. 把 §2.1 的"关键约束"改写成"由 `DomainPurityTest` 强制，违反即构建失败"，从文档承诺变成可执行断言。

# 二、P1（MVP 前必须解决）

## P1-1 三个合计的语义没定义；`include_in_gross` 是死配置；§4.4 的"合计=明细加总"只对其中一个成立

**问题**
`pay_item.include_in_gross`（`schema:190`）的含义是"是否计入应发合计"，`pay_record` 的三个合计注释是 `gross_amount`=应发、`deduction_amount`=扣款、`net_amount`=实发 = gross − deduction（`schema:266-268`）。

但 §4.4 又说「合计永远等于明细加总」。这两句不能同时成立：设有一条 `include_in_gross=0` 的增项（例如报销、代发补贴），它不进 gross；那么它进不进 net？
- 若进：`net ≠ gross − deduction`，字段注释错；
- 若不进：这条明细纯粹装饰，**`include_in_gross=0` 等于让这笔钱消失**，更糟。

当前种子数据所有科目 `include_in_gross=1`，所以两个定义恰好重合，问题被掩盖，一旦第 3 期接个税（以 gross 为基数）就会暴露。

**为什么是问题**
§4.4 自称"财务对账的底线"。底线是一个没定义的等式，等于没有底线。而且 `include_in_gross` 现在被写入字典、被前端当作配置项展示——用户勾了"不计入应发"，系统行为却是未定义的。

**位置**
§4.3 ⑤、§4.4；`db/schema-mysql.sql:190`、`:266-268`。

**修复建议**

把三个合计写成互不重叠的定义，并只由 `domain` 里的同一个 `Totals.of(lines)` 计算：

```
gross     = Σ amount where direction=1 AND include_in_gross=1
deduction = Σ amount where direction=2                      -- 扣款全部计入
net       = Σ amount(direction=1) − Σ amount(direction=2)   -- 与 include_in_gross 无关
```
即：`include_in_gross` **只影响 gross 小计**（它天然是未来个税/社保的基数），net 永远是全部明细的净额。这样 §4.4「合计=明细加总」对 net 恒成立，gross 则是一个语义明确的子集。

同步改：`schema:268` 的注释改为"实发 = Σ全部增项 − Σ全部减项"，并在 §4.4 写明三个等式。若 MVP 决定暂时不支持非 gross 项，就**删除 `include_in_gross` 列**，等第 3 期再加——比留一个语义未定义的开关安全。

## P1-2 记录级没有并发控制，两人编辑同一记录会静默覆盖金额；明细的删除/编辑边界也没有定义

**问题**
`pay_record` 没有 `version` 列（`version_no` 是另一回事且无人使用），`PUT /records/{id}/items` 只写"校验期间状态 + 唯一性"。两人同时打开同一条记录编辑不同科目：后提交者 `upsert` 覆盖，先提交的修改消失，双方都收到成功。股票行情里这是"丢更新"，工资里这是"某人的绩效奖金被吞了"。

同时 `pay_record_item` **没有 `deleted` 列**，删除一个明细只能是物理 `DELETE`，与 §6「系统不提供物理删除」和「所有金额变更留痕」冲突；`/records/{id}/items` 也未定义：清空某科目时是删行还是置 0？编辑 `COMPUTED` 科目时是否拒绝（`pay_item.editable=0` 存在但接口没说用它）？

**为什么是问题**
编辑窗口长（财务会开着页面核对十几分钟），丢更新是必然发生的。而且"金额变更必须留痕"是 §6 的硬要求，物理删除后连"曾经有过这笔"都查不到。

**位置**
`db/schema-mysql.sql:249-307`（无 `version`、`pay_record_item` 无 `deleted`）；§5.3 `PUT /records/{id}/items`；§6 事务/审计两行。

**修复建议**

1. `pay_record` 增加 `version INT NOT NULL DEFAULT 0`，明细编辑走 `UPDATE pay_record SET version=version+1, ... WHERE id=? AND version=?`，`affected=0` 返回 409"该记录已被他人修改，请刷新"。前端表单必须带回 `version`。
2. 编辑事务内先 `SELECT ... FOR UPDATE` 该 `pay_record` 行，把同一条记录的所有明细写串行化；`uk_record_item(record_id,item_code)` 只防重复插入，防不了覆盖。
3. 明细不删行：清空 = 置 `amount=0` 并加 `source` 保持原值；确实要移除的科目（例如录错的行）用 `pay_record_item` 加 `deleted TINYINT DEFAULT 0` 软删，或干脆不允许删除，只允许置 0（工资表里一条 0 元明细比消失的明细更可审计）。
4. 接口层面拒绝三类写入：`pay_item.editable=0` 的科目、`category='COMPUTED'` 的科目（必须走重算）、不属于本期间的记录（防越权）。
5. 审计不要交给通用 AOP：一个批量编辑请求里可能改 10 个科目，AOP 拿不到"哪个科目从多少改到多少"。由 record service 显式写 `pay_audit_log`，一条明细一行（`biz_id=record_id`，`field_name=item_code`，`old_value/new_value` 为金额字符串）。
6. `recalculate` 同理必须加乐观锁，否则"重算"与"手工编辑"交错会互相覆盖。

## P1-3 汇总有两份缓存（`pay_period` 合计列 + `pay_summary_monthly`），刷新时机未定义，解锁后必然失真

**问题**
同一个数字被存了三处：`pay_record` 明细、`pay_period.total_gross/total_net/employee_count`、`pay_summary_monthly.gross/net`。后两者：

- 谁、在什么时机写？`pay_summary_monthly` 只写了"期间锁定时刷新"（`schema:365` 注释）。`pay_period` 的三个合计列**完全没写**，可以是任何值。
- 解锁 → 编辑 → 重新锁定：若"锁定刷新"只在第一次锁定执行，第二次锁定时是否再刷？未定义。若不刷，年报用的是旧数。
- 刷新与锁定不在同一事务：锁定提交成功、刷新失败（异常/重启），汇总表停在旧状态，没有任何标记说明它过期了。
- 年报说"仅统计 LOCKED 及以后"，但它读的是汇总行——汇总行不知道自己对应的期间现在是不是已被解锁回 `EDITING`。期间从 LOCKED 被解锁后，汇总行还在，年报照样统计。
- 汇总按 `(company_id, period_ym, dept_id)` 键；部门被删/改名后，旧 `dept_id` 行变成孤儿，若刷新用逐部门 upsert 而不是"先删本期全部再插"，孤儿永远清不掉。

**为什么是问题**
这是"财务数字对不上"的第二大来源（第一是明细）。而且两份缓存互相独立，谁也不知道哪份是对的。

**位置**
`db/schema-mysql.sql:214-216`（`pay_period` 合计列）、`:353-365`（`pay_summary_monthly`）；§5.5 报表；§4.6 锁定。

**修复建议**

1. **MVP 直接删除 `pay_summary_monthly`**。理由是可量化的：C7 下 2000 人 × 12 月 = 2.4 万条 `pay_record`/年，明细约 24 万行/年，`SUM() GROUP BY dept` 是毫秒级；而这张表要覆盖 §5.5 声称的"按部门/类型/科目"三个维度，现有键只有部门一维，**"按类型""按科目"根本用不上它**，等于为了一个用不满的缓存背上一整套一致性问题。去掉它，报表直接查明细，一致性由数据库保证。
2. 如果坚持保留（例如未来数据量翻 100 倍）：刷新必须与锁定**同一个事务**（2000 行聚合在一秒内，完全做得到），且刷新方式必须是 `DELETE WHERE company_id=? AND period_ym=?` + 批量 `INSERT`，不能逐部门 upsert；解锁时立刻删除本期汇总行；年报在查询时 `JOIN pay_period` 校验当前 `status IN ('LOCKED','ARCHIVED')`，不信任汇总行自身。
3. `pay_period.total_gross/total_net/employee_count` 同样处理：**从读时计算**（`SELECT SUM(gross_amount) FROM pay_record WHERE period_id=? AND deleted=0`），或者干脆删掉这三列。用 `UPDATE ... SET total_gross = total_gross + ?` 增量维护在并发编辑下会丢更新，不要走这条路。
4. 加一个夜间一致性检测（24 万行全表扫描是秒级，成本可忽略）：找出 `net_amount <> Σ明细` 或 `= 0` 但明细非空的记录，输出告警。这条 SQL 是 §4.4 唯一能被持续验证的方式。

## P1-4 接口清单缺口（对照 C1–C10 与 §4 各能力）

**问题**
§5 的接口无法支撑设计里已经承诺的能力。逐条对照：

| 缺失接口 | 对应设计承诺 | 后果 |
|---|---|---|
| `GET/POST/PUT /companies`、`/depts` | C1 多法人主体、§4.9 四条隔离线 | 公司/部门只有种子数据，运维无法新增主体、无法维护部门树；多主体功能不可运营 |
| `PUT /roles/{id}/grants`（`sys_role_grant`） | §4.7 权限点 | 权限只能靠 SQL 改库，且无审计 |
| `PUT /users/{id}/roles` | §4.7 | 用户与角色绑定无接口 |
| `POST /periods/{id}/archive` | §4.6 `ARCHIVED` 状态 | 有状态、无入口，终态永远到不了 |
| `DELETE /periods/{id}` | §4.6 `DRAFT 允许删除` | 无接口，且 `pay_period` 没有 `deleted` 列（见 P1-11） |
| `POST /periods/{id}/reset`（清空本期重来） | §4.3 ⑦/§4.6 | 失败生成或整体重来无路可走（P0-4 的直接后果） |
| `POST /periods/{id}/records`（补录一名员工） | §4.6 `EDITING 允许手工编辑` | 生成后才入职/被资格规则漏掉的人无法入表 |

| `GET /records/{id}/history` | §6 "所有金额变更留痕" | 审计表有了，但没有面向记录的查询视图（`/audit-logs` 是全局的，财务用不了） |
| `POST /auth/logout`、`PUT /auth/password` | §5.6 | — |
| `GET /exports/{jobId}` 或明确同步导出上限 | §5.5 导出 | 导出是同步流式还是异步任务未定义，跨主体年报可能超时 |

另外三处语义未定：
- `POST /periods` 的 body 没有 `companyId`；`uk(company_id, period_ym)` 决定了必须指定主体（见 P1-12）。
- §5.1 `PUT /comp-profiles/{id}` 写着"修改"，但 §4.1 描述的真实行为是"截断旧区间 + 新建区间"（创建语义）。用 PUT 表达创建，天然不幂等。应改为 `POST /employees/{id}/comp-profiles/change`，入参 `effectiveDate / baseSalary / fixedItems / reason`，返回新区间 id。

**为什么是问题**
接口清单是开工清单。缺 `companies/depts` 意味着 C1 只能靠手工 SQL；缺 `run errors/conflicts` 意味着 §4.2 精心设计的"告诉他去上海分公司找"只活在弹窗里，跨主体冲突的实际处理流程无法闭环（分支财务卡住 → 找 IT）。

**位置**
§5.1–5.6；§4.2、§4.6、§4.9；`db/schema-mysql.sql:19-105`（组织权限六表只有种子）。

**修复建议**
按上表补齐；优先级：`companies/depts` + `run errors/conflicts` + `reset` + `archive` 属 MVP 必需，其余可拆到第一期后半。补完后再用"每一条 C 和 §4 的每个能力，至少有一个可调用接口"做一次对照检查——当前文档没有需求 1–5 的原文，建议在附录里补上，否则这份对照检查本身无法复核（见 P2-1）。

## P1-5 科目字典可被修改，历史重算会算出不同结果；同 code 的主体科目与全局科目冲突规则缺失

**问题 A：字典没有版本/快照**
`pay_record_item` 冗余了 `item_name/category/direction/sort_no`（好），但**没有冗余 `precision_scale` 与 `include_in_gross`**。而重算（解锁后单条重算、或重跑生成）会重新读取当前字典：
- 某科目 `precision_scale` 从 2 改成 4 → 旧记录当时按 2 舍入，重算后金额变化；
- `include_in_gross` 翻转 → gross 变化；
- 这正是"历史工资表永远不会被改写"（§4.1）的反例。

**问题 B：`company_id=0` 全局科目没有归属行**
`sys_company` 里不存在 id=0 的行。`pay_item.company_id=0` 的科目任何 `JOIN sys_company` 都取不到名称；更麻烦的是任何"按公司过滤"的拦截器会把 0 排除掉（见 P1-10）。

**问题 C：同 code 覆盖规则缺失**
`uk_item_code(company_id, item_code)` 允许"集团 `OT_ALLOW`"与"北京 `OT_ALLOW`"并存。核算时取并集（§4.9 末段）→ 同一个 `item_code` 出现两条定义，`pay_record_item` 的 `uk_record_item(record_id,item_code)` 会撞，而 `item_name/direction` 也可能不同。

**为什么是问题**
薪酬系统的核心承诺是"已锁定的历史不可变"。字典能改而记录不冻结字典版本，这个承诺只在"不再重算"的情况下成立；而 C3 的解锁更正恰恰要求重算。

**位置**
§4.1、§4.3 ⑤、§4.5 模板动态列、§4.9「工资项」末段；§5.2 `PUT /items/{id}`；`db/schema-mysql.sql:181-203`、`:290-307`。

**修复建议**

1. `pay_record_item` 增加 `precision_scale TINYINT NOT NULL`（写入时从字典快照），并把 `include_in_gross` 一起快照。这样任何一条历史明细分录的"当时定义"是自洽的，重算只依赖快照 + 档案快照。
2. §5.2 的不可改字段从"类别/方向"扩展到"类别/方向/`precision_scale`/`include_in_gross`"，判定条件明确为"已出现在任意 `pay_record_item` 中"。2000 人规模 `EXISTS` 查询成本可忽略。
3. 同 code 覆盖规则二选一并写进文档：**推荐**"主体科目覆盖全局科目"（按 `company_id DESC` 取第一条）；或者禁止复用 code（建主体科目时校验全局同 code 不存在）。两者选一个，不要留给实现者。
4. `pay_item` 增加 `calc_rule VARCHAR(32)`，把"哪个计算策略"变成数据而不是 Java 类名（见 P1-9）。

## P1-6 导入管道"预校验不落库"与"提交需要数据"矛盾；批次状态机与文件生命周期未定义

**问题**
§4.5 流程是 `上传 → 预校验（不落库）→ 回显 → 用户确认 → 提交（事务内 upsert）`。但：

- `POST /import/{batchId}/commit` 需要一个 batchId，所以校验后**必须有批次行落库**——"不落库"到底指什么？
- 提交时行数据从哪来？若靠内存/会话缓存，应用重启或负载到另一台就丢；若重新解析文件，文件何时、以什么路径落盘？`pay_import_batch.file_path` 有列但流程里没有落盘步骤。
- 错误明细 `pay_import_error` 是否在校验阶段就写？若不写，用户第二天再点"下载错误报告"就没了。
- `payroll.storage.local-path: ./data/import` 是相对路径，取决于进程 CWD；容器化后 CWD 一变，历史文件全部找不到（而 `file_path` 是"可追溯、可重放"的唯一依据）。
- `payroll.import.max-rows: 50000` 而 C7 只有 2000 人——5 万行的文件必然 25 倍重复，L1 会全量拒绝，但仍要解析完 5 万行才报错。

**为什么是问题**
导入是"预校验 → 确认 → 提交"两段式，中间隔着人的思考时间（几分钟到一天）。所有中间状态必须有明确归属，否则重启就是一次数据丢失。

**位置**
§4.5；§5.4；`db/schema-mysql.sql:313-343`；`application.yml:34-44`。

**修复建议**

1. 明确"不落库"= **不写核算数据（`pay_record/pay_record_item`）**；批次行、错误行、原始文件必须落。
2. `POST /import/validate` 的动作序列：① 计算 hash → ② 插入批次行（`VALIDATING`，靠 `uk_period_file` 防并发，见 P0-5）→ ③ 以 `{storage}/{periodId}/{batchId}.xlsx` 落盘（绝对路径，挂卷）→ ④ 流式校验并写 `pay_import_error` → ⑤ 批次置 `VALIDATED`，返回统计。
3. `POST /import/{batchId}/commit`：从 `file_path` **重新流式解析**（不要缓存行数据），事务内 upsert，置 `COMMITTED`，写 `committed_by` 与 `finished_at`。重放能力由此获得。
4. 状态机补全：`VALIDATING → VALIDATED → COMMITTED`，失败 `FAILED`；`VALIDATED` 超过 7 天未提交的批次由清理任务置 `EXPIRED`（否则文件与行永远堆着）。
5. `storage.local-path` 改为必填绝对路径（无默认值），启动时校验可写；`file_path` 存相对 `storage` 根的路径，换根目录不影响。
6. `max-rows` 收紧到 `max(2000, 在职人数 × 1.2)` 或直接 5000，在读到第 N+1 行时立即拒绝，不要解析完再报。

## P1-7 计薪资格（谁该出现在本期）与折算规则只存在于 SQL 和散文里，无法单测，也没有参数表

**问题**
§4.3 ①「加载期间内在职/离职员工 × 期间末生效的薪酬档案」——"期间内在职/离职"到底是什么边界（`hire_date` 在期间内？`leave_date` 在期间末之后？`status=3 停薪留职` 算不算？），全文没有定义。§4.3「月中入职/离职、停薪留职的折算规则做成期间级参数，不写死在代码里」——但只有 `pay_period.hpd` 一个参数，**没有任何参数表承载折算规则**。

**为什么是问题**
"多算一个人/少算一个人"是工资表最常见的错误，也是最容易在 SQL 里写错的逻辑。它现在住在"应用层加载"里，恰恰是 §2.1 声称要脱离数据库才能验证的那部分——结果是**最该被穷举测试的规则，成了唯一测不了的规则**。

**位置**
§4.3 ①②；`db/schema-mysql.sql:217`（`hpd` 是唯一的期间参数）；`emp_employee.hire_date/leave_date/status`。

**修复建议**

1. 把 ① 拆两半：
   - **SQL 预筛（放宽，宁多勿少）**：`hire_date <= 期间末日 AND (leave_date IS NULL OR leave_date >= 期间首日)`，只负责减少数据量，不负责判定。
   - **纯策略（domain，可穷举测试）**：`EligibilityPolicy.evaluate(EmployeeSnapshot, PeriodRange) → {INCLUDE, EXCLUDE, PRORATE_BY_DAYS}`，`status=3`、`leave_date` 与期间末/期间首的相对位置、部分月入职等全在这里判定。参数化测试覆盖"入职日=期间首日/末日/次日"等边界。
   - 加一条**一致性测试**：对任意员工，若 `policy` 判定 INCLUDE 则必须被 SQL 预筛捞到（否则就是漏算）。这条测试能在不连库的情况下用小样本 + 一条手工 SQL 断言。
2. 折算参数落表，不要散在代码里：
   ```sql
   CREATE TABLE pay_period_param (
     id BIGINT PRIMARY KEY AUTO_INCREMENT,
     company_id BIGINT NOT NULL, period_ym CHAR(7) NOT NULL,
     param_key VARCHAR(64) NOT NULL,  -- PRORATE_RULE / SENIORITY_RATE / STOP_WORK_RULE ...
     param_value VARCHAR(255) NOT NULL,
     UNIQUE KEY uk_param (company_id, period_ym, param_key)
   );
   ```
   期间未配置时回落到主体级默认，主体未配置时回落到集团默认（`company_id=0`）。`pay_period.hpd` 可以作为它的一个 key 的特例保留。
3. 折算公式本身（按自然日 / 按计薪日 / 按 `hpd`）也要作为 `param_key` 的一个枚举，避免"参数表建了但公式硬编码"。

## P1-8 导入与生成都缺"员工归属主体 = 期间主体"的校验，跨主体错发只会在第二家被发现

**问题**
`pay_import_batch` 归属于某主体的某期间，导入行按 `emp_no`（集团唯一，C8）匹配员工。但**校验清单（§4.5：格式/科目存在性/员工存在性/期间状态/数值范围）里没有"该员工当前归属主体是否等于期间主体"**。同理 §4.3 ① 写的是"按员工当期归属主体分组"——这句话是旧的"集团一次生成"模型（见 P1-12）。

后果：上海的导入文件里混进了一个实际归属北京的工号 E001 → 上海期间里建了一条 E001 的记录（此时北京还没生成，L3 不冲突）。第二天北京生成 → 北京自己的员工无法发放，L3 报"已在上海分公司"。**错误发生在一处，代价落在另一处，且第一家完全感知不到**。

**为什么是问题**
跨主体的人员信息同步本来就容易滞后（调动的时效性）。L3 只能保证"不会发两次"，不能保证"发在正确的主体"。而工资表归属错主体，在财务口径上等于错账。

**位置**
§4.5 预校验清单；§4.3 ①；§4.9「人员归属的处理」；`db/schema-mysql.sql:249-288`（`pay_record.company_id` 与期间的 company 无任何约束）。

**修复建议**

1. §4.5 预校验增加一条规则：`emp_employee.company_id = pay_period.company_id`，不满足则整行失败，错误码 `EMP_COMPANY_MISMATCH`，文案带员工当前主体名 + 期间主体名。
2. 生成同理：只加载 `company_id = 期间主体` 的员工，并且写入后断言 `pay_record.company_id == pay_period.company_id`（服务端从期间行取，不接受客户端传入）。
3. 提供一个"跨主体人员变动"提示：若某员工的 `emp_employee.updated_at` 晚于期间首日且 `company_id` 在本期内被改过，导入/生成时给警告（不是错误），提示"该员工本月发生过主体调动，按 §4.9 默认整月归属新主体"。这能挡住最多的一类真实误操作。
4. 若第 2 期的"调动单"要做按天分割，这条规则要同步扩展为"按生效日切分"。当前先按整月归属实现，并在文档里写明这是已知简化。

## P1-9 加密与查重盐的生命周期未定义；盐一旦变化，L3 防线会整体失效

**问题**
- §4.8 只写了 "AES-256 密文"，没有算法模式（GCM/ECB）、IV 存哪里、密钥如何派生。
- `application.yml:41` 的默认值 `dev-only-32-byte-key-change-me!` 实际是 **31 个字符**。若按 `new SecretKeySpec(key.getBytes(), "AES")` 使用，启动/首次加密直接 `InvalidKeyException: Invalid AES key length: 31 bytes`；若先 SHA-256 派生则必须写进文档，否则实现者只能靠试。
- `id_no_cipher VARBINARY(256)` 没有 key 版本列：密钥轮换后，所有旧密文永久无法解密（§6 要求"长期保存、不物理删除"）。
- **最关键的**：`uk_id_hash` 依赖 `PAYROLL_ID_SALT`。盐一旦变化（或丢失后用新盐重建），同一个人的哈希变了 → 同一被重新导入为**新的员工记录**，得到新的 `employee_id`。而 L3 的唯一键是 `(employee_id, period_ym)`——两条不同的 employee_id 可以各有一条有效记录，**L3 完全拦不住同一个人被两个员工档案各发一次**。也就是说 L3 的安全性完全寄托在"员工身份去重"上，而后者的稳定性只靠一个环境变量。

**为什么是问题**
§4.2 说 L3 是"唯一兜底"。它其实只是第二道，第一道是身份去重；第一道断了，第二道形同虚设。而盐是一个运维手册里都不会提的环境变量。

**位置**
§4.8；§4.2；`application.yml:39-41`；`db/schema-mysql.sql:118-120`、`:142`。

**修复建议**

1. 明确加密契约并写进 §4.8：`AES/GCM/NoPadding`，每行随机 12 字节 IV，存储格式 `[1B 版本][12B IV][密文][16B tag]`，十六进制/二进制直接进 `VARBINARY`；密钥由 `PAYROLL_AES_KEY` 经 `SHA-256` 派生为 32 字节（或直接要求 32 字节并启动校验长度）。任何情况下不得使用 ECB。
2. 启动时**失败即退出**：若 `PAYROLL_AES_KEY`/`PAYROLL_ID_SALT` 仍是默认值且 `spring.profiles.active=prod`，抛异常终止，不要只写注释。
3. `emp_employee` 增加 `key_version TINYINT NOT NULL DEFAULT 1`，密文格式里也带版本；提供"密钥轮换"运维脚本（读旧钥→写新钥→更新版本），否则轮换 = 数据丢失。
4. **盐写进备份清单**：`PAYROLL_ID_SALT` 必须与数据库备份同批备份、同批恢复，且**永不复用为新的值**。在 README 与运维文档中各写一条。
5. 提供一个身份合并工具的最小子集：`POST /employees/{id}/merge`（把第二个档案的 `pay_record` 迁移到第一个、标记第二个 `deleted=1`），因为重复员工一旦产生，L3 就无法自动阻止，必须有人工纠正路径。

## P1-10 数据范围（`COMPANY/DEPT_SUB/DEPT/SELF`）没有实现机制；`company_id=0` 的全局科目会给通用拦截器挖坑

**问题**
§4.9 只写"查询强制拼主体条件"，§4.7 只列了数据范围枚举值。没有说明用 MyBatis-Plus 的 `DataPermissionInterceptor`、自定义 `InnerInterceptor`、还是每个 Mapper 手写。在 20 个 Mapper、上百条查询里手写，漏一条就是跨公司泄漏；而这类泄漏不会报错、只会多出数据。

`pay_item.company_id=0` 的全局科目与"强制拼 `company_id IN (我的主体)`"直接冲突：拼了就看不到集团通用科目，不拼就漏数据。

**为什么是问题**
C1 明确 `company_id` 是**真实隔离维度**。隔离靠"记得每条查询都加条件"是做不到的；`sys_dept.ancestors` 前缀匹配（`DEPT_SUB`）本身也是易错 SQL（`FIND_IN_SET` vs `LIKE ',1,2,%'`），手写必然出现两种写法并存。

**位置**
§4.7(2)、§4.9 四条隔离线；`db/schema-mysql.sql:39`（`ancestors`）、`:184`（`pay_item.company_id=0`）。

**修复建议**

1. 定下唯一机制：一个 `DataScopeInnerInterceptor`（或 `DataPermissionInterceptor` 的 `MultiDataPermissionHandler`），从 `SecurityContext` 取 `DataScope`，按表名注入：
   - `pay_period / emp_employee / pay_record / pay_summary_monthly` → `company_id IN (...)`；
   - `sys_dept` → `company_id IN (...) AND (ancestors LIKE '%,{deptId},%' OR id = {deptId})`（`DEPARTMENT_SUB`）；
   - `pay_item` → **例外规则**：`(company_id = 0 OR company_id IN (...))`。
2. 用 enumer 常量 + 按表名注册，禁止在 service 里手拼字符串；对不在登记表内的表默认拒绝（`throw`），逼着新表登记范围，而不是默认放行。
3. `SELF` 范围只对 `emp_employee`/`pay_record` 有意义（`employee_id = 当前用户.employee_id`），对 `pay_item`/`sys_dept` 无意义——范围与表的组合需要一个二维登记表，否则会出现"用 SELF 查科目表返回空"的诡异现象。
4. 加一条集成测试：以每个数据范围各构造一个用户，断言对每张业务表的查询结果集合与预期完全一致（不只看"能看到"，还要看"看不到"）。
5. `company_id=0` 的"全局科目"在 `sys_company` 里没有对应行，任何 `JOIN sys_company` 的展示查询都要 `LEFT JOIN` + 兜底名称"集团通用"。建议在 `sys_company` 里插入一行 `id=0` 的哨兵记录（migration 里显式指定 id），把"全局"变成一等公民。

## P1-11 期间与记录的生命周期字段自相矛盾：C3 遗留版本字段、缺 `deleted`、解锁字段单槽覆盖

**问题**

1. `pay_record` 有 `record_status (DRAFT/CONFIRMED)`、`version_no`、`superseded_by`。这三个字段来自"C3 之前的补发/扣回"模型，现在无人定义：`record_status` 的 `CONFIRMED` 由谁置？期间锁定是否等于全部记录 CONFIRMED？报表若要按 `record_status` 过滤（很像会有人这么写），结果是空集。`superseded_by` 在"就地修改、不生成新版本"的 C3 模型下永远为 NULL。**这是第二套状态机**，与 §4.6 的期间状态机并存，迟早有人用错。
2. §4.6 说 `DRAFT` 允许删除期间，但 `pay_period` **没有 `deleted` 列**，接口也没有（P1-4）。
3. `locked_by/locked_at/unlock_reason` 是单槽字段。一个期间可以被反复解锁/锁定 N 次，第 N 次会覆盖第 N-1 次的解锁原因。设计指望审计表兜底，但没写清楚"期间行只表示当前状态、完整历史在 `pay_audit_log`"。

**为什么是问题**
工资系统的状态字段会被报表、导出、权限判断从各种角度引用。一个没有定义的状态枚举（`record_status`）等于埋了一个"看起来能用、实际恒为默认值"的陷阱。而解锁历史是 C3 更正路径的唯一凭据，单槽字段会把它覆盖掉。

**位置**
`db/schema-mysql.sql:270-272`（`record_status/version_no/superseded_by`）、`:209-228`（无 `deleted`）、`:220`（`unlock_reason`）；§4.6。

**修复建议**

1. **删除** `record_status`、`version_no`、`superseded_by` 三列，或在文档中给出完整定义与唯一写入方（推荐删除：C3 下它们没有语义，且`version_no` 与 P1-2 要加的乐观锁 `version` 名字冲突，极易误用）。
2. `pay_period` 增加 `deleted TINYINT NOT NULL DEFAULT 0`；删除期间的规则写成"仅 `DRAFT` 且 `NOT EXISTS(records)` 时允许逻辑删除"。
3. 明确：`locked_by/locked_at/unlock_reason` 只反映**当前**状态，解锁历史以 `pay_audit_log` 为准；解锁必须在同一个事务里写一条 `action=UNLOCK, old_value=锁定信息, new_value=解锁原因` 的审计。或者直接建 `pay_period_transition(period_id, from_status, to_status, operator_id, reason, created_at)`，把状态迁移变成一等数据——在高危操作上，这比"期望审计表记得写"可靠。
4. 补"编制/锁定/解锁"三个动作的审计事件规格（字段、前后值格式），否则审计切面写出来人人不一样。

## P1-12 期间创建与生成缺少"主体上下文"定义；`ALL` 范围用户建期间时行为未定

**问题**
- `POST /periods` 的请求体没有公司字段，但表上有 `uk(company_id, period_ym)`，必须有主体。
- 谁有权为哪个主体建期间、生成、导入、锁定？§4.7 只有功能权限点 + 数据范围，没有把两者组合成"对某主体某期间的写权限"的规则。
- §4.3 ① 写"按员工当期归属主体分组"——这是"集团一次生成、按主体分组落库"的旧模型，与 C10（各分公司各做本主体）和 `pay_period.company_id` 冲突。按这句话实现会出现一次生成写入多个主体的 `pay_record`，期间统计（`pay_period.total_gross`）立刻失真。

**为什么是问题**
多主体系统最容易出的不是算法错误，是"用错了主体"。这三个问题合起来，会让第一个实现者把生成写成"集团级批处理"，而这个错误会渗透到 run、统计、汇总的每一层。

**位置**
§5.3 `POST /periods`、`POST /periods/{id}/generate`；§4.3 ①；§4.7；§4.9；`db/schema-mysql.sql:227`。

**修复建议**

1. 期间创建：body 必填 `companyId`（或 `periodYms` 批量 + `companyIds` 批量）。权限判定 = 用户拥有 `payroll:period:create` 且 `companyId ∈ 用户数据范围`。`ALL` 范围用户批量建期间是合理的运维动作，应显式支持 `POST /periods/batch`，不要让他靠循环单条调用。
2. 生成：`period.company_id` 是唯一主体来源，从 DB 行读取，**不接受客户端传入**；员工筛选条件强制 `emp_employee.company_id = period.company_id`（P1-8），并在 run 收尾断言"本期所有 `pay_record.company_id` 唯一且等于期间主体"。
3. 把 §4.3 ① 的表述改为"加载**本期间主体**下、期间内在职/离职员工 × 期间末生效档案"，删掉"按归属主体分组"。
4. 权限组合规则写成一句话表：**功能权限点控制"能不能做这个动作"，数据范围控制"能对哪些主体做"**，任何写接口两者都要校验，缺一不可。

## P2-2 种子数据与 §4.9 的策略矛盾

**问题**
`db/schema-mysql.sql:409-413` 给 `PAYROLL_CLERK` 种子了 `data_scope='ALL'`；种子 `sys_role.company_id=1` 硬编码，依赖 `sys_company` 自增恰好为 1（该 insert 未指定 id）。

**为什么是问题**
一个"薪酬专员"角色直接拿到集团全部主体，与 §4.9"只有集团 HR / 审计能拿 ALL"正面冲突；而硬编码 company_id=1 只在"空库首次初始化"时成立，一旦 `schema-mysql.sql` 被拿到别的环境（或 DEFAULT 公司被删后重建）执行，角色就挂到了不存在的主体上。

**位置**
`db/schema-mysql.sql:395`（`sys_company` 种子）、`:409-413`（角色种子）。

**修复建议**
`PAYROLL_CLERK` 的 `data_scope` 改为 `COMPANY`；`sys_company` 种子显式写明 `id`（同时插入 P1-10 建议的 `id=0` 集团哨兵）；角色 insert 的 `company_id` 用 `(SELECT id FROM sys_company WHERE company_code='DEFAULT')` 子查询。

## P2-3 审计：列表页逐条留痕、金额第二份明文拷贝、无保留策略

**问题**
§4.7 要求"查看他人工资写查看审计"。若 `GET /periods/{id}/records`（列表页，2000 行 × N 页）每页都写 N 条审计，审计表年增百万行且拖慢列表；`pay_audit_log.old_value/new_value TEXT` 会把每个金额变更再明文存一份；审计表没有保留期/归档策略。

**为什么是问题**
审计表被自己的噪声撑大之后，"谁看了谁"这个真正的安全事件会被淹没；而列表页查询被审计写入拖慢，是最容易被运维当成"性能问题"去优化掉监控的典型路径。明文金额第二份拷贝则会让"只有证件号需要加密"的边界变得含糊。

**位置**
§4.7(3)、§6 审计/日志两行；`db/schema-mysql.sql:371-389`。

**修复建议**
查看审计按"人 × 期间 × 会话（或天）"记一条，不逐条记；金额变更的审计由 record service 显式写紧凑结构（`record_id + item_code + 金额字符串`）并限制长度；文档明确"金额在库内不加密（`pay_record` 本就明文），仅证件号/手机号加密"，避免第 3 期误以为审计表可替代加密；审计表按年归档到历史库（与 §6 的 90 天备份对齐）。

## P2-4 历史记录的数据范围依赖 `dept_id` 快照，部门被移动/删除后不可见

**问题**
`pay_record.dept_id` 是快照，而 `DEPT_SUB` 数据范围用 `sys_dept.ancestors` 前缀匹配**当前**部门树。部门在期间之后被移动（`ancestors` 变化）或被删除（`deleted=1`）时，主管看不到历史工资。

**为什么是问题**
工资历史需要被查阅的时点恰恰是"人已经调走、部门已经重组"之后。范围规则一旦依赖当前树形，历史数据会随组织调整"消失"，且不报错——用户只会以为"这个月没这个人"。

**位置**
§4.7(2)；`db/schema-mysql.sql:39`（`ancestors`）、`:249-288`（`pay_record.dept_id` 快照）。

**修复建议**
`pay_record` 增补 `dept_path_snapshot VARCHAR(512)`（写入时的 `ancestors` 值），历史查询优先用快照路径匹配；部门删除一律改为"停用"（已有 `status` 字段），禁止 `deleted=1`。

## P2-5 认证与会话未定义

**问题**
`POST /auth/login` 只有登录，没有登出/续期/令牌类型/有效期说明；权限点在角色变更后何时失效（缓存？每请求查？）也未写。

**为什么是问题**
§4.7 的权限点是全部数据隔离的前提。若权限点被缓存在令牌里且没有失效机制，一次"撤销导出权限"要等到令牌过期才生效；若每次请求查库，则要在 C6（不加 Redis）的前提下接受每次请求两条额外查询。两条路都可行，但必须现在选。

**位置**
§5.6；§4.7；`pom.xml`（已引 `spring-boot-starter-security`，无 JWT 依赖）。

**修复建议**
选 JWT 无状态（C6 下不引入 Redis 的最简解）：access token 2h + refresh token，权限点与数据范围内嵌；角色/授权变更时提供 `POST /users/{id}/force-logout` 并在服务端维护一个最小的 token 失效表（`sys_token_blacklist`，只存 jti + 过期时间，可由定时任务清理）。补 `POST /auth/logout`、`PUT /auth/password`。

## P2-6 导出接口的同步/异步与上限未定义

**问题**
`POST /reports/export` 未说明返回文件流还是 jobId，也未设行数上限。

**为什么是问题**
2000 人 × 12 月的明细导出约 24 万行：同步流式会让一个请求占住连接数分钟（Hikari 池 20，几个并发导出就能拖垮列表查询）；不设上限则内存与磁盘都不可控。

**位置**
§5.5；`application.yml:1`。

**修复建议**
单主体月度走同步流式 EasyExcel（≤1 万行，约 1 秒）；跨主体/年度走异步任务 + `GET /exports/{jobId}` 下载（复用 `pay_run` 的进度模式）；两者都写 `action=EXPORT` 审计，记录筛选条件与行数。

## P2-7 冗余字段无约束

**问题**
`pay_record.period_ym` 与 `pay_record.company_id` 都可由 `period_id` 派生，但没有任何约束保证三者一致。

**为什么是问题**
`period_ym` 是 L3 唯一键的一部分：一旦某条记录的 `period_ym` 与期间不一致（导入/生成时传错、或手工修数），L3 就对该记录失效，而且这种失效**只在跨主体撞车时才会暴露**，平时完全看不出来。

**位置**
`db/schema-mysql.sql:252-253`、`:283`。

**修复建议**
服务端生成/导入时**一律从 `pay_period` 行取值写入**，不接受客户端传入；加夜间校验 `SELECT ... FROM pay_record r JOIN pay_period p ON r.period_id = p.id WHERE r.period_ym <> p.period_ym OR r.company_id <> p.company_id`，结果必须为 0。

## P2-8 精度策略：本期应统一 `precision_scale=2`

**问题**
C2 下所有输入都是金额（元，两位小数），`DECIMAL(18,4)` 是存储精度，不是业务精度；而 `pay_item.precision_scale` 允许按科目设置到 4 位。

**为什么是问题**
展示层统一保留 2 位时会出现"明细显示值之和 ≠ 合计显示值"。§4.4 已经承认这个现象并规定"以合计为准并标注"，但财务每月对账都会把它报成缺陷，且这类工单无法用"设计如此"说服对方。

**位置**
`db/schema-mysql.sql:189`；§4.4、§5.2。

**修复建议**
MVP 在 `POST/PUT /items` 强制 `precision_scale=2`（新建校验 + 已使用的科目不可改），4 位仅作为列精度保留给第 3 期的个税/社保计算。

## P2-9 工龄口径与工龄工资规则未定

**问题**
`emp_employee` 同时有 `hire_date`（本单位）与 `work_start_date`（社会）。§4.3 只说"工龄按期间末日计算"，没说用哪个日期、`seniority_years` 如何舍入、工龄工资的费率与封顶配置在哪里。

**为什么是问题**
`SENIORITY_PAY` 是 MVP 里除合计外唯一的计算科目。口径不定，实现者只能任选一个日期写死，上线后一旦业务说"应该算社会工龄"，就要改代码重算，而重算会动到已锁定期间（C3 的解锁更正路径）。

**位置**
§4.3 ②⑤；`db/schema-mysql.sql:128-129`、`:263`。

**修复建议**
在 P1-7 的 `pay_period_param` 中增加 `SENIORITY_BASE=HIRE_DATE|WORK_START_DATE` 与 `SENIORITY_RULE`（分档费率，JSON 或子表）；舍入规则（按满年向下取整 / 保留两位小数）写进 `EligibilityPolicy` 并作为纯函数单测。

## P2-10 软删除 + 唯一索引让误录数据永久占位；无回收路径

**问题**
`uk_emp_no` 与 `uk_id_hash` 都不带 `deleted` 条件，且系统不提供物理删除（§6）。

**为什么是问题**
误建一个员工（工号敲错、证件号敲错）后，那个工号和哈希就**永久**被占：无法新建正确的记录（会撞 `uk_emp_no` 或 `uk_id_hash`），也无法把错误记录改对（改工号同样撞键）。结果是只能人工改库，绕过审计。

**位置**
`db/schema-mysql.sql:140`、`:142`；§6 留存一行。

**修复建议**
提供 `POST /employees/{id}/purge`：仅当 `deleted=1` 且无任何 `pay_record`/`comp_log` 引用时硬删除，写审计。不要把 `uk_emp_no` 改成条件唯一来"解决"——`uk_id_hash` 不能同样处理（一人多档会破坏 L3，见 P1-9），两列规则不一致反而更危险。

# 四、建议的开工顺序（最小可动工集）

# 附：本次评审认可的设计点（避免被后续改动破坏）

- `active_key` 生成列 + 唯一索引实现"有效行才参与唯一约束"的写法是对的，`emp_comp_profile` 的开口区间应复用同一模式（P0-6）。
