## 1 模块落地：包、依赖方向、环

### 1.1 结论

**新增三个包，依赖方向固定如下；领域层 `domain.payroll` 一行不改。**

```
                          ┌──────────────┐
                          │    common    │  Result / BizException / Money
                          └──────┬───────┘
                                 │
        ┌────────────────────────┼───────────────────────────┐
        │                        │                           │
 ┌──────▼──────┐          ┌──────▼──────┐             ┌──────▼──────┐
 │ domain.entity│          │  security   │             │    audit    │
 │ (共享内核)   │◄─────────│ CurrentUser │             │ (新增,只被写)│
 └──────┬──────┘          │ Token       │             └──────▲──────┘
        │                 │ PermInterceptor            │
        │                 │ DataScopeEnforcer          │
        │                 └──────┬───────┘              │
        │                        │                      │
        │        ┌───────────────┼──────────────┐       │
        │        │               │              │       │
 ┌──────▼──────┐ │        ┌──────▼──────┐ ┌─────▼─────┐ │
 │    org      │─┘        │  employee   │ │   item    │ │
 │ (实现端口)  │          └──────┬──────┘ └─────┬─────┘ │
 └──────┬──────┘                 │              │       │
        │                        │              │       │
        │                 ┌──────▼──────┐       │       │
        └────────────────►│   period    │◄──────┘       │
                          └──────┬──────┘               │
                                 │                      │
                          ┌──────▼──────┐               │
                          │   record    │  PayRecordWriter + pay_record mappers
                          └──┬───┬───┬──┘               │
                             │   │   │                  │
                   ┌─────────┘   │   └────────┐         │
                   │             │            │         │
            ┌──────▼──────┐ ┌────▼─────┐ ┌────▼─────┐   │
            │     run     │ │importjob │ │  report  │───┘
            └─────────────┘ └────┬─────┘ └────┬─────┘
                                 │            │
                                 └────────────┘
                                    （均只读 period/record，不互依赖）

            ┌──────────────┐
            │    admin     │ → security, org, auth.mapper（不依赖 report/importjob）
            └──────────────┘
```

三条硬规则：

1. **只允许向下依赖**：`report` / `importjob` / `admin` 可以被 Controller 依赖，但**不得被** `employee` / `period` / `record` / `run` / `item` 依赖。任何反向 import 即视为设计违规。
2. **`report` 不依赖 `record` 的类**：报表聚合 SQL 归 `report.mapper` 自己所有，只读 `pay_record` / `pay_period` 表。这样 `report` 与 `importjob` 之间没有共同依赖点，不会因为 `record` 内部重构互相牵连。代价是与表结构耦合——用「明细等价测试」（§2.5）兜住。
3. **`importjob` 必须复用 `record` 的写入器**，不得自己写明细、自己算合计、自己刷期间合计。`RecordService` 里现在是三个 private 方法（`applyItem` / `recalcTotals` / `refreshPeriodTotals`），把前两个抽成 `record.PayRecordWriter`（public、事务内调用、**不自己开事务**），第三个保留给调用方在本批末尾调一次。导入 5000 行时逐行刷期间合计是 O(n²)，必须由调用方控制刷新时机。

### 1.2 先清掉的两处既有环（不先做，新包会复制）

**环 A：`run ↔ record`（真实存在）**

- `record.RecordService` import `run.mapper.PayRecordMapper`、`run.mapper.PayRecordItemMapper`；
- `run.GenerateService` import `record.RecordAssembler`。

`pay_record` / `pay_record_item` 是**记录的持久化**，放在 `run` 包里是历史偶然。修法：两个 Mapper 迁到 `record.mapper`（或独立的 `persistence` 包），`run` 只保留 `PayRunMapper` 与 `GenerateService`。修完后方向是单向 `run → record`，且 `GenerateService` 写记录也统一走 `PayRecordWriter`。

**环 B：`security ↔ employee/period/org`（更危险）**

`security.DataScopeEnforcer` 直接 import 了 `employee.mapper.EmployeeMapper`、`period.mapper.PeriodMapper`、`org.mapper.DeptMapper`；同时这三个包的服务都在 import `DataScopeEnforcer`。这是**横切组件反向依赖业务**，后果不是编译问题，而是「每加一个业务包，都要回头改 security」。三个新包里 `report` 与 `importjob` 都会依赖它，环会被复制成四份。

修法（两件事，都在 `security` 内部完成，不改调用方签名以外的东西）：

1. **去掉业务 Mapper**：`assertPeriodVisible(Long)` 改成 `assertPeriodVisible(PayPeriodEntity)`、`assertEmployeeVisible(Long)` 改成 `assertEmployeeVisible(EmpEmployeeEntity)`，由调用方先 `selectById`（它们本来就要查）。`DataScopeEnforcer` 从此只依赖 `domain.entity` + `AuthMapper` + 一个部门树端口。
2. **部门子树改成端口**：新增 `security.DeptTreePort { Set<Long> subtreeIds(Long rootDeptId); }`，由 `org.DeptService` 实现。`security` 只认识接口，`org` 依赖 `security`（单向），环消失。顺带把现在拼字符串的 `ancestors LIKE '%,"+id+",%'` 改成「先取子树 id 集合，再 `.in()`」——一次性解决注入面、可读性和索引问题（评审 02 的 V7 已实测该 LIKE 走不了索引）。

### 1.3 包名：`system` → `admin`

`com.insbean.payroll.system` 在 Java 里是自找麻烦：包内任何地方写 `System.currentTimeMillis()` 都要先确认没有被同名类型遮蔽；读代码的人也会把它和 `sys_*` 系统表混淆。**建议用 `com.insbean.payroll.admin`**（`UserAdminController` / `RoleAdminController` / `DeptAdminController` / `CompanyAdminController` / `AdminSafetyGuard`）。若坚持 `system` 也不影响结构，但这是一次零成本的改名窗口。

### 1.4 领域层要不要变：不变

- `domain.payroll`（`PayrollCalculator` / `WorkingDays` / `PayrollRules`）与本阶段三块功能**零交集**：报表只读已落库结果，导入只改已有明细，系统管理不碰计算。
- 不要为了「年度汇总」往领域层塞聚合逻辑——聚合需要 DB 和租约，一进去就破坏了「domain 不依赖 Spring、可脱离数据库单测」这条前提（§2.1 的关键约束）。
- 唯一需要写进领域层文档的规则是**不变式而不是代码**：报表侧 `net = gross − deduction`（§2.6）。

### 1.5 风险等级：中

不先做环整理也能编译、能跑，所以短期「看起来没事」；代价是三个新包各自发明一套数据范围用法、各自 import `run.mapper`，到 M2 再拆成本翻倍。**返工风险 > 运行风险**。

## 2 汇总数据的来源

### 2.1 结论

**查询时实时聚合，作为唯一真源。`pay_summary_monthly` 在 M1.5 不写、不读，建议迁移脚本直接 `DROP TABLE`（零写入者、零读取者、零数据）。**

年度汇总不需要 `ARCHIVED` 动作就能算对；它需要的是**完整性提示**，不是新状态。

### 2.2 三种方案的正确性对照

| 方案 | 锁定后解锁重算会怎样 | 新增写路径时要做什么 | 年度按人查询能否复用 | 结论 |
|---|---|---|---|---|
| **锁定时刷新**（DDL 注释的原设计） | 汇总表**静默过期**：解锁→改数→重新锁定若忘记刷新，报表永远错，且没有任何报错 | 每一处写 `pay_record(_item)` 的代码都必须记得刷汇总；今天是 generate/import/changeset/unlock/lock 五处，M2 只会更多 | **不能**：表只有部门粒度，`groupBy=EMP` 仍要扫明细 | **否决** |
| **查询时实时聚合** | 下次查询自动正确，无失效面 | 什么都不用做 | 能 | **采用** |
| 两者并存 | 两个真源，必须写一致性校验，否则没人知道该信谁 | 同上 + 对账任务 | 部分 | **否决** |

### 2.3 为什么这个数据量不需要预聚合

- 月度：`pay_record` 单期间 ≤ 2000 行，一次 `GROUP BY dept_id` 扫 2000 行。
- 年度：`2000 人 × 12 月 = 2.4 万行`，一次 `GROUP BY employee_id` 扫 2.4 万行。
- 即使全部主体合计 10 家 × 2000 人 = 2 万人、24 万行/年，MySQL 8 在一次索引扫描 + 哈希聚合下仍是百毫秒级。C7 已锁定 < 2000 人，距离需要物化的量级差两个数量级。
- 物化的收益是「省一次 2000 行的聚合」，成本是「引入一个必须与所有写路径同步的第二真源」。这是典型的用高正确性风险换不存在的性能收益。

执行方式（避免大表全扫的关键，不是索引技巧）：

1. **先解析期间集合**：`SELECT id, company_id, period_ym FROM pay_period WHERE period_ym LIKE '2026-%' AND status IN ('LOCKED','ARCHIVED') [AND company_id IN (...)]`。`pay_period` 是小表，这一步免费。
2. **再按期间 id 聚合**：`pay_record WHERE period_id IN (...) AND deleted = 0`，走既有 `idx_period_emp(period_id, employee_id)` / `idx_period_dept(period_id, dept_id)`。
3. 不要写 `WHERE period_ym LIKE '2026-%'` 直接扫 `pay_record`——`period_ym` 上没有单列前导索引（`uk_emp_ym_active` 前导列是 `employee_id`），会退化成全表扫。第 1 步的意义就在这里。

### 2.4 `ARCHIVED` 需不需要

**不需要它来实现年度汇总。** 理由：

- `ARCHIVED` 在本系统里只有枚举、没有动作（`06-需求覆盖审计` 已指出）。它不改变任何报表口径：年度本来就包含 `LOCKED`，把 `ARCHIVED` 一并纳入过滤只是为将来留口。
- 年度汇总真正缺的不是状态，而是「**这一年已经封账、之后重算要留痕**」这个产品语义。而这是**年粒度**的，不是期间粒度：把 12 个期间逐个置 `ARCHIVED` 会引入第二个终态，并且让「12 月发现错误要更正」变成不可逆操作，比现在更糟。
- 因此：M1.5 **不实现归档动作**；`PeriodStatus.ARCHIVED` 继续保留但不可达；年度查询 `status IN ('LOCKED','ARCHIVED')` 为将来兼容。

**但必须补一个真实风险的对策：年度报表会静默重述。** 1 月出了 2026 年报，3 月有人解锁 2026-11 改了数，年报就变了，而管理层手里那份 PDF 不会变。对策不引入新状态，只做两件事：

1. 年度查询返回时，前端用已有的 `/periods?companyId` 自己算「应锁 12 个月 / 实锁 N 个月」，页面上明示「**该年度尚未封账，数据可能变动**」；缺哪几个月直接列出来。不改契约。
2. 导出审计行写入「参与期间 id 列表 + 各期间 `version` + 行数」的指纹（JSON 塞进 `pay_audit_log.new_value`）。重出时人工可比对指纹，能一眼看出「这份年报和上个月那份不是同一批数据」。

### 2.5 年度口径落到现有模型的唯一办法

R18-1「自然年 + 归属期间，13 薪/年终奖按归属期间计入」在当前表结构下的实现方式必须说死，否则实施时一定会走偏：

- 系统里**唯一的时间维度就是 `pay_record.period_ym`**（发放动作在系统外，导出也不含银行代发）。所以「归属期间」= **记录所在的期间**。
- 结论：13 薪/年终奖必须录入到**归属月**的期间（如 2026-12），而不是次年 2 月的发放期间。若录到 2027-01，年报会算进 2027——这是口径问题，不是 bug。
- 这条要写进操作手册和导入模板说明。**不要**为此新增 `attribution_ym` 字段：没有发放动作，多一个「归属月」只会在 99% 的场景下与 `period_ym` 相同，却让所有汇总多一层歧义。真到第 2 期要对接发放/报税时再加。

### 2.6 报表读数的两条铁律

1. **永不读 `pay_period.total_gross/total_net`，永不读 `pay_summary_monthly`**。它们都是展示缓存，`total_*` 只在 changeset 里被刷新，generate/import 后是否同步没有任何约束。报表一律从 `pay_record` 聚合。
2. **`net` 由 SQL 现算 `SUM(gross_amount) - SUM(deduction_amount)`，不要 `SUM(net_amount)`**。存量的 `net_amount` 是写入方各自维护的；读时现算等于对历史数据做一次不变量校验，任何写入 bug 都不会被固化进报表。

### 2.7 风险等级：高（如果做缓存）/ 低（采用本方案）

选「锁定时刷新」的风险是**高**：它不会报错，只会让报表与明细长期不一致，且发现问题时已经过了几个月，无法判断从哪个月开始错的。选「实时聚合」的风险是**低**：唯一代价是将来数据量涨到百万行级别时要重新评估，而那时会有明确的性能证据。

## 3 数据范围如何贯穿

### 3.1 结论

**Service 显式调用，并配一个「唯一收口」；不做数据范围注解 + 拦截器。**

功能权限继续用 `@RequirePerm` + `PermissionInterceptor`（它只回答「能不能做这件事」）；数据范围回答「能看谁的数据」，这两件事的性质不同，不能合并。

### 3.2 为什么否决「注解 + 拦截器」

1. **一个请求会读多种实体，且列的别名不同**。导出要同时读 `pay_record`、`pay_period`、`sys_dept`。拦截器无法知道该给哪张表、哪个别名加条件。
2. **JOIN / 子查询 / 聚合会把它变成 SQL 重写器**。MyBatis-Plus 的 `DataPermissionInterceptor` 类方案对 `SUM(...) GROUP BY`、`LEFT JOIN sys_dept d` 这类语句要么漏、要么错，而且改错时是静默的。
3. **按 id 取单条必须「查后判」而不是「SQL 加条件」**。`GET /records/{id}` 若靠 SQL 过滤，越权与不存在都返回空，前端无法区分 404/403；而且 `pay_record` 的快照列（`company_id/dept_id/employee_id`）与人员表的当前值不同，需要按快照判。现有 `assertRecordVisible(record)` 的形状就是对的。
4. **它会作用于所有 SQL**，包括 `sys_user` / `sys_role` / `sys_role_grant`。系统管理的数据范围语义（按 `sys_user.company_id`）和工资数据完全不同，全局改写必然出事。

### 3.3 必须修的三处（否则复用即泄露）

**① `applyRecordFilter` 对 `ALL` / `COMPANY` 是空操作——这是当前最大的隐患**

```java
case ALL, COMPANY -> { /* 主体级过滤由调用方按期间的 company_id 完成 */ }
```

编制台能活下来，是因为 `RecordService.grid` 在调用前自己加了 `eq(company_id, period.companyId())`。**报表没有「一个期间」这个锚点**：年度查询会跨 12 个期间、可能跨多个主体。只要 `ReportService` 漏写一次公司条件，一个 `COMPANY` 范围的部门主管就能看到全集团年报。这不需要恶意，只需要一次复制粘贴。

修法：**`applyXxxFilter` 永远输出完整谓词**，`ALL` 输出不限制、`COMPANY` 输出 `company_id = 当前主体`，绝不允许「由调用方补」。同时把 `CurrentUser` 补上 `deptId`（`AuthUserRow` 里已经有，拦截器已经在查），去掉 `deptIdOf()` 每次请求再查一次库的隐式成本。

**② 把 SQL 字符串换成「已解析范围对象」**

现在的 `wrapper.apply("dept_id IN (SELECT ... ancestors LIKE ...)")` 之所以安全，只是因为拼进去的是 `Long`。一旦将来有人拼进一个字符串参数就是注入。改成：

```
ResolvedScope { level, companyId, employeeId, Set<Long> deptIds }
  · applyRecord(wrapper)   // 永远调用，ALL 也不跳过
  · applyEmployee(wrapper)
  · applyUser(wrapper)     // 系统管理专用，按 sys_user.company_id
```

`deptIds` 来自 `DeptTreePort.subtreeIds()`（§1.2），每请求解析一次即可（子树规模 < 100）。

**③ 系统管理不能复用工资那套过滤**

`sys_user` 没有 `dept_id = 快照` 的语义，只有 `company_id` + `dept_id` 当前值。给 `admin` 单独提供 `applyUserFilter`：`ALL` → 不过滤；其余 → `company_id = 当前主体`。角色同理（`sys_role.company_id`）。**不要**让 `admin` 调 `applyEmployeeFilter`。

### 3.4 四个复用点的具体做法

| 落点 | 做法 | 漏了会怎样 |
|---|---|---|
| **报表查询** | 设**唯一收口** `ReportQueryService`（月度/年度/工资条三个方法），每个方法第一行 `scope.applyRecord(wrapper)`。`ReportController` 之外**不允许**任何类直接查 `pay_record` 做报表 | 跨主体/跨部门看到工资 |
| **导出** | 导出**只能调用 `ReportQueryService` 的同一方法**，禁止为导出另写一条 SQL。导出 = 把查询结果序列化 | 屏幕上看不到、导出文件里有（最经典的泄露路径） |
| **导入** | 逐行校验 `emp_no` 对应员工是否在范围内，不在则**该行报错**（不是整批拒绝，也不是静默写入）；期间本身先过 `assertPeriodVisible` | 部门主管可以给自己看不见的人改工资 |
| **系统管理** | `applyUserFilter` / `applyRoleFilter` + 授权放大守卫（§6.3） | 分公司管理员改集团角色 |

### 3.5 不漏的工程保障

光靠「记得调用」不可靠，加三道低成本闸门：

1. **收口**：报表只有一个入口类（上面第 1 行），别的类拿不到 `ReportMapper`。
2. **范围矩阵集成测试**：`report` / `export` / `import` 三组端点，每组都用 5 个 scope（`ALL/COMPANY/DEPT_SUB/DEPT/SELF`）× 2 个主体 × 2 个部门的固定种子跑一遍，断言各自可见行数。这是门 4 的硬证据。
3. **一条等价性测试**（同时是 §2 的正确性证据）：对已锁定期间，`GET /reports/monthly` 各部门 `gross/deduction/net` 之和，必须**逐分等于** `GET /periods/{id}/grid` 对该部门行按方向加总的结果。报表与编制台走的是两套 SQL，这条测试是它们唯一的一致性保证。
4. （可选）ArchUnit 包依赖测试固化 §1 的规则。内网离线构建需预先拉依赖，建议放最后做。

### 3.6 风险等级：高

数据范围是需求 5 原文的落点，也是三个新包**唯一**的共同横切关注点。这里做错不会报错、不会崩，只会让某家分公司的工资出现在另一家主管的浏览器里——事后无法从日志区分「正常查看」和「越权查看」，因为查看审计此时还没建。**必须先修 `COMPANY` 空操作，再动报表第一行代码。**

## 4 导出

### 4.1 结论

**同步返回 + 流式写出。三种导出全部同步；不引入异步任务、不引入下载令牌、不落服务器文件（临时文件用完即删）。**

计算依据：一个期间 2000 行 × 约 10 列 = 2 万单元格；年度按人 2000 行；工资条 2000 人 × 约 30 行 ≈ 6 万行。EasyExcel 写出量级是每秒数万行，**全链路 < 5 秒**，离 60 秒网关超时有一个数量级的余量。异步方案要引入任务表、进度轮询、下载令牌、过期清理、权限二次校验五套东西，换来的只是「本来就不慢」的东西不慢。

### 4.2 响应不套信封，错误又要 JSON：干净的做法

现状有一个好基础：**没有全局 `ResponseBodyAdvice`**，`{code,msg,data}` 是 Controller 自己 `Result.ok(...)` 构造的。所以：

- 成功的导出端点写 `void`，直接操作 `HttpServletResponse`，天然不会被套信封。
- 失败时异常照旧冒泡到 `@RestControllerAdvice`，返回 `ResponseEntity<Result>` JSON，`code` 与 HTTP 状态一致（R8 已定）。

唯一必须遵守的顺序规则：

```
① 参数校验 + 数据范围 + payroll:export 权限 + 生成全部行到内存模型（或临时文件）
② 写审计（独立事务 REQUIRES_NEW，失败即中止导出）
③ 设置 Content-Type / Content-Disposition / Content-Length
④ 流式写出
```

**②之前抛出的一切异常都能变成干净的 JSON 错误；④之后再抛异常，响应已提交，任何 advice 都写不进去。** 所以把「所有可能失败的事情」全部压到 ①，写阶段只剩 I/O。这不是技巧，是 HTTP 的物理约束。

具体三条：

1. **不要返回 `byte[]`**（计划 Task 20 写的是 `byte[] export(...)`）。6 万行的 xlsx 在 10–20MB 量级，并发几个导出就是一次 OOM。用 `EasyExcel.write(response.getOutputStream())` 流式写；若行数不确定需要 `Content-Length`，先写临时文件再 `Files.copy`，`finally` 删除。
2. **文件名**：中文/空格用 `filename*=UTF-8''...`（RFC 5987），同时保留 ASCII 兜底 `filename="monthly-2026-11-20261126T101500.xlsx"`，否则个别浏览器会保存成乱码。
3. **审计写在前、行数写进审计**：`action=EXPORT`，`new_value` 存 `{reportType, params, rowCount, periodIds, periodVersions}`。审计失败 → 导出失败（高危动作 fail-closed）。`pay_audit_log` 是只增不改，所以不要想着「导出完成再回填状态」；一次写全。

### 4.3 前端的一个必踩坑（必须写进契约说明）

`axios` 用 `responseType: 'blob'` 时，4xx 的 JSON 错误体会以 **Blob** 形式出现在 `error.response.data`，直接 `JSON.parse` 会失败。必须封一个 `downloadFile()`：

```
if (content-type 包含 application/json) → await blob.text() → JSON.parse → 抛带 msg 的错误
else → 用 Content-Disposition 解析文件名 → createObjectURL 下载
```

这条不写进前端任务书，联调时一定会出现「导出失败但页面没提示，只下载了一个 200 字节的坏文件」。

### 4.4 三种导出与契约缺口（门 2 必须裁定）

R18-2 锁定「汇总报表 + 期间工资表 + 员工工资条」三类，但**冻结的 openapi 只有 `/reports/export`，且 `ReportType` 是封闭枚举 `MONTHLY | ANNUAL`**。后两类在当前契约里**无法表达**。这不是实现问题，是契约缺口，必须在门 2 补一次最小契约修订（v1.1），否则实施时只能私开端点，破坏「契约唯一」。

建议最小修订（三选一，推荐 A）：

- **A. 扩枚举**：`ReportType` 增 `PERIOD_SHEET`、`PAYSLIP`；`ReportExportParams` 增 `periodId`（前两者必填）、`employeeId`（工资条单人可选，缺省全期间）。复用同一端点、同一权限、同一审计、同一套错误语义。改动最小，前端一个下载函数通吃。
- B. 新增两个端点 `POST /reports/period-sheet/export`、`POST /reports/payslip/export`：更清晰，但权限/审计/错误处理要复制三份。
- C. 不做工资条：与 R18-2 冲突，否决。

**工资条的版式建议**：不要「一人一个 sheet」。2000 个 sheet 会撞 Excel 的 sheet 名限制（≤31 字符、禁 `[]:*?/\`）、生成慢、打开卡。用**单 sheet 重复块**：每人一个标题区 + 明细区 + 空行分隔，A4 打印分页交给打印设置。实现简单、行数线性、无命名冲突。

### 4.5 四个关注点逐条

| 关注点 | 做法 | 残余风险 |
|---|---|---|
| **大文件** | 流式写；行数上限由「一个期间 ≤ 2000 人」「年度 ≤ 2.4 万行」自然兜住；工资条 ≤ 2000 块 | 客户端断连导致写一半；服务端只是停止写出，不留垃圾（临时文件 `finally` 删） |
| **超时** | 同步路径 < 5s，网关默认 60s 足够；若前端同时点多个导出，浏览器并发限制会排队，不需要服务端限流 | 内网 nginx 若把 `proxy_read_timeout` 调过小（如 10s）会截断；运维文档写明导出路径 ≥ 60s |
| **权限** | `@RequirePerm("payroll:export")` + §3 的数据范围（导出**必须**走同一个 `ReportQueryService`） | 只校验功能权限、忘了数据范围 = 导出比屏幕看得更多 |
| **审计** | 响应提交前写一条 `EXPORT`，含条件、行数、期间版本指纹；写失败即导出失败 | 审计表无 `status` 列，写「已开始」就一定是「已开始」；行数在写前已确定，所以审计内容仍然准确 |

### 4.6 明文导出的额外提醒

R18-3 已锁定导出明文、静态存储加密。要点不是「不脱敏」而是「明文文件一旦离开系统就不受控」：

- 服务端**不持久化**导出文件（流式，无残留）；临时文件 `finally` 删除。
- 页眉/页脚写「导出人 + 导出时间 + 查询条件」——这不是安全控制，只是溯源线索，别把它当水印防泄露。
- 若某个导出需要证件号/手机号，那是**另一个决策**：R18-3 说的是「导出不搞脱敏」，不等于「工资条里必须带证件号」。建议工资条/工资表默认**不含**证件号，需要时单独确认。这条要在门 2 落成一句话，否则实施时两边都会猜。

### 4.7 风险等级：高

- 安全面：导出是本系统**唯一**把全量工资变成可外发文件的出口，权限/范围任一漏掉就是批量泄露。
- 工程面：响应已提交后的异常无法 JSON 化，是「看起来能跑、出错时变成坏文件」的典型；必须用「准备/写出」两段式结构从设计上杜绝。

## 5 导入

### 5.1 结论

**批次表 + 原始文件重放。提交时重新校验，不信任预校验结果。不引入 staging 表、不在内存持有解析结果。**

### 5.2 为什么是重放而不是内存

| 事件 | 内存持有 | 批次表 + 重放 |
|---|---|---|
| 预校验后服务重启/发版 | 用户白传一次，且拿到的 `batchId` 失效 | 无影响，文件在盘上 |
| 预校验后改了科目/人员/期间状态 | 用旧快照提交 → **静默写入过期数据** | 提交时重校验 → 明确报错 |
| 两个浏览器提交同一批次 | 两个线程各自持有一份 | 批次行 `FOR UPDATE` 串行化 |
| 审计「这份文件到底导了什么」 | 无痕迹 | 文件 hash + 路径 + 批次行 |
| 内存占用 | 5 万行 × 一行对象，几百 MB 起 | 流式读，常数内存 |

重放的代价是重新解析一次 xlsx：5 万行 EasyExcel 流式读在秒级，完全可接受。**不要**为此建 staging 表——那是一张必须和主表同步、必须清理、必须处理半成品批次的新表，正确性成本远高于解析成本。

### 5.3 状态与并发：不加新枚举也能串行化

契约里的 `ImportBatchStatus` 只有 `VALIDATING / VALIDATED / COMMITTED / FAILED`，**没有 `COMMITTING`**。不要为了加一个中间态去改契约。正确做法是把「提交」做成一个**单事务**，用行锁表达「正在提交」：

```
commit(batchId):
  ① SELECT * FROM pay_import_batch WHERE id=? FOR UPDATE   -- 串行化同一批次
     status != VALIDATED → 409
  ② SELECT * FROM pay_period WHERE id=? FOR UPDATE          -- 串行化同一期间的所有写
     status 非 DRAFT/EDITING → 409
  ③ 抢期间租约（owner = "import:"+batchId，TTL 10min，finally 释放）
     抢不到 → 409「本期有生成/导入任务进行中」
  ④ 重新读原始文件 → 重跑校验器 → 任何一行失败 → 整批 409 + 新错误报告
  ⑤ 写入（500 行一批 JDBC batch）→ 每条记录 recalc → 末尾刷新一次期间合计
  ⑥ status = COMMITTED, finished_at = NOW()
  ⑦ 提交事务；写审计
```

- 崩溃在任何一步，事务回滚 → 批次仍是 `VALIDATED`，可重试；不会出现「状态说已提交、数据没进去」。
- ① 的 `FOR UPDATE` 同时解决了「同一批次并发提交」；② 的期间行锁解决了「不同批次并发写同一期间导致合计互相覆盖」（这是比同批次并发更隐蔽的问题：两批各改不同员工，但都重算期间合计，后者会把前者的合计覆盖掉——行锁让它们排队，两次刷新都基于完整数据）。
- ③ 的租约与 `GenerateService` 共用，保证「生成」和「导入」不并发；短写路径（changeset）靠 ② 的行锁排队，不需要租约。

### 5.4 幂等：hash 查重只针对「已提交」

契约写的是「**已提交过**的文件 hash 会被拒绝（409）」。所以：

- 校验时：`EXISTS(SELECT 1 FROM pay_import_batch WHERE period_id=? AND file_hash=? AND status='COMMITTED')` → 409。
- 提交时**再查一次**（①之后），防两个批次同时校验、先后提交。
- 不能把「同 hash 的 VALIDATED 批次」也拒掉：用户预校验后发现问题、修了期间状态再重传同一文件是正常操作；把 VALIDATED 也算「已用」会让同一文件永远传不上去。
- 也不能为此加唯一索引：MySQL 没有部分唯一索引，`UNIQUE(period_id, file_hash)` 会把 VALIDATED 也拦住。**查重是服务层规则，安全性由 ①+② 的行锁保证**（同期间提交串行 → 先查后插无竞态）。

### 5.5 导入的写边界：只改已有记录，不创建记录

**结论：导入是「修改管道」，不是「创建管道」。目标员工在本期间没有 `pay_record` 的，该行报错「本期无核算记录，请先生成」。**

理由：创建一条记录需要基本工资、工龄、入职离职折算、固定津贴——那是 `PayrollCalculator` 的职责。导入绕过计算器直接建记录，会产出「有变动项、没有固定项、合计只等于绩效」的假记录，而且它会被 `uk_emp_ym_active` 占住，之后生成时变成「本期已有」走 UPDATE，永远补不回固定项。这是最难排查的一类错账。

推论：
- `FIXED` 导入写的是**本期固定项金额**（`pay_record_item.source=IMPORT`），受 `pay_item.importable=1` 约束；`BASE_SALARY`（importable=0）与 `SENIORITY_PAY`（COMPUTED）**永远不可导入**。这正好与种子数据一致（`POST_ALLOW importable=1, editable=0`）：**可导入 ≠ 可手工编辑**，两者是独立的开关。这一点要在任务书里写明，否则实施者会以为 `editable=0` 就不能导。
- 若业务真正想要的是「人员/调薪的批量初始化」，那是**另一个管道**（`POST /employees/import`，审计 P1-4），写 `emp_employee` / `emp_comp_profile`，不能复用本契约的 `periodId`。门 2 要说清楚，否则 M1.5 交付的 `FIXED` 导入会被验收方认为「不是他们要的那个」——`06-需求覆盖审计` 第六节第 7 条已经提过这个歧义。

### 5.6 校验规则（预校验与提交共用同一份实现）

必须逐行检查，缺一条就是脏数据入口：

| 类别 | 规则 | 失败处理 |
|---|---|---|
| 文件 | 扩展名/魔数 xlsx、≤10MB、≤5 万行、表头含「工号」 | 整批 FAILED，批次行记原因 |
| 表头 | 未知科目列 → 报错；模板里的列可缺 | 行级/批级 |
| 期间 | 存在、可见、`DRAFT/EDITING` | 整批 409/403 |
| 员工 | `emp_no` 存在、未删除、**在数据范围内** | 行级 |
| 记录 | 本期间存在 `pay_record` | 行级 |
| 科目 | 存在、`importable=1`、方向与列一致 | 行级 |
| 金额 | 非负、可解析、**小数位 ≤ `precision_scale`** | 行级 |
| 文件内重复 | 同一 `emp_no` 出现两次（L1 防线） | 行级，列出冲突行号 |
| 模式 | `UPSERT / APPEND / INSERT_ONLY` 三选一 | 批级 |

小数位超过科目精度时**报错而不是四舍五入**：手工编辑静默 `HALF_UP` 是交互场景的妥协，批量导入把 0.005 悄悄变成 0.01 是财务事故。宁可让用户改文件。

### 5.7 存储

`payroll.storage.local-path` 已经配好，`pay_import_batch.file_path` 也已存在（注释写的是 MinIO，与实际 local 不一致，改成「相对 storage 根的路径」）。落盘名用 `hash` 或 UUID，**不用客户端文件名拼路径**（路径穿越）；原始文件名只存 `file_name` 列用于展示。错误报告 `pay_import_error` 只存前 5000 行（配置已存在），超出在报告里写「仅显示前 5000 条」。

### 5.8 风险等级：高

导入是**唯一**能批量改变金额的入口，一次逻辑错误就是 2000 人同错一个月，且逐条更正的成本极高（只能解锁→重导）。所有「信任预校验结果」「导入创建记录」「同期间并发提交」的设计都会产出这类事故，且都不会立刻报错。

## 6 系统管理与权限缓存

### 6.1 结论

**不引入权限缓存。** 现状（`PermissionInterceptor` 每请求调 `findPermissions` + `findDataScopes`）就是本系统的最优解，不要优化它。

### 6.2 全量替换对正在登录的用户意味着什么

先说清现状事实：

- token 是**无状态**的，payload 只有 `userId:expireAt` + HMAC（`TokenService`），**权限不在 token 里**。
- 每个请求都从库里现查权限点与数据范围。
- `PUT /roles/{id}/grants` 是「先删后插」的单事务。

由此可以给出确定的语义：

| 场景 | 结果 | 说明 |
|---|---|---|
| 管理员移除某角色的 `payroll:export` | **该角色下所有用户的下一次请求立即 403** | 没有缓存，不需要失效，不存在「改了还生效」 |
| 用户正打开编制台，编辑中被移除 `record:edit` | 保存时 403；**未保存的改动丢失** | 前端收到 403 后重新拉 `/auth/me`，提示「权限已变更，请刷新」，并把本地 dirty 状态保留在内存里不要清空——这是体验问题，不是安全问题（服务端从未放行） |
| 两个并发请求撞上替换事务 | 各自看到替换前或替换后的**完整**集合，不会看到空集合 | 先删后插在同一事务内，InnoDB 对读者原子 |
| 停用角色（`status=0`） | 立刻生效 | `AuthMapper` 的 JOIN 已带 `r.status=1` |
| 删除用户角色 | 立刻生效 | 同上 |
| 修改角色 `data_scope`（放宽） | 立刻生效；因为「取最宽者」，**加角色只会放宽、不会收紧** | 这是模型固有语义，必须写进管理页提示，否则管理员会以为「加一个窄角色会限制他」 |

**所以「改了角色但用户还是老权限」在本设计里不可能发生——前提是不要加缓存。** 若加 Caffeine/Redis，就必须自己造一套「授权变更 → 失效」协议，而这张表一年改不了几次，每请求两条走索引的小查询在 2000 用户规模下的成本可以忽略。**用缓存换来的那点 CPU，不值得换一类最难复现的线上问题。**

### 6.3 必须补的三个守卫（否则系统管理本身成为提权面）

契约只写了「`dataScope` 只能授予自身范围或更窄」，这不够。

1. **授权放大守卫**：非 `ALL` 操作者，其授予/保留的每个权限点必须 ∈ 操作者自身权限集合；否则一个分公司管理员（有 `sys:role:edit`、没有 `payroll:export`）可以给自己建一个带 `payroll:export` 的角色并挂上去，**自我提权**。`sys:role:edit` 本身不是全权限，契约也没说它是。
2. **数据范围序**：`ALL > COMPANY > DEPT_SUB > DEPT > SELF`。创建/修改角色与全量替换 grants 时都要校验；`SELF` 保留但按 R18-4 不再是主场景。
3. **自锁守卫（`AdminSafetyGuard`）**：
   - 不能停用自己（契约已写，实现时容易漏）。
   - 不能通过自己的操作让自己失去 `sys:role:edit` / `sys:user:edit`（例如把自己最后一个管理角色摘掉、或把该角色唯一的 `sys:role:edit` 删掉）。
   - 不能停用/删除**最后一个**仍持有 `sys:role:edit` 的启用用户——否则系统永久失去可管理性，只能改库。
   - 角色 `company_id` 必须等于被分配用户的 `company_id`（`ALL` 操作者除外），否则分公司管理员可以把别家角色挂到本家用户上。

### 6.4 契约要求「重置密码后已签发 token 全部作废」——现在做不到

`TokenService` 的 token 只有 `userId + expireAt + HMAC`，服务端不存会话。改密码后旧 token 仍在有效期内可用，**与契约 §`/users/{id}/reset-password` 的描述直接冲突**。

最小修法：`sys_user` 增加 `token_version INT NOT NULL DEFAULT 0`；签发时把版本写进 payload（`userId:expireAt:ver`），拦截器已经 `findById` 拿到用户行，顺手比较版本，不匹配 → 401。重置密码、停用用户时 `token_version+1`。

- 升级影响：token 格式变更，**部署时所有在线会话失效一次**。内网系统可接受，但要写进发布说明。
- 不需要为「角色变更」升版本：权限是每请求现查的，升版本只会把用户踢下线，没有意义。

### 6.5 全量替换的审计

`pay_audit_log` 零写入者（P1-10），系统管理正好是它的第一个真实用户。每次 `PUT /roles/{id}/grants` 写一条：`biz_type=ROLE`、`action=GRANT_REPLACE`、`old_value`/`new_value` 各存 JSON 数组（新增/移除的差集）。用户角色变更、角色删除、密码重置同理。**这是合规要求里唯一能在事后回答「谁在什么时候把导出权限给了谁」的证据**，不能省。

### 6.6 风险等级：中

不做缓存 + 每请求查库，正确性风险极低；真正的风险集中在**提权与自锁**（§6.3）和**token 不失效**（§6.4），两者都是「功能正常但安全语义错」的类型，不会在常规联调里暴露。

### 7.2 门 3 实施推荐顺序

按 R17「不互相阻碍一律并行」，分三波：

**第 0 波（地基，串行，必须先做完）**
1. 依赖整理：`pay_record` 两个 Mapper 迁出 `run`；抽 `record.PayRecordWriter`；`DataScopeEnforcer` 去业务 Mapper + `DeptTreePort` + 永远输出谓词 + `CurrentUser.deptId`。
2. 横切件：`audit` 包（`AuditService`，`REQUIRES_NEW`）；`sys_user.token_version`（DDL + token 载荷 + 拦截器校验 + 重置密码自增）。
3. `pay_summary_monthly` 处置（推荐 `DROP TABLE` + 迁移脚本注释）。

> 为什么地基必须在最前：它同时被 `report`（范围）、`importjob`（写入器/范围）、`admin`（token/审计）依赖。放在后面做，等于三个包各写一套再拆，返工量是现在做的三倍。这一波的验收证据是「既有 79 单测 + 4 端到端全绿」——纯重构不改行为。

**第 1 波（三块并行，互不依赖）**
4. `admin`（系统管理）：最简单、无外部依赖，且它是「权限区分」可验收的前提（P0-5/P0-6 互为前提）。验收 = §6.3 三条守卫 + 重置密码旧 token 失效的集成测试。
5. `report`（月度/年度查询）：只读，依赖地基的范围组件。验收 = §3.5 的范围矩阵 + 与编制台的逐分等价测试 + 未锁月份为空。**不做导出**。
6. `importjob`：可与 `report` 并行，依赖地基的写入器与租约。验收 = 预校验不落库、提交重校验、同批次并发提交 409、同期间两批并发合计正确、导入不改别部门员工、文件内重复报行号。

**第 2 波（依赖第 1 波）**
7. `export`：必须等 `report` 的查询收口稳定，且必须先做 §4.4 的契约 v1.1 修订。验收 = 范围矩阵在「导出文件行数」上再跑一遍（与屏幕一致）、审计行存在且含指纹、无权限 403 JSON、金额为文本、中文文件名。

**第 3 波（收口）**
8. 全量联调（Task 26）+ 门 4 的独立评审复跑。

> 并行提示：前端可在第 1 波期间用契约 v1.1 mock 开工报表页与系统管理页；导入向导建议等第 1 波 `importjob` 的错误码定稿后再做，否则错误文案会反复改。

### 7.3 门 2 需要裁定的 5 件事（不裁定则第 1 波会卡住）

1. 契约 v1.1：`ReportType` 是否按 §4.4 A 方案扩两种导出。
2. 工资条/工资表是否包含证件号（R18-3 只说「导出明文」，没说「必须带证件号」）。

## 8 我反对的既有设计（汇总）

1. **反对 `pay_summary_monthly` 的存在方式**：零写入者却被 DDL 注释描述为「期间锁定时刷新」，这是给未来实现者埋的第二真源陷阱。要么删表，要么在注释里写死「M1.5 起不启用」。
2. **反对把 `ARCHIVED` 做成期间级归档动作**：它是死枚举，年度报表不需要它；真需要封账应该做年粒度，否则 12 月更正会变成不可逆。
3. **反对 `DataScopeEnforcer` 留在 `security` 且直接依赖业务 Mapper**：横切组件反向依赖业务，且 `applyRecordFilter` 对 `ALL/COMPANY` 静默 no-op——这条现在没出事，只是因为编制台自己补了条件，报表一定会踩。
4. **反对 `pay_record` 的两个 Mapper 放在 `run.mapper`**：造成 `run ↔ record` 包级环。
5. **反对计划里 `byte[] export(...)` 的签名**：6 万行导出的正确姿势是流式，不是字节数组。
6. **反对把新包命名为 `system`**：与 `java.lang.System` 和 `sys_*` 表名双重混淆，建议 `admin`。
7. **反对在 M1.5 给权限加缓存**：现状每请求查库是正确设计，加缓存等于自己造一类「改了不生效」的线上问题。
8. **反对导入创建记录**：绕过计算器的记录会永久占住 `uk_emp_ym_active`，之后生成也补不回来。
9. **反对异步导出**：三种导出都在 5 秒量级，异步换来的复杂度（任务表/轮询/令牌/清理）没有任何收益。
10. **反对「导出另写一条 SQL」**：屏幕与文件必须是同一套查询，否则范围差异一定会在某次迭代中出现。
