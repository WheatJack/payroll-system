## 一、事务与并发

### C1. 同一生效日的薪酬档案「第二次更正」必然 500 —— `CompProfileService.java:169-173`（唯一键见 `db/schema-mysql.sql:168`）

```
profileMapper.deleteById(sameDay.getId());   // 逻辑删除 → deleted=1
...
profileMapper.insert(entity);                // 同 (employee_id, effective_from) 再插一行 deleted=0
```

- **问题**：`emp_comp_profile` 的唯一键是 `uk_emp_effective(employee_id, effective_from, deleted)`。同一天第一次改薪：旧段 `deleted 0→1`，新段 `deleted=0`，成功。**同一天再改一次**：把新段 `deleted 0→1`，与第一次留下的 `(employee, 该日, deleted=1)` 撞唯一键 → `DuplicateKeyException` → 全仓兜底翻译成 **409「数据重复，请刷新后重试」**（`GlobalExceptionHandler.java:100`），而实际上什么都没重复，用户重试仍然失败。
- **为什么危险**：录错一次工资是常态（打错一位数）。第二次更正会**永久失败**，HR 只能改生效日绕开——这会把工资的生效日期挪走，等于篡改工资历史。错误提示完全指错方向，运维会去查「重复数据」，查不到。
- **为什么测试发现不了**：`CompProfileServiceTest:132` 只覆盖了「同一天重新保存**一次**」；没有任何用例做两次连续同日期保存。
- **改法**（任选其一，推荐 1）：
  1. 不要用 `deleted` 参与唯一键。改成 `uk(employee_id, effective_from)` + 真删除旧段（或把 `effective_from` 加一个版本列/改为 `uk(employee_id, effective_from, status)` 并保证同时最多一条 `status=1`；MySQL 用生成列 `active_key = IF(status=1 AND deleted=0,1,NULL)` 更稳）。
  2. 若坚持 `(…, deleted)`：作废时不要写 1，改写该行 `deleted = 该行 id`（唯一值），让每一代历史段互不冲突。
  3. 至少把 `DuplicateKeyException` 在这一处捕获，翻译成「该生效日已有作废记录，请使用不同的生效日或联系管理员」，不要落到通用 409。
- 顺带：第一次「作废」也会和**历史回填/重复执行脚本**撞键（任何把 `deleted` 置 1 的批处理），风险不止 UI 路径。

### C2. FIXED 类导入的金额在「重新生成」时被静默抹掉 —— `GenerateService.java:309-323 / 391-413`，对照 `ImportService.java:416-444`

- **链路**：`/import?bizType=FIXED` 是受支持的能力（`ImportValidator.java:346-355` 允许 FIXED 类 importable 科目导入；`POST_ALLOW` 即 FIXED 且 importable=1）。`ImportService.upsertItem` 把结果写成 `category=FIXED, source=IMPORT`。
- 重算时 `processBatch` 只保留两类已有金额：
  - `loadVariableAmounts`：**只**保留 `category == "VARIABLE"`（`:391-401`）；
  - `loadManualItems`：**只**保留 `source == "MANUAL"`（`:404-413`）。
  - `source=IMPORT && category=FIXED` 两边都不匹配 → 该明细被 `recordItemMapper.delete(...)` 整体删除，再按薪酬档案重新插入。
- **为什么危险**：HR 先导入固定津贴（如岗位津贴按人微调 1500），再因为新入职/离职补跑一次生成（`EDITING` 期间允许），导入结果**无声消失**，工资少发且没有任何告警——`progress` 全绿、run=SUCCESS。等发现时期间可能已锁定。
- **为什么测试发现不了**：`ImportServiceTest` 与 `GenerateServiceTest` 各自覆盖得都不错，但**没有一条用例是「先导入 FIXED、再 startGenerate」**；单测的 setup 里恰好是先生成后导入，顺序掩盖了问题。
- **改法**：把「重算时要保留的手工/外部金额」定义成一个显式规则，例如新增 `loadPreservedAmounts`：`source IN ('MANUAL','IMPORT')` 覆盖所有类别（IMPORT 的 FIXED 就是「本期覆盖档案」的语义）；或导入 FIXED 时改写 `source=MANUAL`（但其语义是"人改的"，不推荐）。另加一条回归用例：`import(FIXED) → startGenerate → item 金额不变`。

### C3. 生成失败（有员工没算出来）仍然可以锁定，漏算的人被永久留在外面 —— `PeriodService.java:198-229`、`GenerateService.java:179-183, 523-531`

- 现状：部分员工失败 → `pay_run.status=FAILED` + `pay_period.last_run_fail_count=N`，期间状态仍是 `EDITING`。`lock()` 只校验 `status==EDITING`、租约未过期、锁定人≠编制人，**没有任何一处检查 `last_run_fail_count > 0` 或最近一次 run 是否 FAILED**。
- **为什么危险**：锁定期是复核人（PAYROLL_REVIEWER）做的，编制人这一侧的失败弹窗他一关就看不到了；`lastRunFailCount` 只是列表页的一个数字。锁定后 `syncRecordStatus` 把已有记录置 CONFIRMED，报表只统计已锁定期间 → **少发的人从头到尾没有任何一处硬拦截，且此后再改必须走解锁这个高危动作**。代码自己在 `GenerateService:178` 写了「HR 会据此直接锁定，把漏算的人永久留在外面」，但只在**生成侧**改了 run 状态，**锁定侧**没有配套闸门。
- **为什么测试发现不了**：`PeriodServiceTest` 的 8 个锁定用例里没有「先制造 `last_run_fail_count>0` 再 lock」；`lastRunFailCount` 在全仓测试中零引用。
- **改法**：`lock()` 内加硬校验：`lastRunFailCount > 0` → 409「本期有 N 人未生成成功，请先处理失败明细后再锁定」；或要求请求体显式带 `acknowledgeFailures=true`（并写入审计）。同时给 `pay_run` 增加「本期最近一次 run 状态」的读取（按 `period_id` 取最新一条），而不是只依赖期间上的计数。

### I1. 租约过期时间用 JVM 时钟、判定条件用 MySQL `NOW(6)` —— `PeriodMapper.java:20-32`、`PeriodService.java:272-278, 213-215`

```sql
WHERE id = #{id} AND (processing_owner IS NULL OR processing_expire_at < NOW(6))
```

`expireAt` 是 `LocalDateTime.now().plus(ttl)` 在 **JVM** 里算的，`NOW(6)` 是 **MySQL 会话时区**的时间（`time_zone` 默认 SYSTEM，容器里通常是 UTC）。JDBC 参数里带 `serverTimezone=Asia/Shanghai`，但 `LocalDateTime` 是不做时区换算直接写字的。

- **为什么危险**：只要 JVM 与 DB 主机时区不一致（容器化部署最常见的状态），租约就是错的：
  - JVM=UTC、DB=+08（或反向）：刚抢到的租约在 DB 看来已是 8 小时前 → **并发生成拦不住**，两个生成任务交错写同一批记录（每批都在行锁上排队，但 A 批 1、B 批 1、A 批 2… 交叉执行，`version_no` 被叠加、期间合计可能取自中间态）；
  - DB 比 JVM 慢 8 小时：租约 8 小时后才过期 → **进程崩过一次，该期间 8 小时内无法重新生成**（一直 409「正在处理中」）。
- **为什么测试发现不了**：`PeriodServiceTest:63-67` 用 `DATE_SUB(NOW(6), INTERVAL 1 MINUTE)` **直接在 SQL 里造过期时间**，恰好把被审查的时间源换成了 DB，永远走不到「JVM 与 DB 时钟不一致」这条分支。
- **改法**：过期时间在 DB 侧算——`UPDATE ... SET processing_expire_at = DATE_ADD(NOW(6), INTERVAL #{ttlSeconds} SECOND)`；或统一 `spring.jackson.time-zone` 之外再显式 `connectionTimeZone=LOCAL`/容器 `TZ` 双端对齐，并加一条「租约在 DB 里写入后立即读取，断言剩余 TTL≈配置值」的集成测试。`lock()` 里拿 Java 时钟比较 `processingExpireAt` 也要同步改为 DB 侧判定（或同一时区）。

### I2. `openRun` 在 try/finally 之外：一次 DB 抖动会把租约占满 10 分钟 —— `GenerateService.java:169-176`

```java
if (!periodService.tryAcquire(...)) throw ...;
PayRunEntity run = openRun(periodId, operatorId);   // ← 在 try 之外
Progress progress = new Progress();
try { ... } finally { periodService.release(periodId, owner); }
```

- `openRun` 的 `runMapper.insert` 抛异常（连接池耗尽、唯一键、超时）时 `finally` 根本不会执行，期间处理租约保留 10 分钟，用户反复点生成全部 409，只能等 TTL。`markEditing` 之类后续步骤都在 try 内，唯独第一条写语句在外。
- **改法**：把 `openRun` 移进 try，或在 `tryAcquire` 成功后立刻 `try { ... } finally` 包住整个后续；`release` 本身失败只记日志。

### I3. 进程崩溃后残留 `RUNNING` 的 run 没有回收，且租约一过期就能锁定半成品 —— `GenerateService.java:174-206`、`PeriodService.java:212-216`

- 生成是**同步**执行（注释已承认）。JVM 被杀/部署重启时：`pay_run` 永远停在 `RUNNING`，`processing_owner` 在 10 分钟后过期；此后：
  1. 前端轮询 `/runs/{id}` 永远拿到 `RUNNING`，没有任何超时判定；
  2. 若该期间此前已有一次成功生成（状态已 `EDITING`），复核人可以立刻锁定——而第 k+1 批之后的数据还是**上一版**（薪酬档案已改、导入已提交），期间合计是拼接出来的。
- **改法**：① 读取进度时若 `status=RUNNING && startedAt + leaseTTL < now()`，视为 `FAILED`（并回写 `error_msg=“进程中断”`）；② `lock()` 增加「本期无 `RUNNING` 的 run」检查；③ 或提供启动时/定时任务把超时 `RUNNING` 批量置 FAILED。

### I4. 事务回滚后 `Progress` 计数器不回滚 → run 里的成功人数与实际库里的行数不一致 —— `GenerateService.java:259-268, 337-341, 375`

- `progress.success++` 在 `processBatch` 的循环里执行，而 `processBatch` 整体在一个 `TransactionTemplate` 事务内。一旦该批在**计算器之外**抛异常（例如 `PayCategory.valueOf(entity.getCategory())` 遇到脏值、`employmentMapper.findDeptAt` 超时、`recordMapper.updateById` 死锁重试失败、`insertItems` 撞键），事务整体回滚，但 `progress` 已经把这一批前面的人算成成功了。
- 结果：`closeRun` 写下 `emp_success=N`，但库里少一整批（最多 500 行）。run 是 FAILED，可「成功 1800 / 失败 200」这种数字会被 HR 当成「只差这 200 人」去处理，实际缺的更多。此外错误信息只留下最后一条异常，没有「第几批回滚」的信息。
- **改法**：让 `Progress` 按批提交——`processBatch` 返回本批的 `(success, failed, skipped, errors)`，事务成功返回后再合并进 `Progress`；或在 `transactionTemplate.execute` 的 lambda 里用局部计数器，commit 后合并。异常路径记录 `batchIndex`。

### I5. 导入的「预校验」和「提交」都在事务内做文件 IO + 全量 Excel 解析 —— `ImportService.java:174-245, 320-358`

- `validate()` 标了 `@Transactional`，事务里做了：落临时文件、算 SHA-256、复制到存储目录、插批次行、**然后解析整个 xlsx（上限 5 万行）**、批量插错误行、更新批次。解析慢时事务一直开着，并且批次行的唯一键索引锁在整个解析期间不释放——同一文件并发上传会长时间卡在唯一索引上。
- `commit()` 更严重：`applyInTransaction` 先 `SELECT ... FOR UPDATE` 锁住 `pay_period` 行（`:336`），**然后在持锁状态下重新解析整份 Excel**（`:341`），再逐行写库。这意味着一次 5 万行的导入提交会**把该期间锁住几分钟到几十分钟**：生成、编制台保存、锁定全部排在后面等行锁，容易触发前端超时、连接池耗尽、以及 InnoDB `lock wait timeout`。
- **为什么测试发现不了**：单测文件只有几行，解析 + 逐行写都在毫秒级；并发/大数据量验收走的是生成路径，不是 5 万行导入。
- **改法**：① `validate` 拆成「事务外 解析/落盘/校验 → 事务内 只写批次与错误行」两段；② `commit` 把重放解析移到加锁之前（校验结果只是「预览快照」，提交时再在事务内做**轻量**校验：期间状态 + 记录版本/归属），或限定单批次行数（如 5000）并在 UI 上分批；③ `apply` 改为分批（每 500 行一个事务）并显式提交，避免单事务几万次 DML。

### I6. 导入提交逐行 N+1，5 万行会在**一个事务**里发出十几万条 SQL —— `ImportService.java:388-400, 416-473`

每行每项：`upsertItem` = `SELECT` + `UPDATE`/`INSERT`；`recalcRecord` = `SELECT pay_record` + `SELECT pay_record_item` + `UPDATE pay_record`。3 个科目 × 5 万行 ≈ 75 万次往返，全部在 `applyInTransaction` 的单个事务里，且持期间行锁（见 I5）。

- **改法**：一次 `IN` 查出本批次所有 record 与已有 item（按 recordId/itemCode 建 Map），内存比对后 `batch`（`rewriteBatchedStatements=true` 已开）插入/更新；合计用内存里的 item map 现算，不再逐行回查。规模再大时按 500 行/事务分批。

### I7. `commit` 没有校验批次归属，任意有 import 权限的同主体账号可提交他人的批次 —— `ImportService.java:295-337`，对照 `:282-291`

- `get()` / `errors()` 都调了 `assertBatchReadable`（非 ALL/COMPANY 只能看自己发起的批次），但 `commit()` 和 `applyInTransaction()` 只校验了期间可见。同主体、同部门的另一个账号可以直接 `POST /import/{别人的batchId}/commit`：把别人尚未提交的导入提交掉，或消耗掉「一次性提交」的机会。审计里 `IMPORT/UPDATE/commit` 记的操作人是提交者，而 `pay_import_batch.operator_id` 是上传者，事后追责会指向错的人。
- **影响有限但不该存在**（校验器会按数据范围逐行拦截，跨部门的批次会 403 回滚）。**改法**：`commit()` 入口就调 `assertBatchReadable(batch)`；或明确「同部门可协作提交」并把提交者写进批次/审计。

### I8. 导入原始文件落在相对路径 `./data/import`，容器重启/多实例后「提交」必然失败 —— `ImportService.java:111, 126, 190-196, 341`

- 文件按内容 hash 存本地磁盘；`commit` 时依赖 `Path.of(batch.getFilePath())` 重新解析。只要：① 部署成容器（cwd 在镜像内，`./data` 不在挂载卷里）；② 滚动发布会换实例/换目录；③ 多副本部署——文件就不在了。此时 `validator.validate(Path.of(...))` 抛 `NoSuchFileException`（`RuntimeException`），前端拿到 **500「系统异常」**，批次永久停在 VALIDATED，且流程里没有任何一条路径能重新上传（同文件 hash 撞唯一键 → 409）。
- 表结构注释写的是「MinIO 对象路径」，实现却是本地路径，二者语义不同。
- **改法**：改绝对路径并挂持久卷（`payroll.storage.local-path=/var/lib/payroll/import`），多实例必须用对象存储；`commit` 前 `Files.exists` 检查并返回 409「原始文件已不可用，请重新上传」（不同 hash 才可能重传，需给批次加取消/重建入口）；同时给文件加保留期清理策略（现在只增不删，长期会占满磁盘）。

### I9. 薪酬档案并发保存无锁，区间校验是 TOCTOU —— `CompProfileService.java:137-193, 231-240`

- `loadTimeline` 是普通读，没有 `FOR UPDATE`，也没有按 `employee_id` 的锁。两个 HR 同时给同一员工改薪（或一个人双开页面提交两次），都能读到相同的 timeline、都通过 `assertNoOverlap`，最终插入两条**重叠**的区间。
- 重叠后 `effectiveAt` 用 `ORDER BY effective_from DESC LIMIT 1` 取「较晚的一条」——即**后插入的那条**，但两条的金额可能不同；再叠加「按生效日截断」的逻辑，后续保存可能把别人的段截掉。工资会按不确定的档案发放。
- 唯一键 `(employee_id, effective_from, deleted)` 只挡同一天，挡不住「A 段 1/1~6/30、B 段 3/1~∞」这种交叉。
- **改法**：`save()` 开头对员工行加锁（`SELECT id FROM emp_employee WHERE id=? FOR UPDATE`），或对 `emp_comp_profile` 的 `employee_id` 使用 `SELECT ... FOR UPDATE`；`assertNoOverlap` 保留为兜底，并把冲突翻译成 409 可操作提示。

### M1. `lock()` / `unlock()` 是「读快照 → 改 → 写」，没有行锁 —— `PeriodService.java:198-257`

- 两个复核人同时点锁定：都读到 `EDITING`，都 `updateById` 成功，写两条 LOCK 审计；解锁同理（两条 UNLOCK、`unlock_reason` 后者覆盖前者）。
- 不会造成数据损坏，但审计里会出现两条互相矛盾的高危动作记录，合规核查时无法解释。
- **改法**：`lock`/`unlock` 用 `periodMapper.selectForUpdate`（与 `assertWritableForUpdate` 一致），并把状态判断放在锁内。

### M2. `transfer()` 对「当前开放区间」的读取无锁 —— `EmployeeService.java:227-241`

两个并发调动（或「改部门」与「调动」并发）都能读到同一个 `end_date IS NULL` 的区间，各自关闭并追加一条，产生**两条开放区间**。`findCompanyAt/findDeptAt` 用 `start_date DESC, id DESC` 取最新，短期内看起来没错，但历史重算时同一日期命中哪条取决于 id，结果不可复现。**改法**：先锁员工行或对 `emp_employment` 按 `employee_id` 做 `FOR UPDATE` 读开放区间。

## 二、SQL 与数据访问

### I10. `requireItem` 对「全局科目 + 主体同名科目」的解析不确定，且与计算/重算路径口径相反 —— `ItemService.java:142-151`，对照 `:41-53`、`:59-71`、`RecordService.java:285-289`、`ImportService.java:403-408`

- `create()` 只靠 `uk_item_code(company_id, item_code)` 去重，**允许主体建一个与全局（company_id=0）同 code 的覆盖科目**。
- 此时三条路径各说各话（三者用的都是「同一份列表、不同的合并/排序语义」）：
  - `toDomainDefs`（生成/计算）：`listEnabled` 按 `sort_no,id` 排序后 `defs.put()`，**后写覆盖先写** → 排序靠后的那条（通常是 id 更大的主体科目）生效；
  - `includeInGross`（`RecordService`/`ImportService`）：`Collectors.toMap(..., (a,b)->a)` **保留先出现的**——与上一行恰好相反；
  - `requireItem`（编制台保存）：`in (0, company)` + `eq(code)` + `LIMIT 1`，**没有 ORDER BY**。走 `uk_item_code(company_id, item_code)` 索引时通常先扫到 `company_id=0`，即很可能返回**全局定义**，但这是执行计划决定的、不保证。
  三者任意两条不一致，就会造成：计算引擎按一套精度/方向/是否计入应发算一次，编制台保存与导入重算按另一套算一次 → **同一行的 gross 可以不同**，前端「合计 = 明细加总」的自校验会间歇性失败，而两种口径都不会报错。
- **为什么测试发现不了**：`ItemServiceTest` 覆盖了「合并全局与主体科目」，但用的都是**不同 code**；没有任何用例构造同名覆盖。
- **改法**：二选一，不能两头都要：① 禁止同名覆盖（`create` 时若 `company_id=0` 已存在同 code，拒绝并提示「请直接改全局科目或换 code」）；② 明确「主体覆盖全局」，并把解析收敛到一个方法（例如 `resolveDefs(companyId)` 返回 `Map<code, def>`，`requireItem`、`toDomainDefs`、`includeInGross` 全部复用同一份，且排序显式 `ORDER BY company_id DESC` 取主体优先）。同时给 `requireItem` 加 `ORDER BY company_id DESC`。

### I11. 已使用的科目仍可改 `include_in_gross`，历史行「合计 ≠ 明细加总」 —— `ItemService.java:106-125`（对照 `:153-157`）

- 改 `category` / `direction` 时有 `requireUnused` 拦（`countUsedRecords>0 → 409`），但改 `include_in_gross` **没有任何保护**。
- 已有记录的 `gross_amount/deduction_amount/net_amount` 是**落库快照**（`pay_record`），而编制台/导入重算时会按**当前**科目定义重新加总（`RecordService:262-279`、`ImportService:450-473`）。翻转某科目的 `include_in_gross` 后：
  - 没被触碰过的记录：`grid` 显示的是快照 gross，明细求和会与它差出该科目的金额；
  - 被触碰过的记录：重算后 gross 与别的记录口径不同。
  - 导出的工资表用快照合计，工资条明细列用科目值 → 同一份文件里「列加总 ≠ 合计」。
- **改法**：`include_in_gross` / `precision_scale` 与 `direction` 同等待遇（已使用即禁止修改，或提供「仅对未锁定期间生效」的迁移期语义）；若必须允许，编制台/导入重算必须按**记录生成时的科目快照**判定，而不是当前字典。

### I12. 「科目是否被用过」的判定不带主体，跨主体误伤 —— `PayItemMapper.java:12-15`

```sql
SELECT COUNT(*) FROM pay_record_item WHERE item_code = #{itemCode}
```

- `pay_item` 的 code 只在主体内唯一，不同主体完全可能都用 `PERF_BONUS`。主体 A 的 `PERF_BONUS` 从未被用过，但主体 B 用过 → A 改类别/方向被 409 拒绝，提示「该科目已被工资表使用」但 A 无任何使用。
- 反向风险：如果把 code 当业务唯一键做别的判断（如清理），也会跨主体串。
- **改法**：`pay_record_item` 没有 `company_id`，需 `JOIN pay_record r ON r.id = i.record_id AND r.company_id = #{companyId}`（`pay_record` 有 `idx_company_period`，加 `record_id` 主键回表可接受）；或在 `pay_record_item` 冗余 `company_id`。

### I13. 报表/导出按 `period_ym` 过滤，`pay_record` 上没有以它开头的索引 —— `ReportMapper.java:21-44, 67-79`、`ExportService.java:372-388`、`db/schema-mysql.sql:300-340`

- `pay_record` 现有索引：`(company_id, period_ym)`、`(period_id, …)`、`(employee_id)` 等。月度报表/年度报表/导出都是 `period_ym = ?` 或 `period_ym BETWEEN ?`（年度），**AND `period_id IN (SELECT ...)`**。
- ALL 范围账号不带 `company_id`（`applyRecordFilter` 输出 `1 = 1`），于是 `period_ym` 上没有可用前缀 → **全表扫描**；年度报表是 12 个月的范围扫描。`inSql` 的子查询本身也要扫 `pay_period`（小表）。
- 2,000 人 × 12 月的真实数据已可感知；更大体量下报表页会稳定超过前端的 10s 超时。
- **改法**：`ADD KEY idx_period_ym (period_ym)`（或 `(period_ym, company_id)` 让它对带主体过滤的查询也有用）；年度查询可改为 `period_id BETWEEN` 或直接用 `pay_record.period_ym` 的前缀 `LIKE '2026-%'`，并确认 `EXPLAIN` 走 range。

### M3. 导入表头重复列会被静默合并 —— `ImportValidator.java:150-186, 300`

两列映射到同一个 itemCode（例如模板被复制了一列、或两列标题同名）时，`amounts.put(key, amount)` 后写覆盖前写，文件里「看起来两列都填了」，实际只取最后一列，且不产生任何错误行。**改法**：`mapping` 构建时若发现重复 key，直接 400「模板存在重复列：xxx」。

### M4. 同一文件提交后永久无法再次导入 —— `ImportService.java:213-217`、`db/schema-mysql.sql:384`

唯一键 `(period_id, biz_type, file_hash)` 使「同一份文件」在一个期间内只能导入一次，**包括已 COMMITTED 的批次**。解锁重开期间后想再导一次同样的变动表（补算场景），会得到 409「该文件已提交或正在处理」，且没有任何强制/覆盖入口。若是刻意设计（防重复发钱），至少要把提示改成「该文件已导入过，如需再次应用请复制为新文件或联系管理员」，并在 UI 上给出已完成批次链接。

### M5. 导入文件只增不删，长期撑满磁盘 —— `ImportService.java:194-196, 253-267`

每个不同内容的上传都会落一份 `hash.xlsx`，永不清理（只有「validation 事务回滚」才删）。按 5 万行/30MB、每月几十次上传，一年就是十几 GB 且没有任何配额/清理任务。**改法**：加保留期（如 90 天）+ 定期清理任务；或对象存储生命周期策略。

## 三、异常处理

总体结论：没有发现 `catch (Exception e) {}` 式吞异常；`catch` 块均有日志或明确翻译；全仓不使用受检异常，因此不存在「受检异常静默不回滚」的问题。以下为仍有风险的几处。

### I14. 生成/导入的「部分成功」语义在异常路径上不自洽 —— `GenerateService.java:187-202`、`ImportService.java:371-386`

- 生成：`catch` 里无条件 `closeRun(run, "FAILED", ...)`。如果失败发生在**全部批次已提交之后**（`markEditing` / `totalsRefresher.refresh` / `markRunFailureCount`），数据其实已经完整，run 却被改成 FAILED，`error_msg` 记录的是收尾阶段的异常；HR 会以为需要重跑（虽然幂等，但会再占用一次租约、再覆盖 `version_no`）。
- 导入：`refreshValidationFailure` 在新事务里刷失败明细，如果它自己再失败（DB 抖动），异常会覆盖原始的 `ImportConflictException`，前端从「有 N 行失败」变成 500，用户丢失可操作的失败清单。
- **改法**：生成侧把「收尾步骤」包成 try/catch，只记日志并把 run 保持 SUCCESS（或新增 `SUCCESS_WITH_WARNINGS`）；导入侧 `refreshValidationFailure` 再包一层，失败时至少返回原错误 + 「错误明细刷新失败」。

### M6. 生成收尾的 `persistSkips` / `markRunFailureCount` 只记 `e.getMessage()`，丢栈且失败后无补偿 —— `GenerateService.java:506-531`

- 这两步在事务外、单语句自动提交。失败时日志里只有一个字符串，没有异常类型/栈，线上排查「为什么进度页没有跳过名单」时完全无从下手。
- `persistSkips` 先 `deleteByRun` 再逐条 `insert`，两步之间失败（或中途失败）会留下「旧名单已删、新名单不全」的状态，而前端把空名单当成「没人被跳过」。
- **改法**：`persistSkips` 放进一个 `TransactionTemplate` 里（删 + 插原子）；日志用 `log.warn("...", e)` 带栈；失败时在 `progress.warnings` 里留一条「跳过明细保存失败」。

### M7. `markEditing` 的校验读的是快照，且失败会把已完成的 run 标 FAILED —— `PeriodService.java:186-195`（被 `GenerateService.java:182` 调用）

`markEditing` 里 `requirePeriod` + `assertWritable` 用的是普通 SELECT，与 `updateById` 之间没有锁；同一毫秒另一个线程把期间锁定了的话，这里会把 `status` 从 `EDITING` 写回 `EDITING` 并改 `compiled_by`（对 LOCKED 期间会抛 409，但异常会传播到生成器的 catch → run FAILED）。**改法**：`markEditing` 内部用 `selectForUpdate`；生成器对收尾阶段的异常单独处理（见 I14）。

### M8. 全局兜底把 `DuplicateKeyException` 之外的数据完整性异常都变成 500 —— `GlobalExceptionHandler.java:87-108`

`DataIntegrityViolationException`（超长、NOT NULL、外键、CHECK 失败）不在处理列表里，落到 500「系统异常，请联系管理员」。例如 `employee_type` 超长、`sys_dept.ancestors` 超长、`pay_item.category` 非法值，前端只能看到系统故障，用户不知道怎么改。**改法**：增加 `DataIntegrityViolationException → 409`，并按异常类别给可操作提示（长度/必填），同时日志里带上表名与列名（日志可见，响应不可见）。

## 四、金额与精度

### I15. 用户可控的超大指数数值可把 JVM 打爆 —— `RecordService.java:304-313`（`changeset`）、`ImportValidator.java:283-287`（Excel 单元格）

```java
new BigDecimal(raw.trim()).setScale(scale, RoundingMode.HALF_UP)
```

`raw` 来自 HTTP 请求体 / Excel 单元格，长度几乎不受限（导入的 `raw_value` 才截断到 512，**解析发生在截断之前**）。`new BigDecimal("1E+999999999")` 本身只占几十字节，但 `setScale(2, HALF_UP)` 会尝试构造约 **10 亿位**的 BigInteger → 直接 OOM（`OutOfMemoryError` 不是 `RuntimeException`，不会被生成器的 catch 兜住；变化集路径还会让整个 Tomcat 线程池慢慢被吃光）。

- **为什么测试发现不了**：金额用例都是正常量级；`MAX_DECIMAL_18_4` 的范围校验在 `setScale` **之后**，救不了。
- **改法**：解析前限制 `raw.length() <= 32`，并拒绝 `e/E` 指数写法（或先 `new BigDecimal(raw, new MathContext(20))` 再 `setScale`），同时把范围校验前移到 `signum/scale` 层面；导入侧对单元格长度做同样的前置校验。

### I16. 薪酬档案 4 位精度在「读取 → 前端 → 回写」链路被截到 2 位 —— `CompProfileService.java:269-271`、`:106`

`store()` 用 `scale=4` 落库，但 `display()` 一律 `setScale(2)` 下发；`update()` 又直接取 `req.baseSalary()`（来自前端回填的 2 位值）重新 `store(4)`。任何 `xxx.xx34` 的基本工资在编辑一次（哪怕只改调薪原因）后变成 `xxx.xx00`。

- **为什么危险**：基本工资是加班费/经济补偿的法定基数（schema 注释已写明），4 位精度正是为此留的；静默丢分会在后续算薪与劳动仲裁口径上产生差额，且没有任何审计提示（审计里记的是 `Money.format` 两位，也看不出变化）。
- **改法**：下发改 4 位（或按「至少 2 位、有效位保留」的 `Money.format` 口径），`update` 只在请求显式包含 `baseSalary` 时才采用；并在改薪审计里记录完整 4 位值。

### M9. 导出把 `BigDecimal` 转 `double` 写进 Excel —— `ExcelWriter.java:126-135`

`DECIMAL(18,4)` 允许 14 位整数 + 4 位小数，超过 15–16 位有效数字后 `double` 开始丢位；`#,##0.00` 格式还会把 4 位小数的金额显示成 2 位（值本身保留）。日常工资量级（≤8 位）安全，但「合计」行在大体量/多主体汇总时可能踩线。**改法**：金额本身写字符串（保精度），靠 `CellStyle` 数字格式展示；或按业务上限（如 1e12）在导出前断言并降级。

### M10. 折算因子是「先除到 10 位、再乘、再舍入」，与「一次舍入」的注释不完全一致 —— `PayrollCalculator.java:57-64`

`factor = days.divide(hdivisor, 10, HALF_UP)` 之后 `raw.multiply(factor).setScale(scale)`。理论上存在「因子第 10 位进位后乘出 1 分差」的构造值。实际影响几乎为零（误差 ≤ 5e-11 × 金额），但既然文档写着「只舍入一次」，建议改成单步：

```java
raw.multiply(BigDecimal.valueOf(days)).divide(divisor, scale, RoundingMode.HALF_UP)
```

顺带把 `setScale` 与折算合成一条表达式，避免后人误以为可以调整因子精度。

### M11. 合计口径对「未知科目」默认计入应发，而计算引擎默认报错 —— `GenerateService.java:433-447`、`RecordService.java:267`、`ImportService.java:458`

三处都是 `includeByCode.getOrDefault(code, true)`：明细里出现字典中没有的 code（科目被物理删除、历史脏数据）时，编制台/导入把它**计入应发**；而生成路径因为 `def == null` 直接抛「工资项定义缺失」让该员工失败。同一份脏数据的三种处理方式，会产出不同金额。**改法**：统一为「未知科目不计入应发 + 记一条 warning」，或统一失败并给出可操作提示。

## 五、资源与内存

### I17. 导出/报表在「准备数据」阶段全量加载，SXSSF 只解决了写文件那一段 —— `ExportService.java:372-406`、`ReportService.java:89-99`

- `lockedRecords()` 无上限地把该期间该主体（或 ALL 范围的**所有主体**）的 `pay_record` 全部读进 List；`itemAmounts()` 再把这些记录的所有 `pay_record_item` 读进 Map；`paySheet()` 又把这些行映射成 `List<List<Object>>`。SXSSF 的窗口只作用于最后的写盘，峰值内存 ≈ 记录数 × 列数 × 对象开销。5 万行 × 15 列（含包装对象）在 512MB 堆的容器里很危险。
- 工资条（PAYSLIP）走同一条路径，且 `employeeIds` 只做 `IN` 过滤，日积月累的整个期间仍会全量读。
- **改法**：`pay_record` 用游标/分页（`stream` + `ResultHandler` 或按 id 分段）逐段取，每段再按 `record_id IN` 拉明细并立刻写行；或者导出任务化（异步生成 + 下载链接），避免请求线程持有全量数据。**至少**加一条「单次导出行数上限」并在超限时提示分批。

### I18. 生成路径每员工 2–4 次查询，每批还全量锁/全量载明细 —— `GenerateService.java:291-356`

- 每员工：`compProfileService.effectiveAt`（1 查档案 + 1 查津贴）、`employmentMapper.findDeptAt`（1）、`deptMapper.findNameById`（1）、`recordAssembler` 无查询、`recordMapper.updateById/insert`（1）+ `insertItems`（每项 1 次 insert）。
- 每批（500 人）还额外：`lockByPeriod` **锁住本期间本主体的全部记录**（不是本批 500 条）+ `loadVariableAmounts` / `loadManualItems` 各**全量**拉一次本期所有明细（`:291-295`）。
- 2,000 人 ≈ 1.2 万次查询，且期间行锁在整个批次里持有；分批数越多，重复的全量加载越多。规模上到 1 万就会明显超时。
- **改法**：① 档案与津贴按 `employee_id IN (batch)` 一次查回，按员工 map；② 部门名按批内 `dept_id` 一次查；③ 变动项/手工项在**整个生成开始时**加载一次（按 period），而不是每批重复；④ `lockByPeriod` 只为「本批员工」加锁（`employee_id IN (...)`），减少锁范围。

### M12. 员工分页每行回查一次部门名 —— `EmployeeService.java:328-338`

`toDto` 里 `deptMapper.findNameById(e.getDeptId())`，一页 500 行就是 500 次查询。`CompProfileService` 已经用了「批量查后分组」的写法，这里可以复用。**改法**：page 后收集 `deptId` 去重，一次查出 `id→name`。

### M13. 导出文件名/临时文件的生命周期边角 —— `ImportService.java:142-169`、`ExcelWriter.java:71`

- `template()` 只 catch `IOException`：如果在 `createTempFile` 之后、`write` 之前抛 `RuntimeException`（如 `header()` 里的 NPE），临时文件不会被删（`catch` 不匹配，`finally` 也没有）。
- `ExcelWriter.write` 的临时文件在 `/tmp`（默认系统临时目录），若 JVM 在「写完、尚未返回」之间崩溃，会留下**含全量工资**的 xlsx 直到系统清理。**改法**：`template` 改成 `try/finally` 删除；导出临时目录改为受控目录（与导入同一持久卷/专用目录，权限更严），并加一个启动时的陈旧文件清理。

### M14. 并发导出没有配额 —— `ReportController.java:60-77`

每个导出请求都会在磁盘上生成一份完整 xlsx 并在响应期间占用连接与临时文件。N 个人同时导年度全量，会同时占 N 份磁盘 + N 份内存。没有并发上限、没有排队。**改法**：加信号量（如同时最多 2 个导出）+ 队列/429，或改异步导出。

## 六、安全

### I19. 系统管理员可以为 HR 建号并设置密码，再以该账号直接读取全部薪酬 —— `UserAdminService.java:106-141, 215-232`、`ScopeGuard.java:70-83`

- 这是**设计上的**（`ScopeGuard` 注释明确写「系统管理员可以给 HR 建号」），但组合起来打破了「薪酬与系统管理两条线」：
  1. 仅持 `sys:user:edit` 的账号 `POST /users` 建一个用户，密码自己定；
  2. `POST /users/{id}/reset-password` 也由自己执行；
  3. 直接登录 → 拿到 `payroll:*` 全部权限（`resolveRoles` 只拦「给自己加 payroll」，不拦「给别人加然后登录」）。
- 结论：`sys:user:edit` 实际上等价于「可读取全部工资」。如果这是可以接受的运营现实，应写进安全基线；如果不接受，需要额外控制。**改法**：给「创建/重置一个持有 `payroll:*` 的用户」单独要求一个权限点（如 `payroll:user:grant`），或强制双人审批（与锁定/解锁同一级别），并把这些动作写入高危审计。
- 另：`AuthService.login`（`:40-49`）无失败次数限制、无锁定、无失败登录审计；`BCrypt` 之外的密码策略只有「≥8 位」（`UserAdminService:114-116`）。离线爆破/撞库没有阻力。**改法**：按用户名+IP 限速、连续失败锁定、记录失败登录审计。

### M15. AES 密钥派生太弱、且没有密钥版本 —— `CryptoService.java:43-53`

- `SecretKeySpec(sha256(passphrase), "AES")`：单轮 SHA-256，无盐、无迭代。若运维把 `PAYROLL_AES_KEY` 设成一个可猜的短语（yml 只校验非空），等同弱密钥。建议至少 PBKDF2/Argon2（固定 salt 存配置）或要求注入 32 字节随机密钥（`base64`）。
- 密文格式 `IV||ciphertext||tag` 里**没有 keyVersion**；而盲索引有 `id_no_hash_version` 字段、AES 没有对应字段 → 一旦轮换 AES key，所有历史证件号/手机号将无法解密（或需要一次性全量重加密且不可回滚）。建议密文前加 1 字节版本 + 预留 `id_no_key_version` 列。
- 另外 `decrypt` 的失败信息「密文可能被篡改」会直接回给前端（若某个接口触发）——属于内部细节，建议统一成 500 泛化文案，细节只进日志。

### M16. 审计缺少来源 IP / User-Agent —— `AuditService.java:42-65`（表结构 `pay_audit_log.ip/user_agent` 已存在）

高危动作（导出、解锁、授权）目前只能回答「谁、何时、改了什么」，无法回答「从哪台机器来」。真实事故里（凭证泄露/内鬼）这是第一条要查的线索。**改法**：从 `RequestContextHolder` 取 `HttpServletRequest` 填 ip（`X-Forwarded-For` 首段时注意代理信任）与 UA，脱敏后截断。

### M17. 数据范围校验在「记录级别操作」上依赖逐行查询，且 `DEPT/ DEPT_SUB` 不附加主体条件 —— `DataScopeEnforcer.java:92-111, 128-140, 182-185`

- `assertRecordVisible` 每行调用一次 `deptIdOf(current)`（一次 DB 查询），`DEPT_SUB` 还会 `findSubtreeIds`（又一次）。`RecordService.applyChangeset` 对每个 change 调一次 → 一个 200 行的保存会多出 200–400 次查询（与 I13 叠加）。
- `applyRecordFilter` 的 `DEPT` 分支是 `dept_id = ?`，没有 `company_id = ?`。`sys_dept.id` 全局唯一，「按部门过滤」目前不会跨主体泄漏；但一旦未来引入部门 id 复用/跨主体共享组织，这里会成为越权入口。**改法**：`DEPT/ DEPT_SUB` 同时附加 `company_id = current.companyId()`；`deptIdOf`/子部门集合在请求内缓存（`CurrentUser` 上加一次懒加载字段），不要在循环里查库。

### M18. 委托给前端的 `companyId` 只在部分入口被二次校验 —— `EmployeeController.java:36-46`、`PeriodController.java:26-33`

`EmployeeController.list` 与 `PeriodController.list` 都**忽略**客户端可传的 `companyId`，直接用当前用户主体——这是安全的但功能受限：ALL 范围用户查询不到其它主体的员工/期间（前端只能看到自己主体）。反过来，`ReportController` 接受 `companyId` 且 `ReportService` 有校验。功能不一致会让 ALL 账号在人员/期间页看不到全集团数据，容易被误判为「数据丢了」。**改法**：统一支持 `companyId` 参数（ALL 可任意，非 ALL 走 `assertCompanyVisible`）。

## 九、最危险的三个（一句话版）

1. **C1** 同一生效日的薪酬档案第二次更正必定 500（唯一键 `(employee_id, effective_from, deleted)` 与「作废旧段」冲突），录错的工资无法在正确日期上更正。
2. **C2** FIXED 类导入的金额在下一次「重新生成」时被静默删除，run 仍报 SUCCESS，直接导致少发。
3. **C3** 生成有失败员工时期间仍可锁定，漏算的人被永久排除在工资表之外，且复核侧没有任何硬拦截。

> 次危险（若时区不一致即升级为 Critical）：**I1** 租约混用 JVM 时钟与 MySQL `NOW(6)`，测试恰好用 SQL 造过期时间，永远测不出这个问题。
