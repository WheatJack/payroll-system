## 3. 详细发现

### H-1 部门级编辑者可触发/写入全公司工资数据（越权写 + 资源耗尽）

**攻击向量**：数据范围（DEPT / DEPT_SUB）只被用于"读取"的 SQL 下推，**写路径只做 company 级可见性校验**。`payroll:record:edit` 功能权限一旦与 DEPT 范围组合（系统允许创建这样的角色），该账号即可对任意期间发起全公司重算；导入提交同理，行数据只按公司校验、不按部门过滤。

**代码位置**
- `run/GenerateService.java#startGenerate`：仅 `dataScope.assertPeriodVisible(periodId)`（公司级）。
- `run/GenerateService.java#generate`：`employeeMapper.findCandidates(period.getCompanyId(), ...)` —— 取**全公司**员工，无 dept 过滤；`processBatch` 只校验期间状态。
- `importjob/ImportService.java#commit / apply`：`validator.validate(..., period.getCompanyId(), ...)` 与 `apply()` 均按公司，不判断行是否在本部门范围。
- `period/PeriodService.java#create`：仅 `assertCompanyVisible`。

**复现步骤**（请用**自建测试期间/测试员工**，勿对真实期间执行）：

```bash
# 1) admin 建一个 DEPT 范围、含 record:edit 的角色并分配给部门账号（系统允许）
curl -s --noproxy '*' -X POST $B/roles -H "Authorization: Bearer $ADMIN_TOK" \
  -H 'Content-Type: application/json' \
  -d '{"companyId":1,"roleCode":"DEPT_EDIT","roleName":"部门编辑","dataScope":"DEPT",
       "status":1,"permissions":["payroll:record:view","payroll:record:edit"]}'
# 2) 该部门账号对任意期间发起生成
curl -s --noproxy '*' -X POST $B/periods/$WITABLE_PERIOD_ID/generate \
  -H "Authorization: Bearer $DEPT_TOKEN"
# 3) 观察：全公司每个部门的记录都被重算/重写（而不是只限该账号所在部门）
```

**实际结果**
- 用 DEPT（部门 8）账号 `pentest_deptedit` 对**已锁定**期间 23 发起生成：返回 `409 期间已锁定，禁止修改`，而**不是 403**——说明它已通过数据范围校验，只卡在期间状态。
- 对可写期间（24/EDITING、1874 人）该调用会进入 `generate()`，按 `companyId` 遍历全部 1874 人并重写记录（代码路径确认，未对真实期间执行）。
- 同一账号 `POST /periods {"companyId":1,"periodYm":"2031-01"}` 成功创建了**全公司**期间（返回 200，期间 id=26，已清理）。

**期望结果**：DEPT/DEPT_SUB 账号对生成/导入/建期间应被 403，或写操作严格限定在其部门子树内的员工/记录。

**风险等级**：高（工资数据完整性；越权跨部门写入；重计算可被反复触发造成资源耗尽）

**修复建议**：
1. `GenerateService` 增加"写入集合 ⊆ 可见集合"的强制校验：DEPT/DEPT_SUB 只处理本部门子树员工，SELF 拒绝；或直接要求 `dataScope ∈ {ALL, COMPANY}` 才允许生成。
2. `ImportService` 在 validate/commit 时对每一行 `recordId` 调用 `dataScope.assertRecordVisible(record)`，越界行计入失败并禁止提交。
3. `PeriodService.create` 明确期间创建所需的最小范围（建议 ALL/COMPANY）。

### M-1 跨部门新建人员：返回 403 但人员已落库

**攻击向量**：`EmployeeService.create` 只校验 `companyId` 可见 + 部门属于该主体，**不校验 dept 是否在操作者数据范围内**；而 `EmployeeController.create` 在**事务提交后**再调用 `employeeService.get(id)`，后者触发数据范围校验抛 403。结果：写入成功、响应却是失败。

**代码位置**：`employee/EmployeeService.java#create`（仅 `assertCompanyVisible` + `requireDeptOfCompany`）；`employee/EmployeeController.java#create`（create 后 `get(id)`）。

**复现步骤**：

```bash
# 使用 DEPT 范围（部门 8）、具 record:edit 的账号
curl -s --noproxy '*' -X POST $B/employees -H "Authorization: Bearer $DEPT_EDIT_TOK" \
  -H 'Content-Type: application/json' \
  -d '{"empNo":"pentest_E1","name":"pentest测试","idNo":"999999199001010011",
       "mobile":"13800000000","employeeType":"REGULAR","deptId":9,"hireDate":"2025-01-01"}'
# 再查库确认
SELECT id,emp_no,dept_id,deleted FROM emp_employee WHERE emp_no='pentest_E1';
```

**实际结果**：HTTP `403 {"code":403,"msg":"无权访问该人员数据"}`；但数据库中确实存在 `id=2020, emp_no=pentest_E1, dept_id=9, deleted=0`（已清理）。即"失败响应 + 成功写入"。

**期望结果**：创建时按数据范围校验 `deptId`，越界直接 403 且**不落库**；或 controller 不要在 create 事务之外用受限查询回读。

**风险等级**：中（跨部门数据写入、PII 数据完整性；响应误导导致业务误判）

**修复建议**：`EmployeeService.create` 增加 `dataScope.assertDeptVisible(req.deptId())`（DEPT 必须等于本部门、DEPT_SUB 必须在子树内）；`EmployeeController.create` 直接由 service 返回 DTO，避免二次受限查询。

### M-2 导入批次 `commit` 缺少发起人校验（他人批次可被提交）

**攻击向量**：`GET /import/{batchId}` 与 `GET /import/{batchId}/errors` 都调用了 `assertBatchReadable`（非 ALL/COMPANY 只能看自己发起的批次），但**`POST /import/{batchId}/commit` 没有**。部门级账号只要知道/枚举到 batchId，就能提交别人发起的整期间批次（其内容包含其他部门行）。

**代码位置**：`importjob/ImportService.java#commit`（运行版本只做 `assertPeriodVisible`）。

**复现步骤**：

```bash
# 用 DEPT 范围、具 payroll:import:submit 的账号（pentest_import）
curl -s --noproxy '*' $B/import/8 -H "Authorization: Bearer $DEPT_IMPORT_TOK"            # 他人批次
curl -s --noproxy '*' -X POST $B/import/8/commit -H "Authorization: Bearer $DEPT_IMPORT_TOK"
```

**实际结果**
- `GET /import/8` → `403 无权查看他人发起的导入批次`
- `POST /import/8/commit` → `409 期间已锁定，禁止修改`
- 同一批次两个接口返回不同授权结果：commit **已越过授权检查**，只因目标期间 LOCKED 才失败。若期间可写，则会执行提交。

**期望结果**：commit 与 get/errors 使用同一套 `assertBatchReadable`，非本人批次直接 403。

**风险等级**：中（越权写 + 跨部门工资改动）

**修复状态**：工作区最新源码 `ImportService.commit` 已新增 `assertBatchReadable(existing)`（`git diff` 可见），**但 21:14 运行构件未包含**。建议重新构建部署后再回归。

### M-3 生成进度接口泄露全公司跳过人员名单（跨部门 PII）

**攻击向量**：`GET /runs/{runId}` 只做 `assertPeriodVisible(run.periodId)`（公司级），随后返回 `skippedDetails`（工号、姓名、原因）与 `skipped` 映射，**未按数据范围过滤**。

**代码位置**：`run/GenerateService.java#progress`。

**复现步骤**：

```bash
# DEPT_SUB（部门 8）账号读取期间 24 的生成批次
curl -s --noproxy '*' $B/runs/33 -H "Authorization: Bearer $DEPT_TOK"
```

**实际结果**：HTTP 200，返回 `skippedDetails` 32 条，含 `BJ00116/BJ00125/SH01018/SZ01680/SZ01998 …`；经库核对，这些员工分属部门 **9/14/16/18**，均不在部门 8 的范围内。即部门账号拿到了全公司被跳过人员名单。

**期望结果**：`skippedDetails` 按数据范围过滤（DEPT 仅本部门子树，SELF 仅本人），其余人只保留计数。

**风险等级**：中（跨部门 PII 泄露：姓名 + 工号 + 失败原因）

**修复建议**：在 `progress()` 返回前对 `skippedDetails` 做可见性过滤，或按 `record/dept` 快照判断；`progress.total/success/failed` 是否暴露也应按范围收敛。

### M-4 未认证可访问 Swagger / OpenAPI

**攻击向量**：`springdoc` 的文档端点不在 `/api/**` 下，绕过了 `PermissionInterceptor`，无需登录即可访问，暴露完整 API 面与全部请求/响应模型。

**代码位置**：`pom.xml` 引入 `springdoc-openapi-starter-webmvc-ui:2.5.0`；未见对 `/v3/api-docs`、`/swagger-ui/**` 的鉴权或关闭配置。

**复现步骤**：

```bash
curl -s --noproxy '*' -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/v3/api-docs
curl -s --noproxy '*' -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/swagger-ui/index.html
curl -s --noproxy '*' http://127.0.0.1:8080/v3/api-docs | head -c 400
```

**实际结果**：两者均 `200`。`/v3/api-docs` 含 37 个路径、83 个 schema（含 `LoginRequest`、`EmployeeSaveReq`、`RoleGrantReq` 等），文档未配置 `securitySchemes`。未在其中发现真实口令/密钥（`Passw0rd`、`secret` 计数为 0）。

**期望结果**：生产环境关闭文档，或至少要求认证（`springdoc.api-docs.enabled=false` / 加拦截）。

**风险等级**：中（未授权信息暴露，显著降低后续攻击门槛）

**修复建议**：生产 profile 关闭 `springdoc`；如保留，需纳入 Bearer 鉴权并限制来源。

### M-5 登录无频率限制/无锁定，可在线暴力破解

**攻击向量**：`POST /auth/login` 对失败次数无计数、无延时、无验证码、无锁定。

**复现步骤**：

```bash
for i in $(seq 1 15); do
  curl -s --noproxy '*' -o /dev/null -w '%{http_code} ' -X POST $B/auth/login \
    -H 'Content-Type: application/json' -d "{\"username\":\"hr01\",\"password\":\"wrong$i\"}"
done; echo
# 失败后正确口令仍可登录
curl -s --noproxy '*' -o /dev/null -w '%{http_code}\n' -X POST $B/auth/login \
  -H 'Content-Type: application/json' -d '{"username":"hr01","password":"Passw0rd!"}'
```

**实际结果**：连续 15 次（另一次 60 次压测）全部为 `401`，无 `429`、无锁定；随后正确口令返回 `200`。说明可无限次在线尝试。

（说明：60 次压测中出现的 10 次 `500` 与当时 MySQL/后端并行重启时间重合，非登录逻辑本身。）

**期望结果**：按账号/IP 失败计数 + 指数退避/锁定/验证码，并对 401 统一延迟（同时消除 L-1 的时间差）。

**风险等级**：中（结合弱口令可被爆破；当前口令策略仅 `>=8` 位、无复杂度）

**修复建议**：引入登录失败计数（如 5 次锁 15 分钟）、统一失败耗时（无论用户是否存在都执行一次 bcrypt），必要时加验证码/告警。

### M-6 系统管理员可接管薪酬账号，绕过"不能给自己授予薪酬权限"的职责分离

**攻击向量**：系统管理线（`sys:*`）与薪酬线（`payroll:*`）本应隔离；代码也硬拦了"给自己所在角色新增 payroll 权限"。但 `PUT /users/{id}/reset-password` 的 `assertCanManageAccount` **只比较 sys 权限和范围，不比较 payroll 权限**，因此 ALL 范围的系统管理员可以重置任意薪酬账号密码后登录，从而获得工资数据；同样可新建薪酬账号再登录。

**代码位置**：`admin/UserAdminService.java#resetPassword`、`#assertCanManageAccount`；`admin/RoleAdminService.java#replaceGrants`（自提权拦截）。

**复现步骤**：

```bash
# admin 重置一个薪酬账号（测试账号）的密码
curl -s --noproxy '*' -X POST $B/users/$PAYROLL_USER_ID/reset-password \
  -H "Authorization: Bearer $ADMIN_TOK" -H 'Content-Type: application/json' \
  -d '{"newPassword":"Taken0ver!"}'
# 以该账号登录后读取工资表
curl -s --noproxy '*' -X POST $B/auth/login -H 'Content-Type: application/json' \
  -d '{"username":"pentest_dept","password":"Taken0ver!"}'
curl -s --noproxy '*' -o /dev/null -w '%{http_code}\n' $B/periods/24/grid \
  -H "Authorization: Bearer $TAKEN_TOKEN"
```

**实际结果**：重置返回 200；登录成功；`GET /periods/24/grid` 返回 200（可读工资数据）。对照实验：admin 直接给自身角色 5 加 `payroll:record:view` 被正确拒绝（`403 不能给自己授予薪酬权限`）。

**期望结果**：按合规要求决定——若确需职责分离，则重置密码/停用/删除目标账号也应比较 payroll 权限，或对"含 payroll 权限且非本人"的账号操作要求双人复核/二次授权。

**风险等级**：中（职责分离可被单一系统管理员绕过；是否算缺陷取决于组织的内控要求）

### L-1 用户名枚举（登录耗时差异）

**攻击向量**：用户不存在时在 bcrypt 之前短路返回，存在时执行 bcrypt，耗时相差约 8 倍；错误提示相同，但时间侧信道可枚举有效用户名。

**复现步骤**：

```bash
for i in $(seq 1 10); do
  curl -s --noproxy '*' -o /dev/null -w '%{time_total}\n' -X POST $B/auth/login \
    -H 'Content-Type: application/json' -d '{"username":"hr01","password":"x"}';
done
for i in $(seq 1 10); do
  curl -s --noproxy '*' -o /dev/null -w '%{time_total}\n' -X POST $B/auth/login \
    -H 'Content-Type: application/json' -d '{"username":"nosuchuser","password":"x"}';
done
```

**实际结果**：存在用户中位 74.1ms，不存在用户中位 8.8ms（各 12 次采样）；返回体均为同一 `401 用户名或密码错误`。

**期望结果**：两条分支耗时一致（不存在时也做一次 bcrypt 假比对）。

**风险等级**：低

### L-2 错误映射不当：多处应 4xx 却返回 500

**攻击向量**：向未处理器路径/错误方法/错误 Content-Type/非法文件发起请求，触发 `GlobalExceptionHandler` 的兜底 `Exception` 分支。

**复现步骤**：

```bash
curl -s --noproxy '*' -o /dev/null -w '%{http_code}\n' $B/nope -H "Authorization: Bearer $TOK"
curl -s --noproxy '*' -o /dev/null -w '%{http_code}\n' -X DELETE $B/auth/login
curl -s --noproxy '*' -o /dev/null -w '%{http_code}\n' -X POST $B/auth/login \
  -H 'Content-Type: text/plain' -d 'x'
echo 'not excel' > /tmp/junk.xlsx
curl -s --noproxy '*' -o /dev/null -w '%{http_code}\n' -X POST \
  "$B/import/validate?periodId=24&bizType=VARIABLE" -H "Authorization: Bearer $TOK" \
  -F 'file=@/tmp/junk.xlsx'
```

**实际结果**：分别为 `500`（应为 404）、`500`（405）、`500`（415）、`500`（应为 400）。响应体统一为 `{"code":500,"msg":"系统异常，请联系管理员"}`，**未泄漏堆栈/SQL/表名**（这点是好的）。

**期望结果**：404/405/415/400，并区分"用户输入错误"与"系统故障"，避免监控误报。

**风险等级**：低（可用性/可观测性，不是直接安全漏洞）

### L-3 姓名/备注中的 XSS 内容服务端不转义

**攻击向量**：在人员姓名/备注写入 `<script>`/`onerror` 载荷，服务端原样存储并在 JSON 中返回。

**复现步骤**：

```bash
curl -s --noproxy '*' -X POST $B/employees -H "Authorization: Bearer $DEPT_EDIT_TOK" \
  -H 'Content-Type: application/json' \
  -d '{"empNo":"pentest_XSS1","name":"<script>alert(1)</script>",
       "idNo":"999999199001010033","mobile":"13800000001","employeeType":"REGULAR",
       "deptId":8,"hireDate":"2025-01-01","remark":"<img src=x onerror=alert(1)>"}'
curl -s --noproxy '*' $B/employees/$NEW_ID -H "Authorization: Bearer $DEPT_EDIT_TOK"
```

**实际结果**：写入成功，读取原样返回 `name":"<script>alert(1)</script>"`、`remark":"<img src=x onerror=alert(1)>"`。
**当前不可直接利用**：前端 `frontend/src` 全量检索无 `v-html`；导出用 POI `setCellValue(String)`（字符串单元格，见 `report/ExcelWriter.java:136`），Excel 不会当公式执行。因此属于"缺少纵深防御"，一旦未来出现 `v-html`/CSV 导出即变成存储型 XSS/公式注入。

**期望结果**：输入白名单或输出编码；CSV 导出时对 `= + - @` 开头做前缀转义。

**风险等级**：低（当前 PoC 不可触发）

### L-4 部门级账号可创建全公司期间

**攻击向量**：`POST /periods` 仅校验 `companyId` 可见，不要求 ALL/COMPANY 范围。

**复现步骤**：

```bash
curl -s --noproxy '*' -X POST $B/periods -H "Authorization: Bearer $DEPT_EDIT_TOK" \
  -H 'Content-Type: application/json' -d '{"companyId":1,"periodYm":"2031-01"}'
```

**实际结果**：返回 `200` 并创建期间（id=26，已清理）；跨主体 `companyId=3` 被正确拒绝 `403`。

**期望结果**：期间是公司级对象，建议要求 `dataScope ∈ {ALL, COMPANY}`。

**风险等级**：低（可造成期间列表污染，不直接泄露数据）

### L-5 重型接口无速率限制；查看操作写审计可膨胀

**攻击向量**：`POST /periods/{id}/generate`（遍历全公司）、`POST /reports/export`、`POST /import/{id}/commit` 及 `GET /periods/{id}/grid` 均无节流。`grid` 每次查看都会写一条 `pay_audit_log`。

**实际结果**：并发 50 个 `GET /employees?size=50` 全部 200、无错乱；重型接口可被同一 token 反复调用（未做压测以免影响真实数据）。

**期望结果**：对生成/导出/导入加分布式限流与并发租约（生成已有期间级租约，但导出/查看未限流）；审计按需采样或独立写入。

**风险等级**：低（资源耗尽/审计表膨胀）

---

### L-6 缺少 CSP/HSTS 等响应头

**实际结果**：响应含 `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`，但无 `Content-Security-Policy`、`Strict-Transport-Security`，`X-XSS-Protection: 0`。

**期望结果**：生产 HTTPS 前置下补 HSTS 与 CSP；API 纯 JSON 场景影响有限。

**风险等级**：低

## 4. 通过项（这些防线实测有效，建议保持）

1. **认证/令牌**
   - 无 token、空 Bearer、`Bearer null`、junk、错误 scheme、`Bearer<无空格>` 均 401。
   - 篡改 payload（userId 1→3）、payload 与签名拼接、翻转签名字符、使用不同密钥伪造 → 全部 401。
   - 改密后旧 token 立即 401（tokenVersion 生效），新口令可登录。
   - 登录失败提示统一（"用户名或密码错误"），不存在/密码错不区分文案。
2. **功能权限矩阵**：仅 `payroll:record:view` 的账号对 13 个写/管理接口全部 403；`sys:*` 管理员访问薪酬接口全部 403（两条线隔离在功能权限层有效）。
3. **数据范围（读）**
   - `GET /employees/{id}` 1..60 扫描：DEPT_SUB(部门 8) 仅 13 个本部门 id 返回 200，其余 403；SELF 无关联人员返回 0 行。
   - `/periods/{id}/grid`：DEPT_SUB 232 行（全为部门 8）、SELF 0 行、ALL 1874 行；期间合计按可见记录重算。
   - `comp-profiles` 单条/更新、`reports/monthly|annual`、`export`（PERIOD_SHEET/PAYSLIP）均按数据范围过滤；导出按部门仅 231 行 vs 全量 1819 行。
   - 分页 `deptId` 越界交叉过滤返回 0。
4. **IDOR（记录级）**：`PATCH /periods/24/records` 改他部门记录 → `403 无权访问该核算记录`；本部门记录传入非法金额 → 400 且事务回滚（版本号/金额均未变）。
5. **参数校验/注入**
   - SQL 注入载荷（`' OR '1'='1`、`'; DROP TABLE`、`UNION SELECT`、反斜杠）经 `keyword`/`itemCode`/`groupBy`/`periodYm` 全部安全（参数绑定 + 正则/枚举白名单）。
   - 金额 `NaN`/`Infinity`/`1e999`/`--1`/负数/超长/空/`1,000`/`0x10` 全部 400；`DECIMAL(18,4)` 上限在服务层拦截。
   - 日期 `2025-02-30`、`2025-13-01`、错误类型、嵌套 JSON（2000 层）、数组代替标量 → 400。
   - 分页 `current/size` 负数/0/非数字 → 400 或回落默认；超大 size 被 MyBatis-Plus 默认上限 500 截断，未出现全表导出。
6. **防自我提权**：分公司管理员（COMPANY 范围、无 grant:all）尝试给自己加 ALL 角色 / SYS_ADMIN / payroll 权限 / 创建 ALL 角色 / 重置 admin / 停用删除 admin —— 全部 403，提示准确。
7. **敏感数据**：人员接口仅返回 `idNoMask`/`mobileMask`；库内 `id_no_cipher`/`mobile_cipher` 为密文；导出文件内无 18 位身份证、无 11 位手机号；审计不记录明文证件/手机号。
8. **并发/资源**：50 并发同 token 读全部 200 无错乱；55MB 上传 → 413；CORS 不对任意 Origin 放行（预检 403、无 `Access-Control-Allow-Origin`）；路径穿越（`..%2f`、`%2e%2e`）无文件泄漏。
