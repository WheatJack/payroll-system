# 27 · 生产就绪演练：管理侧（系统管理员 + 部门主管）

- 演练对象：工资核算系统后端 `http://127.0.0.1:8080/api/v1`（前端 `http://localhost:5175`）
- 演练日期：2026-11-28
- 演练方式：**不使用浏览器**。全部用 `curl --noproxy '*'` 直连接口 + MySQL 直查复核；菜单范围按前端路由/布局的权限门禁推导并逐条对应接口验证。
- 演练账号：`admin`（SYS_ADMIN）/ `hr01`（薪酬专员）/ `hr02`（薪酬复核），密码 `Passw0rd!`
- 自建账号统一 `OPS_` 前缀：`OPS_clerk`(40)、`OPS_reviewer`(41)、`OPS_mgr`(42)，以及一次性探针 `OPS_probe`(43)；自建部门 `OPS_DEPT_A`(22)、`OPS_DEPT_B`(23)；自建期间 `2025-11`(33)。
- **清理状态**：演练结束后已删除上述账号/部门/期间，`payroll.seniority-pay-per-year` 恢复 `100`、`payroll.calendar.holidays` 恢复空，员工 199 的调动历史已还原，锁定演练期间 13 的 `locked_by/locked_at/unlock_reason` 已还原，解锁产生的 1821 条零值 YTD 已清除。
- 环境说明：测试期间有另一路浏览器演练在同一库上操作（期间 30/32 等仍在使用），本报告只使用独立新建的期间 33 和当时无锁的期间 13，未改写他人正在核对的数据。

## 0. 结论摘要

| 角色 | 可用性结论 | 评分 |
|---|---|---|
| 系统管理员（SYS_ADMIN） | **账号/角色/部门/参数四类配置都能闭环**，但被"三权分立"挡在全部薪酬数据之外：改完工龄单价后**无法自己重新生成期间验证**，也看不到任何工资/报表；审计只有表没有界面。 | **6 / 10** |
| 部门主管（DEPT_MANAGER） | **只读边界守得很干净**：期间/编制台/三类报表全部只含本部门，未锁定期间被 403 挡住，改工资/导出/锁定全部 403，系统管理菜单与接口都不可见。缺点是这个角色**只能看、不能做任何团队管理动作**，且看不到"当前口径是本部门"的显式标识。 | **8 / 10** |

**最大的三个坑**

1. **系统管理员不是"超级用户"**：`admin` 没有任何 `payroll:*` 权限，不能生成、锁定、导出、看敏感字段，甚至不能自己验证改完的参数是否生效。任务书里"管理员改参数→重新生成→抽查"的动作，实际必须切到 `hr01` 才能完成。这是有意的三权分立，但**运维/排障时需要同时持有两个账号**，且界面上没有任何提示。
2. **解锁是"半还原"**：`unlock` 服务层把 `lockedBy/lockedAt` 置空后调用 `updateById`，MyBatis-Plus 默认忽略 null 字段，**数据库里锁定人和锁定时间仍在**；期间列表会把一个 `EDITING` 期间显示成"锁定人：薪酬复核"，同时留下 1821 条全零 YTD 台账。管理员会以为没解锁成功。
3. **删除都是软删除，测试账号/部门会永久堆积**：`DELETE /users`、`DELETE /depts` 只置 `deleted=1`，`sys_user_role` 关联行还留着。本库已有 `rol_mgr_6568`、`acc_*`、`reg_*` 等几十个历史验收账号；没有"彻底清理"入口，只能进数据库硬删。对生产不是功能缺陷，但对"演练/验收后复原"是实打实的负担。

## 1. 角色一：系统管理员的一天（admin）

### 1.1 开三个账号：无角色 → 分配角色

**步骤 A：先建无角色账号**

```bash
curl -s --noproxy '*' -X POST $B/users -H "Authorization: Bearer $A" \
  -H 'Content-Type: application/json' \
  -d '{"companyId":1,"username":"OPS_clerk","password":"Passw0rd!","realName":"薪酬专员","deptId":1,"status":1}'
```

| 项 | 内容 |
|---|---|
| 期望 | 创建成功，`roleIds=[]`、`permissions=[]` |
| 实际 | `200 {"code":0,...,"roleIds":[],"permissions":[]}`，三个账号均如此 |
| 顺畅度 | 顺。但**无角色账号仍可登录**：`POST /auth/login` 返回 200，`permissions=[]`、`dataScope=SELF`；访问 `/periods` 得 403。前端 `resolveLandingPath([])` 返回 null，会落到 `/no-access` 兜底页。新同事在这段时间里"能登录但什么都看不到"，如果没有交接说明会以为账号坏了。 |

**步骤 B：分配角色**

```bash
curl -s --noproxy '*' -X PUT $B/users/40 -H "Authorization: Bearer $A" \
  -H 'Content-Type: application/json' -d '{"roleIds":[1]}'
```

| 账号 | 角色 | 实际返回权限 | dataScope |
|---|---|---|---|
| OPS_clerk | PAYROLL_CLERK(1) | `record:view, record:edit, import:submit, export, sensitive:view` | ALL |
| OPS_reviewer | PAYROLL_REVIEWER(2) | `record:view, period:lock, period:unlock, export` | ALL |
| OPS_mgr | DEPT_MANAGER(3) | `record:view` | DEPT_SUB（deptId=8 北京研发中心） |

- **旧 token 立即生效**：分配角色前拿到的 token 不重新登录，下一请求就带上了新权限（`PermissionInterceptor` 每请求查库），不需要让用户重新登录。
- **菜单范围（由 `MainLayout.vue` + `router/index.ts` 的 `meta.perm` 推导，并与接口实测一致）**：

| 账号 | 薪酬菜单（人员/工资项/期间/月报/年报/个税） | 导入页 | 系统管理菜单 | 导出按钮 |
|---|---|---|---|---|
| OPS_clerk | 6 项全有 | 有 | 无 | 有 |
| OPS_reviewer | 6 项全有 | 无（缺 `import:submit`） | 无 | 有 |
| OPS_mgr | 6 项全有 | 无 | 无 | 无 |
| admin | **0 项** | 无 | 5 项全有 | 无 |

> **踩坑点（与任务前提不符）**：任务书写"分角色前必须先建无角色账号再改"。实测**直接带 `roleIds` 创建也成功**（探针 `OPS_probe` → `200`，权限立即完整），前端新增用户表单本来就有"角色"多选框（`UserListView.vue:421`）。所以两步法不是必须，只是**低权管理员**给已存在账号加角色的通路。真实管理员按界面上一次性建好即可。

### 1.2 配置系统参数：工龄单价 100 → 120 → 100

```bash
curl -s --noproxy '*' -X PUT $B/configs/payroll.seniority-pay-per-year \
  -H "Authorization: Bearer $A" -H 'Content-Type: application/json' -d '{"value":"120"}'
```

| 项 | 期望 | 实际 | 顺畅度 |
|---|---|---|---|
| 参数写入 | 200，值变 120 | `200 value=120`；`pay_audit_log` 新增 `CONFIG/UPDATE old=100 new=120`（id 4722） | 顺 |
| 重新生成 | 用新参数重算同一期间 | **admin 无法执行**：`POST /periods/33/generate` 需要 `payroll:record:edit`，admin 只有 `sys:*` → 403。改用 `hr01` 生成，run 48 `SUCCESS 1802` | **不顺：必须换号** |
| 抽查工龄 | 20 年员工 2000 → 2400 | 同员工（BJ00014 薛子涵，20 年）：`SENIORITY_PAY` 2000.0000 → **2400.0000** | 顺，重算幂等 |
| 全量核对 | 总额 ×1.2 | 工龄工资合计 1,813,900 → **2,176,680**（精确 ×1.2） | 顺 |
| 改回 100 | 恢复 | 200，审计 id 4727 `old=120 new=100`；再生成后合计回到 1,813,900 | 顺 |

- 参数为**全局即时生效、无生效日期/版本**：改完只影响"以后重新生成"的期间；已锁定的历史期间仍是旧口径。真实管理员若以为"改参数=全公司追溯"，会得到不一致的历史数据。这一点参数页没有任何说明。
- 生成是**异步**的：`POST /generate` 只返回 `runId`，警告、失败明细要再轮询 `GET /runs/{id}` 才看得到。脚本化/自动化时必须自己轮询。

### 1.3 配置法定节假日

```bash
curl -s --noproxy '*' -X PUT $B/configs/payroll.calendar.holidays \
  -H "Authorization: Bearer $A" -H 'Content-Type: application/json' \
  -d '{"value":"2025-11-03,2025-11-04,2025-11-05"}'
```

| 阶段 | 期望 | 实际 | 顺畅度 |
|---|---|---|---|
| 空值 | 参数页显示风险提示 | `GET /configs` 返回 `warning="法定节假日未配置：不足月折算只排除周末，折算天数可能偏多"` | 顺，提示很清楚 |
| 空值时生成 | 生成结果带警告 | 新建 2025-11 期间 33，run 47：`SUCCESS total=1829 success=1802 failed=0`，`warnings=["本期有 11 人按不足月折算，但法定节假日未配置，折算天数可能偏多"]` | 顺，警告只在生成进度里，关掉弹窗就没了 |
| 写入 3 个日期 | 警告消失 | `GET /configs` 的 `warning=null`；重新生成 run 49 → `warnings=[]` | 顺 |
| 清空复原 | 警告回来 | PUT `value=""` → `warning` 立即回来；run 50 → 原警告重现 | 顺 |

- 日期格式只校验 ISO（`YYYY-MM-DD`），**不校验年份/是否落在期间内/是否重复**。写 `2025-11-03` 到 2026 年的期间也不会报错。真实管理员可能把"调休补班"也当节假日填进来，系统无法区分"法定节假日"与"放假日"。
- 参数页能看到的警告只有"为空"这一种；"写了一个不属于本期的日期"没有任何提示。

- 软删除的副作用：`deptCode` 行仍占用；再次建同名编码是否会撞唯一键取决于唯一索引是否含 `deleted`，本次未复测，但历史 `OPS_DEPT_*` 行确实永久留在库里。

### 1.5 处理一次锁定纠纷

> **任务前提与现实不符**：任务书说"hr01 锁错了期间，用 hr02 解锁"。实测 `hr01`（薪酬专员）**没有** `payroll:period:lock`：`POST /periods/13/lock` → `403 无权限执行该操作`。能锁的是 `hr02`（薪酬复核）。所以真实场景只能是"复核人锁错了，复核人自己解锁"，或"复核人锁、管理员找另一个复核人解"。

| 步骤 | 命令 | 期望 | 实际 | 顺畅度 |
|---|---|---|---|---|
| hr01 锁 | `POST /periods/13/lock` (hr01) | 403 | `403 无权限执行该操作` | 符合角色设计，但任务剧本走不通 |
| hr02 锁 | 同上 (hr02) | 200 LOCKED | `200 status=LOCKED lockedBy=2`，期间 13（2025-01，compiled_by=1）通过 C4 校验 | 顺 |
| 空原因解锁 | `POST /periods/13/unlock {"reason":"  "}` | 400 | `400 解锁原因必填` | 顺 |
| 带原因解锁 | `{"reason":"OPS演练：hr01 反馈选错期间，解锁核对"}` | 200 EDITING | `200 status=EDITING unlockReason=...`，响应里 `lockedBy=null` | 表面顺 |
| 审计 | 查 `pay_audit_log` | 有 LOCK/UNLOCK + 操作人 + 原因 | id 4750 `LOCK EDITING→LOCKED operator=2 薪酬复核 ip=127.0.0.1`；id 4751 `UNLOCK old=LOCKED new=原因` | 顺，字段齐全 |
| 解锁后的真实状态 | 列表应显示未锁定 | **`GET /periods` 仍显示 `lockedBy=2`、`lockedAt=2026-11-28 11:15:55`**，而状态是 `EDITING` | **坑（中）**：响应 DTO 来自内存实体显示 null，列表来自数据库显示旧值；`updateById` 忽略 null 导致 `locked_by/locked_at` 没被清空 |
| YTD 回滚 | 解锁应把本期从累计台账减回 | 累计金额确实减回 0，但**留下 1821 条 `paid_months=0` 的全零 `pay_ytd` 行**（原期间从未锁过，本不该有行） | 半还原；本次已手工清掉 |

- 审计**只能查数据库**：系统没有 `AuditController`，前端也没有审计页面/路由。管理员要回答"谁解锁的、原因是什么"，只能进 MySQL。这是管理侧最大的功能缺口之一。

### 1.6 安全检查：新账号的敏感字段权限

```bash
curl -s --noproxy '*' $B/employees/199/sensitive -H "Authorization: Bearer $T"
```

| 账号 | 期望 | 实际 |
|---|---|---|
| OPS_reviewer（复核） | 无敏感权限 → 403 | `403 无权限执行该操作` |
| OPS_mgr（主管） | 403 | `403 无权限执行该操作` |
| admin（系统管理员） | 任务书默认"管理员能看"，但系统设计是三权分立 | `403 无权限执行该操作`（admin 也没有 `payroll:sensitive:view`） |
| OPS_clerk（薪酬专员） | 任务书期望"新账号没有 sensitive 权限" | **`200`，返回明文身份证 `110101197004251293`、手机号 `13758134094`** |

- 原因不是新账号被误授权，而是 **PAYROLL_CLERK 角色本身就带 `payroll:sensitive:view`**（`sys_role_grant` role_id=1）。也就是说**所有薪酬专员默认都能看全员明文证件号/手机号**。如果岗位设计确实需要（参保、开卡），应在制度上说明；如果遵循最小权限，这个默认授权过宽，建议从角色模板拆出去、按人单独授予。
- 敏感查询有审计：`pay_audit_log` 新增 `EMPLOYEE/199/VIEW_SENSITIVE operator=40 薪酬专员`；但 `field_name/new_value` 均为空，只记"谁看了谁"，不记"看了哪些字段"。
- 复核/主管/管理员三条 403 证明**接口层门禁是可靠的**，不是靠前端隐藏按钮。

- 但**页面没有"数据范围：北京研发中心"的显式标识**（《22》已提过，本次仍存在）。同一个"工资期间"页面，HR 看到 1,877 人、主管看到 232 人，界面无从区分，汇报时容易误读为全公司。

## 3. 真实管理员会踩的坑（按影响排序）

| # | 严重度 | 坑 | 证据/复现 | 建议 |
|---|---|---|---|---|
| 1 | 高（流程） | **系统管理员做不了薪酬动作，也无法自验参数** | admin 调 `/periods/33/generate`、`/reports/export`、`/employees/199/sensitive` 全 403；改完工龄单价必须换 `hr01` 生成才能抽查 | 在参数页提示"修改后需薪酬专员重新生成生效"；或给 SYS_ADMIN 一个受审计的"代操作"能力（不建议直接放开） |
| 2 | 中 | **解锁不清理 `locked_by/locked_at`** | 解锁后 `GET /periods` 返回 `status=EDITING` 但 `lockedBy=2`、`lockedAt=...`；DB 同样 | `unlock` 用显式 UPDATE 置 NULL，或实体字段加 `updateStrategy=IGNORED` |
| 3 | 中 | **解锁残留零值 YTD 台账** | 期间 13 解锁后 `pay_ytd` 多出 1821 条 `paid_months=0`、金额全 0 的行 | 减回为 0 时删除行，而不是更新为 0 |
| 4 | 中 | **审计无界面** | 无 AuditController、无前端路由；锁定/解锁/配置/敏感查看的记录只能查 `pay_audit_log` | 增加只读审计页（按业务类型/操作人/时间筛选） |
| 5 | 中 | **软删除导致账号/部门永久堆积** | `DELETE /users/40` 返回 200，`sys_user.deleted=1`、`sys_user_role` 关联行仍在；库内已有大量历史验收账号（`rol_mgr_6568` 等） | 提供"彻底删除"或定期清理任务；至少让用户名/部门编码可复用 |
| 6 | 中 | **调动点错无法当日撤回** | 员工 199 同日改回原部门 → 409（重叠任职区间）；改次日才成功，留下未来生效的 TRANSFER | 前端提示"生效日必须晚于最近一次调动"，或支持撤销当天调动 |
| 7 | 中 | **薪酬专员角色默认带敏感字段权限** | role 1 的授权含 `payroll:sensitive:view`；`OPS_clerk` 直接拿到明文身份证/手机号 | 按最小权限拆分角色，敏感查看单独授权并定期复核 |
| 8 | 低 | 生成/警告是异步且只在进度 DTO 里 | 关掉生成结果弹窗后，警告（如"节假日未配置"）无法回看；`pay_run` 有状态但前端无历史入口 | 期间详情保留"最近一次生成警告" |
| 9 | 低 | 参数无生效日期/版本，历史期间口径不一致 | 100→120 只影响重算，已锁定期间仍按 100 | 参数页注明"仅对重新生成的期间生效" |
| 10 | 低 | 节假日只校验格式 | 可填任意 ISO 日期、可填不属于本期的日期、可与周末重叠 | 增加期间范围/重复校验 |
| 11 | 低 | `/companies` 对所有登录角色开放 | 主管/专员均 `200`，返回全部 4 个法人主体 | 若主体清单属敏感组织信息，应按数据范围过滤；若仅用于下拉可接受 |
| 12 | 低 | 无角色账号的默认 dataScope 是 `SELF` | 新建未授权账号 `dataScope=SELF`，登录落到 `/no-access` | 可接受，但开户交接需说明"分配角色后才可见菜单" |

**做得好的地方（同样要记）**

- 角色权限点是**后端目录 + 白名单**，前端不能自造；越权全部在接口层 403，不依赖隐藏按钮。
- 部门主管的期间列表过滤、编制台 403、报表数据范围下推 SQL、跨部门人员 403，形成"列表—明细—报表"三层一致的边界。
- 配置、用户、部门、敏感查看、锁定/解锁都有审计，且带操作人姓名和 IP。
- 部门删除的三道 409 校验提示明确、可操作。
- 参数改动、生成、报表选择期间等关键动作都有幂等/明确失败语义（重复锁 409、空原因 400、编辑未锁定期间 403）。
