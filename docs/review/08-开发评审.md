## 1 冻结的工资表导出

### 1.1 结论

**能做，EasyExcel 的动态列本身不是难点（半天量级）。难点在"列从哪来"和"金额单元格用什么类型"两个口径，选错第一次提测就返工。**

### 1.2 列从哪来：不要复用编制台的 `withUsedButDisabledColumns`

现状 `RecordService.grid` 的列 = 启用科目 ∪ 本期出现过的科目（`RecordService.java:116-145`）。合并时用 `itemService.list(companyId, null, null)` 回查字典，查不到就兜底成：

```
名称 = itemCode，category = VARIABLE，direction = 1，scale = 2   // RecordService.java:136-142
```

`itemService.list` 走 MyBatis-Plus 逻辑删除，**软删除（`deleted=1`）的科目查不到**，于是：

- 一个历史期间里被删掉的**扣款**科目，会被兜底成 `direction=1`；
- 编制台/导出按方向汇总时，这笔扣款被算进应发 → **gross / deduction / net 三个数全错，且不报错**。
- `status=0`（停用）的科目没问题，`list` 不带 status 过滤，会返回。所以 06 审计里说的"已停用科目"其实能过，**真正炸的是"已删除科目"**。

导出的列**不能依赖任何字典**。正确来源是期间自己的明细快照：

- 列集合与顺序：`pay_record_item` 按 `item_code` 聚合，取 `MIN(sort_no)` 排序、`item_code` 兜底；名称取快照 `item_name`，方向取快照 `direction`，精度取字典 `precision_scale`（字典没了就取该列金额的最大有效小数位）。
- 这样科目后来被改名、停用、软删除、调整 sortNo，导出的"冻结表"都不变。
- 若同一 `item_code` 在期间内出现不一致的 `item_name`/`direction`（正常不应发生），**直接让验收测试红**，不要静默挑一个——这是数据 bug，挑一个等于把它藏起来。

### 1.3 真正的"冻结"：建议在锁定时快照列定义

只按"出现过的科目"导出还有一个问题：某科目本期全员为 0（没有任何明细行），它在编制台上是可见列，导出却没了。而"冻结工资表"应该等于**锁定当时屏幕上那张表**。

建议（低成本，一处 DDL + 一处写）：

- `pay_period` 增一列 `column_snapshot JSON NULL`，`PeriodService.lock` 成功时写入当时的 `GridColumn[]`（code/name/direction/scale/sortNo）。
- 导出 LOCKED/ARCHIVED 期间时优先用快照；没有快照的老期间回退到"按明细聚合"（1.2 的规则）。
- 解锁再锁定会重写快照，语义自然正确。
- 不自增列也可以：只用 1.2 的明细聚合，但要在导出文件的"说明"sheet 里写明"仅包含本期发生过明细的科目"。二选一，**门 2 定**；推荐快照。

### 1.4 列顺序

按快照的 `sortNo` 升序，编号相同再按 `itemCode`。元信息列（工号/姓名/部门/类型/职级/工龄）固定在最左，三个合计列（应发/扣款/实发）固定在明细列之后。**不要**把收入列和扣款列拆成两组重排——HR 对账时是拿导出文件和屏幕逐列对，顺序不一致就要重新学一遍。

### 1.5 金额文本格式：技术上是低难度，产品上是高代价

契约明确"金额列以文本格式写入"（`openapi.yaml:1034`）。实现就是写 `String`，再给单元格设 `@` 文本格式，难度低。

但要提前说清后果：**文本单元格在 Excel 里不能 `SUM`**。财务拿到工资表的第一动作就是拉一列看合计对不对；文本列 `SUM` 返回 0，会直接变成"系统导出的表不能核"。而"防止科学计数法"这个原始理由，对金额根本不成立——金额是 `DECIMAL(18,4)`，用数值单元格 + `#,##0.00` 格式既不会科学计数、又能求和。真正需要文本的是**工号**（`10001` 这类纯数字工号会被 Excel 吃掉前导零/转数值）。

建议改成：**金额写数值单元格 + 数字格式；工号写文本**。这需要改契约一行。若坚持契约原文，就把"导出的表在 Excel 里不能求和"写进验收单，别让实施方背锅。这是本报告认为**最值得现在改**的一条（见 §9）。

### 1.6 合计行

低难度，但有两个具体坑：

- EasyExcel 写完数据再追加合计行时，必须用 `needHead=false` 的 `WriteSheet` 再写一次；否则第二遍会把表头再打一遍。
- 合计要按**明细的精确值**分组求和（`BigDecimal`），最后按 `max(2, 该列展示精度)` 格式化一次。不要"把每行显示值加起来"，否则 4 位小数的列会出现"合计 ≠ 列加总"。
- 追加一列"校验"或在说明 sheet 写一条：`应发合计 − 扣款合计 = 实发合计`，并和 `SUM(pay_record.gross_amount)` 对得上。这条直接变成验收断言。

### 1.7 验收（写死）

构造一个期间，含：正常科目、`status=0` 科目、`deleted=1` 科目、被改过名的科目、4 位小数科目。导出后用 POI 读回断言：

- 列顺序 = 快照 sortNo；
- 已删除列的名称/方向来自快照（不能是 `itemCode`/`direction=1`）；
- 每列合计 = 该列所有单元格精确加总；
- `Σ(dir=1) − Σ(dir=2) = Σ(net_amount)`；
- 合计行与明细行数、表头行数正确（没有重复表头）。

## 2 同一端点：成功 xlsx、失败 JSON

### 2.1 结论

**能做。现有基础是干净的：没有全局 `ResponseBodyAdvice`，`{code,msg,data}` 是 Controller 自己 `Result.ok(...)` 拼的，二进制端点不返回 `Result` 就不会被套信封；异常照旧落到 `@RestControllerAdvice`。唯一必须遵守的规则是"先把整个文件准备好，最后再碰响应"。**

### 2.2 为什么"先写头再流式生成"会坏

HTTP 状态码和响应头一旦写出（或缓冲区被 flush），就不能再改。若在 `EasyExcel.write(response.getOutputStream())` 写到第 800 行时抛异常（POI 异常、审计写失败、客户端断连、懒加载异常），结果是：

- 客户端拿到 `200` + 一个**半截 xlsx**；
- `GlobalExceptionHandler` 想写 JSON 也写不进去（响应已提交），Spring 只会打一条 "response already committed" 日志；
- 前端拿到的是一个能下载、打不开、没有任何错误提示的文件。

这正是问题里担心的"`@ExceptionHandler` 把二进制请求变成 JSON"的**反面**：它根本变不了，因为响应已经提交。真正的防护不是 advice，而是**两段式**。

### 2.3 推荐形状（与 07 §4.2 一致，但修正一处）

07 的顺序规则（准备 → 审计 → 设头 → 写出）是对的。对 07 "不要返回 `byte[]`"这一条，要按规模分开：

| 导出类型 | 规模 | 做法 |
|---|---|---|
| 月度/年度汇总 | 几十到 2000 行 | **`ResponseEntity<byte[]>`**：最简单，且天然满足"失败绝不产生坏文件"；几 MB 内存无压力 |
| 期间工资表 | 2000 × 约 40 列 ≈ 8 万单元格 | 同上，2–5MB；或写临时文件后 `Files.copy` |
| 工资条 | 2000 人 × 约 30 行 ≈ 6 万行 | **临时文件**（`finally` 删除），再 `Files.copy` 到响应；不要 10–20MB 的 `byte[]` |
| 导入错误报告 | ≤ 5000 行 | `byte[]` |

"准备"必须意味着**文件内容已经完整生成**（字节数组或临时文件），而不是"查询结果已经拿到"。07 说的"写阶段只剩 I/O"在 POI 上并不完全成立，临时文件方案能把它变成真的。

### 2.4 `produces` 与 `Accept` 的隐藏 406

- **不要**在导出 mapping 上写 `produces = xlsx`。Spring 的内容协商对**异常响应**同样生效：如果客户端只接受 xlsx，`GlobalExceptionHandler` 返回的 `Result` 没有可接受的类型，会抛 `HttpMediaTypeNotAcceptableException`（406），前端连错误信息都拿不到。
- 显式给 `ResponseEntity` 设 `Content-Type` **不能**绕过 acceptable-types 检查。正确做法是：mapping 不限制 produces；前端下载请求的 `Accept` 带 `*/*`（axios 默认就是 `application/json, text/plain, */*`）。自己封下载函数时不要把它收窄成只有 xlsx。
- 成功用 `ResponseEntity<byte[]>`（`ByteArrayHttpMessageConverter` 处理），失败用 `ResponseEntity<Result>`（Jackson 处理），两个 converter 不会打架。

### 2.5 其他必须补的点

- **拦截器的 401/403 是手写 JSON**（`PermissionInterceptor.java:131-136`），对二进制端点是对的；但它是手拼字符串，msg 目前都是常量所以安全。不要给权限消息加用户输入。
- **审计写在碰响应之前**，独立事务（07 §4.2 的 `REQUIRES_NEW`）。审计失败 = 导出失败，返回 JSON 500，不产出文件。`pay_audit_log.operator_name` 是 NOT NULL，而 `CurrentUser` 里**没有 realName**（只有 userId/companyId/permissions/dataScope/employeeId），审计要多查一次 `sys_user.real_name`，或把 realName 加进 `CurrentUser`（拦截器本来已经查了用户行，零成本）。
- **上传相关的异常现在会变 500**：`MaxUploadSizeExceededException` / `MultipartException` / `MissingServletRequestPartException` 都不在 `GlobalExceptionHandler` 的 400 分支里，会落到 `handleOther` → 500。导入端点必须补 400 + 人话提示，否则 10MB 超限时用户看到"系统异常"。
- 响应头加 `Cache-Control: no-store`、`X-Content-Type-Options: nosniff`（工资数据不进浏览器缓存）。
- 中文文件名用 `ContentDisposition.attachment().filename(name, UTF_8)`（RFC 5987），同时保留 ASCII 兜底。

### 2.6 验收

MockMvc 三条，缺一不可：

1. 200：`Content-Type` 精确匹配、`Content-Disposition` 存在、body 以 `PK\x03\x04` 开头、`Content-Length` 与 body 长度一致、POI 能读回。
2. 403（无 `payroll:export`）：状态 403、`Content-Type: application/json`、body 能解析成 `{code:403,...}`，**不是**文件。
3. **故障注入**：让写出的第 N 行抛异常 → 必须是 500 JSON，绝不能是 200 + 半截文件。这条是两段式设计的唯一证明。

## 3 前端下载与错误解码

### 3.1 结论

**能做，但不是"20 行工具函数"。现有 `client.ts` 的两处设计会让最直觉的写法失败：(a) 成功拦截器把 `response` 丢掉只返回 `data`，拿不到 `Content-Disposition`；(b) `responseType:'blob'` 时错误体也是 Blob，现有错误分支读不到 `msg`。另外全局 `Content-Type: application/json` 会让 multipart 上传失败。**

### 3.2 三个具体坑

1. **响应头丢失**：`client.ts:94-110` 成功分支返回 `envelope.data` 或 `body`，从不返回 `response`。所以用共享 `http` 实例请求 xlsx，拿到的只有 Blob，文件名无从解析。
2. **Blob 错误不可读**：`client.ts:111-123` 里 `error.response.data` 在 blob 模式下是 Blob，`body?.code`/`body?.msg` 全是 undefined，最终展示的是 `DEFAULT_ERROR_MESSAGES` 的状态码兜底文案。后端精心返回的"还有 37 行未通过校验，修正后重新上传"会丢失。
3. **multipart 的 Content-Type**：`client.ts:83` 给实例设了 `Content-Type: application/json`。上传 `FormData` 时必须删掉这个头，让浏览器自己写 `boundary`；否则服务端收到的是 JSON 头 + multipart 体，结果通常是 415 或 `MultipartException` → 500。

### 3.3 做法

- 在 `client.ts` 里加一条**独立的下载/上传通道**（单独的 axios 实例，只共享 token 请求拦截器，`responseType:'blob'`，超时 120s）。不要改共享实例的响应拦截器去兼容 Blob——那会让所有现有调用方的类型和错误语义变复杂。
- 成功：先看 `content-type`。若是 JSON（后端 bug 或网关返回），把 Blob 读成文本按错误处理，**不要保存**；否则解析 `Content-Disposition`（优先 `filename*=UTF-8''`，再 `filename="..."`），`decodeURIComponent`，缺失则前端按报表类型/期间/时间戳兜底命名。
- 失败：`error.response.data instanceof Blob` → `await blob.text()` → 能 `JSON.parse` 且含 `code` 就构造 `ApiError(code,msg,data)`，否则按状态码兜底。401 仍要触发全局登出（把 `handleUnauthorized` 从模块私有导出即可）。
- 触发下载：`createObjectURL` → 插入 DOM 的 `<a download>` → click → `setTimeout(0)` 再 `revokeObjectURL`（Firefox 要求 a 在文档里，Safari 立即 revoke 会失败）。
- 下载请求的 `Accept` 带 `application/json`（见 §2.4），避免 406。
- 导出/上传按钮的 403：展示后端 msg，并**顺手重拉一次 `/auth/me`**（见 §5），别只弹一个"无权限"就结束——此时菜单里可能还挂着用户已经没有的入口。
- 若 `VITE_API_BASE` 是绝对地址（跨域），后端/nginx 要加 `Access-Control-Expose-Headers: Content-Disposition`；同源代理部署则不需要。

### 3.4 验收

- 单测：`parseFilename`（两种形式、中文、缺失）、`toApiError(blob)`（JSON blob / HTML blob / 空 blob）。
- 手工：用过期 token 点导出 → 页面显示"未认证或登录已过期"并跳登录，**没有**下载任何文件；无 `payroll:export` → 显示后端 msg，浏览器 Downloads 里没有 200 字节的坏文件。

## 4 导入

### 4.1 结论

**有坑，其中两个是结构性的：**

- **"预校验不落库"按字面做不到**：要返回 `batchId`、要支持 `GET /import/{batchId}/errors`、`commit` 请求体里又没有数据，所以批次行、错误行、原始文件**必须落**。"不落库"只能解释为"不写 `pay_record` / `pay_record_item`"。
- **提交必须重新读文件、重新校验**，不能信任预校验结果。07 §5.1/§5.3 的"批次表 + 原始文件重放"是正确解，本文补充实现层的几个卡点。

### 4.2 5000 行预校验要多久

| 实现方式 | 估算 | 结论 |
|---|---|---|
| EasyExcel 流式解析 5000 行 × 约 12 列 | 0.4–1s（冷启动 1–2s） | 可忽略 |
| **逐行查库**（员工/科目/记录/明细 4 次/行） | 2 万次往返，本地 3–8s，跨机 1–2ms RTT 下 20–60s | **会超 15s 目标**，且看起来像"EasyExcel 慢" |
| **批量预加载**（5 条查询） | 员工候选 ~2000、科目几十、期间记录 ~2000、明细 ~4 万，合计 0.3–0.8s | 总计 **1–3s**，余量很大 |

所以校验器必须**先批量取数、再纯内存逐行判**：

1. 期间 + `assertWritable` + 数据范围；
2. `findCandidates`（已有，返回本期间应发薪员工）建 `empNo → employee`；
3. 本主体 + 集团通用 `pay_item` 建 `itemCode → def`；
4. 本期间 `pay_record` 建 `employeeId → record`；
5. 这些 record 的全部 `pay_record_item` 按 `recordId` 分组（一次 `IN` 查询）。

50000 行时不能把行全留在内存：用 EasyExcel `ReadListener` 逐行处理，只保留错误列表、文件内 `empNo` 去重集合、计数器，内存常数级。

### 4.3 暂存什么、放哪

- `pay_import_batch`：一个批次一行（`VALIDATING → VALIDATED/FAILED`），必须有；`file_hash` 用于防重提。
- `pay_import_error`：只存错误行（上限 `payroll.import.max-error-rows=5000`）；`fail_rows` 计的是**真实失败数**，不能因为只存 5000 条就写 5000。
- 原始文件：落到 `payroll.storage.local-path`（相对路径写进 `file_path`），提交时重读。
- **不建 staging 表**（07 §5.1 已否决）。成功行只存在文件里。

两个实现层注意：

- `pay_import_batch` **没有 `company_id`**，主体必须从 `period_id` 反查；校验和提交都要 `assertPeriodVisible`。批次查询/下载错误报告还要校验属主（`operator_id` 或同主体 + `sys:user:view`），契约没写，建议补一句。
- 文件落本地盘意味着**单实例**。如果将来多副本部署，validate 和 commit 可能落到不同节点 → "文件不存在"。要么现在写死"单实例部署"并进运维文档，要么换共享存储（MinIO 是 DDL 注释里的原计划，但未实现）。不要留成"看起来支持集群"。

### 4.4 用户改完再传：整份重传

**只传失败行做不到，也不该做。** 原因：

- 成功行没有被暂存，服务端没有"上次那批好数据"可拼；
- 两次上传的期间状态、导入模式、科目字典可能已经不同，拼起来语义不一致；
- 契约里 `commit` 只有 `batchId`，没有"补丁行"的位置。

正确闭环：下载错误报告 → 改原文件 → **整份重新上传**（新 hash、新批次）。UI 文案写死"修正后重新上传整份文件"。

hash 查重的边界（07 §5.4 已写，这里强调实现细节）：

- 只拦 `COMMITTED`（同 `period_id` + 同 hash）→ 409；
- 同 hash 的 `VALIDATED`/`FAILED` 不能拦，否则用户修了期间状态后想重传同一份文件会永远被拒；
- 因此**不能加** `UNIQUE(period_id, file_hash)`（MySQL 没有部分唯一索引，会把 VALIDATED 也拦住）；用 07 的"批次行 `FOR UPDATE` + 期间行锁"保证先查后写无竞态。

### 4.5 部分失败禁止提交：三处都要拦住

1. **校验结果**：`failRows > 0`。
2. **提交端点**：重新校验，有任何错误 → 409，一行都不写（不能只信前端置灰的按钮）。
3. **UI**：提交按钮置灰 + 红色文案"还有 N 行未通过校验，修正后重新上传整份文件"；已校验批次旁边放"下载错误报告"。

另外建议加一个**变更预览**（不是必须，但能消掉导入类系统最大的投诉）：校验完成后显示"将覆盖 N 个手工值 / 新增 M 条明细 / 影响 K 人"。批量预加载的数据结构已经足够算这个 diff，成本很低。

### 4.6 写入路径：不能复用 `RecordService.applyItem`

- `applyItem` 第一件事就是拒 `editable != 1`（`RecordService.java:250-253`）。而 `POST_ALLOW` 是 `editable=0, importable=1`（`schema-mysql.sql:433`）——**导入它必然报"该工资项不允许手工编辑"**。这不是 bug，是两个开关的语义不同：可导入 ≠ 可手工编辑。导入需要自己的写入口，判 `importable == 1 && status == 1`，金额非负、小数位 ≤ `precision_scale` 的规则保持一致。
- 写入时**必须像 changeset 一样 `version_no + 1`**（`RecordService.java:196-205`）。否则另一个浏览器里开着的编制台保存时会用旧 version 成功覆盖导入结果，静默丢数。
- 每条受影响记录重算合计；整批末尾刷新一次期间合计（不要逐行刷，O(n²)）。
- `source='IMPORT'`；`quantity/unit_price` 保持 null。
- 员工本期没有 `pay_record` → 行级报错"本期无核算记录，请先生成"，**不要自动建记录**（07 §5.5 的理由成立：绕过计算器建出来的记录只有变动项没有固定项，还会占住 `uk_emp_ym_active`，之后生成走 UPDATE 也补不回固定项）。
- `FIXED` 导入的现状要提前说清：`importable=1` 的固定项**只有 `POST_ALLOW` 一个**（`BASE_SALARY` 是 0/0）。所以 FIXED 模板基本只有一列。如果业务期望的是"批量初始化人员/调薪"，那是另一个管道（写 `emp_employee`/`emp_comp_profile`），别塞进这个 `periodId` 的契约里。

### 4.7 文件格式（契约没写，必须补）

- 表头必须带 `itemCode`（如 `绩效奖金[PERF_BONUS]`），否则科目改名后模板和历史文件全对不上；解析时**按表头里的 code 建列映射**，不要按列号——用户删列/挪列是常事。
- Excel 数值单元格读出来可能是 `BigDecimal`、也可能被格式化成 `1.0E7`；统一走"取原始单元格 → 规范成字符串 → 严格解析"，禁止 `Double.parseDouble`。
- 千分位/货币符号直接报错（模板说明里写"禁止"），不要清洗后静默接受。
- `10MB` 与 `50000 行` 是矛盾的：50000 行 × 十几列的真实 xlsx 通常 15–30MB，会先撞 `spring.servlet.multipart.max-file-size: 10MB`。二选一：把导入端点的上限调到 50MB，或把 `payroll.import.max-rows` 降到 1–2 万。**现在两边都没改，实施时必炸。**
- 模板/错误报告也是二进制下载，复用 §2/§3 的通道；模板还要一个"说明"sheet（模式、空值规则、金额格式、归属期间口径）。

### 4.8 验收（写死）

- 5000 行合成文件：本机 ≤ 3s（预算 15s），且 `SELECT COUNT(*) FROM pay_record_item` 在 validate 前后不变。
- 同文件重复 validate：`COMMITTED` 前复用同一 `batchId`；commit 过再传 → 409。
- 校验后把期间锁定再 commit → 409，且没有写入。
- 同一批次并发 commit：一个成功、一个 409（批次行锁）。
- 同期间两批并发 commit（改不同员工）：期间合计 = 两批结果之和（期间行锁 + 末尾刷新）。
- 导入后编制台 grid 的 `version` 增加，旧 version 的 changeset 返回 409。
- `POST_ALLOW` 能导入（证明没有复用 `applyItem` 的 `editable` 判断）。
- 一行超过 4 位小数 → 该行报错，不写入，不四舍五入。

## 5 角色授权全量替换

### 5.1 结论

**授权本身能做，而且不需要任何"权限缓存失效"——系统里根本没有缓存。** `PermissionInterceptor` 每个请求都重新查库：`authMapper.findById(userId)` + `findPermissions(userId)` + `findDataScopes(userId)`（`PermissionInterceptor.java:61-77`）；`DEPT`/`DEPT_SUB` 的判定路径再由 `DataScopeEnforcer.deptIdOf` 查一次 `sys_dept`。`PUT /roles/{id}/grants` 提交后，**下一个请求**就生效；正在执行的请求不受影响。

**但同一份契约里的"重置密码后旧 token 全部作废"做不了**——`TokenService` 是无状态 HMAC，payload 只有 `userId:expireAt`（`TokenService.java:39-43`），服务端没有会话、没有吊销表。这是本轮唯一一个"照契约实现不出来"的点。

### 5.2 全量替换的正确语义

- 单事务"先删后插"；读者要么看到旧集合、要么看到新集合，看不到空集（InnoDB 原子性）。
- 去重请求里的权限点：`sys_role_grant` 有 `uk_role_perm`，重复项会直接 500。
- 权限点必须过服务端白名单（`PermissionCode` 常量集合），非法值返回 400；否则拼错的权限点会变成"永远不生效的死数据"，而且没人发现。
- 角色必须存在、未删除、`company_id` 在操作者范围内。
- 角色 `status=0`、用户角色增删、`data_scope` 修改——全部"下一请求生效"，同一条链路。数据范围多角色取最宽者（`PermissionInterceptor.widestScope`），所以**加一个窄角色不会收紧权限**。管理页必须提示这一点，否则管理员会以为"给他加个 SELF 角色就能限制"。

### 5.3 真正要补的是四个守卫（07 §6.3 正确，这里给代码级落点）

1. **授权放大守卫**：非 `ALL` 操作者只能授予自己拥有的权限点。否则一个只有 `sys:role:edit` 的分公司管理员可以新建一个带 `payroll:export` / `sys:user:edit` 的角色并挂给自己——**自我提权**，整张权限表变装饰。
2. **数据范围序**：`ALL > COMPANY > DEPT_SUB > DEPT > SELF`。`POST /roles`、`PUT /roles/{id}`、`PUT /roles/{id}/grants` 都要校验；契约只在 create 的描述里写了一句，实现时容易漏。
3. **用户角色分配的同类守卫**：`PUT /users/{id}` 的 `roleIds` 也是全量替换，同样能自提权。至少：不能改自己的角色；不能分配比自己范围更宽的角色；不能分配其他主体的角色（`sys_role.company_id` 必须等于用户的 `company_id`，`ALL` 操作者除外）。
4. **自锁守卫**：不能停用自己；不能让自己失去 `sys:role:edit`/`sys:user:edit`；不能停用**最后一个**仍持有 `sys:role:edit` 的启用用户。否则系统永久失去可管理性，只能改库恢复。契约里只写了"不能停用自己"，另外两条没有。

### 5.4 重置密码的 token 作废：做不了 → 改法

07 §6.4 的方案正确：`sys_user` 加 `token_version INT NOT NULL DEFAULT 0`，token payload 改成 `userId:expireAt:ver`，拦截器本来每个请求就 `findById` 拿到用户行，顺手比较，不匹配 → 401。重置密码、停用用户时 `token_version+1`。

要点：

- 这是**唯一**不引入会话存储的实现方式；加 Redis 黑名单是过度设计。
- 升级会导致所有在线会话失效一次（token 格式变了），写进发布说明。
- **不要**因为"改了角色"就升版本：权限是每请求现查的，踢下线没有意义。
- 契约必须改：要么按上面实现（token 载荷变了，属于契约级变更），要么删掉"token 全部作废"那句。

### 5.5 前端要知道权限会变

`stores/auth.ts` 的 `permissions` 是登录/`/me` 时的一次快照。管理员改了授权后，用户界面上的按钮不会自己消失，直到刷新或收到 403。建议：

- 业务接口返回 403 时，**去重后**调用一次 `fetchMe()` 并提示"权限已变更"；不要直接登出。
- 管理员保存 grants 后，如果改的是自己所属的角色，也调一次 `fetchMe()`。
- 这些是体验优化，不是安全防线——服务端每个请求都现查，安全语义已经正确。

### 5.6 验收

- 移除某角色的 `payroll:export` → 该角色用户下一次请求 403（不重启、不重新登录）。
- grants 传空数组 → 清空且不报错；传重复项 → 去重成功（不是 500）；传未知权限点 → 400。
- 重置密码 → 旧 token 立即 401（需要 token_version 落地）。
- 分公司管理员无法给自己授予自己没有的权限点、无法分配更宽的数据范围、无法停用最后一个管理员。
- TestDb 需要补 fixture：现有 `ALL_SCOPE_USER` 只有 view/edit/lock/unlock，`hr01` 有 export/import:submit 但没有 `sys:*`；系统管理与导出 IT 都要各自造账号（`TestDb.reset` 已包含全部表，不用改表清单）。

## 6 部门树与 ancestors

### 6.1 结论

**性能完全不是问题；问题是正确性和契约缺口。**

- 2000 人、几十个部门：`deptSubtreeSql`（`DataScopeEnforcer.java:166-169`）是 `ancestors LIKE '%,id,%'` + `dept_id IN (子查询)`。前导 `%` 让 `idx_ancestors` 用不上，但子查询扫的是 `sys_dept`（几十行），主查询走 `pay_record` 的 `idx_period_dept`/全期间 2000 行。**实测量级 < 5ms**，不要为它引入闭包表或递归 CTE。
- 真正要做的是：环校验、级联重算、同主体校验、长度/深度上限、停用可见性、删除入口。

### 6.2 环与层级校验（`PUT /depts/{id}` 必做）

- `parentId != id`；
- 新父不能是自己的后代：`parent.id == id || parent.ancestors.contains("," + id + ",")`；
- 父部门存在、未删除、同一 `company_id`（`companyId` 不可改，跨主体挂父必须拒）；
- 深度/长度：`ancestors` 是 `VARCHAR(512)`，按每级约 8 字符算 60 级左右就会溢出；设一个业务上限（如 10 级）并显式报错，别让 MySQL strict mode 抛 500；
- 改父之后级联重算所有后代的 `ancestors`（几十行，Java 里算完批量 UPDATE 最直观，也可一条 `CONCAT/SUBSTRING`）；
- `uk_dept_code(company_id, dept_code)` 冲突要单独映射成 409 人话；现有 `GlobalExceptionHandler` 只认 `uk_emp_ym_active`/`uk_emp_no`/`uk_id_hash`，其余都返回"数据重复，请刷新后重试"。

### 6.3 三个契约/实现缺口

1. **停用的部门会从树里消失，且永远无法重新启用**：`DeptService.tree` 硬过滤 `status=1`（`DeptService.java:31`）。管理页需要 `includeDisabled=true`（或管理员用单独查询），否则 `status=0` 就是一个单向门。
2. **没有删除端点**：契约只有 `POST`/`PUT /depts`。建议明确"不做物理删除，用 `status=0` 停用"，并让 `PUT` 能切状态；如果业务坚持要删，必须加守卫（无子部门、无在职人员、无历史记录、无用户归属）并软删。**不要**做一个把员工指向已删除部门的删除。
3. **权限依赖缺口**：`GET /depts`、`GET /companies` 现在要求 `payroll:record:view`（M1 Controller），`GET /roles` 要求 `sys:role:view`。一个只有 `sys:*` 的管理员进不了管理页（树/主体/角色全加载不出来）。要么允许 `sys:*:edit` 也能 GET，要么补 `sys:dept:view`/`sys:company:view`。这是管理页联调第一天就会撞到的。

### 6.4 其他

- `deptSubtreeSql` 不过滤 `status`：停用部门的下级仍然在数据范围内。这大概率是对的（停用部门不等于收回数据权限），但要明确写下来。
- `assertRecordVisible` 的 `DEPT_SUB` 分支对**每条被改记录**调一次 `findSubtreeIds`（`DataScopeEnforcer.java:171-177`）。一次 500 行的 changeset 就是 500 次子查询。按 07 §3.3 改成"每请求解析一次 `ResolvedScope`"顺手解决。
- `DEPT` 分支直接比较 `record.deptId` 与用户当前 `dept_id`（`authMapper.findDeptId` 每请求查一次）。人员历史期间在旧部门、用户后来调岗，就看不到旧数据——这是设计语义，不是 bug，但要在权限说明里写清楚。
- 部门树前端 `buildDeptTree` 已有；管理页只需父节点选择和停用开关，不需要拖拽（拖拽排序是 `pay_item` 的事）。

### 6.5 验收

- 三级部门 A→B→C，把 B 挂到 C 下 → 400；把 B 挂到 A 下 → 成功，C 的 `ancestors` 级联更新，`DEPT_SUB` 数据范围仍能看到 C 的员工。
- 跨主体挂父 → 400；`deptCode` 重复 → 409 且 msg 可读；`status=0` 后管理列表仍可见并能改回 1。
- 用一个 `DEPT_SUB` 账号跑报表：只看到本部门及下级；停用下级部门后范围不变（或按决定变），有测试固定。

## 7 金额精度

### 7.1 结论

**有坑，而且是"静默丢数"级别的坑。前端必须改；后端不要加 `setScale(2, UNNECESSARY)`——这段代码现在已经不存在了，`recalcTotals` 明确不做二次舍入，重新加回去会让 4 位小数明细直接抛 ArithmeticException、整批 changeset 回滚。**

### 7.2 前端：三处双重舍入

- `stores/grid.ts:97`：`nextRow[itemCode] = round(amount, 2)`。这是所有编辑的最终落点。
- `PayrollGridView.vue:124`：先 `round(cleaned, column.scale)`，再调 `store.edit` → 又被 round 到 2。
- `PayrollGridView.vue:260`：粘贴同一路径，先按 `column.scale` 再被 round 到 2。

后果：一个 `precision_scale=4` 的科目，用户输 `1.2345`：

1. `MoneyInput` 按 4 位提交 `1.2345`；
2. `store.edit` 存成 `1.23`；
3. `buildChangeset` 拿 `1.23` 和原始值比较，不同就发给后端；
4. 后端按 4 位存 `1.2300`。**四分钱在没有任何提示的情况下消失了**，而且从 UI 上无法看出发生过截断。

改法：

- `edit(recordId, itemCode, amount, scale)`，按**列精度**舍入；只有拿不到列定义时才默认 2。`onEditCommitted` 和粘贴两处都传 `column.scale`。
- 展示：`money.format`（`money.ts:111`）一律 `round2`。对 4 位列，单元格显示 2 位、footer 用精确加总再 `round2`，会出现"显示合计 ≠ 显示单元格之和"（3 个 `0.005` 显示为 3×`0.01`，合计显示 `0.02`）。统一规则：**单元格展示位数 = `max(2, column.scale)`；合计位数 = `max(2, 该表最大列精度)`**。这样"显示合计 = 显示单元格之和"恒成立。
- `MoneyInput` 的 `scale` 已经支持，输入/提交按 `column.scale`；展示按 `max(2, scale)`。`scale=0` 的科目输入整数、展示 `100.00`，可以接受，写进说明。
- `sameAmount`/`eq` 本身没问题，问题只在 store 的硬编码。

### 7.3 后端：现状是对的，别改错方向

| 位置 | 现状 | 结论 |
|---|---|---|
| `RecordService.applyItem` | 按 `def.getPrecisionScale()` 舍入（`:255-257`） | 保持 |
| `RecordService.recalcTotals` | 精确加总，不 setScale（`:294-313`） | **不要**加 `setScale(2, UNNECESSARY)`；4 位明细会抛异常并回滚整批 |
| `RecordService.money` | `max(2, 有效小数位)`（`:336-342`） | 保持 |
| `PeriodService.money` | **硬 2 位**（`:259-263`） | 改成与 `money()` 同一规则；`pay_period.total_*` 是 `DECIMAL(18,4)`，存储没丢，只是列表显示 2 位、编制台 footer 可能 4 位，两个页面会对不上 |
| `GridRow.seniorityYears` | 强制 2 位（`:355-356`） | 保持（工龄按年，2 位合理） |

### 7.4 契约必须改一句

`openapi.yaml:1551` 的 `Money` 描述是"展示保留两位小数，实际精度 DECIMAL(18,4)"，而 `precisionScale` 支持 0–4。**这两句话就是前端写死 2 位的直接依据**。不改契约，修完前端下次还会被改回去。建议改成：

> 存储/计算 4 位；展示位数 = `max(2, 科目 precisionScale)`；合计在计算层按精确值加总，最后按展示位数格式化一次。

### 7.5 验收

- 前端单测：4 位列编辑 → `dirty` 保留 4 位 → `buildRequest` 发 4 位；当前实现在这条上必红。
- 后端 IT：4 位科目走 changeset → 重新 grid 仍是 4 位；`gross/deduction/net` 等于明细精确加总；期间 DTO 显示 4 位。
- 导出：4 位列在文件里保留 4 位（或按 §1.5 的展示规则），合计与明细一致。

### 8.2 看起来简单但会返工的点（按返工代价排序）

| # | 看起来简单 | 实际会怎样 | 正确做法 |
|---|---|---|---|

## 9 需要调整契约的地方

按"不改就会卡住"排序。P0 = 不改做不出来/做出来是错的；P1 = 不改会反复返工或验收扯皮。

### P0

1. **导出范围只有 `/reports/export` + `MONTHLY|ANNUAL`，装不下已锁定的三类导出**。按 07 §4.4 A 扩 `ReportType`：`MONTHLY / ANNUAL / PERIOD_SHEET / PAYSLIP`，`ReportExportParams` 增 `periodId`（前两者必填）、`employeeId`（工资条可选，缺省全期间）。工资条建议单 sheet 重复块，不做一人一 sheet。设计文档里的 `GET /reports/employee/{id}` 仍未进契约，若工资条只做导出可不补。
2. **`POST /users/{id}/reset-password` 宣称"token 全部作废"**。二选一：加 `sys_user.token_version` 并改 token payload（推荐），或删掉这句话。
3. **`/import/validate` 的"不落库"表述**改为"不写 `pay_record`/`pay_record_item`；持久化批次、错误行与原始文件，提交时重放并重校验"。同时把模板格式写进契约：表头含 `itemCode`、列可缺、空值语义、金额 ≤4 位且禁千分位、行数上限与 10MB 的关系。
4. **`User` 的 mobile 承诺与 `sys_user` 表不符**：`Create/Update` 收 `mobile` 且描述"后端加密存储并只回显掩码"，但 `sys_user` 只有 `mobile_mask`，没有 `mobile_cipher/mobile_hash`。要么加列，要么改成"只存掩码、不保存明文"（内网 HR 场景可接受）。
5. **人员/调薪初始化 vs 本期固定项导入的歧义**：`FIXED` 目前只有 `POST_ALLOW` 一列可导。门 2 必须明确 M1.5 只做"本期固定项金额覆盖，不改薪酬档案"；`POST /employees/import` 属另一个管道，不在这期。

### P1

6. **`MonthlyReportRow` 缺 `deptName`**（`AnnualReportRow` 有）。不加，月报页只能显示部门 ID；人员列表已经因为同类问题显示裸 ID（06 审计 P1-5），别再复制一次。
7. **`employeeCount` 没定义**：明确"月度 = 该月该组去重人数；年度 = 该年去重人数，**不是** 12 个月相加"。
8. **导出金额单元格类型**：文本 vs 数值（推荐数值 + `#,##0.00`，工号文本）。若维持文本，把"Excel 中不可求和"写进验收单。
9. **部门**：无删除端点（明确只停用）；`GET /depts` 看不到 `status=0`（加 `includeDisabled`）；`GET /depts`/`GET /companies`/`GET /roles` 的权限点与管理页依赖不匹配（补 `sys:dept:view`/`sys:company:view` 或允许 `sys:*:edit` 访问 GET）。
10. **导入批次属主**：`commit` 与 `GET /errors` 未定义谁能操作；建议 `operator_id` 或同主体 + `sys:user:view`。
11. **报表的 `companyId` 缺省与 `ALL` 用户**：明确不传时按操作者主体过滤；`ALL` + `groupBy=DEPT` 必须传 `companyId`（`AnnualReportRow` 没有 `companyId`，否则两家同名部门会混在一起）。
12. **`ARCHIVED` 不可达**：要么加归档动作，要么在契约里写明"年度只统计 LOCKED，ARCHIVED 为将来保留"。
13. **DDL 增量**：`pay_record` 加 `(company_id, period_ym)` 索引（年度先解析期间 id 也可，但加了更稳）；`sys_user.employee_id` 加唯一索引以支撑"已被其他账号关联 409"；`pay_import_batch` 加 `(period_id, status, file_hash)` 索引；`pay_period` 加 `column_snapshot`（若采纳 §1.3）。

## 10 最难的三个点

1. **导入的两阶段一致性**：没有 staging 表、文件只能重放、提交要重校验、还要同时处理"批次行锁 + 期间行锁 + 租约 + version 递增 + 合计只刷一次 + hash 只拦 COMMITTED + 部分失败三处拦截"。这里任何一个环节漏掉都不报错，只会让 2000 人多发/少发一个月。它是三块里唯一"逻辑错 = 财务事故"的部分。
2. **导出的双响应 + 前端下载通道**：不是 Excel 难，是"响应已提交后无法回头"和"axios 拦截器丢头/Blob 错误"这两个物理约束叠加。必须从设计上拆成"准备/写出"两段，并给前端单独一条下载/上传通道；用共享实例或直接流式写，第一次故障注入就会产出坏文件。
3. **权限闭环**：授权本身不难（无缓存，下一请求生效），难在"重置密码作废 token"必须动 token 载荷，以及四个守卫（自提权、范围放大、跨主体角色、最后一个管理员）。这些不会在正常联调中暴露，却决定这张权限表是不是装饰。

（第 4 名是精度：不难，但它是唯一一个"现在不改，导出和导入都要跟着返工"的横切项，所以排在第 1 步做。）
