# 21-异常恢复测试

> 测试角色：可靠性与异常恢复测试工程师
> 测试日期：2026-11-27
> 被测环境：后端 `http://127.0.0.1:8080/api/v1`（`mvn spring-boot:run`），MySQL 容器 `payroll-mysql`（127.0.0.1:3307），账号 `hr01`/`hr02`/`admin`，密码 `Passw0rd!`
> HTTP 客户端：`curl --noproxy '*'`
> 测试基线：16 个期间、16081 条有效 `pay_record`、1905 名在职人员、0 条 RUNNING 批次
> 测试期间其他评审会话在修改源码（`GenerateService`/`PeriodService`/`ImportService`/`GlobalExceptionHandler`），杀进程实验在 21:55 之前的构建上完成；当前构建已复核 404/405、期间锁定新增校验等行为，未发现会推翻本报告结论的语义变化。

## 结论摘要

**最危险的三个问题**

1. **生成过程被强杀后，期间进入“半成品 + 10 分钟锁死 + 列表数据失真”状态**：已提交 492 条记录（按 500 人一批提交），但期间仍是 `DRAFT`、`employee_count=0`、合计为 0，`pay_run` 永远停在 `RUNNING`；重启后再次生成会被租约挡住 10 分钟，期间列表显示 0 人而编制台能查出 492 人。只能等租约到期（或人工清租约）后手动重试，**不会自动恢复**。
2. **数据库不可用/连接池被慢请求占满时，所有接口统一“挂 30 秒再报 500”**：登录、查询、写入全部在 30.01s 后返回 `{"code":500,"msg":"系统异常，请联系管理员"}`；并发一高会迅速占满 Tomcat 线程，故障从“数据库不可用”扩散为“整站不可用”。
3. **锁定期间的状态可被数据库手工改写绕过且系统不检测**：把 `pay_period.status` 从 `LOCKED` 改成 `EDITING` 后，`locked_by/locked_at` 仍在、记录仍是 `CONFIRMED`，但 changeset 写入返回 200 并成功修改了一条“已确认”的记录，系统没有任何一致性校验或告警。

**需要人工介入才能恢复的情况**

- 生成中途被杀：必须等待 **10 分钟租约自然过期**（或由 DBA 清空 `processing_owner/processing_expire_at`）并**人工重新点击生成**；期间列表的 0 人/0 金额在重试前一直失真；遗留的 `pay_run.status=RUNNING` 行没有启动对账，永远停在 RUNNING（不影响新批次，但会误导排障）。
- 锁定状态被手工篡改：没有自愈机制，必须人工把状态改回 `LOCKED`（并核对被改过的记录）。
- 导入在 `validate` 阶段被杀：批次事务会回滚，不会留下批次行；但按文件 hash 存储的原始文件可能成为孤儿文件（低危，需人工清理磁盘）。

## 2. 中途失败

### 2.1 生成 1800+ 人过程中杀掉后端（SIGKILL，模拟进程崩溃）

**操作**：新建期间 `2029-03`（id=25，DRAFT），`POST /periods/25/generate` 发出后 **1.6s** 对 JVM 执行 `kill -9`；随后重启后端、复测、模拟租约到期后重试。

| 检查点 | 系统表现 | 期望表现 | 严重度 |
|---|---|---|---|
| 期间状态 | `DRAFT`，`employee_count=0`，`total_gross=0`，`compiled_by=NULL` | 应能标识“半成品/失败” | 高 |
| 租约 | `processing_owner=generate-25-...`，`processing_expire_at` = 崩溃后 **约 10 分钟** | 进程死亡后应快速释放或可判别 | 高 |
| 已生成记录 | **492 条**（首批 500 人减去 8 名跳过），492 个不同员工，**每条记录均有 2 条明细，0 条零明细记录** | 批内原子、批间可部分提交（现状符合） | 低（记录级完整） |
| 批次 `pay_run` | 新行 `status=RUNNING`，`emp_total=0`，`finished_at=NULL` | 应标记 FAILED/ABORTED 或启动时对账 | 中 |
| 重启后进度接口 | `GET /runs/34` 仍返回 `RUNNING`，`total=0` | 不应永久 RUNNING | 中 |
| 重启后列表 vs 编制台 | 列表：0 人、0 元；`GET /periods/25/grid`：**492 行** | 两者应一致，或列表标注“部分生成” | 高 |
| 租约未到期时重试生成 | 409 `该期间正在处理中，请稍后再试`（实测剩余约 9.5 分钟） | 可快速重试或明确倒计时 | 高 |
| 租约未到期时锁定 | 409 `期间尚未生成，只有编制中的期间可以锁定`（虽然已有 492 条记录） | 可接受（禁止锁定半成品），但提示不准确 | 中 |
| 租约到期后重试生成 | 200，耗时 5.06s，最终 **1874 条记录、0 重复、0 零明细**，期间变 `EDITING`、合计已刷新、租约释放 | 应自动或一键恢复 | 中（可恢复但需人工） |
| 旧批次 34 | 重试成功后仍永久 `RUNNING` | 启动时应把孤儿 RUNNING 批次改为 FAILED | 中 |

**额外验证（已有数据的期间重算中途被杀）**：对 `2029-02`（1874 条）发起重算并在 1.6s 杀掉，首批尚未提交，`version_no` 分布保持不变，期间合计保持旧值，新增批次同样停在 `RUNNING`。说明“重算崩溃”可能留下**新旧混合**（本批已提交 vs 未提交），且没有“生成代次/批次号”写到记录上，事后无法仅凭记录判断哪些是新算的。

> **数据一致性结论**：崩溃后处于不一致状态——`pay_record` 已有部分数据，但 `pay_period` 仍为 DRAFT/0 人/0 合计，`pay_run` 永久 RUNNING。**不能自愈**：必须等 10 分钟租约过期（或人工清租约）后手动重试；重试成功后数据恢复一致。单条记录本身是完整的（批事务保证），不存在“有记录头无明细”的半条记录。

### 2.2 导入 500 条提交过程中杀掉后端

**操作**：对期间 `2029-02` 准备 500 行变动项文件（P2），`validate` 成功（batch 14，`VALIDATED`），`POST /import/14/commit` 发出后 **0.8s** `kill -9`；重启后重试提交并验证重复提交。

| 检查点 | 系统表现 | 期望表现 | 严重度 |
|---|---|---|---|
| 批次状态 | 仍为 `VALIDATED`（没有卡在中间态） | 可重试 | 低（符合） |
| 已写入明细 | 0 条新增（原有 20 条来自上一批次），事务完整回滚 | 全有或全无 | 低（符合） |
| 期间合计 | 未变化 | 不出现只算一半的合计 | 低（符合） |
| 原始文件 | `data/import/<sha256>.xlsx` 仍存在（9743 字节） | 重试可读 | 低（符合） |
| 重启后重试提交 | 200，500 行全部写入，批次变 `COMMITTED` | 可重试 | 低（符合） |
| 再次提交 | 409 `该批次已提交，不能重复提交` | 409 | 低（符合） |
| 并发双提交 | 一个 200、一个 409（行锁生效），只提交一次 | 仅一次成功 | 低（符合） |

> **数据一致性结论**：导入提交中途崩溃**不会**留下半截数据，可安全重试。遗留风险仅在 `validate` 阶段被杀：批次行随事务回滚，但按 hash 存储的原始文件可能成为孤儿文件（磁盘层面，低危）。

## 3. 数据库异常

### 3.1 MySQL 停止 30 秒以上，期间调用接口

**操作**：`docker update --restart=no` → `docker stop payroll-mysql`（实测停机约 2.5 分钟，覆盖 30 秒要求）→ 期间调用登录、期间列表、人员列表、写接口 → `docker start` → 不重启后端，持续探测恢复。

| 请求 | 系统表现 | 期望表现 | 严重度 |
|---|---|---|---|
| `POST /auth/login` | **30.01s 后** HTTP 500 `系统异常，请联系管理员` | 快速失败（<1s）503 `数据库暂不可用` | 高 |
| `GET /periods` | 30.01s 后 HTTP 500 同上 | 同上 | 高 |
| `GET /employees` | 30.01s 后 HTTP 500 同上 | 同上 | 高 |
| `POST /periods`（写） | 30.01s 后 HTTP 500 同上 | 同上 | 高 |
| 8 秒后再次请求 | 仍然 30.01s → 500 | 同上 | 高 |
| 响应体是否泄露堆栈 | 否，只有统一文案 | 不泄露 | 低（符合） |
| 数据库恢复后（后端未重启） | 首次探测即 200，耗时 0s；后续读写正常 | Hikari 自愈，无需重启 | 低（符合） |

> **结论**：错误提示“可读”但没有区分度（统一 `系统异常`），且 HTTP 状态是 500 而非 503；更严重的是**每个请求固定阻塞 30 秒**（Hikari `connectionTimeout` 默认 30s，且创建连接失败会在超时窗口内重试）。故障期间 Tomcat 线程会持续堆积，数据库单点故障会迅速放大为整站不可用。

### 3.2 连接恢复后的自愈

- 未重启后端，DB 恢复 healthy 后第一次 `GET /periods` 返回 200（0s），后续登录/读写正常。
- Hikari 未出现“坏连接池需要重启”的情况，**自愈成立**。

## 4. 重复操作

| 场景 | 操作 | 系统表现 | 期望表现 | 严重度 |
|---|---|---|---|---|
| 连续两次生成（并发） | 同一期间同时发两个 `POST /generate` | 一个 200（4.44s），一个 409 `该期间正在处理中，请稍后再试`；最终 1874 条、0 重复 | 仅一个执行 | 低（符合） |
| 连续两次生成（顺序） | 第一次成功后再点一次 | 200，幂等重算；记录仍 1874 条、无重复，仅版本号递增 | 幂等 | 低（符合） |
| 连续提交同一导入批次（并发） | 同时发两个 `POST /import/{id}/commit` | 一个 200 `COMMITTED`，一个 409 `该批次已提交`；数据只写一次 | 仅一次生效 | 低（符合） |
| 连续提交同一导入批次（顺序） | 成功后再提交 | 409 | 409 | 低（符合） |
| 连续锁定同一期间（顺序） | 第一次 200；再点一次 | 409 `期间已锁定，无需重复锁定` | 409 | 低（符合） |
| 连续锁定同一期间（并发） | 同时发两个 `POST /lock` | **两个都返回 200**，`pay_audit_log` 写入 **2 条 LOCK**；最终状态一致（同一锁定人/时间） | 一个 200、一个 409 | **中**（审计重复、前端误判成功） |

> 并发重复锁定的根因：`PeriodService.lock()` 先普通 `SELECT` 再 `UPDATE`，没有 `SELECT ... FOR UPDATE`，两个事务都读到了 `EDITING`。新增的“最近批次必须 SUCCESS / 失败人数为 0”校验不能阻止同一瞬间的两个请求。

## 5. 状态不一致

### 5.1 锁定后手工把 `pay_period.status` 改成 `EDITING`

**操作**：期间 `2029-01` 已 LOCKED（`locked_by=2`、1874 条记录 `CONFIRMED`）；直接 SQL 执行 `UPDATE pay_period SET status='EDITING' WHERE id=23`；然后调用 changeset、重新锁定。

| 检查点 | 系统表现 | 期望表现 | 严重度 |
|---|---|---|---|
| changeset 写入 | **200 成功**，写入了 `P2=77.77` 并重算了记录合计，而被修改的记录 `record_status` 仍是 `CONFIRMED` | 检测到 `locked_by/locked_at` 仍存在时拒绝写入或告警 | **高** |
| 记录状态 | 被修改后仍为 `CONFIRMED`，期间状态为 `EDITING`，`locked_by/locked_at` 原样保留 | 状态机应保持一致 | 高 |
| 重新锁定 | 200 成功，`locked_at` 被覆盖 | 可接受，但应识别数据已被改动 | 中 |
| 自愈/告警 | 无 | 应有启动/写入前一致性检查 | 高 |

> 该场景需要数据库写权限，但它暴露的是**系统对“锁定即确认”这一核心不变量没有任何运行时校验**：写路径只检查 `status` 字段，不核对 `locked_by/locked_at/record_status` 是否自洽。一旦有人误操作或发生数据修复脚本，已确认工资可被静默改写。

## 6. 超时与慢查询 / 连接池耗尽

**操作**：在 MySQL 侧开启一个事务，对 `pay_period.id=24` 执行 `SELECT ... FOR UPDATE` 并 `SLEEP(35)` 持有行锁；同时向该期间发 **20 个并发 changeset 写请求**（每个都会先 `SELECT ... FOR UPDATE` 期间行），占满 Hikari `maximum-pool-size=20`；随后发第 21 个普通读请求。

| 请求 | 系统表现 | 期望表现 | 严重度 |
|---|---|---|---|
| 20 个写请求 | 全部在 **34.0s** 后返回 409 `数据已被他人修改，请刷新`（行锁释放后才执行到版本校验） | 可接受（有超时上限） | 中 |
| 第 21 个读请求（池已满） | **30.016s** 后 HTTP 500 `系统异常，请联系管理员` | 快速失败 503/429，或隔离只读接口 | 高（与 DB 故障叠加） |
| 连接释放后的请求 | 200，耗时 1.96s；再下一次 0.008s | 自动恢复 | 低（符合） |
| 连接池/进程 | 无需重启后端，池自动恢复 | 自愈 | 低（符合） |

> **结论**：系统不会整体永久卡死，但“池被占满”时新请求固定等 30 秒再 500；若并发持续，Tomcat 线程会被同步请求拖住，最终影响所有接口。缺少 bulkhead/熔断/快速失败。

## 7. 其他错误出口

| 场景 | 系统表现 | 期望表现 | 严重度 |
|---|---|---|---|
| 不存在的路径 `GET /api/v1/health` | 404 `{"code":404,"msg":"接口不存在"}`（测试期间由其他修复会话补上） | 404 | 低（符合，当前构建） |
| 错误的 HTTP 方法 `GET /api/v1/auth/login` | **500** `系统异常，请联系管理员` | 405 Method Not Allowed | 低 |
| 错误的 HTTP 方法 `DELETE /api/v1/periods` | **500** 同上 | 405 | 低 |
| 非法 JSON | 400 `请求参数格式不正确` | 400 | 低（符合） |

> `HttpRequestMethodNotSupportedException` 未进入 `GlobalExceptionHandler` 的专门分支，落到兜底 500；不影响数据，但监控会把客户端错误统计成服务端故障。

## 8. 会导致数据不一致且不能自愈的异常（重点）

| 异常 | 不一致表现 | 能否自愈 | 恢复方式 |
|---|---|---|---|
| 生成中途进程崩溃/被杀 | `pay_record` 部分写入；`pay_period` 仍 DRAFT、0 人、0 合计；`pay_run` 永久 RUNNING；租约占 10 分钟 | **否** | 等租约过期（或人工清 `processing_owner/processing_expire_at`）+ 人工重新生成；旧 RUNNING 批次需人工/脚本清理 |
| 锁定状态被手工改写 | `status=EDITING` 但 `locked_by/locked_at` 仍在、记录 `CONFIRMED`；已确认数据可被继续修改 | **否** | 人工核对并恢复状态；无校验/告警 |
| 手工插入孤儿记录 | 编制台可见、人员详情 404；期间汇总不刷新 | **否** | 人工定位并修复 |
| 导入提交中途崩溃 | 无（事务回滚，批次仍 VALIDATED） | 是（重试） | 重新提交 |
| 数据库短时不可用 | 无数据不一致 | 是（Hikari 自动重连） | 无需操作 |
| 连接池被占满 | 无数据不一致 | 是（连接释放后恢复） | 无需操作 |
| 重复生成 / 重复提交导入 / 顺序重复锁定 | 无 | 是（409） | 无需操作 |
| 并发重复锁定 | 数据一致，但审计重复、双 200 | 是（状态一致） | 无需操作（建议修复） |

## 10. 建议（按优先级）

1. **生成批次启动对账**：应用启动时把超过 TTL 的 `pay_run.status=RUNNING` 改为 `FAILED/ABORTED`，并把对应期间标记为“部分生成/需重跑”；至少让列表页显示真实的已写入人数和合计。
2. **缩短故障感知**：为 Hikari 设置更短的 `connectionTimeout`（如 3–5s）、`validationTimeout`，数据库不可用时返回 **503** + 明确文案，而不是 30s 后 500；对数据库相关接口加熔断/快速失败。
3. **锁定路径加行锁**：`PeriodService.lock()` 改为 `SELECT ... FOR UPDATE` 后再判状态，消除并发双 200 与重复审计。
4. **状态一致性校验**：写入前除 `status` 外，校验 `locked_by/locked_at` 与 `record_status` 自洽；发现矛盾时拒绝写入并告警。
5. **跨字段校验**：离职日期不得早于入职日期；金额增加业务上限；对 2 位精度科目的 `0.001` 类输入给出“四舍五入为 0”的提示。
6. **错误码补齐**：为 `HttpRequestMethodNotSupportedException` 返回 405。
