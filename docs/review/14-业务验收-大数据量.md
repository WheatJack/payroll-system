# 14 · 业务验收 — 大数据量下的性能与交互

- 环境：后端 `http://127.0.0.1:8080/api/v1`，前端 `http://localhost:5175`，2026-11-27
- 账号：`hr01`（薪酬专员，ALL）/ `hr02`（薪酬复核，ALL，可锁定/解锁）
- 数据：**2010 名员工**；期间 `13` = `2025-01`（编制中）**1821 条核算记录**，16 个工资项列；`2025` 年 6 个锁定期间（02–07），年度报表 1852 人

## 截图结论（布局是否正常）

- **编制台 1440×900（1821 行，未筛选）**：布局正常——工具栏、筛选区、提示条、表头、表体、表尾合计、底部方向汇总栏自上而下排列，无塌陷/重叠/错位；页面高度恰好占满视口，无整页滚动条；表尾「合计」行固定在表格底部且可见；底部「应发合计 35,320,173.57 / 扣款 0.00 / 实发 35,320,173.57」与表尾逐列合计一致。
- **筛选后（综合部 3 人）**：布局正常；底部汇总随筛选变为 30,000.00；**唯一布局瑕疵**：表尾首列的「合计（筛选后）」在 100px 宽的工号列内折成两行（「合计（筛选」/「后）」），行高被撑高。
- **横向滚动（scrollLeft=1200）**：表头/表体/表尾横向同步，左侧固定「工号/姓名」列保持固定且与主表行高对齐，无错位。
- **年度报表 1852 行**：布局正常，无重叠；表格全量渲染，滚动可用。
- 说明：Claude_Browser 面板在测试期间被另一验收会话切走（切至 `/reports/monthly`），最终截图取自独立 Chromium 1440×900；此前 Claude_Browser 截图结论一致。

## 不可用 / 高风险汇总

**❌ 不可用（1 条）**
1. **生成过程中锁定期间 → 半成品数据被锁定**：锁定接口不检查生成租约，锁定在 0.59s 内成功；生成在下一批次被 409 中断，已提交的 497 条留在库中，期间状态为 LOCKED，表头人数/合计仍是旧值（5 人 / 43,606.16），与编制台实际 497 行不一致。

**⚠️ 严重体验问题（4 条）**
1. **进入 1821 行编制台假死**：首屏 10.2s 才出现数据，23s 后才完全可交互；每次「清除筛选」等价于重开一次（14–20s）。
2. **单格编辑链条过长**：静置状态下单击 1.0s、双击 2.0s、回车 1.9s、保存 2.9s（墙钟 11.7s）；三个操作叠加即 15s 以上。
3. **滚动不流畅**：可见窗口竖直 ~52ms/帧、水平 ~209ms/帧；根因是未启用虚拟滚动（1821 行 × 16 列 + 固定列克隆 = 33.6 万 DOM 节点）。
4. **2 分钟内存 168–606MB**：存在明显堆尖峰（未确认泄漏，但 336k DOM 的基线本身很重）。

**⚠️ 功能缺陷（3 条）**
1. **职级筛选不切换合计标签**：`frontend/src/views/period/PayrollGridView.vue` 的 `filterActive` 只判断 `deptId/employeeType/keyword`，漏了 `jobLevel`，导致只筛职级时表尾仍显示「合计」而不是「合计（筛选后）」（数值本身已按筛选变化）。
2. **员工分页 `size=500` 静默截断为 200**：接口返回 200 条、total=2010，无任何提示；前端若按请求 size 计算页数会少页。
3. **非法/畸形 changeset 静默成功**：用 `{recordId, version, itemCode, newValue}`（错误结构）调 `PATCH /periods/13/records` 返回 `200 {"updated":1}` 并把行 version +1，但未写入任何明细——客户端会误以为保存成功（本次并发测试中实际遇到）。

**说明（测试副作用）**
- 期间 13（2025-01）的测试改动已全部还原，`total_gross` = 35,320,173.57，员工数 1821。
- 期间 10（2027-08）被用于「生成 + 锁定」并发测试：解锁后重新生成因跨主体重复返回 409，最终为 **EDITING / 1482 条**（原为 5 条），属于本测试造成的半成品状态；如需复原请重新灌数。
