### P0-1 密钥默认值兜底 + 默认串本身不是合法 AES-256 密钥

**问题**
- `application.yml:38-41` 提供 `${PAYROLL_ID_SALT:dev-only-salt-change-me}` 与 `${PAYROLL_AES_KEY:dev-only-32-byte-key-change-me!}`，注释写"生产环境必须通过环境变量注入"——注释不是控制。
- 该默认串按 UTF-8 计为 **31 字节**（`dev` 3 + `-only` 5 + `-32` 3 + `-byte` 5 + `-key` 4 + `-change` 7 + `-me!` 4 = 31）。直接作为 `SecretKeySpec(key.getBytes(), "AES")` 会抛 `InvalidKeyException`。开发者为了跑通只能自行补位或做散列，产生的 KDF 不受控、不可审计。
- 密钥与数据库口令、`docker-compose.yml`、README 同处一个交付仓。

**为什么是问题**
私有化交付是"jar + application.yml + compose 一起进客户内网"。默认密钥等于公开密钥：任何拿到数据库备份、数据卷或直连权限的人（包括客户自己的 IT、运维外包、离职人员）可以解密全部证件号。而"默认值能跑"会让部署方永远想不起来覆盖它——这是默认密钥最典型的失效方式。同时，把 31 字节字符串补成 32 字节的临时写法，往往变成用同一个字符串做 SHA-256 当密钥，等于 AES 密钥强度退化为口令强度。

**位置**
`application.yml:38-41`；`docs/详细设计.md` §4.8（L292 "密钥从环境变量/密钥文件注入，不进代码库"）；`docker-compose.yml:6-10`；`README.md:16-21`

**修复**
1. **删除所有默认值**：写成 `${PAYROLL_AES_KEY}`（无冒号），缺失即启动失败。
2. 用 `@ConfigurationProperties` + `@PostConstruct` 做启动自检：Base64 解码后必须 **恰好 32 字节**；启动时对固定串做一次 encrypt→decrypt 自测；`prod` profile 下若密钥缺失或匹配 `dev-only` 前缀，打印明确错误并 `System.exit(1)`。
3. 密钥生成与保管：
   - 生成：`openssl rand -base64 32`，由财务负责人/系统管理员在部署现场生成，不经过开发。
   - 存放：Docker secret 或只读 bind mount（`/run/secrets/payroll_aes_key`，属主为应用专用 OS 账号，权限 `0400`）。**不要放环境变量**——环境变量在 `docker inspect`、`/proc/<pid>/environ`、JVM heap dump 中均可见。
4. **三把密钥分离且独立生命周期**：AES 数据密钥、HMAC 盲索引密钥（见 P0-3）、数据库口令。三者不得互相派生。
5. 增加版本列 `enc_key_version`（`emp_employee`）并编写轮换手册：新版本双读、批量重加密、验证后再下线旧密钥。没有版本列就无法轮换，只能停机全量重刷。
6. 备份与密钥**分开保管**（见 P1-4）：密钥不进入数据库备份包，否则加密在恢复场景下自废。

### P0-3 证件号"加盐哈希"方案在两个方向上都不可行，必须改为 HMAC 盲索引

**问题**
`docs/详细设计.md` §4.8（L288）与 `schema-mysql.sql:119,142` 定义：`id_no_hash = SHA-256(salt + 证件号)`，并在该列上建唯一索引 `uk_id_hash`。这是一个**两难且无解**的方案：

| 实现方式 | 跨行查重/唯一性 | 抗彩虹表 | 结论 |
|---|---|---|---|
| `SHA-256(id)` | 可以 | 否 | 否决 |
| `SHA-256(全局固定盐 + id)`（当前设计） | 可以 | 仅当"盐"保密；盐随 `application.yml`/jar 下发即失效 | 否决：这是胡椒（pepper），不是盐，且无轮换、无版本、无审计 |
| `SHA-256(每行随机盐 + id)` | **不可以**：同一证件号每行哈希不同，唯一索引失效 | 是 | 否决 |
| `HMAC-SHA256(独立索引密钥, 归一化(id_type + id))` | 可以 | 是（密钥保密前提下），可轮换 | **采用** |

**为什么是问题**
1. **概念混淆导致实现必然出错**："盐"（随机、每记录不同、防离线预计算）与"确定性查重"在数学上互斥。只要需要唯一索引，就必然要一个跨行稳定的值；这个值一旦稳定，就必然可离线验证。**唯一正确的出路不是加盐，而是把确定性建立在独立保管的密钥上（HMAC）**，把"密钥不可得"当作安全边界。
2. **身份证号是低熵标识**：地区码 6 位 + 生日 8 位若已知（对目标个人几乎总是已知），顺序码仅 3 位、校验位由前 17 位确定——**约 1000 次计算即可反推一个特定人的证件号**。全空间 10^18 的直觉在这里完全不成立。因此哈希/盐泄漏的后果是"定向反推"，不是"概率撞库"。
3. **当前 DDL 还有两个功能性缺陷**：
   - `id_no_hash NOT NULL` + `id_no_cipher NOT NULL`：`employee_type` 包含 `OUTSOURCE`/`LABOR`，这类人员可能没有身份证。业务上必须填，实现上只能填占位串（如 `N/A`），而占位串的哈希是常量——**第二个无证件人员就会撞唯一键**。
   - `uk_id_hash` 不含 `deleted`：与 `uk_emp_no` 同样的问题，误建后逻辑删除的记录永久占用该证件号（见 P2-2）。
4. `GlobalExceptionHandler.java:45-47` 把约束名翻译成"该证件号码已存在人员记录"，使这一列成为可被利用的**存在性预言机**（见 P1-8）。

**位置**
`docs/详细设计.md` §4.8 L288；`schema-mysql.sql:118-119,142`；`GlobalExceptionHandler.java:45-47`

**修复（可直接照做）**

1. **算法定性**：明确这是"键控哈希 / 盲索引（blind index）"，不是加盐哈希。
   ```
   id_no_hash = HMAC-SHA256(K_index, normalize(id_type, raw_id_no))
   ```
   `K_index` 为独立的 32 字节随机密钥，**不复用 AES 数据密钥**，独立轮换、独立保管。
2. **强制归一化**（不做这一步，同一个人必然出现两条记录）：
   ```
   s = raw.trim().toUpperCase()            // 全角转半角、去空白
   if id_type == 'ID_CARD':
       15 位 → 转 18 位（或明确拒绝 15 位并给出提示，二选一，不能两种都放进来）
       18 位末位 X 统一大写
   输入 = id_type + ":" + s                // 证件类型必须参与，避免不同类型同号被判重
   ```
3. **空值语义**：`id_no_cipher` 与 `id_no_hash` 均改为 **NULL 可空**（MySQL 唯一索引允许多个 NULL），有证件才建盲索引；**禁止空串参与哈希**。外包/劳务人员无证件时走"工号唯一 + 人工核验"。
4. **轮换能力**：增加 `id_no_hash_ver TINYINT NOT NULL DEFAULT 1`；轮换时新增 `id_no_hash_v2` 列双写，后台批量重算后切换唯一索引、删除旧列。没有版本列，换密钥 = 唯一性永久失效。
5. **列类型**：`id_no_hash BINARY(32)`（或 `CHAR(64) CHARACTER SET ascii`），不要用 `utf8mb4 CHAR(64)`（索引项 256 字节）。
6. **密钥防护**：`K_index` 与 AES 密钥分离；数据库备份单独泄漏不足以反推；**任何 API、日志、导出中不得出现哈希值**（它是 membership oracle）；禁止在错误信息或前端响应中比较哈希。
7. **若业务拒绝引入第二把密钥**：唯一可行替代是**放弃证件号全局唯一**，改为工号全局唯一（C8 已具备）+ 新建人员时人工核验。这与 C1（多主体同一人只有一条记录）冲突，因此不推荐；但必须显式决策，不能两边都要。
8. 手机号哈希同理（当前设计"哈希列，不唯一"）：如果不需要按手机号精确检索，就**不要存哈希**；需要就用同一 `K_index` + 同一归一化规则。

### P0-4 AES-256 只写了算法名，缺少模式/IV/AAD；明文不得落在实体上

**问题**
§4.8 与 `schema-mysql.sql:118,121,125` 只说明" AES-256 密文 VARBINARY"，**未指定分组模式、IV 策略、完整性校验**。

**为什么是问题**
- 默认实现极易落到 **ECB**：同一证件号在库中密文相同，等于恢复了可比较特征，还暴露"两个员工同号"这类信息。这正是加密要消除的东西。
- **CBC 无认证**：密文可被翻转/拼接，解密端拿到被篡改的明文而不自知。
- 更隐蔽的风险在代码结构：如果把 `idNo` 作为 `String` 明文属性挂在 MyBatis 实体上、由某个切面统一解密，那么任意一次 `Result.ok(entity)`、任意一次 Lombok `toString()` 进日志、任意一次 MyBatis 参数日志，都会把明文漏出去。薪酬系统的解密泄漏通常不是密码学被攻破，而是**这条泄漏路径**。

**位置**
`docs/详细设计.md` §4.8 L284-292；`schema-mysql.sql:118,121,125`；`application.yml:38-41`

**修复**
1. **算法固定为 AES-256-GCM**：
   ```
   iv  = SecureRandom(12 bytes)            // 每次加密全新，绝不复用
   ct  = AES-GCM(K_data, iv, plaintext, aad)
   存  = iv || ct || tag（VARBINARY）
   aad = "emp_employee.id_no:" + id_type   // 绑定表/列/类型，防止跨列跨行搬运密文
   ```
   禁止 ECB / CBC / 固定 IV / 确定性 AES。
2. **明文不出现在持久化对象上**：实体只有 `byte[] idNoCipher`，没有 `String idNo`。需要明文的地方只有一个入口：
   ```
   SensitiveFieldService.decrypt(employeeId, Field.ID_NO, Purpose.VIEW)
   ```
   该入口内部强制：权限点 `payroll:sensitive:view` → 写审计 → 返回一次性值。审计/日志/DTO 都拿不到明文。
3. **DTO 分层**：列表 DTO 永远不含密文也不含明文；详情 DTO 的敏感字段仅在具备权限时填充。二次确认必须是**服务端重新认证**（重输密码/TOTP），不是前端 `confirm()`——否则 devtools 一开就能看到完整值。
4. **单元测试（作为验收条件）**：
   - 同一明文两次加密密文不同；
   - 篡改任意 1 bit 解密必须失败；
   - 把 A 行密文搬到 B 行、把手机号密文放进证件号列，解密必须失败（AAD 生效）。
5. **预留字段同规则**：银行卡（"金融账户"，PIPL 第 28 条明确列举的敏感个人信息）在 phase 3 接入时不得新增明文列，且代发文件生成纳入 P1-3 的导出管控。
6. 行级增加 `enc_key_version TINYINT`（与 P0-1 的轮换配套）。

### P0-5 `data_scope` 三条确定性越权路径：字段可篡改、路径无校验、`ALL` 发放失控

**问题**
1. **mass-assignment**：`sys_dept.ancestors`（`schema:39`）是普通可写列。若部门新增/修改接口直接绑定请求体（MyBatis-Plus 最常见的写法 `@RequestBody Dept d` + `updateById`），任何有部门编辑权的人可把自己部门的 `ancestors` 改成 `,1,`，随后以 `DEPT_SUB` 范围看到**全集团**工资。
2. **路径无完整性**：`ancestors` 由应用维护。部门移动时若未在事务内重算整棵子树，范围会**静默变大**（仍指向旧父节点）——不会报错、不会留痕。此外 `LIKE ',1,%'` 前缀匹配**不包含部门自身**，必须额外 `OR dept_id = X`，漏写即"看不到本部门"或"多看别部门"，两种都出现过。
3. **`ALL` 发放与设计矛盾**：§4.7 与 C9 明确"`ALL` 仅集团 HR / 审计可拥有"，但种子数据 `schema:409-413` 把 `ALL` 给了 `PAYROLL_CLERK`（薪酬专员）和 `PAYROLL_REVIEWER`（薪酬复核）。多主体部署时，任一分公司专员即是全集团范围。
4. **`SELF` 的空关联**：`sys_user.employee_id` 可为 NULL，若 `SELF` 实现为"按 employee_id 过滤"而 NULL 时未拦截，常见写法会退化为"不过滤"（default-allow）。

**为什么是问题**
数据范围是本系统唯一的横向隔离线。它失效时不会报错、不会触发异常、不会进入常规告警，唯一的痕迹是查看审计——而查看审计本身可能没有范围过滤（见 P0-6）。这是一个典型的"静默越权"，可能持续数月无人发现。

**位置**
`docs/详细设计.md` §4.7(2) L269-276、§4.9 L240；`schema-mysql.sql:33-51(39,50),74-89(79),408-413`

**修复**
1. **`ancestors` 永不为输入**：从所有 DTO 移除该字段；实体上加 `@JsonIgnore` 或 `@TableField(updateStrategy = FieldStrategy.NEVER)`；只由服务端在部门移动事务内重算子树。
2. **范围计算不依赖前缀字符串**：MySQL 8 支持递归 CTE，2000 人规模的开销可以忽略：
   ```sql
   WITH RECURSIVE scope AS (
     SELECT id FROM sys_dept WHERE id = #{userDeptId} AND deleted = 0
     UNION ALL
     SELECT d.id FROM sys_dept d JOIN scope s ON d.parent_id = s.id WHERE d.deleted = 0
   ) SELECT ... WHERE dept_id IN (SELECT id FROM scope)
   ```
   登录时解析为 dept id 集合缓存亦可。`ancestors` 仅保留用于树形展示。若坚持前缀方案，必须封装**唯一入口**并加 daily 一致性校验（校验每个部门满足 `ancestors == parent.ancestors + ',' + parent.id`）。
3. **范围条件必须进 SQL WHERE**：用 MyBatis 拦截器统一注入，禁止"查出来再内存过滤"（分页会漏、count 会错、join 会绕）。所有手写报表 SQL 必须纳入同一拦截器或进入白名单审查，并在 CI 中检查是否含范围片段。
4. **范围按主体生效**：内部表示为 `Map<companyId, level>`，不是单个枚举"取最宽"。否则"在 A 公司有 COMPANY、在 B 公司只有 DEPT"会被合并成"在 B 公司也是 COMPANY"。
5. **`SELF` 且 `employee_id IS NULL` → 返回 0 行**，并写权限告警日志。
6. **`ALL` 的发放**：新增权限点 `sys:role:grant:all`；角色 CRUD 校验"新角色的 `data_scope` ≤ 操作者自身范围"；种子数据把 `PAYROLL_CLERK`/`PAYROLL_REVIEWER` 改为 `COMPANY`。
7. **测试用例（必须有）**：跨主体、跨部门、深层部门、`SELF` 空关联、部门移动后、部门逻辑删除后、`OR company_id = 0`（集团通用科目）不得削弱员工表范围。

### P0-6 权限模型缺少系统管理类权限点，三权分立的根被绕开

**问题**
§4.7(1) 只定义了 7 个 `payroll:*` 权限点，但 §5.6 暴露了 `/users` `/roles` `/audit-logs`。**没有任何权限点管辖用户、角色、授权、审计查询、配置、归档**。谁能创建用户、谁能给自己加角色、谁能修改 `data_scope`、谁能读审计，全部未定义（大概率实现成"登录即可访问"）。

**为什么是问题**
内控的基本前提是：**能修改权限的人必须不在被权限约束的业务链里**。如果"锁定人 ≠ 编制人"可以被一个能自助改角色的人绕过（给自己加 `payroll:record:edit`，编完后自己锁），这条控制就等于不存在。同理，如果 `/audit-logs` 不设权限与范围过滤，任何登录用户都能读到全集团的工资变更值（`old_value/new_value`）——审计表本身变成最大的泄漏面。

**位置**
`docs/详细设计.md` §4.7 L258-267、§5.6 L357-364；`schema-mysql.sql:99-105`

**修复**
1. 补齐权限点：

| 权限点 | 说明 |
|---|---|
| `sys:user:manage` | 用户创建/停用/重置口令 |
| `sys:role:manage` | 角色 CRUD（含 `data_scope` 调整） |
| `sys:role:assign` | 给用户分配角色 |
| `sys:role:grant:all` | 授予 `ALL` 范围（单独拆出，见 P0-5） |
| `sys:audit:view` | 审计查询 |
| `sys:config:manage` | 密钥/参数配置变更 |
| `payroll:period:archive` | 归档（终态操作） |
| `payroll:record:view:self` | 本人工资查询（第 2 期） |

2. **系统管理岗与业务岗互斥**：持有 `sys:user:manage` / `sys:role:assign` 的角色**不得包含任何** `payroll:record:view`、`payroll:sensitive:view`、`payroll:record:edit`、`payroll:period:lock`、`payroll:export`。系统管理员能建账号，但看不到工资。
3. `/audit-logs` 必须同时校验 `sys:audit:view` + 数据范围 + 二次确认；审计查询本身再写一条审计。
4. 用户/角色/授权/范围变更全部写审计（见 P1-1），并纳入月度/季度复核报告。
5. 启动自检：计算"能读工资的用户集合"与"能改角色/账号的用户集合"，交集非空即告警（配置错误）。

### P0-7 "编制人 ≠ 锁定人"按身份判定会被正常业务流程绕过，改为角色互斥 + 编辑痕迹

**问题**
§1.1 C4 与 §4.6 L230、§4.7(3) 只写"编制人 ≠ 锁定人"。若"编制人"取 `pay_period.created_by`，则主管只要在 `EDITING` 期间编辑任意一条记录再锁定，就绕过了——他既是编辑者也是锁定者。若改为"最后编辑人"判定，在只有两人的场景下又会死锁（主管改完没人能锁）。

**为什么是问题**
C4 把审批移到系统外之后，**系统内只剩这一条内控**。它失效意味着一个人的操作闭环可以完成从造表到锁定的全过程。工资是最容易发生单人舞弊的会计科目（虚增人员、虚列金额），而这条控制是唯一的系统性防线。

**位置**
`docs/详细设计.md` §1.1 C4 L28、§4.6 L230、§4.7(3) L278-280；`schema-mysql.sql:218-221`

**修复（两人场景下可成立的设计）**
1. **角色互斥，而非身份互斥**：
   - 持有 `payroll:period:lock` / `payroll:period:unlock` 的角色**不得包含** `payroll:record:edit`、`payroll:import:submit`；
   - 持有编辑/导入权限的角色**不得包含** lock/unlock。
   - 两人时：A = 编制 + 导入；B = 锁定 + 解锁。B 发现错误 → 解锁 → 退回 A 修改 → B 重锁。不存在死锁，且**每一次更正天然经过两个人**。
2. **分配时校验**：任何角色变更后，对每个主体计算 `users(edit) ∩ users(lock)`，非空则拒绝并提示冲突账号。这是可实现的、强于运行时判断的控制。
3. **运行时兜底**：`pay_period.last_edit_by`（任何写操作更新）必须 ≠ 本次 `locked_by`；锁定时把 `locked_by`、`last_edit_by`、编辑人集合写入锁定快照（见 P0-9）。
4. **一人一号**：`sys_user.employee_id` 在有效用户中唯一（应用层校验或带条件的唯一索引），禁止共享账号；否则"两个人"可以退化成"一个人两个账号"。
5. **单人主体的处理必须 fail-closed**：若某主体只有 1 名员工，系统拒绝形成"编辑 + 锁定同一人"的组合，由集团 HR 代持该主体的锁定权（写入运维手册）。不能为了"方便"放行单人闭环。
6. 锁定动作记录 `locked_at`、`ip`、`user_agent`，与快照绑定。

### P0-8 导入原始文件与错误报告把 PII 明文落回磁盘，绕过全部加密

**问题**
- §1 L19 与 README 明确原始 Excel 存本地目录 `./data/import`，`schema:319` 存路径；而 §5.1 有 `POST /employees/import`——员工导入模板**必然包含证件号、手机号**。
- `pay_import_error.raw_value`（`schema:338`）保存原始值，错误报告可下载（§5.4），无权限点、无审计。
- `application.yml:34-37` 的本地路径为相对路径，容器内文件权限未定义。

**为什么是问题**
字段级加密的全部意义是"库/备份泄漏 ≠ 明文泄漏"。而一个 group-writable 的目录里躺着全量身份证 Excel，等于把加密作废——攻击者不需要碰数据库，也不需要密钥。同理，错误报告会被下载、转发、存在财务人员桌面，是最容易扩散的载体。

**位置**
`docs/详细设计.md` §1 L19、§4.5 L192-209、§5.1 L308、§5.4 L345；`schema-mysql.sql:313-343(319,338)`；`application.yml:34-37`

**修复**
1. **落地即加密**：在 `storage` 抽象层强制加密（信封加密：随机 DEK + 主密钥包裹），文件名随机化，目录 `0700` 归应用专用账号。后续换 MinIO 时继承同一策略。
2. **员工导入的最小留存**：提交成功后不再保留完整原文中的 PII 列。二选一：
   - 保留"重放所需"的最小列（工号 + 业务列），PII 列掩码后保存；
   - 整文件加密保存，`pay_import_batch` 增加 `purge_at`，到期自动清理。
3. **`pay_import_error.raw_value`**：对 PII 列只存掩码（`****1234`），不存原值；错误码与行号足以定位。
4. **错误报告下载**纳入 `payroll:export` 同级控制 + 写审计 + 加水印（见 P1-3）。
5. **临时文件**：EasyExcel 可能写 `/tmp`，用 tmpfs 挂载并在处理后立即删除；禁止在 `/tmp` 留原始上传件。
6. 备份/快照策略必须覆盖 `data/` 目录（加密 + 权限），不能只备份数据库。

### P0-9 锁定版本没有不可变快照，"解锁→改→重锁"会销毁已发薪版本

**问题**
- `pay_record` 定义了 `version_no` / `superseded_by`（`schema:271-272`），但 C3 的更正流程是**原地 UPDATE**，这两个字段没有使用路径。
- `pay_period.unlock_reason` 是单列（`schema:220`），**第二次解锁会覆盖第一次**。
- §6 L376 只承诺"不提供物理删除"，但没有"每个锁定版本必须可还原"。

**为什么是问题**
《会计档案管理办法》（财政部、国家档案局令第 79 号）将会计凭证、会计账簿的保管期限定为 30 年，并要求真实、完整、可用、安全。工资表一旦发放，**"当时锁定并据此发放的那个版本"就是会计凭证附件**。被原地改掉后，能证明当时状态的只剩审计日志——而审计日志可能不完整（P1-1），且不包含完整计算上下文。审计、税务检查、劳动仲裁都要求出示"原版"，而不是"改后的版本 + 一份变更记录"。

**位置**
`docs/详细设计.md` §4.6 L211-230、§6 L376、§7 L387；`schema-mysql.sql:209-228(220-221),249-288(271-272)`

**修复**
1. **每次锁定生成不可变快照**：
   ```sql
   CREATE TABLE pay_period_snapshot (
     id              BIGINT NOT NULL AUTO_INCREMENT,
     period_id       BIGINT NOT NULL,
     lock_version    INT NOT NULL,
     locked_by       BIGINT NOT NULL,
     locked_at       DATETIME NOT NULL,
     editor_ids      JSON NOT NULL,          -- 本期所有编辑过的人
     record_count    INT NOT NULL,
     total_gross     DECIMAL(18,4) NOT NULL,
     payload         LONGBLOB NOT NULL,       -- 确定性序列化(records+items) → gzip → AES-GCM
     manifest_hash   CHAR(64) NOT NULL,       -- SHA-256(规范化明文 payload)
     prev_snapshot_id BIGINT NULL,
     PRIMARY KEY (id),
     UNIQUE KEY uk_period_ver (period_id, lock_version)
   )
   ```
   快照表**只允许 INSERT**，应用账号无 UPDATE/DELETE；`payload` 用 P0-4 的同一 AES-GCM 方案加密。
2. **重锁生成新版本**（`lock_version + 1`），历史版本全部保留。
3. **解锁→重锁自动生成差异报告**：对比上一锁定版本，逐条列出新增/删除/金额变化 + 合计差额；导出/打印供财务签认，作为线下审批的替代证据，随快照归档。这比"填个原因"强一个数量级。
4. **解锁历史独立成表**：
   ```sql
   pay_period_unlock_log(period_id, unlock_no, operator_id, reason_code,
                         reason_text, approval_ref, unlocked_at, relock_deadline,
                         relocked_at, relocked_by)
   ```
   `pay_period.unlock_reason` 字段废弃。
5. **提供只读的版本对比与"还原为某版本"**（还原 = 生成新版本，不覆盖历史）。

## 2 P1（MVP 发布前必须解决）

### P1-1 审计日志"只增不改"没有任何强制；`old_value/new_value` 明文存敏感值

**问题**
- `schema:371-389` 无触发器、无授权限制、无链式校验。应用使用同一个 `payroll` 账号（compose 中与 root 同级）可对审计表执行 UPDATE/DELETE。
- `old_value/new_value TEXT`（`schema:378-379`）注释写"敏感值需加密后写入"，但类型是 `TEXT`、无 `data_class`、无强制机制——实现时几乎一定会把整个实体或整个字段值写进去，包含金额甚至证件号明文。

**为什么是问题**
内控上审计是"事后唯一证据"，能修改的审计等于没有审计。而且审计表通常会被授予更宽的角色（审计员、集团 HR），一旦里面是明文金额 + PII，它就变成第二个泄漏库，摧毁 §6"日志禁止明文"的初衷。

**位置**
`docs/详细设计.md` §6 L375、§5.6 L364；`schema-mysql.sql:371-389(378-379)`

**修复**
1. **数据库授权**：应用账号对 `pay_audit_log` 仅 `SELECT, INSERT`；业务表不给 `DELETE`（逻辑删除已满足）。以独立 DDL 脚本落地，并在部署检查中验证。
2. **触发器**：`BEFORE UPDATE` / `BEFORE DELETE` → `SIGNAL SQLSTATE '45000'`。防应用 bug 与普通 DBA；root 可绕过，故配合第 3 条。
3. **哈希链 + 库外锚点**：
   - 增加 `seq BIGINT`、`prev_hash CHAR(64)`、`row_hash CHAR(64)`；`row_hash = SHA-256(seq || 规范化字段 || prev_hash)`。
   - 单行锚点表 `pay_audit_anchor(id=1, seq, last_hash)`，同一事务内 `SELECT ... FOR UPDATE` 串行化（2000 人规模开销可忽略）。
   - **每日把 `(日期, seq, last_hash, 行数)` 导出到数据库之外**（财务负责人邮件、独立日志主机、WORM 目录）。DBA 单方面改库会导致链断裂且与外部锚点不符——这是"可检测"而非"不可篡改"，但在私有化场景中是可达成的最高水位。
4. **值分级**：增加 `data_class TINYINT`（0 = 明文 / 1 = 金额 / 2 = PII）。
   - 金额 → AES-GCM 存 `VARBINARY`，查看时按权限解密，并"审计之审计"；
   - **PII 不存值**：只存 `field_name` + 掩码（`****1234`）+ 变更标记。审计的职责是"谁在何时改了哪个字段"，不需要成为第二份证件号。
5. **切面按显式字段白名单工作**：未登记字段默认拒绝写入（fail closed）；禁止序列化整个实体；单条 ≤ 4KB，批量按行拆 + `batch_id`。
6. **补齐事件**：登录成功/失败、登出、用户/角色/授权变更、密钥轮换、配置变更、导出、解密查看、归档。`biz_type` 扩展 `AUTH / USER / ROLE / CONFIG / EXPORT / VIEW`。
7. **保留期** ≥ 30 年（随会计档案），按年分区。
8. **VIEW 审计要定义粒度**：详情、批量解密、导出才记；列表渲染不记。否则 2000 人 × 每日访问会淹没审计表并让链计算变贵。

### P1-2 解锁只有"高危权限 + 填原因"，缺少期限、复核证据、通知与异常阈值

**问题**
§4.6 L225、§5.3 L336 对解锁的全部要求是"需权限 + 填原因"。没有时限、没有重锁期限、没有通知、没有频率上限。`unlock_reason` 单列还会覆盖历史（已在 P0-9 处理）。

**为什么是问题**
解锁等价于"对已发放工资的写权限"，是全系统风险最高的动作。一个期间长期停在 `EDITING`，"锁定"就名存实亡；没有外部审批引用，线下审批在系统里不可追溯；没有通知，越权解锁不会被任何人及时看到。

**位置**
`docs/详细设计.md` §4.6 L223-226、§5.3 L336、§7 L387；`schema-mysql.sql:220`

**修复**
1. `payroll:period:unlock` 独立于 `lock`，且与编辑权互斥（P0-7）。
2. 必填 **结构化原因码**（录入错误 / 口径变更 / 补录漏项 / 仲裁要求 / 其他）+ `approval_ref`（线下审批单号 / 邮件主题 / 签字件编号）。
3. **解锁即通知**：站内 + 邮件给配置的接收人（集团 HR / 财务负责人 / 审计），内容含期间、主体、解锁人、原因、上一锁定版本摘要。
4. **自动重锁**：解锁时设定 `relock_deadline`（默认 24h 或当天下班前），到期自动锁定并告警；超期升级告警。
5. **频次阈值**：同一期间解锁 > 2 次、同一用户 30 天内解锁 > 3 个期间 → 告警。
6. 重锁时强制勾选"差异已复核"（记录勾选人），差异报告随快照归档（P0-9）。
7. **关闭窗口**：已归档、或距会计期间结束超过 N 个月（配置项，建议 6 个月）不得解锁，转线下专项流程。

### P1-3 导出管控缺少"导出物证据链"与体量阈值

**问题**
§4.7(3) 与 §5.5 只有"独立授权 + 水印 + 审计"三句话。审计里只有一条 `EXPORT`，没有导出参数、行数、内容摘要、文件本身；水印无实现细节；CSV 与错误报告未纳入；默认导出权还发给了 CLERK/REVIEWER（见 P1-6）。

**为什么是问题**
工资批量导出是数据外带的第一通道。没有"导出了什么、多少、谁、内容指纹"，发生泄漏时无法界定范围——而 PIPL 第 57 条的事件报告恰恰要求说明影响范围。

**位置**
`docs/详细设计.md` §4.7(3) L280、§5.5 L355、§5.4 L345

**修复**
1. 新建 `pay_export_log`：
   ```
   export_id, requester_id, report_type,
   params_json (期间/主体/部门/筛选条件), scope_snapshot,
   row_count, total_amount, columns_json,
   file_sha256, file_path, format,
   watermark_trace_id, created_at, downloaded_at, download_count
   ```
   审计表只记 `EXPORT` 事件并关联 `export_id`。
2. **水印具体化**：服务端生成，内容 `用户名 + 工号 + 时间 + trace_id`；每个 sheet 首行 + 页脚 + 文档属性均写入；`trace_id` 与 `pay_export_log` 一一对应，拿到任意一份外流文件可反查导出人与时间。前端加水印无效，不做。
3. **禁止 CSV / 纯文本导出**（无法可靠水印、最易扩散），仅允许 XLSX / PDF。
4. **体量阈值**：> 200 行或跨主体导出需 `payroll:export:bulk`（单独授权）+ `approval_ref`；默认 `payroll:export` 仅限本人范围且 ≤ 200 行。
5. **下载与导出分开审计**：导出走一次性签名 URL（短 TTL），**实际下载**再写一条审计。
6. 错误报告下载、工资条导出、自定义报表同规则。
7. 频次/时段异常告警（如非工作时间大批量导出）。

### P1-4 备份策略与 30 年档案要求不匹配；密钥托管缺失

**问题**
§6 L374："日备全量 + 保留 90 天；每周归档一次"——没有定义"归档"是什么、存哪里、留多久；没有备份加密、没有密钥托管、没有恢复演练。

**为什么是问题**
90 天备份只覆盖误操作与短期故障，不覆盖 30 年会计档案"可还原、可自证"的要求。若密钥只存在于当前部署，磁盘故障或人员交接后 30 年的密文将永久不可读；若备份与密钥放在一起，加密又白做。

**位置**
`docs/详细设计.md` §6 L374、L376

**修复**
1. **区分两类**：运行备份（90 天，用于 DR）与会计档案包（永久，30 年）。
2. **每月**对每个已锁定期间生成档案包（P0-9 快照 + 审计切片 + manifest + 顶层 hash），**双份异介质保存**（本机 + 离线/异地），每年至少一次抽样恢复演练并留记录。
3. **备份加密 + 密钥托管**：AES/HMAC 密钥以双人控制的密封件或企业密钥库保存；`key_version` 与档案包一起归档；轮换前先验证旧版本仍能解密全部历史。
4. **到期销毁流程**：《会计档案管理办法》要求销毁须经单位负责人签署意见、编制销毁清册、监销；PIPL 要求最短必要。系统提供"到期档案清单"报表，销毁在系统外执行并回写销毁登记（不物理删除库内记录，销毁针对档案包副本）。
5. **宿主层**：全盘加密、应用专用 OS 账号、限制 sudo、Docker 卷权限 0700。

### P1-5 PIPL：敏感个人信息定性、合法性基础、PIA 与告知全部缺失

**问题**
设计文档全文没有个人信息保护章节：无数据分类分级、无合法性基础说明、无 PIA/DPIA、无员工告知文本、无受托处理（集成商）协议、无个人权利响应流程。

**为什么是问题**
证件号、银行账号（属 PIPL 第 28 条明确列举的"金融账户"）是敏感个人信息；工资虽未明文列举，但按第 28 条定义（泄漏易导致人格尊严或财产安全受危害）与监管实践，应按敏感个人信息管理。第 28/29/30/55/56 条对敏感个人信息有强制要求，**不因内网私有化而豁免**。

**位置**
全文（缺章节）；§4.8 L284-292

**修复**
1. **合法性基础不是"同意"**：劳动关系下的工资核算依第 13 条第(2)项（履行合同所必需）+ 第(3)项（法定义务：劳动法、工资支付、会计法、个税）。**不要设计"同意勾选框"作为工资处理的依据**——同意须自愿，劳动关系下难以成立，反而制造合规瑕疵。第 29 条的"单独同意"针对以同意为基础的处理；此处不适用，但**第 30 条的告知义务仍然必须履行**。
   - 对任何**超出**合同履行/法定义务的可选处理（工资条推送到微信、生物识别考勤、员工照片、营销用途），才需要单独同意，并在功能上做成可撤回。
2. **产出《员工个人信息处理告知书》**，作为劳动合同/员工手册附件：处理者身份、目的、字段清单、保存期限、共享对象（集团内主体、代发银行）、权利行使方式与联系方式。系统首次登录展示并记录"已阅"——注意措辞是"已阅"而非"同意"。
3. **完成 PIA（个人信息保护影响评估）** 并留存报告 ≥ 3 年：处理必要性、对个人权益的影响、安全措施。敏感信息处理与大规模处理均属触发情形。
4. **指定个人信息保护负责人**（规模未达强制门槛也建议指定），公开联系方式。
5. **受托处理**：若集成商/运维方在部署与运维期可接触生产数据，签 DPA（委托处理协议），约定目的限制、保密、审计、删除；远程接入需审批 + 全程录屏/日志。
6. **个人权利**：建立"本人信息查询/更正/删除请求"受理台账；对会计档案留存期内的删除请求，以法定义务为由书面拒绝并说明期限。
7. **安全事件预案**：泄漏范围可用审计 + 导出日志 + 档案包定位到人/文件/时间；明确报告路径（个人 + 监管）。
8. **可简化 vs 不可简化**：

| 可简化（内网带来的真实便利） | 不可简化 |
|---|---|
| 跨境传输（第 38-39 条）不适用 | 加密 / 去标识化（第 51 条） |
| 无公开网站，无 Cookie/同意管理 | 访问控制与审计 |
| 个人自助门户可用线下流程替代（第 2 期上线时补身份核验） | PIA（第 55 条） |
| 数据本地化要求无额外动作 | 告知（第 17/30 条） |
| | 事件响应（第 57 条） |
| | 受托方管理（第 21 条） |

### P1-6 最小必要：字段与角色可见范围需要重新论证

**问题**

**为什么是问题**

**位置**
`docs/详细设计.md` §4.7(3) L280、§5.1；`schema-mysql.sql:111-147(116,122-123),409-419`

**修复**
1. **建立"字段-目的-保存期-角色"矩阵**作为评审附件；新增字段必须更新矩阵。逐项确认：`gender` 是否参与任何计算（当前不参与）；`mobile` 在 MVP 是否有用途（若仅第 2 期推送用，可延迟采集或标注非必填）；`id_no` 的法定必需性出现在 phase 3（个税/社保），告知书中应写明"为后续个税/社保申报"。
2. `DEPT_MANAGER` 默认只看**部门汇总**（聚合）；个人明细需单独权限并审计。若业务坚持可见，须在告知书中说明。
3. 去掉种子数据中 CLERK/REVIEWER 的 `payroll:export`，改为独立角色或按主体显式授予；`payroll:sensitive:view` 默认不授予任何人。
4. `remark` 等自由文本字段在前端提示"禁止录入敏感信息"，并在服务层对明显格式（18 位身份证、11 位手机）做告警。

### P1-7 认证与会话：高敏操作没有二次认证，账号生命周期未定义

**问题**
有 `spring-boot-starter-security` 依赖与 `/auth/login`，但设计未定义密码策略、失败锁定、会话超时、并发会话、MFA/step-up、离职停用。

**为什么是问题**
解锁、导出、查看证件号三个高危动作只靠一个登录态。内网终端失陷后，攻击者拿到有效会话即可完成整套舞弊，审计只能追到一个合法账号。

**位置**
`docs/详细设计.md` §5.6 L359-362、§4.7(3) L281-282；`pom.xml:36-39`

**修复**
1. **step-up 认证**：`period:unlock`、`export:bulk`、`sensitive:view` 要求重新输入密码或 TOTP，有效期 5 分钟且与动作绑定（一次授权只能做一次动作）。
2. 管理员与高权限角色**强制 MFA**（TOTP，可离线）。
3. 密码：≥ 12 位、禁用弱口令表、BCrypt cost ≥ 10；失败 5 次锁定 15 分钟并写审计；不做 90 天强制轮换（NIST 建议），但泄漏后强制改。
4. 会话：空闲 30 分钟、绝对 8 小时；单账号并发会话上限；登出即服务端失效。
5. **账号生命周期**：`sys_user` 关联 `employee_id`；员工离职（`leave_date`）后自动/定时停用账号并审计；`UNIQUE(employee_id)` 防一人多号。
6. 登录、登出、失败、锁定全部写审计；登录接口限速。

### P1-8 异常处理泄漏与错误信息可作为存在性/越权预言机

**问题**
- `GlobalExceptionHandler.java:35-49` 用 `raw.contains("uk_id_hash")` 区分约束并返回"该证件号码已存在人员记录"。任何有建员工权限的人可逐个试证件号，探测其是否在集团存在（跨主体），无审计、无限速。
- `handleBiz`（L17-20）直接回显 `e.getMessage()`，业务层若拼入数据（"工号 E001…"）可控性差。
- 缺少 `AccessDeniedException`（会被兜底成 500 而不是 403）、`HttpMessageNotReadableException`（应 400）、`MaxUploadSizeExceededException`（应 413）。
- `log.warn("唯一约束冲突: {}", raw)` 会打印完整 SQL 与键值。

**为什么是问题**
证件号是否存在于集团，本身即个人信息，且跨主体存在性破坏数据范围。500/403 混淆会让越权尝试看起来像系统故障，绕过基于错误码的告警。

**位置**
`GlobalExceptionHandler.java:17-20, 35-49, 51-56`

**修复**
1. 唯一冲突**预检在服务层按数据范围做**：有 `ALL` 范围者显示"已存在（工号 E001，主体 X）"；无范围者只显示"证件信息与已有记录冲突，请联系集团 HR 核实"，并写审计（`action=SENSITIVE_MATCH`）。
2. 该接口限速（如 10 次/分钟/用户）+ 异常频次告警。
3. 不依赖数据库错误文本：以服务层预检为主，SQLState 23000 + 约束名映射为辅（MySQL 错误文案随版本/语言变化）。
4. 新增 `@ExceptionHandler(AccessDeniedException)` → 403、`HttpMessageNotReadableException` / `MethodArgumentTypeMismatchException` → 400、`MaxUploadSizeExceededException` → 413。
5. `BizException` 约定只允许"错误码 + 受控文案（枚举）"，不允许拼接业务数据；错误码表纳入评审。
6. 日志只记录约束名，不记录 SQL 原文与键值。

### P1-10 组织完整性与快照字段的交叉校验缺失

**问题**
- 无外键（可接受），但 `emp_employee.company_id` 与 `dept_id` 可属于不同主体（`schema:113,127`）。
- `pay_record.dept_id/dept_name` 快照与 `period.company_id` 无任何校验（`schema:253,258-259`）。
- 部门逻辑删除后，范围解析对 `deleted=1` 的部门处理未定义。

**为什么是问题**
范围计算依赖 dept/company 一致。一条错配记录会让某部门主管看到另一主体的工资，或让记录在汇总中消失（对账不平、少发/多发）。

**位置**
`schema-mysql.sql:111-147(113,127),249-288(253,258-259)`

**修复**
1. 服务层强制：保存员工时校验 `dept.company_id == employee.company_id`；保存记录时校验快照 dept 属于 period 主体。
2. 每日/每周一致性 SQL 巡检（员工-部门-主体、记录-期间-主体、汇总 vs 明细合计），异常告警。
3. 部门删除前置校验：存在在职员工或未归档期间记录时禁止删除。
4. 范围解析对 `deleted=1` 部门显式处理（保留在历史范围、排除在新范围），并写测试。

### P1-11 期间状态与写路径：归档不可逆、写校验必须落到数据库层

**问题**
§4.6 L228 说"锁定是数据库层面的约束"，但 DDL 没有任何数据库层约束（无触发器、无 CHECK）。状态校验只在应用层，一次直连 SQL 或一个漏改的接口就能写入 `LOCKED` 期间。`ARCHIVED` 不可解锁只写在文档里。

**为什么是问题**
"锁定后不可写"是本系统对会计档案的核心承诺。纯应用层承诺在私有化 + 有 DBA 的环境下不成立。

**位置**
`docs/详细设计.md` §4.6 L228-230；`schema-mysql.sql:213`

**修复**
1. 触发器（或统一写入口存储过程）校验：`pay_record` / `pay_record_item` 的 INSERT/UPDATE 前检查所属 period 状态 ∈ (`EDITING`)，否则 `SIGNAL`。
2. `status` 改为 `ENUM` 或加 CHECK 约束；状态迁移只允许白名单（`DRAFT→EDITING→LOCKED→ARCHIVED`，`LOCKED→EDITING` 仅经 unlock 接口）。
3. 应用账号对 `pay_record*` 不给 `DELETE`；逻辑删除（`deleted=1`）同样纳入锁定校验——锁定后连逻辑删除都禁止。
4. 归档为终态，任何写操作在数据库层拒绝。

### P1-12 传输与部署基线：HTTPS、CSRF/会话、容器与镜像

**问题**
未提 TLS（内网 HTTP 明文）；SPA + 会话方式的 CSRF/存储策略未定；`mysql:8.0`、`minio:latest` 未固定 digest；应用容器未定义运行用户；`data/import` 卷权限未定义。

**为什么是问题**
内网嗅探/ARP 欺骗可抓取登录态与工资数据；`latest` 在离线交付时不可复现，供应链不可控。

**位置**
`docs/详细设计.md` §1 L13、§6 L377；`docker-compose.yml:3,31`

**修复**
1. 全站 HTTPS（企业 CA 或自签 CA），HSTS；后端到 DB 走 TLS 或 unix socket。
2. 会话：`HttpOnly + Secure + SameSite=Lax` Cookie + CSRF token；若用 JWT，禁止放 `localStorage`（XSS 可窃），用内存 + 刷新 Cookie。
3. 安全响应头：CSP、`X-Frame-Options`、`X-Content-Type-Options`、`Referrer-Policy`。
4. 镜像固定 digest 并离线扫描 CVE；应用镜像非 root、只读根文件系统、`/tmp` 用 tmpfs。
5. `data/import` 卷权限 0700 + 专用 UID。

## 3 P2（可排期）

### P2-1 掩码列与索引类型
`id_no_mask` / `mobile_mask` 独立成列（`schema:120,123`），库泄漏时泄露"姓名 + 后 4 位 + 主体 + 部门"的组合。可接受，但应在 PIA 中记录该风险；或改为查询时按需生成。`id_no_hash CHAR(64)` 在 utf8mb4 下索引项 256 字节，改 `BINARY(32)` 或 `CHAR(64) CHARACTER SET ascii`。`file_hash` 同理。

### P2-2 逻辑删除与唯一键的冲突
`uk_emp_no` / `uk_id_hash` / `uk_username` 均不含 `deleted`，误建后逻辑删除的记录会永久占用工号/证件号/用户名。提供"合并/注销"管理流程，或把 `active_key` 模式推广到 `emp_employee`（`UNIQUE(emp_no, active_key)`）。

### P2-3 前端解密边界与缓存
明确"列表接口永不下发密文/明文"；前端不得把证件号写入 `localStorage`/`sessionStorage`；离开页面清除敏感 DOM 与内存；打印/截图不可控，靠水印 + 审计兜底，不作为预防手段。

### P2-4 审计的 IP / UA 采集
反向代理下需 `ForwardedHeaderFilter` + 受信代理白名单，否则所有审计 IP 都是代理地址，取证失效；UA 可伪造，仅作辅助证据。

### P2-5 数据库巡检与取证材料
无外键下增加孤儿记录巡检；开启 `binlog` 且 `binlog_row_image=FULL`，保留 ≥ 最近一次全备 + 30 天，用于事后取证与数据恢复。

### P2-6 权限复核与离职
季度权限复核报告（谁有什么角色、范围、最近登录）；特权账号（`sys:role:assign`、`sys:config:manage`）双人复核；离职自动停用并纳入审计。

### P2-7 依赖与镜像供应链
离线仓库固定版本 + CVE 扫描记录；镜像固定 digest；交付物提供签名与校验和清单，客户可校验。

### P2-8 到期销毁与离职去标识化
提供"到期档案清单"报表 + 销毁登记（系统外执行）；员工离职且满足会计留存要求后，可对证件号做去标识化（保留工号、姓名、金额，清除/掩码证件号），边界需与法务确认。这是"永不删除"与 PIPL 最短必要之间的必要调和。

| 复核锁定岗（HR-B） | COMPANY | `record:view`、`period:lock`、`period:unlock`、`export`（≤200 行） | `record:edit` / `import:submit` / `sys:role:assign` |

| 集团审计 | ALL | `record:view`、`audit:view`、`export` | `record:edit` / lock / unlock |
| 系统管理员（IT） | 无 payroll 数据 | `sys:user:manage`、`sys:role:assign`、`sys:audit:view` | 任何 `payroll:record:*` / `sensitive:view` / `lock` / `export` |
| 员工 | SELF | `record:view:self` | — |

不变量（启动自检 + 分配时校验）：
- 每个主体：`users(edit) ∩ users(lock) = ∅`，且两侧都非空；
- 全系统：`users(能读工资) ∩ users(能改账号/角色) = ∅`；
- 密钥保管人 ≠ 数据库管理员（DBA 有密文无密钥，密钥持有人无 DB 权限）。

### 4.3 数据分级建议（用于审计 `data_class` 与导出列控制）

## 5 开工闸门（P0 验收清单）

编码启动前，以下 9 项必须全部有**已定稿的设计结论**（不是"待定"）：

- [ ] P0-1 密钥：无默认值、32 字节校验、启动 fail-fast、三钥分离、版本列与轮换手册
- [ ] P0-2 部署：DB 不映射端口、口令不入库、TLS、最小权限账号
- [ ] P0-3 盲索引：HMAC + 归一化规则 + 可空语义 + 版本列 + 唯一索引定义定稿
- [ ] P0-4 加密：AES-256-GCM + 随机 IV + AAD + 实体无明文字段 + 敏感 DTO 分层
- [ ] P0-5 数据范围：ancestors 不可输入、递归 CTE 方案、按主体范围、SELF default-deny、ALL 发放规则
- [ ] P0-6 权限点：补齐 `sys:*` 与 `archive`，系统管理岗与业务岗互斥
- [ ] P0-7 职责分离：角色互斥矩阵 + 分配时校验 + 运行时 `last_edit_by` 兜底 + 单人主体 fail-closed
- [ ] P0-8 导入：原始文件加密、PII 列最小留存、错误报告掩码与授权
- [ ] P0-9 留痕：锁定快照表、解锁历史表、差异报告、重锁版本链
