| **P0** | **5** | 不解决不能开工：核心约束失效、历史数据会算错、代码写不出来 |

**最关键的三条**

1. **P0-1：`ON DUPLICATE KEY UPDATE` + 集团级唯一索引 = 跨主体静默覆盖。** 详细设计 §4.2 把「批量生成幂等」写成 `INSERT ... ON DUPLICATE KEY UPDATE`，而 `pay_record` 上唯一的唯一键是 `uk_emp_ym_active(employee_id, period_ym, active_key)`（跨主体）。上海分公司生成时撞上北京已存在的记录，MySQL 会把**北京那条**当成冲突行去 UPDATE——如果 SET 子句带 `company_id/period_id`，记录当场被"搬到"上海，北京的工资记录消失且无异常。这不是误拦，是静默数据污染，比"重复发薪"更糟。
2. **P0-2：员工归属主体没有历史表，重算历史期间一定用错主体。** C1 说跨主体调动只改 `emp_employee.company_id`，C3 说更正靠"解锁 → 修改 → 重新锁定"。一旦重算 2025 年的期间，生成逻辑读到的是**今天**的归属主体，写进 2025 年的 `pay_record.company_id`——历史工资表被算到错误法人名下。§4.9 的"按期间末日归属主体"规则用现有表根本无法实现。
3. **P0-3：「一人一月一条」的硬约束与多个合法业务场景直接冲突，业务尚未签字。** 同月跨主体调动（北京已锁定、上海要发）、同月离职再入职（`REHIRE` 枚举已经建好了）、第 2 期若上线补发（Q3 未决）——这三种情况都会被 `uk_emp_ym_active` 拦死。现在必须是产品决策 + 写进 DDL 注释的显式规则，而不是等上线后让财务去物理删行。

## 2 P0 · 不解决不能开工

### P0-1 集团级唯一索引 + `ON DUPLICATE KEY UPDATE` 会跨主体静默覆盖他人记录

**问题**
`pay_record` 上唯一的唯一键是 `uk_emp_ym_active(employee_id, period_ym, active_key)`。详细设计 §4.2「配套三条」第 1 条要求批量生成用 `INSERT ... ON DUPLICATE KEY UPDATE` 实现幂等。这两件事放在一起是致命的。

**为什么是问题**
1. MySQL 的 `ON DUPLICATE KEY UPDATE` **没有冲突目标语法**，撞到任何一个唯一键就更新那一行。上海分公司给张三生成 2026-11 时，撞上的不是"上海的记录"，而是**北京那条**。
2. 只要 UPDATE 子句里带了 `company_id=VALUES(company_id), period_id=VALUES(period_id), dept_id=VALUES(dept_id)`，北京那条记录就被原地改写为上海的记录——**不报错、不留痕、北京当月工资凭空消失**。这比重复发薪更隐蔽：L3 防线不但没拦住，反而成了改写工具。
3. 反过来说，**L2「本主体本期重复」其实根本没有被建模**：没有任何 `(period_id, employee_id)` 约束，L2 和 L3 共用同一个索引。"三层防线"名义上有三层，落库层只有一层。
4. 并发下 `ON DUPLICATE` 也不解决「先查后插」的竞态给业务层的可读性——`DuplicateKeyException` 里拿不到冲突的 `company_id`，§4.2 要求的"提示张三已在上海分公司"还是得回查。

**位置**
`db/schema-mysql.sql:283`（`uk_emp_ym_active`）、`docs/详细设计.md` §4.2 L2 行与"配套三条"第 1 条。

**修复建议**
主修：**禁止对 `pay_record` 使用 `ON DUPLICATE KEY UPDATE`**，改成"锁 → 判 → 写"三步，唯一索引只做并发兜底。

```sql
-- 事务内，每批 500 人
-- ① 以集团级索引做当前读，同时锁住 (employee_id, period_ym) 的间隙
SELECT id, period_id, company_id
  FROM pay_record
 WHERE employee_id = ?          -- active_key=1 等价于 deleted=0，且能用满索引
   AND period_ym  = ?
   AND active_key = 1
   FOR UPDATE;

-- ② 命中且 period_id = 本期  → UPDATE 原位（幂等，这才是真正的 L2）
--    命中且 period_id != 本期 → 抛业务异常，回填对方 company_name（这才是真正的 L3）
--    未命中                   → 裸 INSERT，唯一索引只兜并发
```

> 注意：`FOR UPDATE` 的间隙锁**只在 REPEATABLE READ 下生效**，禁止把隔离级别调到 READ COMMITTED，否则并发插入的兜底会失效。

可选加固：显式声明 L2 约束（虽然被 L3 蕴含，但让意图可读、让 UPDATE 走更短的索引）：

```sql
ALTER TABLE pay_record
  ADD UNIQUE KEY uk_period_emp_active (period_id, employee_id, active_key);
```

结构性替代（更彻底，代价是多一张表）：把"一人一月唯一"从工资记录里剥出来做占位表，冲突信号天然干净且能直接定位对方主体：

```sql
CREATE TABLE pay_emp_period_lock (
  employee_id BIGINT NOT NULL,
  period_ym   CHAR(7) NOT NULL,
  record_id   BIGINT NOT NULL COMMENT '当前占位的核算记录',
  company_id  BIGINT NOT NULL COMMENT '冗余，报错时说"已在 XX 分公司"',
  PRIMARY KEY (employee_id, period_ym)
) COMMENT='集团级发薪占位，L3 唯一真相';
```

### P0-2 员工归属主体没有历史，重算历史期间会用错法人主体

**问题**
`emp_employee.company_id / dept_id` 只有**当前值**，跨主体调动是原地更新（§4.9："只改这个字段 + 部门，不重建记录"），没有任职/调动历史表。而 C3 规定更正路径是"解锁 → 修改 → 重新锁定"，重算必然发生。

**为什么是问题**
1. **重算即错**：2026-11 张三是北京，2027-03 调到上海。此时解锁重算 2026-11，生成逻辑读 `emp_employee.company_id` 得到上海 → 写进 2026-11 的 `pay_record.company_id = 上海`。历史工资表归错主体，集团汇总的跨主体口径当场失真。
2. **"按期间末日归属主体"规则无法实现**：现有表只有当前值，没有任何数据能回答"张三在 2026-11-30 属于哪个主体"。§4.9 这条默认规则目前只存在于文档里，DDL 里没有载体。
3. **审计断链**：C1 多法人 + 内控要求，却无法回答"某员工历史上何时在哪个主体"，人力/审计盘查只能靠回忆。

**位置**
`emp_employee.company_id:113`、`dept_id:127`；`docs/详细设计.md` §4.9「人员归属的处理」。

**修复建议**
新增任职区间表，让归属变成**按日期版本化**的事实（与 `emp_comp_profile` 同构）：

```sql
CREATE TABLE emp_assignment (
  id              BIGINT       NOT NULL AUTO_INCREMENT,
  employee_id     BIGINT       NOT NULL,
  company_id      BIGINT       NOT NULL,
  dept_id         BIGINT       NOT NULL,
  position_name   VARCHAR(64)  NULL,
  job_level       VARCHAR(32)  NULL,
  effective_from  DATE         NOT NULL COMMENT '生效起（含）',
  effective_to    DATE         NULL COMMENT '生效止（含），NULL=至今',
  change_type     VARCHAR(16)  NOT NULL COMMENT 'HIRE/TRANSFER/PROMOTE/LEAVE/REHIRE',
  remark          VARCHAR(255) NULL,
  created_by      BIGINT       NULL,
  created_at      DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_by      BIGINT       NULL,
  updated_at      DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  deleted         TINYINT      NOT NULL DEFAULT 0,
  -- 同一员工最多一条"开口"记录（与 P1-4 同一个技巧）
  open_key        TINYINT      AS (IF(effective_to IS NULL AND deleted = 0, 1, NULL)) STORED,
  PRIMARY KEY (id),
  UNIQUE KEY uk_emp_eff (employee_id, effective_from),
  UNIQUE KEY uk_emp_open (employee_id, open_key),
  KEY idx_company_dept (company_id, dept_id, effective_from)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='任职/调动区间';
```

取数规则与 `emp_comp_profile` 完全一致：
```sql
SELECT company_id, dept_id FROM emp_assignment
 WHERE employee_id = ?
   AND effective_from <= :periodEnd
   AND (effective_to IS NULL OR effective_to >= :periodEnd)
   AND deleted = 0;
```

迁移期兜底：初始化时按 `emp_employee` 回填一条 `effective_from = hire_date, effective_to = NULL` 的记录（历史调动信息已丢失，需业务方补充），并保留 `emp_employee.company_id` 作为"当前值"的冗余读缓存（由任职表维护）。

> 这条如果不做，C1 + C3 的组合在产品上是不成立的。建议列为开工前置。

### P0-3 「一人一月一条」与合法业务场景冲突，业务规则尚未签字

**问题**
`uk_emp_ym_active` 把"同一人同一自然月只有一条有效核算记录"写成了不可绕过的数据库事实。这不是技术缺陷，是**产品规则缺位**——而它决定索引怎么建，必须先定。

**为什么是问题**
会撞上约束的合法场景（全部已在设计里出现）：

| 场景 | 现状 | 后果 |
|---|---|---|
| 同月跨主体调动（11/15 北京 → 上海） | §4.9 默认"整月归期间末日主体" | 北京那条必须先失效；若北京已 LOCKED 并已发放，只能跨主体解锁 + 逻辑删除 + 重生成，**需要两家公司的人都有权限**，流程未定义 |
| 同月离职再入职 | `employee_type` 已内置 `REHIRE` | 同月两次入职要发两次（哪怕合并成一条），规则未定义 |
| 第 2 期补发/扣回（Q3 未决） | 设计第 1 期不做，但表已为将来留了 `superseded_by` | 补发单若归属原期间，`period_ym` 相同 → 直接冲突，届时必须改索引，**是破坏性迁移** |
| 劳务/外包（`LABOR` / `OUTSOURCE`） | 枚举已内置 | 同一人可能同时挂两家主体（兼职、派遣），一律拦死 |

**位置**
`db/schema-mysql.sql:281-283`；`docs/详细设计.md` §4.2、§4.9、Q3。

**修复建议**
1. **把规则写进 DDL 注释和需求文档**：明确"一人一月仅一条，跨主体调动按期间末日归属整月归属，需先对原主体失效再在新主体生成"。规则一旦签字，P0-1 的报错文案、解锁流程、权限模型都要按它写。
2. **为第 2 期预留语义**：在 `pay_record` 上先加一列，避免将来改唯一键：

```sql
ALTER TABLE pay_record
  ADD COLUMN record_kind VARCHAR(16) NOT NULL DEFAULT 'REGULAR'
    COMMENT 'REGULAR正常 / ADJUST补发扣回（第2期）';
-- 将来补发时唯一键演进为：
-- UNIQUE KEY uk_emp_ym_kind (employee_id, period_ym, record_kind, active_key)
```
   第 1 期只有 `REGULAR`，约束效果与现在完全一致；第 2 期加 `ADJUST` 时不需要重建表、不需要停机。
3. **`OUTSOURCE`/`LABOR` 这类多人主体共用的情形**，如果业务确认存在，唯一键必须加 `employee_type` 或 `company_id` 维度——**这条必须现在问清楚**，事后改是破坏性的。

### P0-4 生成列 `active_key` 的写入路径未封锁，且数据库层不阻止物理删除

**问题**
你问的"联动是否成立"——**成立，但风险不在联动**。MyBatis-Plus 的 `@TableLogic` 执行的是 `UPDATE pay_record SET deleted=1 WHERE id=? AND deleted=0`，是普通 UPDATE，STORED 生成列会自动重算为 `NULL`，唯一槽位如期让出。**没有任何"logic-delete 特殊 SQL"能绕过它**（MP 逻辑删除没有特殊 SQL 通道）。

真正的断点在另外三处：

1. **实体映射 → `ERROR 3105`**。字段 `active_key` 会出现在 codegen 生成实体的属性里。MP 3.5.x 默认 `updateStrategy = NOT_NULL`，所以：
   - `insert`：字段为 null → 不拼进 SQL → 能插入；
   - **`updateById`：先 `selectById` 回填 `activeKey=1`，再改个 remark 保存 → SET 里带上 `active_key=1` → `ERROR 3105: The value specified for generated column 'active_key' in table 'pay_record' is not allowed`**。
   这是最常见的 read-modify-write 路径，几乎必踩。
2. **物理 DELETE 与 `REPLACE INTO`**。`DELETE` 会真正释放槽位并丢掉历史；`REPLACE INTO` = DELETE + INSERT，会短暂释放槽位，可被用来绕过"历史不可删"。C3/§6 明确"不提供物理删除"，但 DDL 层没有任何拦截（V6 实测：0 个触发器、0 个外键）。
3. **历史版本读不出来**（与 P1-11 联动）：MP 全局 `logic-delete-field: deleted` 会给所有自动生成的查询拼 `deleted=0`，`deleted=1` 的历史版本在应用层永远不可见——这与 `version_no/superseded_by` 的保留意图直接矛盾。

**位置**
`pay_record.active_key:279`、`application.yml:32-36`（全局逻辑删除配置）。

**修复建议**
```java
// 1) 实体上彻底屏蔽生成列，别让它进任何 INSERT/UPDATE/SELECT
@TableField(exist = false)
private Integer activeKey;
```

```sql
-- 2) 收紧应用账号权限：只给 DML 里的 INSERT/UPDATE/SELECT
REVOKE DELETE ON payroll.* FROM 'payroll'@'%';
GRANT SELECT, INSERT, UPDATE ON payroll.* TO 'payroll'@'%';

-- 3) 纵深防御：禁止删 pay_record（需要 DBA/运维单独账号）
DELIMITER //
CREATE TRIGGER trg_pay_record_no_delete BEFORE DELETE ON pay_record
FOR EACH ROW
BEGIN
  SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'pay_record 禁止物理删除，请改用逻辑失效';
END//
DELIMITER ;
```
> 触发器会对批量生成每行多一次校验，但本表一期只 2000 行，成本可忽略。
> 若团队不接受触发器，至少有 **2)** 的授权收紧 + 代码评审规则「禁止 `REPLACE INTO pay_record`」。

### P0-5 `period_ym` 是冗余列却没有格式约束，重复校验可被静默绕过

**问题**
`pay_record.period_ym` 冗余自 `pay_period`，是集团级唯一索引的组成部分，但**没有任何 CHECK，也没有任何一致性校验**。

**为什么是问题**
1. **值漂移直接废掉唯一索引**。已实测：`'2026-1' = '2026-01'` → 0（NO PAD + 逐字符比较），`'2026-11' = '2026-11 '` → 0。只要有一处 import/UI/异步任务把月份写成 `2026-1`、`2026/11`、`26-11`，就与 `2026-01` 分属两个唯一槽位——**L3 防线当场失效，且没有任何报错**。`CHAR(7)` 只保护了"不超长"（V12 实测：`CAST('2026-11 ' AS CHAR(7))` 截断为 `2026-11`），保护不了语义。
2. **与 `period_id` 不一致时，两层防线同时失效**。冗余列没有跨表约束，生成代码写错一个值，唯一索引就用错误的月份分组，而列表查询用的是 `period_id`——查重和查询看的是两套事实。

**位置**
`pay_record.period_ym:252`、`pay_period.period_ym:212`、`pay_summary_monthly.period_ym:356`。

**修复建议**

```sql
-- 三处都加格式约束（MySQL 8.0.16+ 默认强制 CHECK）
ALTER TABLE pay_record
  ADD CONSTRAINT ck_record_period_ym
  CHECK (period_ym REGEXP '^[0-9]{4}-(0[1-9]|1[0-2])$');
ALTER TABLE pay_period
  ADD CONSTRAINT ck_period_ym
  CHECK (period_ym REGEXP '^[0-9]{4}-(0[1-9]|1[0-2])$');
ALTER TABLE pay_summary_monthly
  ADD CONSTRAINT ck_summary_period_ym
  CHECK (period_ym REGEXP '^[0-9]{4}-(0[1-9]|1[0-2])$');
```
> 状态：推断（只读限制未建表验证；REGEXP 为确定性函数，MySQL 8 允许出现在 CHECK 中）。

配套两条：
1. **只允许由 `period_id` 反查得出 `period_ym`**，禁止从导入文件/前端直接取；在 `PayRecordMapper` 里统一由 `PayPeriod` 填充。
2. 加一条日巡检对账 SQL（见 §7），漂移即告警。

更彻底的做法：引入**集团期间维度表**作为唯一真相，`pay_record` 存 `group_period_id`，唯一索引 `(employee_id, group_period_id, active_key)`——彻底消除字符串漂移这一类 bug。C7 规模下改动不大，但会牵动 `pay_period` 结构，属于架构取舍，建议至少写进 ADR 备选。

## 3 P1 · MVP 前必须解决

### P1-1 期间锁定没有数据库层约束，与设计宣称矛盾

**问题** §4.6 写"锁定是数据库层面的约束"，README 关键约束第 5 条写"校验必须在服务端和数据库层做"。但实测（V6）：`CHECK` 0 个、外键 0 个、触发器 0 个。DDL 里**没有任何东西**阻止往 LOCKED 期间写记录。

**为什么是问题** 锁定期之后任何一条 UPDATE 都会改写已发放的工资。财务系统的第一内控在文档里有、数据库里没有；一旦有异步任务/后台脚本绕过服务层，事后无法察觉。

**位置** `pay_period.status:213`、`pay_record`。

**修复建议** 双保险：
```sql
-- ① 每次写事务开头：SELECT ... FOR UPDATE 锁期间行（1 次 I/O，2000 人/期完全够）
SELECT status FROM pay_period WHERE id = ? FOR UPDATE;
-- 应用层若 status IN ('LOCKED','ARCHIVED') 直接拒绝

-- ② DB 层兜底
DELIMITER //
CREATE TRIGGER trg_pay_record_guard_ins BEFORE INSERT ON pay_record
FOR EACH ROW
BEGIN
  IF (SELECT status FROM pay_period WHERE id = NEW.period_id)
     IN ('LOCKED','ARCHIVED') THEN
    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = '期间已锁定/归档，禁止写入';
  END IF;
END//
-- 同样建 BEFORE UPDATE 版本
DELIMITER ;
```

### P1-2 快照字段不充分，历史工资表仍会被"现在的数据"改写

**问题** `pay_record` 已快照 `emp_no/emp_name/dept_id/dept_name/job_level/employee_type/hire_date/seniority_years/base_salary_snapshot`，但仍缺 6 项，且其中一项是**复核口径级别的漏**：

| 缺什么 | 为什么必须快照 |
|---|---|
| **`hpd`（本期计薪天数）** | `pay_period.hpd` 是可编辑参数。解锁更正时如果有人改了 hpd，**已锁定的历史工资表口径随之漂移**，但不影响已落库金额——下次重算就变了。这是"同一份工资表两次算不一样"的经典来源 |
| `company_name` | `company_id` 只有 ID；主体改名后历史工资表导出显示新名字，档案核对不上 |
| `position_name` | 岗位是工资表常见列；`emp_employee.position_name` 会随调动变 |
| `comp_profile_id` | 复算/审计时必须知道"这条是按哪个薪酬版本算的" |
| `dept_ancestors` | 部门重组（换父节点）后，历史"按部门层级汇总"的归属会变 |
| `pay_record_item.precision_scale` | 只快照了 `item_name/category/direction`；科目舍入位数改了，历史明细的"该保留几位"就无从判断 |

**修复建议**
```sql
ALTER TABLE pay_record
  ADD COLUMN company_name    VARCHAR(128) NOT NULL DEFAULT '' COMMENT '主体名称快照',
  ADD COLUMN position_name   VARCHAR(64)  NULL                COMMENT '岗位快照',
  ADD COLUMN hpd             DECIMAL(6,2) NULL                COMMENT '本期计薪天数快照',
  ADD COLUMN work_start_date DATE         NULL                COMMENT '参加工作时间快照',
  ADD COLUMN leave_date      DATE         NULL                COMMENT '离职日期快照（NULL=未离职）',
  ADD COLUMN comp_profile_id BIGINT       NULL                COMMENT '取数所用薪酬档案版本',
  ADD COLUMN dept_ancestors  VARCHAR(512) NOT NULL DEFAULT '' COMMENT '部门祖先路径快照';

ALTER TABLE pay_record_item
  ADD COLUMN precision_scale TINYINT NOT NULL DEFAULT 2 COMMENT '落库时的舍入位数快照';
```
> 注意：`hpd` 一旦落到记录级，就应视为"生成时的输入"，后续重算必须**沿用记录上的值**还是"沿用期间当前值"，需要明确——建议：重算一律取期间当前值，但**锁定后冻结期间 hpd 不可改**（服务层 + 触发器）。

### P1-3 `pay_record` 没有 `pay_run_id`，§3.2 的 ER 关系没落地

**问题** §3.2 画的是 `pay_period 1─n pay_run 1─n pay_record`，但 `pay_record` 只有 `period_id`，没有 `run_id`。批次和记录之间没有任何可追溯的关联。

**为什么是问题** 生成失败重跑时无法知道"哪些记录是上一次失败批次写的、要不要回滚"；单条重算（`POST /records/{id}/recalculate`）也无法留痕"是谁、哪次跑出来的"。`pay_run` 的 `emp_success/emp_failed` 因此变成无法验证的自报数字。

**修复建议**
```sql
ALTER TABLE pay_record
  ADD COLUMN pay_run_id BIGINT NULL COMMENT '首次生成批次（重算不改写）',
  ADD KEY idx_run (pay_run_id);
```

### P1-4 `emp_comp_profile` 的生效区间可以重叠，取数可能命中两行

**问题** `uk_emp_effective(employee_id, effective_from)` 只防"同一天开两段"，不防区间重叠：`2024-01-01 ~ 2026-12-31` 与 `2025-01-01 ~ NULL` 可以共存。§4.1 明说"区间不重叠由应用层校验 + uk 兜底"——**这个 uk 兜不住重叠**。

**为什么是问题** 取数 SQL 是 `effective_from <= 末日 AND (effective_to IS NULL OR effective_to >= 末日)`，重叠时返回 2 行。生成逻辑如果 `selectOne` 会抛 `TooManyResultsException`（还算好），如果 `LIMIT 1` 就是**随机金额**——工资金额随机是灾难级。

**修复建议** 用生成列把"同一员工最多一条开口区间"变成数据库事实（与 P0-2 同一个技巧）：
```sql
ALTER TABLE emp_comp_profile
  ADD COLUMN open_key TINYINT AS (IF(effective_to IS NULL AND deleted = 0, 1, NULL)) STORED,
  ADD UNIQUE KEY uk_emp_open_profile (employee_id, open_key);
```
这条保证"开口区间唯一"，剩下"历史区间首尾相接"由应用层维护（写入时强制 `effective_to = 下一段 effective_from - INTERVAL 1 DAY`）。再配一条巡检 SQL（§7）扫重叠。

### P1-5 「主体专属科目 + 集团通用科目」并集会导致同一 `item_code` 撞唯一键

**问题** §4.9：`pay_item.company_id = 0` 表示集团通用，也可为某主体建专属科目，"核算时取并集"。而 `pay_item` 的唯一键是 `uk_item_code(company_id, item_code)`——**允许同一 `item_code` 同时存在于 company 0 和 company 1**。并集取出来后，`pay_record_item` 的 `uk_record_item(record_id, item_code)` 当场冲突，或静默只写入一条。

**修复建议** 二选一，写进设计：
- **A（推荐）**：`item_code` 改为**集团全局唯一**（`UNIQUE(item_code)`），主体差异化用 `status` 或新列 `company_scope` 表达，物理上杜绝并集冲突；
- **B**：保留现状，但明确"主体专属科目不得与集团通用科目同名编码"，新增科目时做校验，并在并集加载时按 `company_id` 去重+显式优先级。

### P1-6 `id_no_hash NOT NULL + 全局 UNIQUE` 让"无证件号人员"无法录入

**问题** `id_no_hash CHAR(64) NOT NULL` + `UNIQUE`。没有证件号的员工（外籍、退休返聘、实习）三人都算出 `SHA-256(salt)` 同一个值 → 第二个人起全部撞唯一键。

**修复建议**
```sql
ALTER TABLE emp_employee MODIFY id_no_hash CHAR(64) NULL COMMENT 'SHA-256(salt+证件号)；无证件号时为 NULL';
```
MySQL 唯一索引允许多个 NULL，问题自然消失。同时 `id_no_cipher` / `id_no_mask` 也应允许 NULL。

### P1-7 金额精度链路上的浮点隐患（列定义没问题，读取链路有问题）

**结论先说**：`DECIMAL(18,4)` **够用且偏大**。18 位 4 小数 = 14 位整数，上限 `99999999999999.9999`（V14 实测）；2000 人合计远小于此，`SUM()` 还会自动提升精度到 19 位整数。**列定义本身不是风险点**。

真正的浮点隐患全在链路两端，共 6 处：

1. **Excel 导入（最严重）**。EasyExcel 3.x 按数值单元格读进 `BigDecimal` 时，底层走的是 POI 的 `double`。已实测危害：`ROUND(2.665E0,2) = 2.66`，而 `ROUND(CAST(2.665 AS DECIMAL(10,3)),2) = 2.67`——**同样的输入，double 路径少 1 分钱**。5000 行导入里只要有一批小数第三位是 5，就会静默错分。
   → 修法：导入统一按**字符串读取**（`cell.getStringValue()` / `BigDecimal.valueOf(double)`），落库前 `setScale(4, HALF_UP)`；并且**禁止 `new BigDecimal(double)`**（走二进制真值）。
2. **DTO / 实体用 `double`/`float`**。规约一句话：全项目禁止 `double/float` 出现在金额字段，包括 DTO、VO、Excel 模型、Map 里的值。
3. **`Map<String,Object>` 接 JSON**。Jackson 默认把浮点解析成 `Double`，写进 `pay_audit_log.old_value/new_value` 的 JSON 一样会丢精度。开启 `DeserializationFeature.USE_BIG_DECIMAL_FOR_FLOATS`。
4. **`BigDecimal.equals` vs `compareTo`**。`1.0` 与 `1.00` 的 `equals` 为 false。对账必须用 `compareTo`，否则"金额没变"被判成"变了"、或反之。
5. **`divide()` 未指定 scale**。`divide(x)` 遇到非终止小数直接抛 `ArithmeticException`；`divide(x, n, mode)` 又可能与 MySQL 的 `ROUND` 不一致。规约：一律 `divide(x, 4, RoundingMode.HALF_UP)`。
6. **`ROUND()` 语义对齐**。MySQL 对 DECIMAL 调 `ROUND` 是 half-away-from-zero，与 Java `HALF_UP` 一致；但**对 double 调 `ROUND` 不是**（V13 已证）。所以"在 SQL 里 ROUND 一下就行"这个念头在 double 列上不成立——好在 schema 里 0 个 float/double 列（V5 已实测）。

补充一致性问题：`precision_scale` 是 TINYINT 且**没有任何强制**，但金额列统一存 4 位小数。若某科目 `precision_scale=2` 而落库忘做舍入，会出现 `100.1250` 与展示值 `100.13` 并存，`SUM` 与展示合计对不上。建议在 §4.4 的"落库前按 precision_scale 舍入"旁边补一句**这是不可绕过的写入契约，且由 P1-2 的 `precision_scale` 快照固化**。

### P1-8 `ancestors LIKE '%,5,%'` 全表扫描，`idx_ancestors` 是废索引

**已实测（V7）**：`type=ALL`，`possible_keys=NULL`。前导通配符 `%,5,%` 让 B+ 树索引完全不可用，`KEY idx_ancestors (ancestors(191))` 对任何真实查询都无效。`FIND_IN_SET(5, ancestors)` 同样 `type=ALL`。

**为什么现在还能接受**：C7（<2000 人）→ 部门表最多几百行，全表扫几毫秒。**但这是"数据量小救了设计"，不是设计对了**。真正的风险不是慢，是**权限过滤会拼进每一条工资查询**——一旦部门数增长或查询变复杂，它会成为所有列表页的共同瓶颈，且很难事后改。

**修复建议**（按代价从低到高）：

**A. MVP 用（推荐，今天就能上）**：部门表只有几百行，一次性读进内存构建子树 ID 集合（带 5 分钟本地缓存），SQL 用 `IN`：
```sql
-- 权限过滤，索引可用
... WHERE period_id = ? AND dept_id IN (1,3,7,12,18) AND active_key = 1
```

**B. 中期**：把 `ancestors` 改成**右匹配可用**的路径格式（前导分隔符去掉），让 `LIKE` 能用索引：
```sql
-- ancestors 存成 '/1/5/'（含自身），查询：
... AND (dept_id = 5 OR ancestors LIKE '/1/5/%')
-- LIKE '/1/5/%' 无前导通配符 → 可走 range 扫描
```
注意：移动部门时必须级联重写整棵子树的 ancestors（现有方案同样有这个要求，只是没写）。

**C. 长期**：部门闭包表，JOIN 走主键：
```sql
CREATE TABLE sys_dept_closure (
  ancestor_id   BIGINT NOT NULL,
  descendant_id BIGINT NOT NULL,
  depth         INT    NOT NULL,
  PRIMARY KEY (ancestor_id, descendant_id),
  KEY idx_desc (descendant_id)
);
```
无论选哪个，**`idx_ancestors(191)` 现在就该删掉**——它对任何查询都没用，只是写放大的负担。

### P1-9 汇总预聚合的维度与 `/reports` 接口不对齐

**问题** §3.1 说 `pay_summary_monthly` 是"预聚合，年度查询不扫明细"，§5.5 的 `/reports/monthly` 要支持"按部门/类型/科目"三个维度。但表里只有 `(company_id, period_ym, dept_id)` 一个维度，**没有类型、没有科目**。

**为什么是问题**
- 按类型汇总：无数据，只能扫 `pay_record`（12 万行/年，可接受）；
- 按科目汇总：只能扫 `pay_record_item`（**48 万行/年**，5 年 240 万），与"年度查询不扫明细"的自我承诺矛盾，也撑不住 P95 ≤ 500ms 的目标。

**修复建议** 补一张科目级预聚合（与主汇总一起在锁定时刷新）：
```sql
CREATE TABLE pay_summary_item_monthly (
  id               BIGINT        NOT NULL AUTO_INCREMENT,
  company_id       BIGINT        NOT NULL,
  period_ym        CHAR(7)       NOT NULL,
  dept_id          BIGINT        NOT NULL,
  employee_type    VARCHAR(32)   NOT NULL,
  item_code        VARCHAR(32)   NOT NULL,
  direction        TINYINT       NOT NULL,
  amount           DECIMAL(18,4) NOT NULL DEFAULT 0,
  employee_count   INT           NOT NULL DEFAULT 0,
  refreshed_at     DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_item_summary (company_id, period_ym, dept_id, employee_type, item_code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='月度科目级汇总';
```
行数量级：部门数(≈100) × 20 科目 × 12 月 ≈ 2.4 万/年，无压力。

### P1-10 导入幂等的 `file_hash` 索引用不上、也不唯一

**问题** `pay_import_batch` 有 `KEY idx_file_hash(file_hash)`（非唯一、全局），但 §4.5 的规则是"命中**已提交**批次则拒绝"。语义是 `(period_id, file_hash, status=COMMITTED)`，现有索引支撑不了，已实测（V: 查询 `period_id + file_hash` 走的是 `idx_period`，然后逐行过滤）。且没有唯一约束，双击"确认提交"可以并发建两个批次。

**修复建议** 用与 `active_key` 同一套技巧做局部唯一：
```sql
ALTER TABLE pay_import_batch
  DROP KEY idx_file_hash,
  ADD COLUMN committed_key CHAR(64) AS (IF(status = 'COMMITTED', file_hash, NULL)) STORED,
  ADD UNIQUE KEY uk_period_committed_file (period_id, committed_key),
  ADD KEY idx_period_hash (period_id, file_hash);
```
失败/校验中的批次可以重复上传，已提交的同一文件在同期间内物理上只能有一份。

### P1-11 MyBatis-Plus 全局逻辑删除与"保留历史版本"的意图冲突

**问题** `application.yml` 配了全局 `logic-delete-field: deleted`，MP 会给所有自动生成的查询拼 `AND deleted=0`；而 `pay_record` 又留了 `version_no` / `superseded_by`，暗示要保留旧版本供追溯。**这两个意图互相矛盾**：旧版本必然 `deleted=1`，在应用层永远查不到，`superseded_by` 指向的记录也永远读不出来。

**为什么是问题** 更进一步：`version_no/superseded_by` 在 C3（更正 = 解锁原地改）下**根本没有产生路径**。留着两列只会让人误以为系统有版本链，写出依赖它们的代码。

**修复建议**
- **推荐（与 C3 一致）**：删掉 `version_no` / `superseded_by`，更正就是原地改，审计靠 `pay_audit_log`。`deleted` 只保留"跨主体调动时失效原记录"这一个用途，语义写进注释。
- 若坚持保留历史版本：明确"历史查询必须走手写 SQL（`@Select`/XML，MP 不会自动拼 `deleted=0`）"，并加一条团队规约。**注意**：自定义 SQL 里漏写 `deleted=0` 是这套配置最常见的线上事故——报表和汇总的自定义 SQL 必须逐条检查。

### P1-12 `pay_record_item` 没有 `deleted` / `created_by`，与全局约定冲突

**问题** DDL 开头约定"所有业务表带 deleted 软删除标志，不提供物理删除"，但 `pay_record_item` 没有。编辑明细时删除一个科目只能 `DELETE`，而且没有 `created_by` 留痕。

**为什么是问题** 明细是金额的直接载体，却是核心四表里唯一没有软删除的。用户在编制台上删掉一个绩效奖金明细，事后无从追溯。同时全局 `logic-delete-field` 配置也要求实体有这个字段才生效——不一致会让人猜。

**修复建议** 二选一并写清楚：
- A：加 `deleted TINYINT NOT NULL DEFAULT 0` + `active_key` 生成列，`uk_record_item` 改为 `(record_id, item_code, active_key)`；
- B：明确"明细是记录的子实体，随记录一起重写，不做独立软删除"，并在 DDL 注释里说明为什么它是唯一例外。

### P1-13 审计日志的索引与留存策略缺位

**问题** `pay_audit_log` 是"只增不改"，且 §4.7 要求"查看他人工资写查看审计（谁看了谁的）"——意味着**每次列表/详情查看都写一条**。它是本系统增长最快的表（可能远超工资明细），但：
- 没有 `(company_id, created_at)` 索引（已实测：`WHERE company_id=? AND created_at>=?` 走 PRIMARY 反向全扫）；
- 没有留存/归档/分区策略；
- `old_value/new_value` 是 `TEXT`（64KB），注释写"敏感值需加密后写入"但**没有任何实现**。

**修复建议**
```sql
ALTER TABLE pay_audit_log
  ADD KEY idx_company_time (company_id, created_at),
  ADD KEY idx_biz_time (biz_type, biz_id, created_at);
```
外加：按月归档（`pay_audit_log_archive`）或按月分区；`old_value/new_value` 要么落库前加密，要么**干脆不存金额明文**，只存"字段名 + 变更前后哈希/引用"，避免审计表成为最大泄露面（§6 要求"应用日志禁止出现金额明文"，审计表同理）。

## 5 八个重点问题的直接回答

### Q1 唯一键与索引是否支撑所有查询路径？

**`uk_emp_ym_active` 会误伤，但不是你想的那种误伤。**
- 技术层面它**不误伤**合法数据：`NULL` 不参与唯一，逻辑删除后槽位正常让出（见 Q2）。
- **业务层面它会误伤**：同月跨主体调动、同月离职再入职、未来的补发单、劳务/外包多人挂靠——见 **P0-3**，必须业务签字。
- 更严重的是**它同时承担了 L2 和 L3**，而 `ON DUPLICATE KEY UPDATE` 会拿它当改写目标 → **P0-1**（跨主体静默覆盖）。

**工资表列表查询**：`idx_period_dept(period_id, dept_id)` 足够支撑"按期间+部门"过滤；`idx_period_emp` 支撑"按期间+人"。缺的是 `ORDER BY emp_no` 的排序索引（V8 实测 filesort），2000 行下无所谓。清单：
- 保留：`uk_emp_ym_active`、`idx_period_emp`、`idx_period_dept`
- 建议替换：`idx_period_dept` → `(period_id, dept_id, emp_no)`
- 建议删除：`idx_employee`（冗余）、`idx_period_status`（期均 2000 行，选择性太低）

### Q2 `active_key` 生成列 + MyBatis-Plus 逻辑删除，联动成立吗？

**成立。MP 的逻辑删除没有"特殊 SQL"，就是一条普通 UPDATE，STORED 生成列在任何 UPDATE 上都重算。** 批量 `UPDATE ... SET deleted=1 WHERE period_id=?`、`ON DUPLICATE KEY UPDATE SET deleted=1` 同样生效。

**但有三处必须处理**（详见 P0-4）：
1. 实体映射了 `activeKey` → `updateById` 会把 `active_key=1` 拼进 SET → **ERROR 3105**。用 `@TableField(exist = false)`。
2. **物理 `DELETE` / `REPLACE INTO` 是真绕过**（槽位真释放、历史真丢失）。收权限 + 禁 REPLACE + 可选触发器。
3. MP 全局 `deleted=0` 过滤让 `deleted=1` 的历史版本在应用层不可见（P1-11）。

### Q3 `DECIMAL(18,4)` 够用吗？有没有遗漏的浮点隐患？

**列定义够用且偏大**（14 位整数，V14 实测上限 `99999999999999.9999`），schema 里 0 个 float/double 列（V5 实测）。**隐患全在读取链路**：Excel 用 double 读（V13 实测 `ROUND(2.665E0,2)=2.66` vs DECIMAL `2.67`，差 1 分）、DTO 用 double、Map 接 JSON、`new BigDecimal(double)`、`equals` 比金额、`divide` 不指定 scale。详见 **P1-7**。

### Q4 快照字段还缺什么？

缺 6 项，其中 `hpd`（计薪天数）和 `dept_ancestors`（部门层级）是**口径级**缺口，`company_name`/`position_name`/`comp_profile_id` 是**追溯级**，`pay_record_item.precision_scale` 是**舍入级**。见 **P1-2**。

### Q5 `ancestors LIKE '%,5,%'` 会全表扫描吗？有更好方案吗？

**会。已实测 `type=ALL`、`possible_keys=NULL`，`idx_ancestors(191)` 完全无效。** 三个方案：应用层子树 ID 集合（MVP 推荐，部门只有几百行）、路径右匹配 `LIKE '/1/5/%'`（可走索引）、闭包表（长期）。见 **P1-8**。

### Q6 字符集、排序规则、时区是否一致？

**全部一致（已实测）**：18 张表均为 `utf8mb4 / utf8mb4_0900_ai_ci`，无一个非 utf8mb4 字符串列；服务端 `utf8mb4 / utf8mb4_0900_ai_ci`；`time_zone=+08:00`、`system_time_zone=CST`、`NOW()-UTC=8h`；JDBC `serverTimezone=Asia/Shanghai`、Jackson `Asia/Shanghai`。

**但有三点要注意**：① DDL 没有显式 `COLLATE`，全靠服务端默认，跨环境会漂；② 时区配置散落三处，换部署形态（K8s）时最容易丢；③ `0900_ai_ci` 是大小写不敏感 + NO PAD（V11 实测），工号 `E001`/`e001` 视为同一个。见 P2-4 / P2-5。

### Q7 该建模却没建模的？

**P0 级**：员工任职/调动区间表（**P0-2**，没有它 C1+C3 的组合不成立）。
**P1 级**：`pay_record.pay_run_id`（P1-3）、科目级预聚合表（P1-9）。
**P2 级**：`sys_company.parent_company_id`（P2-9）、字典表（P2-10）、审计表归档（P1-13 的一部分）。
另外 `详细设计.md` §4.8 提到"银行卡号（预留）"但 DDL 里没有对应字段——第 3 期做代发时需要补，属于已知范围外，仅记录。

### Q8 数据量与索引：过度还是不足？

**总量很小**（<2000 人）：`pay_record` 2.4 万行/年、`pay_record_item` **48 万行/年**、5 年约 240 万行。单表、不分区是**正确**决定（C7），不要引入分区。

**索引结论：`pay_record` 过度（4 个二级索引里 2 个该删），`pay_record_item` 有一个冗余索引压在最热的写入路径上，而 `pay_summary_monthly` / `pay_audit_log` 反而缺索引。** 也就是说——**索引建在了行数最少的表上，行数最大的两张表欠账**。详见 §6 与 P2-1/P2-3。

## 6 容量与索引账

### 6.1 行数预估（<2000 人、12 期/年、20 科目）

| 表 | 每期 | 每年 | 5 年 | 备注 |
|---|---:|---:|---:|---|
| `pay_record` | 2,000 | 24,000 | 120,000 | 主体数 × 2000 分摊，总量约等于 2000/期 |
| `pay_record_item` | 40,000 | **480,000** | **2,400,000** | 2000 × 20，`SUM` / 导出 / 科目汇总的主要数据源 |
| `pay_summary_monthly` | 部门数（约 100） | ~1,200 | ~6,000 | 建议补科目维度后 ≈ 2.4 万/年 |
| `pay_audit_log` | 不定（每次查看都写） | **≥24 万** | **≥120 万** | 增长最快、索引最缺、留存策略最缺 |
| `pay_import_batch` | 少量 | 数百 | 数千 | 索引设计基本无关 |
| `pay_period` | 主体数 | 12×主体 | 60×主体 | 极小 |

**存储**：`pay_record` 约 500 B/行 → 5 年 ≈ 60 MB；`pay_record_item` 约 180 B/行 → 5 年 ≈ 430 MB + 索引。**单库完全无压力**，不需要分区、不需要分库、不需要归档明细。

### 6.2 生成性能预算

一期 2000 条记录 + 4 万条明细，按 500 条/批 ≈ 84 个批次。瓶颈不是数据量，是**每批的事务与索引维护次数**：
- `pay_record` 每插一行维护 1 个 PK + 1 个唯一 + 4 个二级索引 = **6 棵 B+ 树**（删掉 2 个冗余后是 4 棵）；
- `pay_record_item` 每插一行维护 1 个 PK + 1 个唯一 + 1 个冗余二级 = 3 棵（删掉 `idx_record` 后是 2 棵）→ **最大表节省 1/3 索引维护**。

30s 的 SLO 在删掉冗余索引后非常宽松，不需要更多优化。

## 8 日巡检对账 SQL（建议纳入运维手册）

这四条能把本评审里最危险的三类静默错误变成可告警：

```sql
-- ① period_ym 与 period_id 漂移（P0-5：漂移即意味着跨主体查重失效）
SELECT r.id, r.period_id, r.period_ym, p.period_ym AS real_ym
  FROM pay_record r JOIN pay_period p ON p.id = r.period_id
 WHERE p.period_ym <> r.period_ym;

-- ② 合计 ≠ 明细加总（§4.4 铁律的落地检查）
SELECT r.id, r.gross_amount, i.g, r.deduction_amount, i.d, r.net_amount
  FROM pay_record r
  LEFT JOIN (
    SELECT record_id,
           SUM(IF(direction = 1, amount, 0)) AS g,
           SUM(IF(direction = 2, amount, 0)) AS d
      FROM pay_record_item WHERE deleted = 0 GROUP BY record_id
  ) i ON i.record_id = r.id
 WHERE r.deleted = 0
   AND (r.gross_amount <> IFNULL(i.g,0) OR r.deduction_amount <> IFNULL(i.d,0)
        OR r.net_amount <> r.gross_amount - r.deduction_amount);

-- ③ 薪酬档案区间重叠（P1-4）
SELECT a.employee_id, a.id AS seg_a, b.id AS seg_b
  FROM emp_comp_profile a
  JOIN emp_comp_profile b
    ON b.employee_id = a.employee_id AND b.id > a.id
 WHERE a.deleted = 0 AND b.deleted = 0
   AND a.effective_from <= IFNULL(b.effective_to, '9999-12-31')
   AND b.effective_from <= IFNULL(a.effective_to, '9999-12-31');

-- ④ 跨主体同月重复（理论上不可能，出现即说明有人绕过了索引）
SELECT employee_id, period_ym, COUNT(*) AS cnt
  FROM pay_record WHERE deleted = 0
 GROUP BY employee_id, period_ym HAVING cnt > 1;
```
