# 10-验收-薪酬主线

> 验收对象：工资核算系统薪酬主线（人员、薪酬档案、工资项、期间、生成、编制台、导入、边界）。
> 验收方式：真实 HTTP 调用（`--noproxy` 等价实现）+ 数据库复核；未修改任何业务代码。
> 环境：后端 `127.0.0.1:8080/api/v1`，MySQL `payroll-mysql`，账号 hr01/hr02/admin。
> 日期：2026-11-27。

## 结论摘要

- 共执行 **77 个子用例**，覆盖任务要求的 25 项。
- **✅ 通过 67 条，❌ 失败 6 条（归并 5 个根因），⚠️ 存疑 4 条。**
- 失败根因：
  1. 停用已使用科目后重新生成：该员工计算失败，但批次仍返回 `SUCCESS`，期间保持编制中（部分成功当成全成功）。
  2. `precision_scale = 0` 的科目在**生成**路径被当作 2 位小数，金额算错（保存路径正确）。
  3. `payroll:period:unlock` 权限无人持有，且 admin 受“只能授出自己持有的权限”约束无法授权 → 解锁功能不可达。
  4. 停用科目仍可通过 changeset 直接写入（仅前端列被置灰，服务端未拦）。
  5. 超过 `DECIMAL(18,4)` 上限的金额返回 500“系统异常”，不是可读的 400。
- 另有 4 条存疑：离职状态不联动离职日期、`precision_scale` 后端未限 0–4、千分位金额不一致、缺工号列表头报错文案错位。

## 失败明细与根因

### 1）停用已使用科目后重新生成，部分失败仍返回 SUCCESS（最严重）

- 现象：P3（precision=3）已被 T900 的核算记录使用；停用 P3 后重新生成 2027-11。
- 结果：HTTP 200，`pay_run.status=SUCCESS`，但进度 `success=4 failed=1`，错误 `T900: 计算失败：工资项定义缺失: P3`；期间仍为 EDITING，T900 保留旧数据，其余 4 人已重算。
- 根因：`GenerateService.loadVariableAmounts` 不按科目状态过滤，停用科目仍进入 `variableItems`；`PayrollCalculator.item()` 在 `itemDefs` 取不到定义时抛 `IllegalStateException`；`processBatch` 只按员工记 failed 后继续，`startGenerate` 无条件 `closeRun(..., "SUCCESS")`。
- 影响：用户会看到“生成成功”，但个别员工工资未更新，属于静默的数据不一致。

### 2）precision_scale=0 的科目生成金额错误

- 现象：P0（precision=0）薪酬档案金额 1.239，生成后 `P0=1.24`、DB `1.2400`；按科目精度应为 `1`。
- 根因：`PayrollCalculator.item()` 使用 `def.precisionScale() > 0 ? def.precisionScale() : PayrollRules.AMOUNT_SCALE`，把 0 当成“未配置”，回落到 2 位。
- 对比：编制台保存路径 `RecordService.applyItem` 直接使用 `precisionScale`，P0 保存为 `3.0000`，两条路径不一致；前端科目表单精度允许 0，因此用户可触发。
- 影响：按 0 位精度配置的科目，生成金额会产生分位误差。

### 3）解锁权限死锁，锁定期间无法解锁

- 现象：hr02（PAYROLL_REVIEWER）调 `POST /periods/{id}/unlock` → 403；admin 调 `PUT /roles/2/grants` 授予 `payroll:period:unlock` → 403 `不能授予自己未持有的权限点：payroll:record:view`。
- 根因：种子数据中没有任何角色持有 `payroll:period:unlock`；`ScopeGuard.assertPermissionsWithinOperator` 要求授出的权限必须是操作者自身权限的子集，而 admin 只有 `sys:*`，不持有任何 `payroll:*`，因此无法自助补授。
- 影响：锁定后只能直接改数据库才能解锁；PAYROLL_REVIEWER 只有 lock 没有 unlock，复核流程不可逆。`PeriodService.unlock` 的原因校验（400）本身存在，但实际不可达。

### 4）停用科目仍可通过 changeset 写入

- 现象：P3 `status=0` 时，changeset 提交 `P3=9.999` → HTTP 200，金额写入。
- 根因：`ItemService.requireItem` 不校验 `status`，`RecordService.applyItem` 只校验 `editable`；`ColumnSnapshotFactory` 虽把停用已用列标为 `editable=false`，但这只是前端提示，服务端未拦。
- 影响：前端正常操作不会触发，但接口层可绕过停用；若前端缓存旧列或脚本调用，会写出已停用科目。

### 5）超上限金额返回 500

- 现象：changeset `PERF_BONUS=999999999999999.9999` → HTTP 500 `系统异常，请联系管理员`，事务回滚（数据未变）。
- 根因：`RecordService.parseMoney` 接受任意精度 BigDecimal，落库时超出 `DECIMAL(18,4)` 触发数据库异常，被 `GlobalExceptionHandler` 的兜底 `Exception` 处理为 500。
- 影响：用户输入错误被当成系统故障，无法自助纠正。

## 存疑项

1. **离职状态不联动离职日期**（2.5）：`status=2` 且 `leaveDate=null` 的员工仍是核算候选；候选 SQL 只按 `hire_date/leave_date` 判断，不看 `status`。只改状态会继续发薪。
2. **precision_scale 后端不限 0–4**（7.4）：前端 `el-input-number` 限制 0–4，但 API 可创建/更新为 6/10/-2；生成按超精度的值计算后落 `DECIMAL(18,4)` 会被静默截断。
3. **千分位金额不一致**（25.7）：Excel 导入会 `replace(",", "")`，编制台 changeset 不去逗号，`1,234.50` 报格式错误。
4. **缺工号列表头报错文案错位**（23.2）：`ImportValidator.columnMapping` 先按列顺序校验未知键，遇到“编号”列即抛“字典不匹配”，没有走到“模板缺少工号列”的检查；状态码 400 正确，但提示误导。
