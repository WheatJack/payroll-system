## 0. 结论摘要

| 严重度 | 数量 | 说明 |
|---|---|---|
| **Critical** | **2** | 跨账号残留工资数据；期间切换竞态可写错期间 |
| **Important** | **11** | 未保存编辑丢失、大表卡顿、部门树串主体、隐藏 403、凭证存储等 |
| **Minor** | **13** | 死代码、重复常量、小范围健壮性问题 |

**最危险的三个**

1. **退出登录不清 `grid` store**：同一浏览器换账号后，后一个账号会直接看到前一个账号的工资行和未保存修改，并能以其身份保存（C-1）。
2. **编制台加载无「旧响应」守卫**：快速切换期间时，A 期间的响应可能覆盖 B 期间，随后保存会把 A 的 `recordId` 发到 B 期间的接口（C-2）。
3. **编制台合计在每次按键做 O(行×列) 的 Decimal 运算**：5 万行 × 50 列 ≈ 250 万次字符串转 Decimal，输入一个数字即可让主线程卡死数秒（I-2）。

## 1. Critical

### C-1 退出登录/401 不清编制台 store，工资数据与未保存修改跨账号残留

- **文件**
  - `frontend/src/stores/auth.ts:55-60`（`logout()` 只清 token / user / permissions）
  - `frontend/src/main.ts:35-41`（401 全局处理同样只调 `auth.logout()`）
  - `frontend/src/views/period/PayrollGridView.vue:391-399`（`samePeriod` 命中时**不重新拉取**）
  - `frontend/src/stores/grid.ts:221-229`（`reset()` 存在，但全仓只有 `PayrollGridView.vue:387` 调用）
- **问题**：`grid` store 保存了整张工资表的 `rows`、`versions` 和 `dirty`，但 `logout()` 和 401 处理都没有清它。换账号后，只要新账号打开**同一个期间**，`onMounted` 判断 `store.period?.id === periodId && store.rows.length > 0` 成立，就会跳过 `load()`，直接渲染上一个账号留在内存里的行；如果上一个人还有未保存编辑，`dirty` 也一并继承。
- **危险在哪**
  - 薪资是最高敏感数据，HR/财务共用一台电脑或浏览器是常态；后一个账号无需任何请求就能看到前一个账号的工资明细（含未保存的调薪/扣款草稿）。
  - 后一个账号点「保存修改」时，changeset 会以**后一个账号的 token**提交前一个人的编辑，审计上无法区分，且可能覆盖真实数据。
  - 这不是「后端权限没拦住」：期间本身对该账号可见，所以接口会正常返回 200；问题在前端把别人的缓存当成了自己的。
- **改法**
  - 在 `auth.logout()` 内调用 `useGridStore().reset()`（`grid` 不依赖 `auth`，无循环依赖），或在 `main.ts` 注册统一的 `resetUserScopedStores()`，401 与主动登出共用。
  - 在 `grid` store 记录 `ownerUserId` / `ownerCompanyId`，`PayrollGridView` 挂载时若不一致则强制 `reset()` + `load()`。
  - `samePeriod` 跳过刷新只在「同一用户 + 有未保存修改」时成立；无 dirty 时应静默重新拉取，避免长期展示过期数据。
  - 补一条测试：登出后 `useGridStore().rows`/`dirty` 为空。

### C-2 期间切换的响应竞态：旧期间的数据可能被保存到新期间

- **文件**
  - `frontend/src/views/period/PayrollGridView.vue:139-157`（`load()` 没有请求序号，`await` 后直接 `store.load(data)`）
  - `frontend/src/views/period/PayrollGridView.vue:386-389`（`watch(periodId)` 先 `reset()` 再 `load()`，组件实例复用）
  - `frontend/src/views/period/PayrollGridView.vue:353-382`（`save()` 用当前的 `periodId.value` 拼 URL，但请求体来自 store）
- **问题**：从 `/periods/A/grid` 快速切到 `/periods/B/grid` 时，组件不会重建，`watch` 触发 B 的加载；但 A 的在途请求没有取消，也没有 token 校验。若 A 的响应晚于 B 到达，`store.load()` 会把 store 覆盖回 A 的行、列和 `period`；此时 URL 仍是 B。
- **危险在哪**
  - 页面显示 A 的金额，却挂在 B 的地址下；用户以为自己在核对 B。
  - `save()` 发送 `PATCH /periods/B/records`，请求体是 A 的 `recordId` + version。轻则 400/409，重则若两期 `recordId` 有重叠（复制期间、回滚数据等），会把 A 的金额写进 B，属于工资数据错误。
  - 底部合计、导出的 `periodYm`（取自 `store.period`）也可能与页面标题不一致，报表口径错乱。
- **改法**
  - `load()` 开头记录 `const requested = periodId.value`，`await` 后若 `requested !== periodId.value` 直接丢弃响应；或复用 `utils/latest.ts` 的 `createLatestOnly()`。
  - `save()` 前断言 `store.period?.id === periodId.value`，不满足则拒绝保存并提示「期间已切换，请刷新」；保存 URL 直接用 `store.period.id`。
  - 更彻底：为每次加载创建 `AbortController`，在 `watch(periodId)` / `onBeforeUnmount` 时 abort。
  - 补一条并发测试（先发 A 后发 B，A 后到）。

## 2. Important

### I-1 未保存编辑在「切换期间 / 关闭页面」时静默丢失

- **文件**：`frontend/src/views/period/PayrollGridView.vue:386-389`（切期间直接 `reset()`）、`:168-181`（只有「刷新」按钮做了确认）、`frontend/src/stores/grid.ts:65`（`load()` 无条件 `dirty.value = {}`）
- **问题**：刷新有确认，但“从 A 期间跳到 B 期间”和“关闭标签页/浏览器”没有任何保护；`store.load()` 会清空 dirty。
- **危险在哪**：财务在工资表里改了 20 个单元格，点侧边栏去别的期间看一眼，回来发现修改全没了，且没有任何提示——这是工资系统最容易引发投诉的数据丢失形态。
- **改法**：`onBeforeRouteLeave` + `beforeunload` 时若 `store.hasChanges` 弹确认（与 `refresh()` 复用同一段逻辑）；或把每个期间的草稿按 `periodId` 持久化，回来自动恢复；切期间时不要先 `reset()`，先确认再清。

### I-2 编制台合计每次按键做 O(行×列) 重算，5 万行会卡死

- **文件**
  - `frontend/src/components/MoneyInput.vue:59-74`（每输入一个合法字符就 `emit('update:modelValue')`）
  - `frontend/src/views/period/PayrollGridView.vue:189-191`（每次 emit 都 `store.edit`）
  - `frontend/src/views/period/PayrollGridView.vue:207-222`（`totals` 对**每一列 × 每一行**调用 `sumMoneyColumn` → `coerce` + `money.add`）
  - `frontend/src/views/period/PayrollGridView.vue:445-451`（关键词每敲一下都 `setFilter`）
  - `frontend/src/stores/grid.ts:150-166`（`visibleRows` 每次全量过滤）
- **问题**：`totals` 依赖 `dirty`，而 `MoneyInput` 每个合法按键都写 dirty。50,000 行 × 50 列 = 250 万次 `Decimal` 构造/加法，这是**每次按键**的成本；关键词筛选同样是 5 万行/键，且没有防抖。
- **危险在哪**：大数据量验收场景下输入金额会出现数秒白屏/输入丢字，用户会重复点击或直接关页；`loading` 遮罩也挡不住主线程阻塞。属于「数据量一大就不可用」。
- **改法**
  - `MoneyInput` 拆成「本地 draft + 仅在 blur/Enter 提交」；网格编辑场景不要逐键 `emit`。若必须实时，至少 200ms 防抖。
  - 合计改为增量维护：`edit()` 时只对受影响列做 `sub(old) + add(new)`；或把 `totals` 放到 `requestIdleCallback`/`nextTick` 后批量算，并缓存每列结果。
  - 关键词用 `debounce(200)` 再写 store；筛选走 `shallowRef` 行数组，避免每键全表扫描。
  - `MoneyInput` 的 Enter 与随后的 blur 会各 commit 一次（见 M-10），也应一并去重。

### I-3 用户编辑弹窗与筛选器共用同一棵部门树，且不按被编辑用户的主体加载

- **文件**：`frontend/src/views/system/UserListView.vue:19`（`const { companies, deptTree, ... } = useOrgOptions()` 只解构出一个 `deptTree`）、`:116-131`（`openEdit` 只调 `loadRoles(row.companyId)`，没有 `loadDepts(row.companyId)`）、`:232-238`（筛选主体变化时写同一个 `deptTree`）、`:240-249`（弹窗内主体变化才加载，且 `openEdit` 赋值发生在 `dialogVisible = true` 之前，watcher 被 `if (!dialogVisible.value) return` 跳过）
- **问题**：筛选区和编辑弹窗共用 `deptTree`。打开「编辑用户」时，弹窗里的部门树仍是筛选器最后一次加载的主体（通常是当前登录人的主体），而不是被编辑用户所属主体；筛选器切换主体还会覆盖弹窗正在展示的选项。
- **危险在哪**：跨主体编辑用户（集团管理员常见）时，下拉里出现的是错误主体的部门；选中后提交 `deptId`，后端校验会 400/403，或者用户被挂到错误主体的部门下（若后端校验不严），用户的数据范围随之错位。界面上完全看不出「这是别的主体的部门」。
- **改法**：拆成 `filterDeptTree` 与 `formDeptTree` 两个 ref；`openEdit` 中先 `await loadDepts(row.companyId)` 再打开弹窗（或让 watcher 监听 `[props.modelValue, form.companyId]` 且不依赖打开状态）；新建时加载 `form.companyId` 的部门。

### I-4 用户管理页会在无 `sys:role:view` 时静默 403，角色下拉变空

- **文件**：`frontend/src/views/system/UserListView.vue:78-84`（`loadRoles()` → `GET /roles`，`catch` 后 `roles.value = []`）；后端 `src/main/java/com/insbean/payroll/admin/RoleAdminController.java:39-40`（`@RequirePerm("sys:role:view")`）；路由只要求 `sys:user:view`（`frontend/src/router/index.ts:65-69`）
- **问题**：`/users` 页面自身的权限点是 `sys:user:view/edit`，但它依赖 `sys:role:view` 才能列出角色。自定义角色若只给了用户管理权限，打开弹窗会得到一个空角色下拉，且没有任何错误提示。
- **危险在哪**：管理员误以为系统里「没有角色」，新建用户时只能不带角色提交，产出一个无法登录任何页面的账号；编辑用户时也看不到当前角色编码（只显示原始 ID），容易在保存时改错。排障时因为被 `catch` 吞掉，日志里也没有痕迹。
- **改法**：`loadRoles` 前判断 `auth.has('sys:role:view')`，无权限时显示「无角色查看权限，无法分配角色」并禁用保存；或请后端提供一个只需 `sys:user:edit` 的角色选项精简接口；无论哪种，都不要空 `catch`。

### I-5 薪酬档案面板的写入入口完全不看权限（`canEdit` 硬编码 `true`）

- **文件**：`frontend/src/views/employee/CompProfilePanel.vue:24`（`const canEdit = ref(true)`）、`:93-103`（`openAdjust` 无校验）、`:184`（按钮无条件渲染）、`:134-168`（`submit` 无校验）、`:173`（`defineExpose({ reload: load, canEdit })` 无人使用）
- **问题**：只有 `payroll:record:view` 的账号打开「薪酬档案」抽屉，仍会看到「调薪 / 配置薪酬」按钮，可以填写生效日期、基本工资、津贴并点保存。
- **危险在哪**：后端 `CompProfileController.java:37-45` 确实要求 `payroll:record:edit`，所以**不是越权**；但只读用户会被引导填完整张表单，最后才收到 403，体验和「前端隐藏、接口可调」的防御原则都不成立。`canEdit` 这个命名说明作者本意是要控制，但实现遗留了硬编码。
- **改法**：`const canEdit = computed(() => useAuthStore().has('payroll:record:edit'))`；无权限时隐藏/禁用按钮，卡片头部标注「只读」；`submit` 前再断言一次。保留后端校验作为最终边界。

### I-6 大量 `catch {}` 静默吞错，空下拉框被误认为「没有数据」

- **文件**
  - `frontend/src/composables/useOrgOptions.ts:17-19, 32-34`（主体/部门）
  - `frontend/src/views/period/PayrollGridView.vue:159-166`（部门树）
  - `frontend/src/views/employee/EmployeeListView.vue:68-75`（部门树）
  - `frontend/src/views/employee/EmployeeFormDialog.vue:45-58`（部门树）
  - `frontend/src/views/system/UserListView.vue:78-84`（角色）
  - `frontend/src/views/system/RoleListView.vue:67-73`（权限点目录）
  - `frontend/src/views/employee/CompProfilePanel.vue:77-83`（工资项）
  - `frontend/src/views/period/PeriodListView.vue:84-90`（轮询静默，属有意设计）
- **问题**：这些 catch 既不上报也不置错误态，403/500/网络断开与「确实没有数据」在界面上完全一样。
- **危险在哪**：`useOrgOptions` 失败会让月度/年度报表的「法人主体」下拉为空，用户以为没权限或没数据；`CompProfilePanel` 工资项加载失败会让津贴下拉为空，用户无法配置；`RoleListView` 权限目录为空会让授权弹窗变成空白，管理员可能误保存空授权（`replaceRoleGrants` 是全量替换，空数组会清空角色权限）。这是**数据损坏级**的静默失败。
- **改法**：在 `useOrgOptions` 里增加 `error` ref 并在页面展示；所有下拉加载失败时禁用依赖它的提交按钮；对 `listPermissions` 失败明确阻止打开授权弹窗；统一封装 `runSafely(fn, label)`，`ElMessage.error(isApiError(e) ? e.message : label)`。

### I-7 年度「按人」报表可能上万行，`el-table` 全量渲染

- **文件**：`frontend/src/views/report/AnnualReportView.vue:49`（`rows` 全量）、`:243-284`（`el-table` 无分页/虚拟滚动）、`:90-98`（合计每次遍历全部行）
- **问题**：`groupBy=EMP` 时每个员工一行；大主体 1 万员工就是 1 万行 × 7 列全部进 DOM，`show-summary` 还会触发全量求和。
- **危险在哪**：页面打开就卡顿数秒、滚动掉帧，内存占用高；低配办公电脑可能直接无响应。导出虽然走后端，但页面本身就是不可用的。
- **改法**：前端分页（每页 100/200）或改用 `el-table-v2`/`vxe-table` 虚拟滚动；合计仍按全量 `rows` 用 `money.sum` 计算（不要只算当前页）；或推动契约增加服务端分页。月度报表按部门聚合，风险较低，但也建议加同样保护。

### I-8 除报表外没有请求取消/竞态保护，列表可能被旧响应覆盖

- **文件**：`frontend/src/utils/latest.ts:16-29` 只被 `MonthlyReportView.vue:28` 与 `AnnualReportView.vue:37` 使用；`frontend/src/views/employee/EmployeeListView.vue:49-66`、`frontend/src/views/system/UserListView.vue:60-76`、`frontend/src/views/period/PeriodListView.vue:66-78`/`:84-90` 都没有序号守卫；`frontend/src/api/client.ts:97-110` 没有 `AbortController`。
- **问题**：连续改筛选/连点查询时，先发的请求可能后到并覆盖新结果；组件卸载后响应仍会写已销毁组件的 ref，并可能弹出迟到的 `ElMessage`。
- **危险在哪**：用户看到的是上一个关键词/上一页的数据，却以为筛选生效；在人员/用户列表上还可能把 A 页数据当成 B 页操作（点「编辑」打开错人）。配合 `current`/`size` 被响应回写，分页状态也会被旧响应改回去。
- **改法**：把 `createLatestOnly()` 提到所有列表 loader；或统一封装 `useLatestQuery`（内部 `AbortController` + token）。至少在同一 store 的 `load()` 里做 `if (!latest.isLatest(token)) return`。`onBeforeUnmount` 时 abort 在途请求。

### I-9 token 存 `localStorage`，无 CSP，登出不吊销服务端 token

- **文件**：`frontend/src/api/client.ts:12-28`（`payroll.token` 明文存 localStorage）、`frontend/index.html:3-8`（无 `Content-Security-Policy`）、`frontend/src/stores/auth.ts:55-60`（只清本地）、`frontend/src/api/client.ts:81-95`（401 只清本地 token）
- **问题**：Bearer token 长期放在 `localStorage`，任何能执行脚本的入口都可读取；页面没有 CSP 限制；登出只删本地副本，HMAC 无状态 token 在过期前仍然可用。
- **危险在哪**：当前代码**没有** `v-html`/`innerHTML`（已全量 grep，0 命中），应用层 XSS 面很小；风险主要来自第三方依赖（Element Plus / vxe-table / MSW 误打包）或未来新增的富文本/图表。一旦发生 XSS，攻击者可直接带走工资系统凭证；共用电脑上的 token 在登出后仍可被复制使用。
- **改法**
  - 加 CSP（至少 `default-src 'self'`、`script-src 'self'`；Vite 生产构建的内联样式需评估 `style-src`）。
  - 缩短 token TTL + 刷新/轮换；或在 `sys_user.token_version` 上把登出也 +1（后端已有该机制，重置密码在用），前端登出时调一次吊销接口。
  - 若可行，改 httpOnly + SameSite Cookie + CSRF token，彻底移出 JS 可读范围。
  - 至少不要在任何持久化 store 缓存工资数据（与 C-1 一起修）。

### I-10 `api/item.ts` 绕过契约生成的请求类型，字段拼错也能编译

- **文件**：`frontend/src/api/item.ts:14-19`（`createPayItem(payload: Record<string, unknown>)`、`updatePayItem(id, payload: Record<string, unknown>)`）；契约类型已存在于 `frontend/src/api/models.ts:41-42`（`PayItemCreateRequest` / `PayItemUpdateRequest`）但未被使用；同类问题 `frontend/src/api/system.ts:76-79`（`string[]` 强转 `RoleGrantRequest['permissions']`）
- **问题**：前端对工资项的新增/修改完全放弃类型检查；`RoleGrantRequest.permissions` 在契约里是 `PermissionCode[]`（枚举），这里用 `as` 抹平成 `string[]`。
- **危险在哪**：`includeInGross` 少写一个字母、`precisionScale` 写成字符串都能通过 `vue-tsc`；Jackson 会静默忽略未知字段，接口返回 200，用户以为保存成功，实际配置没生效（工资项精度错会导致舍入口径错误）。权限点拼错则后端 400，前端只能靠运行时兜底。
- **改法**：`createPayItem(payload: PayItemCreateRequest)`、`updatePayItem(id: string, payload: PayItemUpdateRequest)`；`replaceRoleGrants(id: string, permissions: PermissionCode[])`，由 `vue-tsc` 在编译期拦截。`PayItemUpdateRequest` 本身允许 `category/direction`，但契约注明已被使用的科目禁止改，提交侧仍应保持当前「不发送」的策略。

### I-11 修改自己的账号后不刷新权限点，菜单/按钮停留在旧状态

- **文件**：`frontend/src/views/system/UserListView.vue:150-176`（`updateUser` 成功后只 `load()`，没有 `auth.fetchMe()`）；对照 `frontend/src/views/system/RoleListView.vue:121-123, 175-177`（改角色/授权后会 `auth.fetchMe()`）
- **问题**：管理员编辑自己的账号（改角色、停用/启用）后，`auth.user.permissions` 仍是登录时的快照；只有刷新页面或重新登录才更新。被移除的菜单项/按钮仍显示，新增的权限入口不出现。
- **危险在哪**：后端会 403，所以不会越权；但界面与真实权限不一致，管理员会以为授权没生效而反复操作；若被降权后仍能点到「保存」，会得到莫名其妙的 403，排障成本高。
- **改法**：`updateUser` 返回后若 `updated.id === auth.user?.userId`，调用 `await auth.fetchMe()`；如权限变化导致当前路由不再可访问，用 `resolveLandingPath()` 重新落页（路由守卫在下次导航时也会兜底）。
