> 评审视角：前端 / 交互（不评审后端领域模型本身，只评审它会怎样落到界面上）

## 1 总评

这份设计在后端是完整的：表结构、三层查重、金额铁律、状态机都经得起推敲。但**前端默认被当成了"后端接口的渲染层"**，而工资表编制台本质上是一个**电子表格应用**——它需要虚拟滚动、固定列、分组表头、单元格编辑、批量保存、未保存状态管理、冲突处理。文档对这些一个都没有展开，只用一行 `el-table-v2（虚拟滚动）` 带过。

按现在的文档直接开工，最可能出现的结局是：编制台在第 3 周发现 `el-table-v2` 做不了合并表头和合计行，临时换库；金额在第 5 周发现某处用了 `Number()`，对账差 1 分钱，全链路返工；导入在第 6 周发现没有批次状态接口，只能同步等 15 秒。这三件事都可以在开工前用 1–2 天定死。

以下按 P0/P1/P2 展开。

## 2 P0（不解决不能开工）

### P0-1 编制台不能用 `el-table-v2`，改用 vxe-table v4

**问题**
§1 技术决策把大表格方案定为 `el-table-v2`。但编制台要同时满足：动态列（约 30–40 列）、多级/合并表头（按科目类别分组）、左右固定列、行虚拟滚动、单元格编辑、合计行、筛选。`el-table-v2` 原生只覆盖「动态列 + 固定列 + 行虚拟滚动 + 排序」，其余每一项都要自研。

**为什么是问题**
- **合并表头没有 API。** Element Plus 2.14 文档的做法是：`#header` 插槽 + `header-height="[50, 40, 50]"` + `HeaderClassNameGetter`，由业务自己接收 `cells/columns/headerIndex`，用 JSX + `cloneVNode` 重算每一组的宽度并插入占位单元格。官方示例按"固定列数分组"切分，而工资项会增删、排序、按主体变化，列分组一变就错位。等于要维护一个「表头引擎」。
- **合计行没有 API。** 文档没有 footer/summary 能力。只能自己造一条与横向滚动同步的假表尾，或者把合计塞成第一行 fake row（无法 sticky 在底部）。而 §4.4 要求"合计永远等于明细加总"，合计条是财务每天盯的东西。
- **编辑只能手写。** `cellRenderer` 里塞 `el-input`，行被虚拟化卸载时输入框直接消失。必须自己做"草稿态持久化 + 滚动时提交 + 重挂载恢复"，否则用户滚一下屏幕丢一个字。
- **筛选没有内置。** 官方 demo 是把筛选 popover 塞进表头后**替换 data**，筛选状态、合计联动、与未保存编辑共存全部自己做。
- **稳定性有已知坑。** 截至 2026-11：`#23914` 超过约 100 列滚动卡顿；`#22933`/`#22928` `scrollToRow` 定位错误（会直接影响"跳到冲突行/某个员工"）；`#22917` 固定列 hover 高亮不同步；`#21480` `estimated-row-height` + 固定列时新增行不显示；`#22076` 滚动条卡顿。官方文档自己写着"该组件**仍在测试中**，生产环境使用可能有风险"。

**位置**
§1 技术决策表「前端」行；需求 3；§6 性能。

**建议方案**
1. 编制台改用 **vxe-table v4（MIT）**，封装在全站唯一的 `<PayrollGrid>` 组件里，其他页面继续 Element Plus。
   - 免费版直接可用：动态列、`vxe-colgroup` 多级表头、左右固定列、行/列虚拟滚动、单元格编辑 + 编辑校验、键盘导航（v4.21 重写）、表尾（`footer-method` 自算）、筛选、列宽拖拽、右键菜单。
   - README 把「单元格复制/粘贴」「区域选择」「数据汇总/聚合函数」列为**企业版**。本项目不依赖：合计用 decimal.js 自算（P0-3），批量金额走导入管道（C2）。若业务坚持要 Excel 式粘贴，三选一：买 vxe 企业版 / 换 Tabulator（MIT，clipboard 模块免费）/ Handsontable（商业授权，内部系统也必须付费，否则弹窗锁死表格）。
2. **2 人日 PoC 必须做完再排期**，验收项：
   - 40 列 × 2000 行 + 左右固定列 + 二级表头，首次渲染 ≤ 2s；
   - 编辑单元格时纵向滚 500 行再滚回，值和焦点状态都在；
   - 横向滚动时左侧固定列和表头分组不错位；
   - 单格输入到重渲染 ≤ 50ms，滚动 ≥ 50fps。
   任一不过，直接切 Tabulator（备选），不要"再调调看"。
3. **明确不选**：
   - `ag-grid` Community：分组表头/固定列/编辑/撤销免费，但**区域选择、剪贴板、聚合/汇总行都在 Enterprise**；合计和粘贴仍要自研，不比 `el-table-v2` 省事。
   - 自研：真 `<table>` + sticky 首列 + 行虚拟技术上可行（约 2–4 周），但没有列虚拟、键盘、筛选、列宽、焦点体系，MVP 不做；只作为 vxe-table 被公司依赖政策否决时的 fallback，且要单独加 3 周。
4. 主题：vxe-table 用 CSS 变量对齐 Element Plus token；因为只有一个包装组件，将来换库成本可控。
5. `el-table-v2` 仍可用在：员工列表、导入历史、审计日志这类 ≤ 200 行、只读、无合并表头的页面；超过 200 行就分页或换 `el-table`。

### P0-2 编制台的数据形态与保存接口：一次拉全量 + changeset 批量保存

**问题**
§5.3 只给了 `GET /periods/{id}/records`（分页 + 筛选）和 `PUT /records/{id}/items`（单条保存）。前者假定"表格是分页浏览的"，后者假定"一次只改一个人"。编制台的真实用法是：几百行同时可见、批量改、最后一起保存。

**为什么是问题**
- **分页 + 服务端筛选 = 编辑必丢。** 财务会反复切部门核对，每切一次就重新请求，页面上未保存的编辑要么被覆盖，要么需要前端另做一层"分页缓存回填"，复杂度翻倍且极易出 bug。
- **逐条保存 = 请求风暴 + 非原子。** 400 人 × 平均 3 个变动项 = 1200 次 `PUT`（合并成 400 次也一样）。每次都要校验期间状态、加行锁、写审计、重算合计；中途网络抖动就留下"一半人存了、一半没存"的工资表，财务无法判断数据是否完整。
- **没有并发控制。** `pay_record.version_no`、`pay_period.version` 在 DDL 里都建了，但接口没有使用。两个薪酬专员同时编一个期间，后保存的静默覆盖前者，审计也查不出丢了什么。

**位置**
§5.3 `GET /periods/{id}/records`、`PUT /records/{id}/items`；§4.3 ⑦；§6 性能；DDL `pay_record.version_no` / `pay_period.version`。

**建议方案**
1. 新增 `GET /api/v1/periods/{id}/grid`：一次返回期间 + 列定义 + 全部记录（含明细）+ 版本号，**不分页**（C7 < 2000 人，单主体通常 200–600 行）。
   - 明细用二元数组压缩，避免每格一个对象：
```json
{
  "code": 0,
  "data": {
    "period": { "id": "12", "periodYm": "2026-11", "status": "EDITING",
                "version": 12, "createdBy": "7", "lockedBy": null },
    "columns": [
      { "itemCode": "BASE_SALARY", "itemName": "基本工资", "category": "FIXED",
        "direction": 1, "dataType": "AMOUNT", "precisionScale": 2,
        "includeInGross": 1, "editable": 0, "importable": 0, "sortNo": 10 }
    ],
    "records": [
      { "id": "9001", "empNo": "E001", "empName": "张三", "deptId": "31",
        "deptName": "销售一部", "jobLevel": "P6", "employeeType": "REGULAR",
        "seniorityYears": "3.50", "grossAmount": "12500.0000",
        "deductionAmount": "200.0000", "netAmount": "12300.0000",
        "versionNo": 3,
        "items": [["BASE_SALARY","9500.0000"],["PERF_BONUS","3000.0000"]] }
    ],
    "meta": { "rowCount": 486, "editableItemCount": 4, "serverTime": "..." }
  }
}
```
   - 500 行 × 15 项约 500KB，gzip 后 60–100KB，内网可接受；2000 行也 < 400KB gzip。
   - 带 `ETag` / `version`，客户端 `If-None-Match` 命中返回 304。
2. 新增 `PATCH /api/v1/periods/{id}/records`：changeset 批量保存。
```json
{
  "periodVersion": "12",
  "requestId": "9f2c2c1e-...",
  "records": [
    { "id": "9001", "versionNo": "3",
      "items": [ { "itemCode": "PERF_BONUS", "amount": "3200.0000" } ],
      "removeItems": ["OTHER_BONUS"],
      "remark": null }
  ],
  "deletes": [ { "recordId": "9010", "versionNo": "1" } ]
}
```
   - 前端每次最多 200 条，串行最多 2 路；`requestId` 做幂等（重试不重复写）。
   - 返回分三类：`applied`（每条重算后的 `gross/deduction/net` + 新 `versionNo`）、`conflicts`（版本不一致，附服务端当前值）、`rejected`（行级校验失败及原因）。
   - **服务端重算值是权威**，前端用响应覆盖本地预览——这是 §4.4 对账不被前端 bug 带偏的唯一方式。
   - 失败语义：单请求单事务（≤ 200 条），失败即 0 条生效；前端按 200 条分块，某块失败只影响该块，并明确提示"第 201–400 行未保存"。
3. `PUT /records/{id}/items` 保留给"单人详情抽屉"和未来的移动端；加 `expectedVersion`。`POST /records/{id}/recalculate` 保留，用于重算单行。
4. `GET /periods/{id}/records` 保留，但只用于部门主管等只读场景；编制台不用它。

### P0-3 金额：字符串 + decimal.js 必须变成工程约束，而不是一句注释

**问题**
§1 只写了一行"JSON 传输用字符串，JS number 精度不可靠"，`JacksonConfig` 也只是把 `BigDecimal/Long` 序列化成字符串。但"前端必须用 decimal.js"落到代码里，有至少 9 个高发丢精度点，而 Element Plus 最顺手的 `el-input-number` 恰好是最危险的组件。

**为什么是问题**
- `el-input-number` 的 `modelValue` 是 `number`，`precision` 只是显示层；输入 `123456789.1234` 在 JS number 里已经不精确。它内部还有 `+`/`-`/`parseFloat`。
- `v-model.number`、`Number(v)`、`parseFloat(v)`、一元 `+v`、`v * 1`、`Math.round`、number 版 `toFixed()`——任何一处都会把 string 降级成 number。
- 合计行如果用 `reduce((a, b) => a + b, 0)`，尾差会以"分"为单位漂移，直接违反 §4.4。
- 按金额排序时字符串是字典序（`"1000.00" < "900.00"`），用户会看到"1000 排在 900 前面"。
- 千分位展示后再解析回 number 会炸；输入框里带逗号、货币符号、全角数字也要处理。

**位置**
§1「金额」行；§4.4；`JacksonConfig.java:22-25`；DDL `pay_item.precision_scale`。

**建议方案**
1. **类型**：`type Money = string & { readonly __money: unique symbol }`（或至少 `type Money = string`）。所有金额在 TS 里声明为 `string`：接口 DTO、Pinia store、组件 props/emits、localStorage 缓存。**类型层面禁止 number 进入金额链路。**
2. **组件**（放在 `src/components/money/`）：
   - `<MoneyInput v-model="draft" :scale="item.precisionScale" :direction="item.direction" />`：内部 `ref<string>`，`emit('update:modelValue', string)`；**绝不使用 `el-input-number`**。
   - 输入中允许 `^-?\d{0,14}(\.\d{0,4})?$`；失焦归一化：
     `new Decimal(v).toDecimalPlaces(scale, Decimal.ROUND_HALF_UP).toFixed(scale)`。
   - 空串保持空串（"无此项"），是否等价于 0 见 P2-7。
   - `<MoneyText :value="str" />`：`new Decimal(v)` → 按字符串插入千分位（**不要经过 number**）→ 固定 2 位。仅"只读展示"允许 `toNumber()`，且不得回写。
3. **运算**：合计、行预览、筛选合计、diff、排序全部用 Decimal：`Decimal.sum(...)`、`.cmp()`、`.eq()`；`toFixed(2)` 只在渲染时调用一次。
4. **校验**：`ElForm` 用自定义 validator（`Decimal.isDecimal` + scale + 范围），不要写 `type: 'number'`。
5. **防回归**：
   - ESLint `no-restricted-syntax` 在 `src/views/payroll/**`、`src/components/money/**` 禁掉 `parseFloat`、`Number(`、一元 `+`、`.toFixed(`；只允许从 `decimal.js` 取值。
   - 单测固定用例：`0.1 + 0.2`、`1.005 → 1.01`、`-1.005 → -1.01`、`99999999999999.9999`、`"1,234.56"`、`"1e3"`（拒绝）、`""`、`"-0"`。
   - 属性测试：随机生成 200 行明细，前端 `Decimal.sum` 必须与后端返回的 `gross_amount` `eq`。
6. **高发点清单**（每一处都要有测试）：输入框 blur 归一化、单元格草稿回填、合计条（全表/筛选/可见列三个口径）、行内 gross/net 预览、导入 diff 预览、金额排序、导出确认弹窗里的合计、通知/日志中的金额、localStorage 缓存。
7. **展示规则（§4.4 落地）**：明细列显示 2 位；`pay_record.gross_amount` 是权威值。若 `Σ 明细显示值 ≠ gross`，合计格显示 ⓘ「明细加总 ¥12,499.99，合计 ¥12,500.00，差 ¥0.01（以合计为准）」，**前端不要"凑平"**。
8. **方向语义**：`direction=2`（扣款）的列，用户**只输入正数**，展示为红色 `-300.00`，列头写"扣款（填正数）"。禁止用户输入负号后再被后端按 direction 二次取负；导入中的负数直接报 `DIRECTION_MISMATCH`，不要静默取绝对值。

### P0-4 编制台的编辑模型：dirty 独立于筛选视图，切换筛选永不丢编辑

**问题**
文档同时设计了"服务端筛选分页"和"手工编辑"，但没有定义编辑态的数据模型。按字面实现，切换筛选 = 重新请求 = 未保存编辑丢失；两人同时编辑 = 后保存覆盖先保存。

**为什么是问题**
编制是长会话（财务常常开着一下午：改几个人 → 切到另一个部门核对 → 再切回来改）。如果每次筛选都丢未保存，用户会被迫"改一格存一次"，正好撞上 P0-2 的请求风暴；如果允许覆盖，工资表会静默丢改动，审计也定位不到。

**位置**
需求 3「筛选搜索」；§5.3；DDL `pay_record.version_no` / `pay_period.version`。

**建议方案**
1. 单一数据源 `usePeriodGridStore`：
```
rows: Record[]                                  // 服务端全量
dirty: Map<recordId, Map<itemCode, string>>     // 只存改过的格
removedItems: Map<recordId, Set<itemCode>>
deleted: Set<recordId>
basePeriodVersion: string
savedAt: string | null
```
2. **筛选/排序/列显隐 = 纯客户端 `computed`**，只影响 `viewRows`，永不发请求、永不清 dirty。C7 规模下筛选 < 100ms。
3. 切换筛选/排序/滚动前先 `commitActiveCell()`（把正在输入的字符串落进 dirty），避免"正在打字时点了筛选"丢当前字符。编辑状态不能只活在 DOM 里（这也是 P0-1 选 vxe-table 后仍要遵守的规则）。
4. **保存永远提交全部 dirty**（包括当前筛选看不到的行），确认条写明"共 37 处修改，其中 12 处不在当前筛选内"。提供「仅显示已修改」筛选供复核。
5. 视觉：行首圆点 + 单元格左上角三角标识已改；顶部常驻"未保存 37 处 · 上次保存 12:31"；Ctrl+S 保存。
6. 离开保护：`beforeunload` + 路由守卫；有 dirty 时「锁定 / 重新生成 / 导入 / 刷新」必须三选一（保存并继续 / 放弃修改 / 取消），并显示 dirty 数量。
7. 冲突处理：保存带 `periodVersion` + 每行 `versionNo`。收到 `conflicts` 时打开抽屉：「工号 / 姓名 / 科目 / 我的值 / 服务端值 / 服务端修改人 + 时间」，逐行选「用我的 / 用服务端 / 手工合并」；未冲突行已成功，不回滚。
8. 多标签页：`BroadcastChannel('payroll-period-{id}')` 广播保存事件；另一个 tab 收到后提示"本期间已在另一标签页保存，请刷新"。

### P0-5 导入管道：预校验必须异步，错误修复要有闭环，部分提交是产品红线

**问题**
§4.5 把预校验写成同步一步，§5.4 没有批次状态/错误明细接口。前端在 15 秒里只能转圈；错误只能下载 Excel；修完重传后无法告诉用户"这次只影响上次失败的 37 行"；更关键的是**没有定义是否允许部分提交**。

**为什么是问题**
- 5000 行校验要查员工、科目、期间状态、跨主体冲突。§6 的"≤15s"是性能目标，不是保证；内网 Nginx 默认 `proxy_read_timeout` 60s，用户等不及刷新/重复上传，会造出多个 batch（文件 hash 幂等只挡已提交批次，挡不住并发 `VALIDATING`）。
- 只有可下载的错误报告，用户要开 Excel、按行号找、改、存、再传，一轮 5 分钟；错误多时无法在页面内定位。
- 部分提交是财务红线：5000 行成功 4963 / 失败 37，若允许提交，这 37 人本月漏发，而系统显示"导入完成"。
- "同一文件 hash 直接拒绝"会挡住"提交失败后原样重试"和"解锁后重导"这两个真实场景。

**位置**
§4.5；§5.4；§6「导入 5000 行预校验 ≤ 15s」。

**建议方案**
1. **异步两段式**：`POST /import/validate` 立即返回 `202 { batchId, status: "VALIDATING" }`（文件先落盘 + 算 hash）；新增 `GET /import/batches/{batchId}` 返回 `{ status, phase, totalRows, processedRows, successRows, failRows, conflictRows }`；前端 800ms 轮询（或 SSE）。
2. **等待态**：步骤条「上传 → 校验 → 确认 → 完成」+ 进度条 + 阶段文案（"读取文件 3,200 / 10,000" → "校验员工" → "校验跨主体冲突"）+ 已用时。超过 60s 显示"仍在校验，可离开本页，完成后在导入历史查看"（batch 后台继续）。上传按钮防重；同 hash 已在 `VALIDATING` 时返回该 `batchId`，不新建。
3. **结果页**：摘要卡（总行/成功/失败/冲突）+ **页面内错误表**（虚拟滚动，先展示前 500 条；列：行号/工号/姓名/科目/原值/错误码/原因/建议）+ 按错误类型筛选 + 「下载完整错误报告」。
4. **修复闭环**（明确选 A，B 放 P2）：
   - **A（MVP）**：错误报告 = **仅失败行 + 原表头 + 新增「错误原因」列**；用户改完**重新完整上传**。因 UPSERT 幂等，重传成功行不会重复；新批次结果页显示"上次批次 #12 失败 37 行，本次覆盖其中 37 行"（可选参数 `retryOfBatchId`）。
   - **B（P2）**：服务端保留解析结果，页面内直接改错误格、只重校验失败行。约 +1 周，MVP 不做。
   - 明确**不做**"只重传失败行后直接提交、跳过已成功行"的隐式行为：会让两次导入的模式/期间状态语义不一致。
5. **部分提交：默认禁止。** `failRows > 0` 时提交按钮置灰，文案"还有 37 行未通过校验，修正后重新上传"。若业务坚持，需独立权限点 `payroll:import:partial` + 输入原因 + 审计 + 批次永久标记"部分导入（37 行未导入）"。建议 MVP 不提供。
6. **同文件 hash 策略**：命中 `COMMITTED` 且期间 `version` 未变 → 拒绝并给出原批次链接；命中 `FAILED` / `VALIDATED` 未提交 → 复用 `batchId` 继续；期间已解锁/版本变化 → 允许重导，但弹窗写明"该文件曾导入过，本次将按所选模式覆盖/累加"。
7. **模式在 validate 前选定**（DDL `pay_import_batch.import_mode` 已存），diff 与提交都用同一模式，不允许在确认页改模式。
8. 确认页必须有**变更预览**（见 P1-5），否则用户是盲签。

### P0-6 SELF 数据范围：工资条必须是独立页面，草稿期间不可见

**问题**
`data_scope = SELF` 的用户（内置 `EMPLOYEE` 角色只有 `payroll:record:view`）在文档里没有任何专属界面。如果直接进 `GET /periods/{id}/records`，会看到什么？DRAFT/EDITING 期间是否可见？工资条是宽表还是卡片？全都没写。

**为什么是问题**
- 编辑期金额是半成品（可能算错、未复核），员工提前看到会引发大量解释成本；更严重的是，若接口只按 `employee_id` 过滤，员工可以遍历 `periodId` 查看自己每个月的草稿和锁定值。
- 40 列的宽表给员工是灾难：横向滚动、分组表头、别人的部门列，完全不是工资条该有的形态。
- 部门主管（`DEPT_SUB`）看草稿同样敏感，必须明确口径。

**位置**
§4.7 数据范围；§5.3；§5.5；C1/C10。

**建议方案**
1. **服务端硬约束**：`SELF` 访问 `GET /periods`、`GET /periods/{id}/records`、`GET /records/{id}` 时，只允许 `status IN ('LOCKED','ARCHIVED')` 且 `record.employee_id = me.employee_id`，否则 403（不要返回空列表让前端猜）。
2. **员工端独立路由** `/my/payslips`（不出现在管理后台侧栏）：
   - `GET /me/payslips?year=2026` → 12 个月卡片（期间、实发、状态；未锁定月份不出现）。
   - `GET /me/payslips/{periodId}` → 工资条：顶部期间 + 实发大字；收入/扣款两组明细（右对齐、2 位小数）；底部应发/扣款/实发；不展示 `source`、审计、内部备注。
3. 管理端编制台只对「有 `record:edit`」或「非 SELF 范围 + `record:view`」的角色开放；`SELF` 用户登录后默认落在「我的工资条」。
4. **部门主管默认**：`DEPT_SUB` + `LOCKED/ARCHIVED` 只读。若业务要求看编辑期，单独开权限 `payroll:record:view:draft`，不要复用 `record:view`。
5. 移动端不单独适配（见 P2-9），但工资条卡片在 1024px 宽下必须可用。

## 3 P1（MVP 前必须解决）

### P1-1 列模型：列集合必须以"本期间明细快照"为准，而不是当前 `pay_item` 全表

**问题**
"列由 `pay_item` 决定"没有说清是哪个时点的 `pay_item`。工资项会改名、停用、新增；`pay_record_item` 冗余了 `item_name/category/direction/sort_no`，说明设计意图是"历史按快照"，但接口没有提供列定义。

**为什么是问题**
若用当前 `pay_item` 渲染历史期间：停用科目消失（历史金额看不到）、新增科目多出空列（列错位）、改名后历史名称被污染。若期间尚未生成，又没有明细可参考。前端无法自己拼出正确的列集合。

**位置**
§4.9「工资项」；§5.3；`pay_record_item` DDL 的冗余字段。

**建议方案**
- `GET /periods/{id}/grid` 返回 `columns`：
  - **已生成**：以 `pay_record_item` 去重出的 `item_code` 集合为骨架，`LEFT JOIN pay_item` 取 `editable/importable/precision_scale/status/最新名称`；展示名优先用明细里的快照 `item_name`。
  - **未生成**：本主体专属（`company_id = 本主体`）+ 全局（`company_id = 0`）且 `status = 1` 的 `pay_item`。
  - 排序：当前字典 `sort_no` 优先，缺省用明细 `sort_no`。
  - 分组表头：一级按 `category`（固定项/变动项/计算项），扣款项单独一组（`direction = 2`），二级为具体科目。
- 若同一 `item_code` 同时存在主体专属科目和全局科目（§4.9 的并集规则），去重规则必须由后端定死（建议主体专属覆盖全局）并且只返回一列；前端以 `itemCode` 作为列 key，**绝不能用 `itemName`**（改名/重名都会让列错位）。
- **列显隐/列宽/冻结是个人偏好**，存 `localStorage`，key 形如 `payroll.grid.{userId}.{companyId}.cols`。不要调 `PUT /items/{id}/sort`——那是全局管理动作，会影响所有人。
- 新增科目对已生成期间默认不出现；提供「显示全部启用科目」开关供补录（仅 `EDITING` 状态可开）。

### P1-2 必须定义工资项数量上限与性能验收

**问题**
工资项数量没有任何上限。40 列和 120 列是两种产品，而文档的性能指标（§6）只覆盖生成和导入，没有表格交互指标。

**为什么是问题**
`el-table-v2` #23914（>100 列卡顿）是证据；任何表格库的横向滚动、表头分组、编辑焦点都随列数线性劣化。列一多，导出、打印、员工查阅都不可用。

**位置**
§6 性能；`pay_item`。

**建议方案**
- 硬上限：单主体启用项 **≤ 50**（含内置 9 个），超过时在科目管理页阻断并提示合并。
- 软策略：编制台默认「有值列」（本期间有非零金额的列）+ 分组折叠（计算项默认折叠）；用户可切「全部列」。
- 验收指标写进 §6：
  - 2000 行 × 40 列首次渲染 ≤ 2s（内网 Chrome 最新版）；
  - 滚动 ≥ 50fps；单格编辑到重渲染 ≤ 50ms；
  - 筛选/排序切换 ≤ 100ms；
  - 保存 200 条 ≤ 800ms（不含网络）。
- 用 2000 × 40 的合成数据做基准测试，纳入 CI 或至少在 PoC 里留脚本。

### P1-3 权限与列：MVP 不做列级权限；要做就"遮蔽 + 后端不下发"，绝不隐藏

**问题**
数据模型只有行级 `data_scope`，`pay_item` 没有敏感/可见性字段；文档没有回答"没有权限的工资项列是隐藏还是脱敏"。

**为什么是问题**
- 隐藏列会让"可见明细加总 ≠ 应发合计"，财务第一时间会当 bug 报，且无法对账。
- 前端隐藏不等于权限：接口照样下发，F12 就能看到，等于没做。
- 脱敏（`••••`）能保住合计可读，但数据模型还不支持声明哪些列需要遮蔽。

**位置**
§4.7；`pay_item` DDL；§4.8。

**建议方案（明确结论）**
- **MVP 不做列级权限**：有 `record:view` 就可见整行全部金额。敏感字段只有证件号/手机号，按 §4.8 掩码；明文需 `payroll:sensitive:view` + 二次确认。
- 若业务坚持列级遮蔽：在 `pay_item` 加 `visibility_scope`（`ALL / MANAGER / HR_ONLY`）或 `sensitive` 标志；**后端按角色不下发该列或下发 `null`**；前端渲染 `••••`（不是移除列），合计仍按全量计算，并在表尾脚注"合计含 2 项隐藏科目"；导出受同一规则约束。
- 任何情况下都不要用前端 `v-if` 隐藏来实现权限。
- 另外，DDL 种子数据把 `PAYROLL_CLERK` 的 `data_scope` 配成了 `ALL`（`schema-mysql.sql:409-411`），分公司专员默认能看到全集团。前端即使做了主体切换器也不能替代服务端范围校验；UI 上建议在期间列表/编制台显式显示当前数据范围（"上海分公司" vs "集团全部"），让越权配置一眼可见。

### P1-4 三层重复校验的交互：预校验不阻断整批，提交整批失败，服务端返回结构化冲突

**问题**
§4.2 只给了文案模板；四个发生点（预校验、提交、生成、解锁重生成）没有各自的 UI 形态；`GlobalExceptionHandler` 返回的是无结构的 409 文案（`GlobalExceptionHandler.java:35-49`），前端无法逐条展示，也无法"跳过某个人"。

**为什么是问题**
L3 跨主体是"张三同时出现在北京和上海"，用户在自己公司界面无法解决。整批阻断会让 500 行都过不去；静默跳过会漏发。必须让用户逐条看到"是谁、在哪家、什么状态"，并自己决定跳过还是先去处理。

**位置**
§4.2 配套第 2 条；§4.5；`GlobalExceptionHandler.java:35-49`。

**建议方案**
- 扩展 `Result.fail` 支持 `data`，统一冲突结构：
```json
{ "code": 409, "msg": "存在跨主体重复", "data": {
  "conflicts": [{
    "rowNo": 37, "empNo": "E001", "empName": "张三",
    "periodYm": "2026-11", "companyId": "2", "companyName": "上海分公司",
    "periodStatus": "EDITING", "recordId": "9001"
  }]
}}
```
前端用字段渲染，不要把"上海分公司"写死在后端文案里（换主体就错）。
- 冲突信息只下发解决冲突所需的最小字段：姓名、工号、期间、对方主体名、期间状态；**不下发对方金额、编制人、`recordId`**（`recordId` 仅当当前用户有跨主体数据范围时下发）。「查看对方记录」只是入口，服务端必须再校验数据范围，不能靠前端置灰。
- **预校验（不落库）**：不阻断整批。冲突行黄色高亮；冲突卡片逐条显示「张三(E001) 2026-11 已在『上海分公司』工资表（编辑中）」+ 操作 `[跳过此员工]`（默认选中，提交时排除）、`[查看对方记录]`（有跨主体权限才可点，否则置灰 + "联系集团 HR"）；顶部「全部跳过」。
- **提交（并发穿透）**：整批失败（不部分提交），弹窗列出 conflicts；批次保留为 `VALIDATED`，处理后可重新提交。
- **生成**：逐员工结果，失败不阻断其他人；抽屉列出失败员工 + 原因 + 另一主体；需要 `GET /runs/{runId}/failures`（见 P1-6）。
- **解锁重生成**：同一套 UI；额外提示"本期已有锁定记录，重新生成将覆盖手工修改"。

### P1-5 导入模式与空值语义必须说人话，并给变更预览

**问题**
`UPSERT / APPEND / INSERT_ONLY` 是技术名词；空单元格含义未定义；没有"这次会改动哪些人"的预览；`bizType = FIXED` 的导入与薪酬档案版本化的关系也没说。

**为什么是问题**
- "APPEND" 对同一人同一项就是金额翻倍；"空单元格"若被当成 0，会把未填的绩效清零。两种都是多发/少发事故。
- 用户看不到 diff，只能在确认页盲签；"我以为只导 10 个人，结果覆盖了 500 人"是导入类系统最常见的投诉。
- DDL 中 `POST_ALLOW` 是 `FIXED` 且 `importable = 1`——说明固定项也能导入，但它是"只影响本期"还是"改档案"，文档没写。若写成改档案，会和 §4.1 的版本化冲突。

**位置**
§4.5；初始化数据 `pay_item`（`POST_ALLOW` 行）。

**建议方案**
- 模式选择用三张单选卡 + 数字示例：
  - **覆盖 UPSERT**：原 1000，导入 200 → 200；空单元格 → 保持 1000。
  - **累加 APPEND**：原 1000，导入 200 → 1200；空单元格 → 保持 1000；**同一文件重复提交会翻倍**，需二次确认。
  - **跳过 INSERT_ONLY**：原 1000，导入 200 → 1000（只补缺项）。
- 空单元格规则写死并在模板「说明」sheet + 上传页红字提示：**空 = 不修改；要清零必须填 0**。整行无工号的直接忽略。
- **确认页变更预览**：受影响 N 人 / M 格；前 100 条 diff（工号/姓名/科目/原值 → 新值，红降绿升），可下载全量 diff；汇总"应发合计变化 +¥12,345.67"。勾选"我已核对差异"后才允许提交。需要接口 `GET /import/batches/{batchId}/diff?page=`（或在 validate 结果里带前 N 条）。
- **FIXED 导入语义**：模板中 `bizType=FIXED` 仅包含 `importable=1` 的固定项（当前只有 `POST_ALLOW`），并明确「只覆盖本期金额，不改薪酬档案」；若业务要改档案，走「薪酬档案」页面，不要合进导入。
- **员工不在本期**：校验阶段报错 `EMPLOYEE_NOT_IN_PERIOD`，提示"先手工加入本期工资表再导入"（依赖 P1-10 的新增接口）；不要静默新建记录。
- 模板列顺序：`工号(必填) | 姓名(只读参考) | 各可导入科目`；列头带 `item_code`（如 `绩效奖金[PERF_BONUS]`）以抗改名；「说明」sheet 写模式、空值规则、金额格式（最多 4 位小数、禁止千分位/货币符号）。

### P1-6 期间生成的异步体验与失败明细

**问题**
`POST /periods/{id}/generate` 异步返回 `runId`，`GET /runs/{runId}` 只有计数，没有失败清单；生成期间前端没有状态约束。

**为什么是问题**
2000 人生成可能 10–30s，期间用户可能继续编辑/导入；因 L3 冲突、无薪酬档案、主体配置缺失导致的失败必须逐人可见，否则财务不知道少了谁。生成还会 upsert 覆盖手工修改，前端如果不提示就是数据事故。

**位置**
§4.3 ①⑦；§5.3；§6。

**建议方案**
- 触发后全局任务条（右上角，可离开页面）；抽屉显示进度、成功/失败/跳过人数、失败员工表（工号/姓名/原因/另一主体）、`[重试失败]`。新增 `GET /runs/{runId}/failures`。
- 生成中：表格 loading 遮罩，禁用保存/导入/锁定；生成前若有 dirty → 保存/放弃/取消。
- 生成完成：强制刷新 grid；若期间已有手工修改，先弹「重新生成将覆盖以下 N 条手工修改（列出）」。
- 失败原因码化：`NO_COMP_PROFILE` / `DUPLICATE_CROSS_COMPANY` / `DEPT_MISSING` / `PERIOD_LOCKED`，前端按码给不同下一步动作。

### P1-7 合计条：三个口径 + 尾差标注 + 编辑预览

**问题**
§4.4 只说"合计 = 明细加总""展示保留 2 位"，没说前端合计行的范围（全表/筛选）、编辑未保存时怎么显示、尾差怎么标、`include_in_gross = 0` 的科目怎么处理。

**为什么是问题**
筛选后合计不跟着变，财务会以为合计错了；编辑未保存时合计不动，用户无法核对本次修改影响；含隐藏/不计应发科目时合计对不上。合计是这张表最重要的输出。

**位置**
§4.4；需求 3。

**建议方案**
- 固定表尾（sticky bottom，不是表格数据行）：左侧「当前筛选 132 人 / 全表 486 人」；每个金额列显示**当前筛选合计**；右侧应发/扣款/实发三个大字。
- 未保存时合计 = 服务端值 + dirty 覆盖，实时计算（debounce 200ms），并显示「含未保存修改」角标；保存后用服务端响应覆盖。
- 尾差：`|Σ 明细显示值 − gross| ≥ 0.01` 时合计格显示 ⓘ，tooltip「明细显示值加总 ¥X，合计 ¥Y，差 ¥0.01（以合计为准）」，可展开差额来源（按 scale 列出）。
- `include_in_gross = 0` 的列头标「不计应发」，并在表尾脚注列出这些项。
- **公式归属**：前端预览公式必须与后端 `domain.payroll` 同源（同一份公式说明 + 同一组测试用例）；保存响应里的 `gross/net` 是权威，前端只在保存前做预览。

### P1-8 锁定/解锁/编制人角色的界面形态

**问题**
C4 规定"锁定人 ≠ 编制人"，但 UI 没有对应形态；`pay_period.created_by` 是否等于"编制人"（生成人？最后修改人？）未明确；解锁原因的长度/展示位置也未定义。

**为什么是问题**
如果锁定按钮只是"没权限就隐藏"，用户不知道为什么点不了，会去找 DBA。解锁是 C3 唯一的更正路径，交互不清晰会导致绕过系统。

**位置**
§4.6；§4.7 内控约束；§5.3；`pay_period` DDL。

**建议方案**
- 顶部状态条：`2026-11 上海分公司 · EDITING · 编制人：李四 · 最后保存 14:02`；LOCKED 时显示 `锁定人：王五 · 2026-12-01 10:00`。
- 按钮可用性 = 权限 ∧ 状态 ∧ 非编制人。不可用时**不要隐藏**，`disabled` + tooltip 写具体原因：「锁定需由非编制人执行」「本期还有 37 处未保存」「生成任务进行中」。
- 锁定前检查（前端 + 后端）：dirty = 0、无 RUNNING run、无未处理冲突、期间人数 > 0；确认弹窗列出人数与合计金额。
- 解锁：danger 弹窗，原因必填（≥ 10 字），显示"解锁后本期所有人可编辑，操作将记入审计"；解锁后顶部红色横幅「本期已解锁（原因：…），修改后请重新锁定」，直到重锁。
- 只读模式：**不渲染输入组件**（性能和防误触），用纯文本 renderer；隐藏保存按钮。
- 解锁 → 修改 → 重锁后，同一期间会出现两份不同的"2026-11 工资表"。界面必须显示**修订号 / 重锁时间**（如 `修订 2 · 重锁于 2026-12-05 09:12`），编制台、导出文件名、员工工资条都要带上，否则财务和员工手里的两份表无法区分。

### P1-9 Long 全量字符串化与统一响应信封的前端契约

**问题**
`JacksonConfig` 把 `Long/BigInteger/BigDecimal` 全部序列化成字符串。受影响的不只是金额：所有 `id`、分页 `total`、`runId`、`version`、`employee_count` 都是字符串；`Result` 统一 HTTP 200 + `code`；`GlobalExceptionHandler` 的 500 也是正常 JSON。

**为什么是问题**
- Element Plus `el-pagination :total` 要 number；
- 前端写 `if (res.code)` 判断时 `0` 是 falsy，成功分支反而进不去；
- `id === 1` 永远 false；路由参数 `Number(route.params.id)` 后与后端字符串比较出错；
- 金额字符串混进排序会被字典序排；
- 后端 `BigDecimal` 从字符串反序列化是精确的（Jackson 支持），但前端一旦发送 number，精度在发出前就丢了。

**位置**
`JacksonConfig.java:22-25`；`common/Result.java`；`GlobalExceptionHandler.java`。

**建议方案**
- 前端 `types/api.ts` 固定：`type Id = string; type Money = string; type Count = number`（`Count` 在拦截器里 `Number()` 转换，计数远小于 2^53，安全）。
- axios 拦截器：`if (body.code !== 0) throw new ApiError(body.code, body.msg, body.data)`；HTTP 200 但 `code ≠ 0` 也走错误分支；HTTP 500 同样解析 `Result`。
- `el-pagination :total="Number(page.total)"`；`current/size` 用 number。
- ID 全链路 string：Pinia key、`Map` key、路由参数、`===` 比较、`row-key`。
- 金额排序用 Decimal comparator（P0-3）。
- 后端把 `Result.fail` 扩展为 `fail(code, msg, data)`，否则 P1-4 的结构化冲突无处安放。

### P1-10 记录级操作缺失：加人、移除、备注、重算

**问题**
文档没有"手工新增一名员工到本期""把某行从本期移除""改行备注"的接口和 UI。`pay_record.remark`、`deleted`、`POST /records/{id}/recalculate` 都在，但只有重算被暴露。

**为什么是问题**
生成按"期间末在职"口径跑，现实里一定会有：新入职没进系统、离职日期填错、借调人员本不该发、某人本月不发需要移除。没有移除就只能把金额清零——但记录仍占用 `uk_emp_ym_active`，还会出现在汇总人数里；没有新增就只能改主数据后全量重生成，影响其他人。

**位置**
§4.3 ①；§5.3；`pay_record` DDL。

**建议方案**
- 新增 `POST /periods/{id}/records`：手工加人（校验主体/期间状态/跨主体重复），`source = MANUAL`。
- 新增 `DELETE /records/{id}`：软删 `deleted = 1`（释放 `active_key`），写审计；UI 行操作「移出本期」，二次确认并说明"该员工本期将不计入汇总"。
- `PATCH /periods/{id}/records` 支持 `remark`（行备注 ≤ 200 字）；行尾图标提示。
- 行操作菜单：`重算 / 备注 / 移出本期 / 查看变更历史`。
- 若业务确认"本月不发"用清零即可，删除接口仍应保留（离职口径错误时需要）。**若业务确认 MVP 必须有"移出本期"，本条升级为 P0。**

## 4 P2（可排期）

### P2-1 查看审计的触发策略
§4.7 要求"查看他人工资写查看审计"。若按行写，编制台一次加载 500 行 = 500 条审计，切筛选/刷新会持续放大，审计表很快不可读。建议：进入期间写一条 `VIEW_PERIOD`（含人数、数据范围）；明文查看敏感字段、导出各一条；前端不要做后台自动轮询刷新。位置：§4.7(3)、§5.6。

### P2-2 导出的交互与范围
`POST /reports/export` 只有一句。建议导出弹窗明确：范围（当前筛选 N 人 / 全表 M 人）、内容（工资表/明细/汇总）、格式（xlsx）；有 dirty 时强制先保存；异步任务 + 进度 + 下载；文件名 `工资表_上海分公司_2026-11_20261126.xlsx`；导出记录进审计并可在"导出历史"重下。位置：§5.5。

### P2-3 Grid 效率增强
MVP 至少要有：方向键/Tab/Enter/Esc、Ctrl+S、编辑中 Esc 取消。P2 再加：从 Excel 粘贴一块（解析 TSV/HTML，`new Decimal` 解析，按当前单元格向下填充，数量不符给提示）、Ctrl+D 向下填充、50 步撤销/重做、复制选中区域。粘贴在 vxe-table 属企业版，可自研或买授权。位置：需求 3。

### P2-4 内网离线与浏览器基线
明确支持 Chrome / Edge 最近两个大版本（Vue 3 + Element Plus 不支持 IE，内网若还有 IE/360 兼容模式必须提前说）。所有图标、字体、静态资源本地打包，不能依赖 CDN；vxe-table v4.7+ 依赖 `vxe-pc-ui`，版本要配对并锁死；npm 依赖走内网私服或离线 tgz。位置：§1、§6「离线构建」。

### P2-5 空状态
四种必须区分：期间未生成（引导「生成基础数据」）、生成 0 人（检查主体/在职口径）、生成全部失败（跳失败明细）、筛选无结果（清空筛选按钮）。位置：§4.6。

### P2-6 编辑器按 `data_type` 渲染
`pay_item.data_type` 有 `AMOUNT/HOURS/DAYS/RATE`，本期只用 `AMOUNT`，但字典可配。组件按 `data_type` 选择编辑器/小数位/单位后缀，不要把金额写死在单元格里。位置：`pay_item` DDL、§4.3 注。

### P2-7 0 / 空 / 删除行的显示语义
"没有该明细行"和"`amount = 0`"是两件事：建议无行显示空白（不适用），0 显示 `0.00`，hover 显示来源（`FIXED/IMPORT/MANUAL/COMPUTED`）；删除单元格 = 删除该明细行（changeset 的 `removeItems`），不是写 0。合计两者等价。位置：`pay_record_item`、§4.4。

### P2-8 错误报告下载细节
中文文件名、Blob 下载、失败重试；超过 5000 行截断时报告首页写明"仅列前 5000 条，完整原因见汇总"；报告包含「建议修正值」列。位置：§4.5。

### P2-9 响应式与移动端
明确 MVP 不支持手机编辑，最小分辨率 1280×800；工资条页面可用到 1024。避免团队在 MVP 投入响应式。位置：全局。

### P2-10 列宽与数字排版
表头列宽按 `item_name` 长度计算 min/max；金额列右对齐、`font-variant-numeric: tabular-nums`；超长表头截断 + tooltip；列头带单位；列宽拖拽后持久化（与 P1-1 的个人偏好同 key）。位置：§1。

### P2-11 单行变更历史
行操作里的「查看变更历史」展示该记录最近 N 次金额变更（来自 `pay_audit_log`），用于对账。MVP 可只做只读弹窗。位置：§4.7、`pay_audit_log` DDL。

### P2-12 明细级备注 / 事由
`pay_record_item` 没有备注字段，只有记录级 `pay_record.remark`。财务导入绩效/奖金时通常要带事由（"Q4 项目奖"），事后对账和员工答疑都需要。若要支持：加 `pay_record_item.remark`，导入模板加可选「事由」列，编制台单元格 tooltip 显示；否则明确不支持，避免模板里出现一个存不下的列。位置：`pay_record_item` DDL、§4.5。
