# 22 · 角色验收：部门主管（DEPT_MANAGER）

- 验收对象：工资核算系统（后端 `http://127.0.0.1:8080/api/v1`，前端 `http://localhost:5175`）
- 验收日期：2026-11-27
- 验收视角：**研发部门主管**——只想看本团队的人力与成本，不应看到其他部门数据，更不应看到全公司合计或与己无关的个人明细工资。
- 验收方式：自建真实 `DEPT_MANAGER` 账号，前端逐页走查 + `curl --noproxy '*'` 直连接口复核；所有写操作与跨范围读操作均实测。

- 测试账号：`rol_mgr_6568`（roleIds=[3]，dataScope=DEPT_SUB，deptId=8 北京研发中心），**验收结束后已通过 `DELETE /users/24` 删除并确认列表为空**。

## 0. 结论摘要

| 严重度 | 问题 | 证据 |
|---|---|---|
| **高** | **未锁定（EDITING）期间的部门合计与全部个人明细对主管可见**。评审文档《05-前端交互》§267 明确建议部门主管只看 LOCKED/ARCHIVED，草稿需单独权限点；实际 `payroll:record:view` 一个权限点同时放开了锁定与未锁定数据 | `GET /periods/24/grid`（2029-02，EDITING）返回 232 行、合计 4,430,767.00 |
| **高（业务口径）** | **主管可看下属每个人的工资明细**（基本工资、津贴、工龄工资、各项奖金/扣款，以及「薪酬档案」里的调薪历史）。系统只有记录级数据范围，没有「部门汇总但不可见个人」的权限粒度；安全评审 §487/§498 已提出该问题但未落地 | `GET /employees/13/comp-profiles` → 基本工资 11,400.00；编制台 232 行逐人科目 |
| 中 | 人员管理的「部门」下拉列出**全公司 14 个部门**（含北京/上海/深圳各中心），选择非本部门后返回空列表。组织架构信息外泄 + 交互困惑 | 下拉选项实测；`GET /employees?deptId=9` 返回 `total=0` |
| 低 | `GET /runs/{runId}` 只校验「期间所属公司」，不校验部门；主管可读取本公司其他部门生成批次的跳过工号与原因 | `run 5/6/7/11` 返回 `T902/T910/... 未配置薪酬档案` |
| 低 | 落地页是「工资期间」财务视角清单；顶部直接显示 `DEPT_SUB` 原始枚举；页面提示「锁定人不能是本期编制人（内控 C4）」「解锁必须填写原因」对主管毫无意义 | 截图与 DOM |
| 低（全局） | `GET /periods/{id}` 对所有角色均 500（该路由未在 OpenAPI 中定义，落到兜底异常）。前端未调用，不影响本角色主流程 | hr01 / admin / 主管均 500 |

**一句话**：**没有发生跨部门或全公司金额越权**（这是最重要的底线，接口层守住了）；但**「未锁定期间的金额」和「下属个人明细」两个口径对主管开放过宽**，且这个角色目前**只能看、不能做任何团队管理动作**，缺少几乎所有主管真正需要的分析能力。

## 2. 登录后第一印象

### 2.1 落地页

登录后落在 **`/periods`（工资期间）**，不是部门概览。合理性：**一半合理、一半不合理**。

- 合理：主管确实关心「本月/上月发了多少」，期间列表直接给出本部门的人数和应发/实发合计。
- 不合理：
  1. 这是**薪酬专员视角的财务台账**（状态机、编制台入口、锁定/解锁规则），不是主管视角的「我的团队」；
  2. **页面没有任何「当前显示的是北京研发中心」的标识**。同一页面 HR 看到的是 1874 人 / ¥36,520,605.92，主管看到 232 人 / ¥4,404,300.00，仅凭界面无法区分口径，极易误读为全公司数据；
  3. 顶部标签直接显示内部枚举 `DEPT_SUB`；
  4. 提示语「锁定人不能是本期编制人（内控 C4）；解锁必须填写原因并写审计」与主管无关（他既不能锁也不能解锁）。

建议：部门主管落地到「团队概览」（本部门人数、本月应发、环比、与编制对比），或在现有页面显著标注「数据范围：北京研发中心」。

### 2.2 左侧菜单（实际）

| 菜单 | 是否该有 | 评价 |
|---|---|---|
| 人员管理 | 该有 | 只显示本部门人员，符合预期；但「薪酬档案」入口暴露个人工资明细（见 §3.1） |
| 工资项 | **不该有** | 全公司工资科目主数据（含 `T_TIEM_A/B`、`P0~P4`、`T_USED`、`PXN` 等测试科目），对只读主管是纯噪音 |
| 工资期间 | 该有 | 本部门合计正确，但含未锁定期间（见 §3.2） |
| 月度报表 | 该有 | 范围正确，仅本部门一行 |
| 年度报表 | 该有 | 范围正确，仅本部门一行 |
| 系统管理（用户/角色/部门/主体/参数） | **正确地没有** | 接口也全部 403，双层一致 |

**该有却没有的菜单**：团队概览 / 我的团队、人力成本分析（趋势、人均、编制 vs 实际）、人员流动（入离职）。详见 §6。

### 3.3 编制台

- 路由 `/periods/24/grid` 可进入，数据**只有本部门 232 行**（`deptName` 全为北京研发中心），合计 4,430,767.00。

## 4. 可执行操作

**结论：部门主管当前是纯只读角色，所有写操作在接口层均被拒绝。**

| 操作 | 期望 | 实际 |
|---|---|---|
| 新增人员 | 拒绝 | 403；按钮不渲染 |
| 编辑人员 | 拒绝 | 403；按钮不渲染 |
| 修改薪酬档案 / 调薪 | 拒绝 | 403 |
| 新建期间 / 生成工资 / 改核算记录 | 拒绝 | 403 |
| 锁定 / 解锁期间 | 拒绝 | 403 |
| 导入工资数据 | 拒绝 | 403；菜单入口不显示 |
| 导出报表 | 拒绝 | 403；按钮不渲染 |
| 用户/角色/参数管理 | 拒绝 | 403；菜单组不渲染 |

**「如果给了编辑权限，会不会能改下属工资？」** 会是，而且**只能改本部门**：

- `EmployeeService.update`、`CompProfileService.create/update`、`RecordService.update` 都先过 `assertEmployeeVisible` / `assertRecordVisible`（代码位置：`EmployeeService.java:115/222/265`、`CompProfileService.java:56/135`、`RecordService.java:155`），DEPT_SUB 只能命中本部门子树。
- 因此即使给主管加 `payroll:record:edit`，他也改不了别部门工资，但**可以改自己下属的工资**。从薪酬内控角度这通常不可接受（编制与审批职责分离），建议不要用「数据范围」来替代「职责分离」：主管角色应保持无写权限，如确需主管维护考勤/绩效，应拆出只影响变动项、且进入复核流程的独立权限点。

## 5. 问题清单（按严重度）

### P1 · 未锁定期间的工资对主管可见

- 现象：`payroll:record:view` 同时覆盖 LOCKED / EDITING / DRAFT。实测 2029-02（EDITING）主管可见 232 人、合计 4,430,767.00，并可进编制台逐人查看。
- 影响：未经复核、随时会变动的金额提前暴露，容易造成「主管看到的数」与最终发放不一致；也不符合评审文档给出的口径建议。
- 建议：给 `record:view` 增加期间状态维度（默认仅 LOCKED/ARCHIVED），草稿另设 `payroll:record:view:draft`；或按角色配置可见期间状态。

### P1（业务口径）· 主管可见下属个人明细工资

- 现象：人员管理 →「薪酬档案」显示基本工资 11,400.00 与调薪历史；编制台显示 232 人全部工资科目。
- 影响：与「部门主管只应看团队成本」的最小权限原则冲突；安全评审 §487/§498 已建议改为「默认只看部门汇总，个人明细需单独权限并审计」，但未实现。
- 建议：
  1. 新增 `payroll:record:view:dept-summary`（只给汇总）与 `payroll:record:view:detail`（个人明细，需审计）；
  2. DEPT_MANAGER 默认只拿汇总；编制台对该角色隐藏金额列或只显示合计；
  3. 若业务坚持可见，至少在查看明细时写入审计（当前 `audit` 包只记录导出/年度查看等动作）。

### P2 · 部门下拉暴露全公司组织架构

- 人员管理、月度/年度报表的「部门」筛选都返回 14 个部门名。虽然选他部门只会得到空列表（不越权），但对主管是无意义信息，也暴露了公司组织划分。
- 建议：DEPT_SUB 用户的部门下拉只返回本部门子树；报表同理。

### P2 · `/runs/{id}` 缺少部门维度校验

- 任何本公司期间的生成批次都可读，返回 `skipped` 中的员工工号与失败原因（如 `T902 未配置薪酬档案`）。不含金额，但属跨部门人员信息。
- 建议：`GenerateService.progress` 在 `assertPeriodVisible` 之后，对 DEPT_SUB 再按 run 的记录/员工过滤，或只返回聚合数字。

### P3 · 登录体验与术语

- 头部 `DEPT_SUB` 原始枚举；「工资项」菜单对只读主管是噪音；期间页 C4 提示无关；没有「当前部门」标识。

## 6. 主管真正需要、系统没有的功能（逐项实测）

| # | 需求 | 能否做出来 | 实测结论 |
|---|---|---|---|
| 1 | **团队薪酬总额趋势**（近 6/12 个月） | ❌ | 只有单期间 `reports/monthly` 和单年度 `reports/annual`；无跨期间聚合接口，前端无图表。只能人工逐月查询 6 次 |
| 2 | **人均成本** | ❌（可手算） | 无 `人均` 字段/接口；只能自己用 4,441,607.49 ÷ 225。报表页不展示 |
| 3 | **编制 vs 实际** | ❌ | 全库无编制/headcount/quota 字段（`grep -rn "编制|headcount|quota|establishment"` 仅命中「编制台/编制人/编制中」），无任何编制数据来源 |
| 4 | **本月 vs 上月对比 / 环比** | ❌ | 月度报表一次只查一个期间；年度报表只按年；无对比视图或同比/环比指标 |
| 5 | **离职率 / 人员流动** | ⚠️ 部分 | 人员管理可按「离职」筛选（本部门 14 人），但无比率、无按月趋势、无入离职统计报表；月度/年度报表只统计工资，不含人员流动 |
| 6 | **导出团队报表** | ❌ | `POST /reports/export` → 403，按钮隐藏。主管无法把团队成本导出给上级/财务 |
| 7 | **团队概览仪表盘** | ❌ | 无此页面；落地页是期间台账 |
| 8 | **薪酬结构/职级分布** | ❌ | 年度报表 `groupBy=EMP` 只到个人，`groupBy=DEPT` 只到部门；无按职级/岗位/员工类型的聚合 |
| 9 | **预算/成本预警** | ❌ | 无预算字段、无阈值告警 |
| 10 | **团队成员异动明细**（新入职、调薪、离职） | ⚠️ 部分 | 人员列表可看到入职日期/状态，薪酬档案可看到调薪历史，但没有「本期异动」汇总 |
| 11 | **子部门切换 / 组织树** | ⚠️ | DEPT_SUB 在数据层支持子树（ancestors），但前端只有一个扁平部门下拉，且包含全公司部门 |

## 7. 可用性评分

**6 / 10**

- **加分**：数据范围在接口层守住了底线——没有跨部门、没有全公司合计、没有提权路径；所有写操作 403；前端按权限隐藏按钮，双层一致。
- **扣分**：
  1. 主管最关心的四件事（趋势、人均、编制对比、环比）一个都没有，导出也被禁；
  2. 开放了未锁定期间的金额和下属个人明细，权限粒度与「部门主管」职责不匹配；
  3. 落地页与话术是财务/HR 视角，`DEPT_SUB`、C4 提示、全公司部门下拉都在增加困惑。

**改进优先级建议**：
1. （P1）`record:view` 按期间状态收口，主管默认仅 LOCKED/ARCHIVED；
2. （P1）拆分「部门汇总」与「个人明细」权限，默认只给汇总，明细查看写审计；
3. （P2）部门下拉/报表筛选只返回本部门子树；
4. （P2）新增「团队概览」页：本月人数、应发合计、环比、人均，再加一条 6 个月趋势；
5. （P3）给主管开放「导出本部门汇总」（不含个人明细），并修正头部枚举与无关提示。
