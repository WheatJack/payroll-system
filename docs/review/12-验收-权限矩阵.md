## 0. 结论摘要

| 类别 | 数量 | 明细 |
|---|---|---|
| 越权（该 403 / 该受限却放行） | **3** | 期间合计泄漏（高）；低权管理员可降级/停用/删除更高权管理员（高）；种子角色数据范围 ALL（中） |
| 功能不可用（该 200 却 403 / 死权限） | **3** | SYS_ADMIN 无法分配任何薪酬角色（高）；解锁权限无人持有（高）；落地页缺两条路由（低） |
| 无 token 访问（认证漏洞） | **0** | 除 `POST /auth/login` 外，全部端点无 token 均 401 |

**最严重的三个问题**

1. **期间列表的合计金额对 SELF / DEPT_SUB 用户回落为"全公司口径"** —— 当该用户在某个期间没有任何可见记录时，`totalGross/totalNet/employeeCount` 直接下发 `pay_period` 的全公司合计。实测：一个 SELF 账号（未关联员工）与一个 DEPT_SUB 账号（部门下无员工）都能在 `GET /periods` 看到 `3 人 / ¥28,200.00`，而 `GET /employees`、`GET /periods/1/grid` 对它们返回 0 行。这正是任务要求重点复查的"totalGross 不能是全公司"。
2. **系统管理员无法为用户分配任何薪酬角色，导致无法通过 API 开通薪酬岗账号** —— `SYS_ADMIN` 只持有 `sys:*`，服务端的"授权权限点必须是操作者自身子集"规则使其对 `POST /users {roleIds:[1|3|4]}` 一律返回 403（实测 `不能授予自己未持有的权限点：payroll:export`）。全系统只有 SYS_ADMIN 能进 `/users`，而没有任何角色同时持有 `sys:user:edit` 与 `payroll:*`，因此"新建薪酬专员/复核/员工账号"在正常界面上是死路，只能靠直接写库（本次验收即被迫如此）。这与安全评审"系统管理员能建账号，但看不到工资"的设计前提冲突。
3. **低权管理员可以降级、停用、删除权限更高的管理员账号** —— `UserAdminService.update()` / `delete()` 没有调用 `assertCanManageAccount()`（只有 `resetPassword()` 调了）。实测一个 COMPANY 范围、仅持有 `sys:user:view/edit + sys:role:view/edit` 的"受限管理员"账号，对持有 SYS_ADMIN 的同主体账号执行 `PUT /users/10 {roleIds:[自己的低权角色]}`、`PUT status=0`、`DELETE` 全部返回 200（成功）。它虽然不能给自己提权（`resolveRoles` 仍限制子集），但可以清除/瘫痪权限更高的账号，属于管理面的横向越权。

### 2.2 矩阵结论

- **功能权限本身没有发现"该 403 却 200"**：每个端点的鉴权结果与 `@RequirePerm` 声明严格一致；越权问题出在**数据范围**与**服务层内控**（见第 3、5 节）。
- 确认**无认证漏洞**：48 个端点中除登录外，无 token 全部 401；伪造 token 亦 401。
- `GET /employees/{id}` 的 403（dmgr 访问别部门员工、viewer 访问任意员工）说明数据范围在**详情读**上生效。
- `SYS_ADMIN` 对全部 `payroll:*` 端点 403，属于**有意设计**（见第 6 节），不计为缺陷；但其带来的账号开通死结见 F-2。

## 6. 重点复查项

### 6.1 `GET /depts`、`GET /companies` 是否"登录即可读"？

**是，且这是当前实现与契约一致的行为。**
- 两者均无 `@RequirePerm`；实测 6 个角色（含 SELF 员工）均 200，无 token 401。
- 但并非无约束：`DeptService.tree()` 先 `assertCompanyVisible(companyId)`；`CompanyController.list()` 对非 ALL 账号强制 `id = current.companyId()`。即"登录可读，但只能读本主体"。
- 与 `DeptController`/`CompanyController` 注释一致（曾误挂 `payroll:record:view` 导致"能改部门却读不到部门"）。

### 6.2 admin 是否仍无法访问 `/periods/1/grid`？是有意设计吗？

**是，401 之外的 403 属有意设计。**
- 实测 `admin → GET /periods/1/grid` = 403。
- 设计依据：`db/schema-mysql.sql` 注释"只授予 sys:*：薪酬专员不该能改用户和角色（三权分立）"；`frontend/src/utils/landing.ts` 注释"SYS_ADMIN 没有 payroll:record:view"；`docs/review/03-安全合规.md` §4.1 角色矩阵对系统管理员"明确禁止：任何 `payroll:record:*`"。
- **不建议给 admin 例外**（会破坏"能改权限的人不读工资"的内控）。真正要修的是它带来的账号开通死结（F-2），而不是让 admin 读工资。

## 7. 缺陷清单

### F-1（高 · 越权）期间列表合计金额对 SELF/DEPT_SUB 用户泄漏全公司口径

- **证据**：DEPT_SUB（D002，无下属员工）与 SELF（未关联员工）账号：`GET /employees` = 0 条、`GET /periods/1/grid` = 0 行，但 `GET /periods` 返回 `2027-03 → employeeCount=3, totalGross=28200.00`、`2027-02 → 3, 28100.00`。
- **位置**：`src/main/java/com/insbean/payroll/period/PeriodService.java`
  - `visibleAggregates()`（L87 起）仅对非 ALL/COMPANY 范围重算，且只返回**有记录**的期间分组；
  - `toScopedDto()` L118–123：`if (aggregate == null) return dto;` —— 此处 `dto` 是 `toDto(period)`，即 `pay_period.total_*` 的全公司值。
- **影响**：工资合计/人数属敏感聚合。任何"范围受限但当前无可见数据"的账号（新调岗、空部门、未关联员工的 SELF 账号）都能持续看到全公司每期合计。
- **建议**：把"范围内无记录"与"未做受限重算"区分开。受限账号在 `aggregate == null` 时应输出 `employeeCount=0, totalGross=0, totalNet=0`（或显式 null），绝不回落到实体行。

### F-2（高 · 功能不可用）SYS_ADMIN 无法为用户分配任何薪酬角色 → 无法开通薪酬岗账号

- **证据**：`POST /users {roleIds:[1]}` → 403 `不能授予自己未持有的权限点：payroll:export`；`roleIds:[3]` → 403 `...payroll:record:view`。而 `/users` 仅 SYS_ADMIN 可进，且没有任何内置角色同时具备 `sys:user:edit` 与 `payroll:*`。
- **位置**：`src/main/java/com/insbean/payroll/admin/UserAdminService.java` L245（`ScopeGuard.assertPermissionsWithinOperator`）；同类限制在 `RoleAdminService.create/replaceGrants`。
- **影响**：新装环境只能靠手工写库开通薪酬岗；这与 `03-安全合规.md` P0-6"系统管理员能建账号，但看不到工资"的前提直接冲突。本次验收的测试账号即因此被迫直接写 `sys_user_role`。
- **建议**（设计层面）：区分"授出权限"与"持有权限"。允许持有账号管理权（如新增 `sys:role:assign` 或复用 `sys:user:edit`）的账号把**预置的**薪酬角色授予他人，同时保持其本人不可读工资；该动作必须强审计，并加"授权不得使自己获得读工资能力"的不变量（启动自检 `users(读工资) ∩ users(改账号) = ∅`）。

### F-3（高 · 越权）用户 update/delete 缺少"不得管理更高权账号"校验

- **证据**：COMPANY 范围的 auditor 对 SYS_ADMIN 账号 10：`PUT {roleIds:[7]}` → 200（降级）、`PUT {status:0}` → 200（停用）、`DELETE` → 200（删除）。
- **位置**：`UserAdminService.update()`（L144–204）、`delete()`（L190–204）均未调用 `assertCanManageAccount()`；该私有方法仅在 `resetPassword()` L213 被调用。
- **影响**：低权管理岗可对更高权管理员实施"降级/停用/删除"，属于管理面横向越权（内部威胁），也是拒绝服务面。
- **建议**：在 `update()`（当目标非本人且涉及 roleIds/status/dept 变更时）与 `delete()` 中同样调用 `assertCanManageAccount(target, me)`；并补一条单测覆盖"低权管理员不得停用/删除更高权账号"。

### F-4（高 · 功能不可用）`payroll:period:unlock` 未授予任何角色，解锁永久 403

- **证据**：`POST /periods/1/unlock` 对 admin/hr01/hr02/dmgr/self/viewer **全部 403**；`sys_role_grant` 中不存在任何 `payroll:period:unlock` 授权。
- **位置**：`db/schema-mysql.sql` L466–476（内置角色授权）；控制点 `PeriodController.unlock`。
- **影响**：期间一旦 LOCKED，任何更正流程（"解锁 → 修改 → 重锁"）在 API 层均不可执行；且因 F-2，管理员也无法创建/授权一个持有该权限点的薪酬角色，形成死结。设计文档明确要求复核岗应持有 unlock（`03-安全合规.md` §4.1、P0-7）。
- **建议**：给 `PAYROLL_REVIEWER` 补 `payroll:period:unlock`（与 lock 同岗、与 edit/import 互斥），或明确提供一个可被授权的"解锁岗"角色。

### F-5（低 · 功能不可用）前端落地页清单缺两条路由

- **证据/位置**：`frontend/src/utils/landing.ts` 的 `LANDING_ROUTES` 未含 `/system/config`（`sys:config:view`）与 `/periods/:id/import`（`payroll:import:submit`）。
- **影响**：仅持有上述权限点的自定义角色登录后落到 `/no-access`（路由本身可手动进入，不构成越权）。
- **建议**：把 `/system/config` 加入清单；导入页依赖期间 id，可保持现状但在兜底页提供可达入口，或把 `import:submit` 视为 `record:view` 的从属权限。

### F-6（中 · 越权风险/种子数据）PAYROLL_CLERK / PAYROLL_REVIEWER 的 dataScope 为 ALL

- **证据**：`db/schema-mysql.sql` L466–469 种子：两个角色 `data_scope='ALL'`。
- **对照**：`docs/review/03-安全合规.md` P0-5 修复项 6 明确"种子数据把 `PAYROLL_CLERK`/`PAYROLL_REVIEWER` 改为 `COMPANY`"；§4.1 矩阵亦为 COMPANY。
- **影响**：当前单主体环境无可见差异；多主体部署时，编制/复核岗将默认看见集团所有主体的工资数据，属最小权限违背。
- **建议**：种子改为 COMPANY，需要集团口径时由 `sys:role:grant:all` 显式授予 ALL。
