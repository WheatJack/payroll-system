# 工资核算系统 · 详细设计

> 状态：设计稿 v0.3 ｜ 日期：2026-11-26
> 范围：主数据 → 薪酬档案 → 期间 → 核算编制 → 导入 → 重复检测 → 权限 → 月/年汇总导出
> 不含：个税、五险一金、银行代发、考勤/绩效对接

---

## 0 需求原文（追溯基线，勿改写）

> **需求 1**：建立统一的人员数据管理，包含人员姓名、性别、工号、证件号码、手机号码、员工类型、职级、工龄、基本工资等信息。
>
> **需求 2**：支持自动生成工资基础数据表（固定项按人员数据管理的初始化的薪酬相关信息自动带出）。
>
> **需求 3**：编制工资表，提供固定数据和变动数据（绩效、工时工资等）的导入和编辑更新功能，实现筛选搜索功能。
>
> **需求 4**：在特定环节支持重复发放检测功能：同一人在同一个期间只允许存在一条有效核算记录。
>
> **需求 5**：区分工资查询权限，支持月度和年度工资汇总查询和导出功能。

**口径说明**：需求 3 原文提到"工时工资"，经确认（C2）本期导入的是**工资金额**，系统不做工时×时薪反算。原文保留不改，以本节说明为准。

需求覆盖对照见 §1.3。

## 4 核心设计

### 4.1 薪酬档案的生效区间

**问题**：需求 2 要求「固定项从人员数据带出」，但基本工资会调。若人员表只存当前值，8 月的工资表在 9 月调薪后重算就会变。

**方案**：`emp_comp_profile` 一行 = 一段生效区间。

```
employee_id | effective_from | effective_to | base_salary
1           | 2024-03-01     | 2025-06-30   | 8000
1           | 2025-07-01     | NULL         | 9500
```

- 取数规则：`effective_from <= 期间末日 AND (effective_to IS NULL OR effective_to >= 期间末日)`。
- **基本工资单独建模成 `base_salary` 列，不混进通用科目**：它是加班费、经济补偿金的法定计算基数，语义特殊，不能被业务随意删改。
- 其余固定津贴（岗位津贴、通讯补贴等）走 `emp_comp_profile_item`，科目可配置。
- 区间不重叠由应用层校验 + `uk(employee_id, effective_from)` 兜底。

**界面上不暴露「版本」概念**：人员详情页只呈现「当前生效薪酬」+ 一条调薪历史时间线。用户点「修改」时，后端把旧区间截断、新建一条，生效日期默认次月 1 日且可改。操作体验就是普通表单编辑，但历史工资表永远不会被改写——这是「可以修改基本工资」和「历史不可变」能同时成立的唯一方式。

### 4.2 需求 4：重复校验的三层防线（本系统最硬的约束）

**「同一人同一期间只允许一条有效核算记录」** —— 在多法人场景下必须拆成三层，少一层就有漏洞：

| 层 | 场景 | 拦截手段 | 时机 |
|---|---|---|---|
| **L1 文件内重复** | 同一张导入表里同一个人出现两行 | 应用层按工号分组，重复即报错并列出冲突行号 | 预校验阶段，不落库 |
| **L2 本主体本期重复** | 同一分公司同一月份重复生成 / 重复导入 | 唯一索引 + `ON DUPLICATE KEY UPDATE` | 落库 |
| **L3 跨主体同月重复** | 张三 2026-11 同时出现在北京和上海的工资表里 | **集团级唯一索引** | 落库 |

L3 才是真正的"重复发放"风险。按 `period_id` 建索引**拦不住**——期间是按主体拆的，两家公司的 `period_id` 不同。索引必须建在 `(employee_id, period_ym)` 上，因此要把 `period_ym` 冗余进核算记录：

```sql
deleted    TINYINT NOT NULL DEFAULT 0,
period_ym  CHAR(7) NOT NULL,
active_key TINYINT AS (IF(deleted = 0, 1, NULL)) STORED,
UNIQUE KEY uk_emp_ym_active (employee_id, period_ym, active_key)
```

利用「NULL 不参与唯一约束」：有效行互相冲突，已删除行互不干扰，历史版本得以保留。

> PostgreSQL 变体：`CREATE UNIQUE INDEX uk_emp_ym_active ON pay_record(employee_id, period_ym) WHERE deleted = 0;`

配套三条，缺一不可：

1. **批量生成幂等，禁止用 `ON DUPLICATE KEY UPDATE`**。唯一键是集团级的，撞键意味着命中的是**别家公司**的记录，盲目 upsert 会把它原地改写——防重复的保险反而变成跨主体静默覆盖。正确做法：
   ```sql
   -- 1) 先按本主体本期间取出已有记录（company_id + period_id 双条件）
   SELECT id, employee_id FROM pay_record
    WHERE period_id = ? AND company_id = ? AND deleted = 0 FOR UPDATE;
   -- 2) 已存在 → 按主键 UPDATE；不存在 → INSERT
   -- 3) INSERT 撞 uk_emp_ym_active → 抛 DuplicateKeyException，翻译成"该员工本月已在某分公司"
   ```
   这样"本主体本期重复"走 UPDATE 幂等，"跨主体同月重复"走异常提示，两条路互不干扰。
2. **报错要能定位到"另一家分公司"**：捕获 `DuplicateKeyException` 后回查该员工同月的有效记录，提示「张三(E001) 2026-11 已在『上海分公司』的工资表中」。只报"重复"没用，财务不知道去哪找。
3. **解锁更正同样受约束**：解锁后重新生成也过这三层，不能因为解锁就绕过。

### 4.3 计算引擎

三类工资项，一条流水线：

```
① 加载    期间内在职/离职员工 × 期间末生效的薪酬档案（按员工当期归属主体分组）
② 派生    工龄（按期间末日计算）
③ 固定    基本工资 + 档案固定津贴 → FIXED 明细
④ 变动    导入/手工录入的**金额**直接落 VARIABLE 明细（绩效、加班工资、奖金、扣款）
⑤ 计算    工龄工资、应发合计 = Σ增项 − Σ减项 → COMPUTED 明细
⑥ 汇总    记录级合计 = 明细直接加总（见 4.4）
⑦ 落库    分批 upsert，每 500 条 flush，避免大事务
```

> **C2 的影响**：变动项导入的是金额，系统**不做工时 × 时薪的反算**。因此本期的计算项只有「工龄工资」和「合计」，计算引擎比原设计简单得多。分录里仍保留 `quantity/unit_price` 字段，是为将来接考勤系统预留，本期不使用。

#### 4.3.1 已确认的计算规则（2026-11-26）

| 规则 | 定义 | 边界 |
|---|---|---|
| 日工资 | `月基本工资 ÷ 21.75` | 中间结果保留 10 位，**只在落明细时舍入一次** |
| 全月在职工资 | `月基本工资` | 不做折算 |
| 入职当月 | `日工资 × 实际计薪天数`（自入职日起算） | 入职日在期间内才触发 |
| 离职当月 | `日工资 × 实际计薪天数`（至离职日止） | 离职日在期间内才触发 |
| 固定津贴 | 全月足额；当月不足月时**同比折算** | 与基本工资同口径 |
| 工龄工资 | `工龄年数 × 100 元` | 工龄 = 期间末日与入职日期的**整年数**（向下取整）；不足一年为 0 |
| 变动项 | 导入/录入金额原样计入 | 不折算、不二次计算 |
| 合计 | `Σ增项 − Σ减项`，**明细直接加总** | 绝不二次舍入，见 §4.4 |
| 同月多条任职 | 取 `start_date` 最大的一条（最新主体） | 整月归属，不做按天分割 |

**尚未定义、实现前需补**：工龄工资是否有封顶、是否满整年才发（当前按满整年发放，无封顶）。

**计算策略接口**（`domain.payroll.ItemCalculator`）：每个 COMPUTED 科目一个实现，MVP 用 Java 类硬编码，后续可换成表达式引擎而不动主流程。

**计薪天数**：默认 21.75（月平均计薪天数）。月中入职/离职、停薪留职的折算规则做成期间级参数，不写死在代码里。

### 4.4 金额铁律：合计永远等于明细加总

这是财务对账的底线，也是薪酬系统最常见的线上事故来源。

- 明细项落库前按各自 `precision_scale` 四舍五入（`HALF_UP`）。
- **合计不做二次舍入**，直接 `SUM(明细)`。
- 只剩一处需要尾差处理：跨科目配平（如按比例分摊），此时生成一条 `ADJ_ROUNDING` 科目的调整明细，**绝不偷偷塞进某一项**。
- 展示层统一保留 2 位；展示合计与明细展示值可能差 1 分钱时，以合计为准并标注。

### 4.5 导入管道

```
下载模板（列头由 pay_item 动态生成）
   ↓
上传 → 计算文件 hash → 命中已提交批次则直接拒绝（幂等）
   ↓
预校验（不落库）：格式 / 科目存在性 / 员工存在性 / 期间状态 / 数值范围
   ↓
回显：成功 N 行、失败 M 行，错误报告可下载（行号 + 列名 + 原因 + 原值）
   ↓
用户确认 → 提交（事务内 upsert）→ 生成 pay_record_item
```

- **导入模式**必须让用户选：`UPSERT`（有则覆盖）/ `APPEND`（有则累加）/ `INSERT_ONLY`（有则跳过）。
- 大文件用 EasyExcel 流式读，避免 POI 全量加载 OOM。
- 防护：单文件 ≤ 5 万行、≤ 10MB；单元格以 `= + - @` 开头一律按文本处理（公式注入）。
- `pay_import_error` 只存前 5000 行，超出在报告里说明。

### 4.6 期间状态机

```
        ┌──────────────── 解锁（需审批 + 审计）────────────────┐
        ▼                                                     │
    [DRAFT] ──生成──> [EDITING] ──锁定──> [LOCKED] ──归档──> [ARCHIVED]
       │                  │                                        │
       └──生成────────────┘                                  只读，终态
```

| 状态 | 允许的操作 |
|---|---|
| DRAFT | 生成、删除 |
| EDITING | 生成、导入、手工编辑、重算单条、锁定 |
| LOCKED | 只读；导出；解锁（需权限 + 填原因） |
| ARCHIVED | 只读；参与年度汇总；不可解锁 |

**锁定是数据库层面的约束**：所有写接口进入前校验期间状态并加行锁，不能只靠前端禁用。

> **C4**：审批走线下，系统内不存在审核/审批状态与待办。系统的全部状态变化只有「生成 → 编辑 → 锁定 → 归档」和「解锁」五种，其中「锁定」与「解锁」都必须是独立权限点，且锁定人不能是本期编制人。

### 4.9 多主体（法人 / 分公司）

四条隔离线，缺一条就会串数据：

| 维度 | 做法 |
|---|---|
| **组织** | `sys_company` → `sys_dept`（部门树按主体独立，`uk(company_id, dept_code)`） |
| **数据** | 员工、期间、核算记录、汇总全部带 `company_id`，查询强制拼主体条件 |
| **权限** | 角色 `data_scope` 新增 `COMPANY`；只有集团 HR / 审计能拿 `ALL` |
| **期间** | 按主体独立开期间、独立锁定，`uk(company_id, period_ym)`，各分公司互不影响 |

**人员归属的处理（关键）**：
- 人员主数据在**集团级唯一**——工号全局唯一、证件号盲索引全局唯一。同一个人不会因为在两家分公司都待过就变成两条人员记录。
- `emp_employee.company_id` 只是**当前归属的冗余展示**；真正的归属依据是 `emp_employment`（员工在各主体的任职区间）。
- 核算时的归属判定：`start_date <= 期间末日 AND (end_date IS NULL OR end_date >= 期间末日)`。**不能读 `emp_employee.company_id`**——否则解锁重算历史期间会用今天的归属写进历史。
- 跨主体调动 = 结束旧区间 + 开新区间，工龄连续。
- 历史工资表不受影响，因为 `pay_record` 存了 `company_id / dept_id / dept_name` 快照。

**需要业务确认的边界**：员工当月跨主体调动时，这个月的工资挂在哪个主体？
- 默认：按**期间末日归属主体**整月归属，不做分割。
- 若需按天分割，要等第 2 期的「员工调动单」，本期不支持。

**工资项**：`pay_item.company_id = 0` 表示集团通用科目；也可为某主体建专属科目。核算时取「本主体专属 + 集团通用」的并集。

### 4.7 权限模型

三件事分开做，不做成一个"管理员"角色：

**(1) 功能权限** — 权限点 + 角色
```
payroll:record:view     查看核算
payroll:record:edit     编制/编辑
payroll:period:lock     锁定期间
payroll:period:unlock   解锁（高危）
payroll:import:submit   导入提交
payroll:export          导出（高危）
payroll:sensitive:view  查看完整证件号/手机号
```

**(2) 数据范围** — 挂在角色上，生效时取最宽者
```
ALL          集团全部主体（仅集团 HR / 审计）
COMPANY      本公司全部部门
DEPT_SUB     本部门及下级（用 sys_dept.ancestors 前缀匹配）
DEPT         本部门
SELF         仅本人
```

**(3) 内控约束**（代码硬校验，不可配置绕过）
- 编制人 ≠ 锁定人（同一期间）
- 导出必须单独授权，且写审计流水
- 查看他人工资写查看审计（谁看了谁的）
- 证件号/手机号列表页脱敏，查看完整值需 `payroll:sensitive:view` 且二次确认

### 4.8 敏感数据处理

| 字段 | 存储 | 展示 | 查重/唯一 |
|---|---|---|---|
| 证件号码 | AES-256 密文 `VARBINARY` | 掩码 `****1234` | SHA-256(salt+号码) 哈希列唯一索引 |
| 手机号码 | AES-256 密文 | 掩码 `138****8000` | 哈希列，不唯一 |
| 银行卡号（预留） | AES-256 密文 | 掩码 | — |

密钥从环境变量/密钥文件注入，**不进代码库、不进配置文件明文**。

## 6 非功能要求

| 项 | 要求 |
|---|---|
| 性能 | 2000 人 × 1 期生成 ≤ 30s；导入 5000 行预校验 ≤ 15s；列表查询 P95 ≤ 500ms |
| 事务 | 生成/导入分批提交（500 条/批），不用单一大事务 |
| 备份 | 日备全量 + 保留 90 天；每周归档一次 |
| 审计 | 所有金额变更、锁定/解锁、查看他人工资、导出全部留痕 |
| 留存 | 工资表按会计档案要求长期保存，系统**不提供物理删除**，只做逻辑失效 |
| 离线构建 | 内网无外网：在有网机器上 `mvn dependency:go-offline` 建离线仓库，或直接构建镜像后导入 |
| 日志 | 应用日志脱敏，禁止出现金额明文与证件号 |

## 7 分期路线

**第 1 期 MVP（约 6–8 周）**
多主体组织 + 人员主数据 + 薪酬档案 + 科目 + 期间 + **各分公司独立编表** + 生成 + 编制 + **金额**导入 + **三层重复校验** + 解锁更正 + 权限 + 月/年汇总导出 + 审计

> 更正的唯一路径是「解锁 → 修改 → 重新锁定」，所以解锁必须是高危权限点并全程审计。补发/扣回不在本期范围。

**第 2 期**
批量重算 + 个人工资条查询与推送 + 数据看板 + 员工跨主体调动单

**第 3 期**
个税与社保公积金 + 银行代发文件 + 考勤/绩效系统对接
