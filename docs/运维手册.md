## 一、环境准备

### 1.1 总览

| 组件 | 版本要求 | 默认端口 | 说明 |
|---|---|---|---|
| JDK | **必须 17** | — | 构建与运行后端 |
| Maven | 3.6+（建议 3.9+） | — | 构建后端 jar |
| MySQL | 8.0 | 宿主机 `127.0.0.1:3307` | Docker 容器 `payroll-mysql` |
| Node.js | 20 LTS 及以上 | — | 构建/开发前端 |
| npm | 10+ | — | 仓库带 `package-lock.json` |
| 浏览器 | Chromium 内核现代浏览器 | — | 编制台使用虚拟滚动，建议 Chrome/Edge 最新版 |

后端端口 `8080`，前端开发端口 **`5174`**（`frontend/vite.config.ts` 中固定），前端通过 Vite 代理把 `/api` 转发到 `http://localhost:8080`。

### 1.2 JDK 17（必须 17）

Spring Boot 3.3 要求 JDK 17+，但**构建时必须用 JDK 17**。用 JDK 21/23 构建会出现 Lombok 静默失效：

- 编译报大量 `找不到符号: 方法 getXxx()`、`找不到符号: 变量 log`；
- 代码本身没有错，实体类的 getter/setter、`@Slf4j` 的 `log` 都没有生成；
- JDK 23+ 默认不再执行 classpath 上的注解处理器，Lombok 作为注解处理器被跳过。

`pom.xml` 已显式配置 `annotationProcessorPaths` 兜底，但仍建议固定 JDK 17，避免不同 Maven/JDK 组合下的偶发问题。

macOS（Homebrew）：

```bash
brew install openjdk@17
export JAVA_HOME=$(/usr/libexec/java_home -v 17)
```

Linux（Temurin 示例）：

```bash
export JAVA_HOME=/usr/lib/jvm/temurin-17-jdk-amd64
export PATH="$JAVA_HOME/bin:$PATH"
```

确认：

```bash
java -version
mvn -v
```

`java -version` 必须显示 `17.x`，`mvn -v` 的 `Java version` 也必须是 17。

如果已经用错 JDK 构建过，清理后重来：

```bash
mvn -DskipTests clean compile
```

### 1.3 MySQL 8 容器

数据库由 `docker-compose.yml` 启动，容器名固定为 `payroll-mysql`。

```bash
docker compose up -d
docker compose ps
```

期望看到 `payroll-mysql` 状态为 `Up ... (healthy)`，端口映射为 `127.0.0.1:3307->3306/tcp`。

关键设计：

- **端口只绑回环**：`127.0.0.1:3307:3306`，局域网内其他机器无法直连数据库。这是薪资数据的底线，不要改成 `3307:3306`。
- 字符集 `utf8mb4`，排序规则 `utf8mb4_0900_ai_ci`，时区 `+08:00`。
- 数据卷 `payroll-mysql-data` 持久化；`db/schema-mysql.sql` 只在**数据卷为空时**由 MySQL 官方镜像自动执行一次。
- 应用连接串写死库名 `payroll`（见 `src/main/resources/application.yml`）。如果改 `MYSQL_DATABASE`，必须同时覆盖 `spring.datasource.url`，否则应用连错库。
- compose 的 healthcheck 命令里硬编码了一个默认 root 口令，不会读取 `.env` 的 `MYSQL_ROOT_PASSWORD`。由于 `mysqladmin ping` 在认证失败时仍会返回“mysqld is alive”，容器通常仍显示 healthy，不影响使用；生产环境建议把 healthcheck 改成 TCP 探测或引用环境变量，避免误导排障。

### 1.4 `.env` 配置

```bash
cp .env.example .env
```

`.env` 已被 `.gitignore` 排除。逐项填写：

```dotenv
MYSQL_ROOT_PASSWORD=<随机强口令>
MYSQL_DATABASE=payroll
MYSQL_USER=payroll
MYSQL_PASSWORD=<随机强口令>
MYSQL_PORT=3307

PAYROLL_ID_SALT=<随机值>
PAYROLL_AES_KEY=<随机值>
PAYROLL_TOKEN_SECRET=<随机值>
```

生成随机值：

```bash
openssl rand -hex 32
```

说明：

- `PAYROLL_ID_SALT`：证件号盲索引的 HMAC 密钥。**一旦有人员数据就不能更换**，否则同一证件号会算出不同哈希，查重与唯一约束全部失效。
- `PAYROLL_AES_KEY`：证件号/手机号可逆加密密钥。**一旦有人员数据就不能更换**，否则历史密文无法解密。
- `PAYROLL_TOKEN_SECRET`：登录 token 的 HMAC 密钥。更换后所有已登录用户立即掉线，可接受，但要在维护窗口做。
- 代码会把任意非空字符串 SHA-256 派生为 32 字节密钥，所以长度不受限；仍建议用 32 字节随机值。
- `MYSQL_ROOT_PASSWORD` 和 `MYSQL_PASSWORD` 只给容器/初始化脚本用；应用运行时只需要 `MYSQL_USER`、`MYSQL_PASSWORD`。

把 `.env` 导入当前 shell：

```bash
set -a; source .env; set +a
```

每次新开终端运行应用或执行数据库命令前都要重新执行这一行。

### 1.6 已知网络坑

#### 本机代理拦截 localhost

如果本机开了全局代理（Clash/Surge 等），`curl http://127.0.0.1:8080` 可能返回 502/503 或超时，但服务其实是好的。所有本机 curl 都加 `--noproxy '*'`：

```bash
curl --noproxy '*' -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/api/v1/nope
```

浏览器访问 `localhost` 时，需要在代理软件里把 `localhost,127.0.0.1` 加入直连/绕过列表。

#### Maven 走代理失败

本机代理可能让 Maven 依赖下载报网络错误。按项目惯例关闭代理相关系统属性：

```bash
JAVA_TOOL_OPTIONS="-DsocksProxyHost= -Djava.net.useSystemProxies=false" mvn -DskipTests clean package
```

内网离线构建见第四章。

#### MinIO 镜像拉不到 / MinIO 是否可用

**当前版本的代码只实现了本地文件存储，没有 MinIO 存储实现。** `payroll.storage.type` 这个配置项目前不会被读取；`docker-compose.yml` 里的 `minio` profile 只是预留，启动它也不会让应用把文件写进 MinIO。

因此：

- 不要执行 `docker compose --profile minio up -d` 期待切换存储；该服务里的账号口令也是硬编码的，即使将来启用也要先改。
- 原始导入文件固定落在 `payroll.storage.local-path`（默认 `./data/import`）；
- 需要共享/集中存储时，把该目录挂到 NFS 或云盘，并显式指定绝对路径，例如：

```bash
java -jar target/payroll-0.1.0-SNAPSHOT.jar \
  --payroll.storage.local-path=/data/payroll/import
```

目录不存在时应用会在首次上传时自动创建。

## 二、从零启动（全新环境）

以下命令按顺序执行，每一步都给出“成功标志”。

### 2.1 取得代码

```bash
git clone <仓库地址> payroll-system
cd payroll-system
```

如果是拷贝的压缩包，直接进入目录即可。确认关键文件存在：

```bash
ls README.md docker-compose.yml .env.example db/schema-mysql.sql db/seed-demo.sql
```

### 2.2 配置 `.env`

```bash
cp .env.example .env
```

按 1.4 节填写。首次启动前确认没有空值：

```bash
grep -E '^(MYSQL_ROOT_PASSWORD|MYSQL_PASSWORD|PAYROLL_ID_SALT|PAYROLL_AES_KEY|PAYROLL_TOKEN_SECRET)=$' .env
```

该命令应无输出。若有输出，说明对应项仍为空，compose 或应用会直接拒绝启动。

### 2.3 启动 MySQL

```bash
docker compose up -d
docker compose ps
```

成功标志：

- `payroll-mysql` 为 `Up ... (healthy)`；
- `docker logs payroll-mysql` 中出现 `ready for connections`。

首次启动时，MySQL 会自动执行挂载进去的 `db/schema-mysql.sql`，建表并写入内置角色、工资项、税率表、社保参数等基础数据。等待约 20–60 秒，然后确认表已建好：

```bash
set -a; source .env; set +a
docker exec payroll-mysql mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -N \
  -e "SELECT COUNT(*) FROM information_schema.tables WHERE table_schema='payroll';"
```

期望输出 `25`（当前 schema 共 25 张表）。如果输出 `0`，说明数据卷不是空的或初始化失败，见 7.10。

> 警告：`docker compose down -v` 会删除数据卷，等于清空数据库。只在确认要重建的全新环境使用。

### 2.4 导入种子账号

schema 只建表，不含部门与登录账号。全新环境必须再导入 `db/seed-demo.sql`：

```bash
docker exec -i payroll-mysql mysql -uroot -p"$MYSQL_ROOT_PASSWORD" \
  --default-character-set=utf8mb4 payroll < db/seed-demo.sql
```

成功标志：命令无报错。确认账号：

```bash
docker exec payroll-mysql mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -N \
  --default-character-set=utf8mb4 payroll \
  -e "SELECT username, real_name FROM sys_user ORDER BY id;"
```

期望至少包含 `admin`、`hr01`、`hr02`。

### 2.5 种子账号

| 用户名 | 初始密码 | 姓名 | 角色 | 能做什么 |
|---|---|---|---|---|
| `admin` | `Passw0rd!` | 系统管理员 | `SYS_ADMIN` | 用户、角色、部门、法人主体、系统参数 |
| `hr01` | `Passw0rd!` | 薪酬专员 | `PAYROLL_CLERK` | 建期间、生成、编制、导入、导出、查看敏感字段 |
| `hr02` | `Passw0rd!` | 薪酬复核 | `PAYROLL_REVIEWER` | 查看、锁定、解锁、导出 |

注意：

- 三个账号同属「默认主体」（`company_id=1`）、同属「综合部」（`D001`）。
- `admin` 只有 `sys:*` 权限，没有薪酬权限，登录后落地页是「用户管理」，看不到工资数据。这是三权分立的刻意设计。
- `hr02` 没有 `payroll:record:edit`，不能建期间、不能生成、不能改数，只能锁定/解锁/查看/导出。
- 种子密码是公开的，上线前必须修改。

### 2.6 登录后第一件事：修改种子密码

**系统没有“个人自助修改密码”页面。** 密码管理只有一条路径：管理员在「系统管理 → 用户管理 → 重置密码」中重置，或调用 `POST /api/v1/users/{id}/reset-password`（需要 `sys:user:edit`）。

操作步骤：

1. 用 `admin / Passw0rd!` 登录。
2. 进入「系统管理 → 用户管理」。
3. 对 `admin`、`hr01`、`hr02` 逐行点击「重置密码」，输入不少于 8 位的新密码。
4. 重置后旧 token 立即失效（`token_version + 1`），当前会话下次请求会跳回登录页。用新密码重新登录。
5. 不能停用或删除自己的账号；删除/停用最后一个系统管理员会被服务端拒绝。

建议上线时再为每位实际操作人单独建账号、分配角色，不要多人共用 `hr01`。

### 2.7 构建并启动后端

```bash
export JAVA_HOME=$(/usr/libexec/java_home -v 17)   # Linux 用 1.2 节的路径
JAVA_TOOL_OPTIONS="-DsocksProxyHost= -Djava.net.useSystemProxies=false" \
  mvn -DskipTests clean package
```

成功标志：`target/payroll-0.1.0-SNAPSHOT.jar` 生成，构建输出 `BUILD SUCCESS`。

启动：

```bash
set -a; source .env; set +a
java -jar target/payroll-0.1.0-SNAPSHOT.jar
```

成功标志（日志最后几行）：

```text
Tomcat started on port 8080 (http)
Started PayrollApplication in ... seconds
```

验证接口：

```bash
curl --noproxy '*' -s -X POST http://127.0.0.1:8080/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"Passw0rd!"}'
```

期望返回 `{"code":0,"msg":"ok","data":{"token":"...","user":{...}}}`。

后台运行（生产建议用 systemd，见 4.2）：

```bash
set -a; source .env; set +a
mkdir -p logs
nohup java -jar target/payroll-0.1.0-SNAPSHOT.jar > logs/payroll.log 2>&1 &
tail -f logs/payroll.log
```

如果缺少任一 `PAYROLL_*` 环境变量，启动会直接失败并打印 `未配置，拒绝启动`，这是刻意设计，不要给它加默认值。

### 2.8 启动前端

开发模式：

```bash
cd frontend
npm ci
npm run dev
```

成功标志：

```text
VITE v6.x  ready in ... ms
Local:   http://localhost:5174/
```

浏览器打开 `http://localhost:5174`，用 `admin / Passw0rd!` 登录，应进入「用户管理」。

说明：

- 端口是 **5174**，不是 5175。`docs/review/` 里部分验收记录写 5175，是验收时另起的端口，以 `vite.config.ts` 为准。
- 如果 5174 被占用，Vite 会自动递增到 5175 并打印实际地址，以终端输出为准。
- 前端默认 `VITE_API_BASE=/api/v1`，由 Vite 代理转发到 `http://localhost:8080`；不需要另配跨域。

### 2.9 首次业务验证

1. 用 `hr01 / 新密码` 登录，应进入「工资期间」。
2. 「人员管理 → 新增人员」建一个测试员工，填写工号、姓名、证件号、部门、入职日期。
3. 在该员工行点「薪酬档案 → 配置薪酬」，填基本工资，**生效日期设为入职日期**，保存。
4. 「工资期间 → 新建期间」，选择当月。
5. 点「生成」，进度结束应显示成功 1 人、失败 0 人。
6. 进「编制台」，应看到该员工一行，基本工资、工龄工资、应发合计有值。
7. 用 `hr02` 登录，在同一期间点「锁定」，应成功；`hr01` 锁定会报「锁定人不能是本期间的编制人」。

## 三、升级部署（已有环境升级到当前版本）

### 3.1 适用范围

`db/m1-upgrade-2026-11-26.sql` 用于**已经按旧版 schema 建过表**的环境。全新环境只执行 `db/schema-mysql.sql`，不需要本文件。

升级前必须：

1. 停止应用写入（停后端或至少停止工资操作）；
2. 做一次完整数据库备份（见第六章）；
3. 确认 `db/schema-mysql.sql` 与当前代码版本一致；
4. 在测试库先演练一遍。

执行：

```bash
set -a; source .env; set +a
docker exec -i payroll-mysql mysql -uroot -p"$MYSQL_ROOT_PASSWORD" \
  --default-character-set=utf8mb4 payroll < db/m1-upgrade-2026-11-26.sql
```

脚本说明：MySQL 的 `ADD COLUMN` / `DROP INDEX` 不支持 `IF NOT EXISTS`，重复执行会在已应用的语句上报「已存在 / 不存在」。逐条判断，**已存在的跳过即可**，不要因为单条报错就中断后续必执行项。

### 3.2 21 节迁移逐节说明

| 节 | 内容 | 作用 | 是否必执行 |
|---|---|---|---|

| 2 | `pay_record.version_no` 默认值 1 → 0 | 新建记录 version=0，与前端乐观锁契约一致 | 建议 |

| 4 | `sys_user.token_version` | 改密码后旧 token 立即失效 | 必执行 |
| 5 | `pay_record(company_id, period_ym)` 索引 | 本主体本期间查询 | 建议 |
| 6 | `pay_import_batch(period_id, status, file_hash)` 索引 | 导入幂等查询 | 建议 |
| 7 | `pay_period.column_snapshot` JSON | 导出列取生成时快照，停用科目不会导致列错位 | 必执行（导出依赖） |

| 10 | 审计 `biz_type/action` 注释扩展 | 允许 REPORT、GRANT_REPLACE 等取值 | 建议 |

| 12 | `sys_config` 表 + 4 条参数 | 月计薪天数、工龄单价、节假日、版本号 | **必执行**（系统参数页依赖） |
| 13 | 复核岗补 `payroll:period:unlock` | 原来无人能解锁，锁定不可逆 | **必执行** |
| 14 | `pay_period.last_run_fail_count` | 部分员工生成失败时提示并禁止锁定 | **必执行** |
| 15 | `pay_run_skip` 表 | 保留完整跳过名单，弹窗关闭后仍可回看 | **必执行** |
| 16 | 存量记录状态回填 | 已锁定/归档期间的 `DRAFT` 记录改为 `CONFIRMED` | **必执行** |
| 17 | `active_key` 生成列 + 唯一键 | 同日多次更正调薪不再撞键 | **必执行** |
| 18 | `pay_record.period_ym` 索引 | 集团级跨期间查询性能 | **必执行** |
| 19 | 薪酬专员补 `payroll:sensitive:view` | 证件号按需查看的唯一权限入口 | **必执行** |
| 20 | 个税社保五张表 + 三个扣款科目 + 税率/城市参数 | 社保、公积金、个税计算的全部依赖 | **必执行** |
| 21 | `pay_ytd.paid_months` | 减除费用按“本年度已计薪月份数”算 | **必执行** |

### 3.3 必执行项缺失时的具体后果

按依赖关系，缺哪一节会坏在哪：

- 缺 **第 20 节**：生成时`taxService` 查询 `emp_social_insurance` / `pay_tax_bracket` 等表，报 `Table 'payroll.xxx' doesn't exist`。每个员工都会进“计算失败”，整期生成失败。
- 缺 **第 21 节**：生成读取 `pay_ytd.paid_months` 报 `Unknown column 'paid_months'`；锁定期间时 `YtdService.accumulate` 也会失败，期间锁不上。
- 缺 **第 17 节**：同一天第二次更正调薪会报 `Duplicate entry ... for key 'uk_emp_effective'`，错误改不回来。
- 缺 **第 16 节**：个税功能上线前已锁定的期间，记录仍是 `DRAFT`；新锁定才会自动转 `CONFIRMED`，历史数据不会自动修。
- 缺 **第 19 节**：`hr01` 点证件号「查看」返回 403。
- 缺 **第 13 节**：`hr02` 解锁返回 403，已锁定期间无法更正。
- 缺 **第 11 节**：老环境没有任何账号拥有 `sys:user:edit` 等权限，系统管理页进不去。
- 缺 **第 12 节**：系统参数页报错/空白，生成时月计薪天数回退 21.75，节假日无法在线维护。
- 缺 **第 7 节**：导出时列快照为空，可能按当前启用科目导列，与已停用科目的历史明细对不上。
- 缺 **第 9 节**：并发上传同一文件可能产生两个批次，重复导入风险。

### 3.4 第 11 节的已知缺口：系统参数权限

第 11 节给 `SYS_ADMIN` 补的是 7 个权限：

```text
sys:user:view / sys:user:edit / sys:role:view / sys:role:edit /
sys:role:grant:all / sys:dept:edit / sys:company:edit
```

当前权限目录还包含 `sys:config:view`、`sys:config:edit`（第 12 节新增的系统参数页需要）。**升级环境执行完第 11 节后，系统管理员仍看不到「系统参数」菜单**。补执行：

```sql
INSERT IGNORE INTO sys_role_grant (role_id, perm_code)
SELECT r.id, p.code
  FROM sys_role r
  JOIN (SELECT 'sys:config:view' AS code
        UNION ALL SELECT 'sys:config:edit') p
 WHERE r.company_id = 1 AND r.role_code = 'SYS_ADMIN' AND r.deleted = 0;
```

执行后让管理员重新登录（或刷新页面）使权限生效。

### 3.5 历史数据的个税台账为空

个税是 2026-11-28 上线的。在此前已经锁定的期间没有写入 `pay_ytd`，表现为：

- 「个税核对」页查历史年份为空；
- 新期间生成时，累计收入、累计社保、累计已预扣税都从 0 开始，个税会明显偏高或偏低。

年中迁移的客户必须录“期初累计”。第 21 节给了示例，按员工逐个录入：

```sql
INSERT INTO pay_ytd
  (employee_id, tax_year, company_id, cum_income, cum_social, cum_fund,
   cum_special_deduction, cum_tax, paid_months, last_period_ym)
VALUES (123, 2026, 1, 80000, 9000, 6000, 12000, 1000, 8, '2026-08');
```

用 `emp_no` 查 `employee_id` 更稳妥：

```sql
SELECT id, emp_no, name, company_id FROM emp_employee WHERE emp_no = 'E200';
```

如果该员工当年已有台账行，用更新而不是插入：

```sql
UPDATE pay_ytd
   SET cum_income = 80000,
       cum_social = 9000,
       cum_fund = 6000,
       cum_special_deduction = 12000,
       cum_tax = 1000,
       paid_months = 8,
       last_period_ym = '2026-08'
 WHERE employee_id = 123 AND tax_year = 2026;
```

口径必须由财务确认：

- `cum_income`：1 月至上线前一期的**应发合计**累计；
- `cum_social` / `cum_fund`：个人部分累计；
- `cum_special_deduction`：专项附加扣除累计；
- `cum_tax`：已预扣个税累计；
- `paid_months`：本年度**已计薪并锁定**的月份数，不是日历月份序号。

录入后让 HR 重新生成尚未锁定的期间，或解锁后重新锁定，使台账重算。

### 4.2 运行方式

生产建议用 systemd，避免终端退出导致进程结束。先创建运行账号并准备目录：

```bash
sudo useradd --system --home /opt/payroll --shell /usr/sbin/nologin payroll
sudo mkdir -p /opt/payroll /etc/payroll /data/payroll/import
sudo chown -R payroll:payroll /opt/payroll /data/payroll
```

示例 `/etc/systemd/system/payroll.service`：

```ini
[Unit]
Description=Payroll System
After=network.target docker.service

[Service]
Type=simple
User=payroll
WorkingDirectory=/opt/payroll
EnvironmentFile=/etc/payroll/payroll.env
ExecStart=/usr/lib/jvm/temurin-17-jdk-amd64/bin/java -Xms512m -Xmx2g -jar /opt/payroll/payroll-0.1.0-SNAPSHOT.jar --payroll.storage.local-path=/data/payroll/import
Restart=on-failure
RestartSec=5
SuccessExitStatus=143

[Install]
WantedBy=multi-user.target
```

`/etc/payroll/payroll.env` 权限设为 `0400`，属主为运行账号，内容至少包含：

```dotenv
MYSQL_USER=payroll
MYSQL_PASSWORD=...
PAYROLL_ID_SALT=...
PAYROLL_AES_KEY=...
PAYROLL_TOKEN_SECRET=...
PAYROLL_HOLIDAYS=2026-10-01,2026-10-02,2026-10-03
```

```bash
grep -E '^(MYSQL_USER|MYSQL_PASSWORD|PAYROLL_ID_SALT|PAYROLL_AES_KEY|PAYROLL_TOKEN_SECRET|PAYROLL_HOLIDAYS)=' .env \
  | sudo tee /etc/payroll/payroll.env >/dev/null
sudo chown payroll:payroll /etc/payroll/payroll.env
sudo chmod 0400 /etc/payroll/payroll.env
```

启用：

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now payroll
sudo systemctl status payroll
sudo journalctl -u payroll -f
```

不要把密钥放在命令行参数里：`ps`、`/proc/<pid>/cmdline` 都能看到。环境变量也会出现在 `/proc/<pid>/environ` 和容器 `inspect` 中，能上 Docker secret / 只读文件挂载更好。

### 4.3 环境变量清单

| 变量 | 是否必填 | 用途 | 备注 |
|---|---|---|---|
| `MYSQL_USER` | 是 | 应用数据库账号 | 建议最小权限账号 |
| `MYSQL_PASSWORD` | 是 | 应用数据库口令 | — |
| `MYSQL_ROOT_PASSWORD` | compose 必填 | MySQL root 口令 | 仅容器初始化/备份用 |
| `MYSQL_DATABASE` | 否 | 初始化库名 | 默认 `payroll`；应用 URL 写死 `payroll` |
| `MYSQL_PORT` | 否 | 宿主机映射端口 | 默认 `3307`，只绑回环 |
| `PAYROLL_ID_SALT` | 是 | 证件号盲索引 HMAC 密钥 | 有数据后不可更换 |
| `PAYROLL_AES_KEY` | 是 | 证件号/手机号 AES-256 密钥 | 有数据后不可更换 |
| `PAYROLL_TOKEN_SECRET` | 是 | 登录 token HMAC 密钥 | 轮换后全员掉线 |
| `PAYROLL_HOLIDAYS` | 否 | 法定节假日，逗号分隔 ISO 日期 | 系统参数为空时回退此变量 |

常用启动参数覆盖：

```bash
java -jar payroll-0.1.0-SNAPSHOT.jar \
  --server.port=8080 \
  --payroll.storage.local-path=/data/payroll/import \
  --payroll.security.token-ttl-minutes=480
```

`springdoc` 默认关闭，生产不要加 `--spring.profiles.active=dev`。`application-dev.yml` 会打开 Swagger，等于把全部接口暴露给未认证访问者。

### 4.4 前端生产部署（nginx）

`dist/` 是纯静态文件，需要 Web 服务器托管，并把 `/api/` 反代到后端。前端使用 HTML5 History 路由，必须做 SPA 回退。

```nginx
server {
    listen 80;
    server_name payroll.internal;

    root /opt/payroll/frontend/dist;
    index index.html;

    # 导入文件上限 50MB，与后端 multipart 配置一致
    client_max_body_size 50m;

    location /api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        # 导出/生成可能较慢，默认 60s 容易截断
        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

注意：

- `proxy_pass` 末尾**不要加斜杠**，否则 `/api/v1/...` 会被改写成 `/v1/...`。
- 应用按根路径 `/` 部署（`createWebHistory()` 未设 base）。若要部署在子路径，需要改前端代码并重新构建，当前版本不支持直接挂子目录。
- 生产建议加 HTTPS；反向代理要传递 `X-Forwarded-For`，登录限流按「用户名 + 客户端 IP」计数，否则所有请求都会被当成同一个 IP。
- 如需跨域直连后端（不用 nginx 同源代理），要配置 `VITE_API_BASE` 和后端 CORS，并暴露 `Content-Disposition` 响应头，否则下载文件名会丢失。内网优先用同源反代。

## 五、HR 日常操作（业务手册）

本章写给不看代码的 HR。所有操作都在浏览器里完成，路径按左侧菜单描述。

### 5.1 月度工资核算完整流程

#### 第 1 步：建期间

路径：`工资期间 → 新建期间`。

- 选择工资年月（如 `2026-11`），点「创建」。
- 同一主体同一年月只能有一个期间，重复创建会直接返回已有期间（幂等）。
- 新期间状态为「草稿」，计薪天数取系统参数（默认 21.75）。
- 只有拥有 `payroll:record:edit` 的账号（如 `hr01`）能建期间。

#### 第 2 步：生成基础数据

路径：`工资期间 → 对应行「生成」`。

- 系统按“期间内在职/离职员工 × 期间末日生效的薪酬档案”生成工资记录。
- 进度弹窗显示：应生成人数、成功、失败、跳过。
- 生成可以重复点；同一人同一期间已有记录会按本主体本期更新，不会产生重复记录。
- 如果人员范围发生变化（例如生成后又把某人改成离职/调岗），重新生成不会自动删除已存在但本期不再应发的人。当前版本没有删除单条核算记录的界面入口，务必在生成前把人员状态和薪酬档案维护正确；发现残留记录请联系实施人员处理。
- 生成成功后期状态变为「编制中」。
- **有失败人数时不能锁定**，必须先处理。

#### 第 3 步：处理跳过名单

生成弹窗里会列出跳过原因，常见两种：

| 跳过原因 | 含义 | 处理 |
|---|---|---|
| 未配置薪酬档案 | 员工没有在期间末日生效的基本工资区间 | 到「人员管理 → 薪酬档案」配置，生效日期要早于或等于期间末日 |
| 离职状态未填离职日期 | 员工状态是离职但没有离职日期 | 到「人员管理 → 编辑」补离职日期；系统不会臆造日期算钱 |

处理完重新点「生成」。跳过明细同时写入 `pay_run_skip`，关掉弹窗后仍可回看（生成进度接口会返回）。

#### 第 4 步：导入绩效/变动工资

路径：`工资期间 → 对应行「导入」`（仅「编制中」状态可见）。

向导分三步：

1. **下载模板**：选择「固定项」或「变动项」，列头由工资项字典动态生成，不要改列名或顺序。
2. **上传并预校验**：选择文件、导入模式，点「开始预校验」。系统只校验不落库，返回成功/失败行数与错误明细（行号、列、原值、原因）。
3. **确认提交**：预校验无失败行后点「提交」，写入明细并重算合计。

导入模式：

- `有则覆盖`（UPSERT）：该员工该科目已有金额则覆盖；
- `有则跳过`（INSERT_ONLY）：已有金额则保留原值。

没有“累加”模式。变动项导入的是**绝对金额**，累加等于重复发薪，已被服务端禁用。

限制：单文件 ≤ 5 万行、≤ 50MB；错误明细最多保留 5000 行；单元格以 `= + - @` 开头按文本处理。导入向导页面上的提示仍写着“≤ 10MB”，那是旧文案，实际以后端 `application.yml` 的 50MB 为准。

#### 第 5 步：编制台改数

路径：`工资期间 → 对应行「编制台」`。

- 表格支持按部门、员工类型、职级、工号/姓名筛选。
- 可直接编辑可编辑科目（变动项、部分固定项）；计算项（工龄工资、社保、公积金、个税、尾差）不可手工改。
- 修改后右上角显示“未保存单元格数”，点「保存修改」才会落库；点「放弃修改」撤销本次未保存内容。
- 保存带乐观锁：如果同一行已被别人改过，会提示冲突并高亮红色行，刷新后重做。
- 切期间、换账号会重新拉取数据；离开页面前有未保存修改会二次确认。

如果发现某人的社保/个税不对，不要手工改这三个扣款项（它们不可编辑）。正确做法是修参保信息/专项扣除/薪酬档案，然后重新生成或单条重算。

#### 第 6 步：复核锁定

路径：`工资期间 → 对应行「锁定」`，由 `hr02`（薪酬复核）操作。

锁定前系统会检查：

- 期间必须是「编制中」；
- 当前没有正在运行的生成任务；
- 上次生成失败人数必须为 0；
- 最近一次生成状态必须是 `SUCCESS`；
- **锁定人不能是本期间的编制人**（谁最后点的生成，谁就是编制人）。

锁定成功后：

- 期间变为「已锁定」，所有写操作返回 409；
- 记录状态从 `DRAFT` 变为 `CONFIRMED`；
- 本期数据累加进个税年度台账 `pay_ytd`（同一事务，失败一起回滚）；
- 写一条 `LOCK` 审计。

#### 第 7 步：出报表

路径：

- `月度报表`：选期间、主体、部门，查看应发/扣款/实发合计。
- `年度报表`：选年度，按人（EMP）或按部门（DEPT）汇总。
- `个税核对`：选年度，查看每人累计收入、累计减除、累计社保/公积金/专项、应纳税所得额、累计已预扣、税负率。

报表只统计**已锁定/已归档**期间。未锁定的月份会在页面上以 `excludedPeriods` 提示，不会静默混入。

#### 第 8 步：导出

- 编制台：`导出工资表`（全表）、`导出工资条`（当前筛选后的人员）。
- 月度/年度/个税核对页：`导出 xlsx`。
- 导出需要 `payroll:export` 权限；只有已锁定/已归档期间可导出，否则返回 409。
- 每次导出写审计（谁、何时、导了哪个范围）。
- 导出的临时文件在后端落盘后立即删除，不会长期留在服务器。

### 5.2 人员入职

#### 单个入职

1. `人员管理 → 新增人员`。
2. 填写：工号（集团唯一）、姓名、性别、员工类型、证件类型/号码、手机号、部门、职级、岗位、入职日期、参加工作时间。
3. 保存后，在该员工行点「薪酬档案」。
4. 在「薪酬档案」页签点「配置薪酬」：填基本工资、固定津贴，**生效日期填入职日期**（默认是“次月 1 日”，新员工必须改，否则当月生成会因“未配置薪酬档案”被跳过）。
5. 保存后时间线出现一条记录。

注意：证件号全局唯一，同一个人跨主体调动不重建人员；重复证件号会报“该证件号码已存在人员记录”。

#### 批量入职

1. `人员管理 → 批量导入`。
2. 下载模板。模板固定 13 列：工号、姓名、性别、员工类型、证件类型、证件号码、手机号、部门编码、职级、岗位、入职日期、参加工作时间、基本工资。
3. 填好后上传，先预校验，再提交。
4. 导入会同时创建人员和薪酬档案，档案生效日取模板里的入职日期。

注意：

- 列头必须逐列匹配，不能改名、不能调顺序；
- 部门编码必须是已存在的 `sys_dept.dept_code`；
- 员工类型只能是 `REGULAR/PROBATION/INTERN/LABOR/OUTSOURCE/REHIRE`；
- 同一文件内工号、证件号重复会在预校验阶段报错；
- 已存在的工号、证件号也会被拦，报“工号已被占用”或“该证件号码已存在人员记录”。

### 5.3 调薪

路径：`人员管理 → 薪酬档案 → 调薪`。

- 填新的基本工资、固定津贴、生效日期、调整原因。
- 默认生效日期为次月 1 日，可按公司规则修改。
- 保存后旧区间自动截断，新开一段；历史工资表不受影响（核算记录存了快照）。
- 同一天可以多次更正，不会撞唯一键（依赖第 17 节的 `active_key`）。
- 当前口径：**月中调薪当月整月按新薪计算**，不做按天分段（待办 T-17）。

如果调薪后发现当月工资已生成，需要重新生成（未锁定）或解锁后重新生成（已锁定）。

### 5.4 离职

路径：`人员管理 → 编辑`。

1. 在职状态改为「离职」。
2. **必须填写离职日期**。只改状态不填日期，生成时该员工会被跳过并提示“离职状态未填离职日期”。
3. 保存。

离职当月按实际计薪天数折算（日工资 = 月基本工资 ÷ 21.75，按离职日前的工作日数计算）。离职日期早于入职日期会被拒绝。

### 5.5 调动

路径：`人员管理 → 编辑 → 改部门`。

- 当前界面只支持**同一法人主体内改部门**；部门下拉只显示该员工所属主体下的部门。
- 界面没有“调动生效日”输入框，服务端默认按当天生效。
- 系统会关闭旧任职区间、追加新区间，类型 `TRANSFER`，工龄连续。
- 历史工资表保留原主体/部门快照，不受影响。
- **跨法人主体调动当前界面未开放**，需要调用 `PUT /api/v1/employees/{id}` 传 `companyId` 和 `effectiveDate`，或等二期调动单。

### 5.6 个税社保配置

#### 参保信息录入

路径：`人员管理 → 行内「薪酬档案」→ 抽屉「参保信息」页签 → 新增参保信息`。

填写：

- 参保城市：当前内置北京（BJ）、上海（SH）、深圳（SZ）；
- 缴费基数：留空 = 按近 12 期平均应发自动计算；填写则按填写值，并受城市基数上下限约束；
- 公积金比例：留空 = 用城市默认比例；填写如 `0.12`；
- 生效日期。

没有参保信息的员工，社保和公积金按 0 计算，页面会提示。

城市参数在 `pay_insurance_param` 表：

- 养老、医疗、失业个人比例；
- 公积金个人比例；
- 基数下限/上限；
- 医疗固定附加（如北京 +3 元）。

新城市或新年度比例需要 DBA 插表，当前没有维护界面。

#### 专项附加扣除录入

路径：同上抽屉 →「专项附加扣除」页签 → 新增。

类型固定六种：子女教育、婴幼儿照护、继续教育、住房贷款利息、住房租金、赡养老人。填写每月金额、生效起止日期、备注。同一员工同一类型同一生效日视为覆盖。

#### 系统参数

路径：`系统管理 → 系统参数`（需要 `sys:config:view` / `sys:config:edit`，通常只有 `admin`）。

| 参数 | 默认 | 作用 |
|---|---|---|
| `payroll.monthly-payable-days` | 21.75 | 月平均计薪天数；新期间建期时作为默认计薪天数，也用于不足月折算分母 |
| `payroll.seniority-pay-per-year` | 100 | 工龄工资每满一年金额 |
| `payroll.calendar.holidays` | 空 | 法定节假日，逗号分隔 `YYYY-MM-DD`；为空时回退环境变量 `PAYROLL_HOLIDAYS` |
| `payroll.system-version` | 1 | 只读，运维参数 |

注意：

- 修改参数**下次生成工资时生效**；已建期间保留自己的计薪天数 `hpd`，不会被追溯修改。
- 节假日为空时，不足月折算只排除周末，可能多算钱，页面会显示黄色警示。上线前务必录入当年法定节假日。
- 系统参数修改写审计。

### 5.7 三个新扣款项与“实发”计算链

工资项的 `direction`：1 = 增加（收入），2 = 减少（扣款）。`include_in_gross` 决定是否计入应发合计。

计算链：

```text
应发合计 gross = Σ(增加项且 include_in_gross=1 的金额)
扣款合计 deduction = Σ(所有减少项金额)
实发合计 net = gross - deduction
```

三个个税社保扣款项都是 `COMPUTED`、不可手工编辑：

| 科目 | 名称 | 计算 |
|---|---|---|
| `SOCIAL_INS` | 社保个人 | 缴费基数 × (养老 + 医疗 + 失业个人比例) + 医疗固定附加；基数受城市上下限约束。基数未填时取近 12 期平均应发，无历史则用本期应发 |
| `HOUSING_FUND` | 公积金个人 | 缴费基数 × 公积金比例（员工指定优先，否则城市默认） |
| `TAX` | 个人所得税 | 累计预扣法，见下 |

个税累计预扣：

```text
累计应纳税所得额 = 累计收入
                 − 5000 × 本年度已计薪月份数（含本期）
                 − 累计社保
                 − 累计公积金
                 − 累计专项附加扣除

累计应纳税额 = 累计应纳税所得额 × 预扣率 − 速算扣除数
本期个税 = max(累计应纳税额 − 累计已预扣, 0)
```

- 已计薪月份数 `paid_months` 只统计**已锁定**期间，不是日历月份。年中上线时第一次生成按 1 个月扣 5000，避免全公司个税为 0。
- 锁定期间时累加台账，解锁时减回；编制中/未锁定期间不进台账。
- 税率表 `pay_tax_bracket` 是 7 级工资薪金预扣率，schema 已初始化。
- 当前不处理年终奖单独计税、劳务报酬等特殊口径。

示例（验收数据）：应发 8600，社保 893.76，公积金 1018.00，个税 50.65，实发 6637.59。

如果个税为 0，先按 7.4 节排查，不要手工改 `TAX` 明细。

## 六、备份与恢复

### 6.1 备份什么

| 对象 | 位置 | 是否可重建 |
|---|---|---|
| MySQL 全库 | 容器 `payroll-mysql` 数据卷 | 否 |
| 原始导入文件 | `data/import/`（或 `payroll.storage.local-path`） | 可从源文件重导，但文件本身丢了就没了 |
| 密钥 | `.env` / systemd EnvironmentFile | **否**，丢失后历史证件号无法解密 |
| 应用 jar / 前端 dist | 构建产物 | 可重新构建 |
| 部署配置 | nginx、systemd、compose | 可重写 |

### 6.2 MySQL 备份

```bash
set -a; source .env; set +a
mkdir -p backup

docker exec -e MYSQL_PWD="$MYSQL_ROOT_PASSWORD" payroll-mysql \
  mysqldump -uroot \
  --single-transaction \
  --routines --triggers \
  --default-character-set=utf8mb4 \
  payroll | gzip > "backup/payroll-$(date +%F-%H%M).sql.gz"
```

成功标志：文件非空，`gzip -t` 通过。

```bash
ls -lh backup/
gzip -t backup/payroll-*.sql.gz
```

说明：

- `--single-transaction` 对 InnoDB 做一致性快照，不锁表，可在业务低峰执行。
- 备份文件包含全部工资明文，必须加密存放、限制权限（`chmod 600`），不要放在 Web 目录。
- 恢复前先确认备份对应的代码版本和 schema 版本。

建议频率：

- 每日 02:00 全量一次；
- 每次升级/迁移前手工一次；
- 保留 90 天，每周一份异地/离线；
- 每季度做一次恢复演练。

cron 示例：

```cron
0 2 * * * cd /opt/payroll && set -a && . ./.env && set +a && docker exec -e MYSQL_PWD="$MYSQL_ROOT_PASSWORD" payroll-mysql mysqldump -uroot --single-transaction --routines --triggers --default-character-set=utf8mb4 payroll | gzip > backup/payroll-$(date +\%F).sql.gz
```

### 6.3 恢复

1. 停止应用，避免恢复过程中有写入：

```bash
sudo systemctl stop payroll
```

2. 确认备份文件完整：

```bash
gzip -t backup/payroll-2026-11-28.sql.gz
```

3. 重建库（会清空现有数据，务必确认备份可用）：

```bash
set -a; source .env; set +a
docker exec payroll-mysql mysql -uroot -p"$MYSQL_ROOT_PASSWORD" \
  -e "DROP DATABASE IF EXISTS payroll; CREATE DATABASE payroll DEFAULT CHARSET utf8mb4;"
```

4. 导入：

```bash
gunzip -c backup/payroll-2026-11-28.sql.gz | \
docker exec -i payroll-mysql mysql -uroot -p"$MYSQL_ROOT_PASSWORD" \
  --default-character-set=utf8mb4 payroll
```

5. 校验：

```bash
docker exec payroll-mysql mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -N payroll \
  -e "SELECT COUNT(*) FROM sys_user; SELECT COUNT(*) FROM pay_record; SELECT MAX(period_ym) FROM pay_period;"
```

6. 启动应用，用 `admin` 登录，抽查一个已锁定期间的报表合计。

### 6.4 丢失后不可恢复的内容

- **加密密钥**：`PAYROLL_AES_KEY` 丢失后，`emp_employee.id_no_cipher` / `mobile_cipher` 永远无法解密，只剩掩码和哈希。备份数据库时必须单独保管密钥，且不要和备份放在同一个包/同一台机器。
- **盲索引密钥**：`PAYROLL_ID_SALT` 丢失后，无法再对已有人员做证件号查重，新增人员可能撞不出重复。
- **审计日志**：`pay_audit_log` 只增不改，数据库里没有删除入口；如果备份丢失或被 DBA 直接删除，操作追溯能力不可恢复。
- **已锁定工资表**：逻辑删除 + 快照设计意味着没有物理删除入口，但数据库损坏且无备份时无法恢复。
- **期初个税累计**：`pay_ytd` 的期初数据来自旧系统，系统无法从工资明细反推出旧系统已预扣税额，必须由财务留档。
- **导入原始文件**：`data/import/` 丢失后，如果数据库还在，工资结果不受影响；但无法重放“当时上传的是哪一版文件”。

留存要求：工资表按会计档案长期保存；审计日志建议至少保存 30 年或按客户合规要求执行；系统本身不提供归档删除功能（`ARCHIVED` 状态当前不可达，见待办 T-10）。

## 七、故障排查（按症状组织）

### 7.1 mvn 报“找不到符号 getXxx / log”

原因：构建 JDK 不是 17，Lombok 注解处理器没执行。

处理：

```bash
java -version
mvn -v
export JAVA_HOME=$(/usr/libexec/java_home -v 17)   # macOS
# Linux: export JAVA_HOME=/usr/lib/jvm/temurin-17-jdk-amd64
mvn -DskipTests clean compile
```

确认 `mvn -v` 里的 Java version 是 17。清理 `target/` 后重试。

### 7.2 前端打不开 / 接口 503

原因：本机代理拦截 localhost，或后端没起，或 Vite 代理目标不对。

处理：

```bash
curl --noproxy '*' -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/api/v1/nope
```

- 返回 404：后端正常（不存在的路径现在正确返回 404）。
- 返回 000/502/503：后端没起或代理拦截。

检查后端进程和端口：

```bash
lsof -iTCP:8080 -sTCP:LISTEN
docker ps
tail -n 100 logs/payroll.log
```

浏览器把 `localhost,127.0.0.1` 加入代理例外。确认 `frontend/vite.config.ts` 的代理目标是 `http://localhost:8080`。

### 7.3 登录返回 429

原因：登录失败渐进延迟。同一「用户名 + IP」15 分钟内失败 5 次后，每次登录先等 2 秒，仍失败返回 429；失败 10 次后等待 10 秒。不是永久锁定。

处理：

- 等 2–10 秒后重试；
- 或换一个账号/换一台机器（限流键包含 IP）；
- 确认密码是否正确；重置密码需要管理员在「用户管理」操作。

查看是否触发审计：

```sql
SELECT * FROM pay_audit_log
 WHERE field_name = 'login_blocked'
 ORDER BY id DESC LIMIT 20;
```

### 7.4 生成后个税为 0

按顺序排查，不要直接改 `TAX` 明细（该科目不可手工编辑）。

```bash
set -a; source .env; set +a
```

1. 看该员工本期记录和三个扣款项（把 `E200` 换成实际工号）：

```sql
SELECT r.id, r.emp_no, r.emp_name, r.gross_amount, r.deduction_amount, r.net_amount
  FROM pay_record r
  JOIN pay_period p ON p.id = r.period_id
 WHERE p.period_ym = '2026-11' AND r.emp_no = 'E200' AND r.deleted = 0;

SELECT i.item_code, i.item_name, i.amount, i.source
  FROM pay_record_item i
  JOIN pay_record r ON r.id = i.record_id
  JOIN pay_period p ON p.id = r.period_id
 WHERE p.period_ym = '2026-11'
   AND r.emp_no = 'E200'
   AND r.deleted = 0
   AND i.item_code IN ('SOCIAL_INS','HOUSING_FUND','TAX');
```

2. 看年度台账：

```sql
SELECT * FROM pay_ytd
 WHERE employee_id = (SELECT id FROM emp_employee WHERE emp_no = 'E200')
   AND tax_year = 2026;
```

3. 看参保信息：

```sql
SELECT * FROM emp_social_insurance
 WHERE employee_id = (SELECT id FROM emp_employee WHERE emp_no = 'E200')
 ORDER BY effective_from DESC;
```

4. 看税率表和城市参数是否为空：

```sql
SELECT COUNT(*) FROM pay_tax_bracket;
SELECT * FROM pay_insurance_param WHERE city_code = 'BJ' AND status = 1;
```

5. 看专项附加扣除是否异常偏大：

```sql
SELECT * FROM emp_special_deduction
 WHERE employee_id = (SELECT id FROM emp_employee WHERE emp_no = 'E200');
```

常见原因与处理：

| 现象 | 原因 | 处理 |
|---|---|---|
| 三个扣款项都不存在 | 工资项 `SOCIAL_INS/HOUSING_FUND/TAX` 缺失 | 执行升级第 20 节 |
| 社保/公积金为 0，个税也为 0 | 应发低于 5000，或专项扣除/已计薪月份把应纳税所得额压到 0 | 核对 `gross_amount`、`paid_months`、专项扣除 |
| `paid_months` 明显大于实际 | 期初累计录错或重复累加 | 修正 `pay_ytd.paid_months`，重新生成 |
| 税率表为空 | 第 20 节没执行或数据被删 | 补执行第 20 节的税率 INSERT |
| 员工没有工资记录 | 无薪酬档案，生成时被跳过 | 配薪酬档案后重新生成，查 `pay_run_skip` |

查跳过明细：

```sql
SELECT s.emp_no, s.emp_name, s.reason
  FROM pay_run_skip s
  JOIN pay_run r ON r.id = s.run_id
  JOIN pay_period p ON p.id = r.period_id
 WHERE p.period_ym = '2026-11'
 ORDER BY s.id;
```

### 7.5 报表查历史年份为空

原因：该期间在个税功能上线前锁定，没有 `pay_ytd` 台账；或该年度本来就没有已锁定期间。

处理：

1. 确认是否有已锁定期间：

```sql
SELECT period_ym, status FROM pay_period
 WHERE period_ym LIKE '2025-%' ORDER BY period_ym;
```

2. 确认台账：

```sql
SELECT COUNT(*) FROM pay_ytd WHERE tax_year = 2025;
```

3. 如果为 0 且财务需要个税核对，按 3.5 节录期初累计。注意：期初累计只能补“上线前”的数据，已经锁定且未进台账的期间需要人工核对后录入，不能简单重算。

4. 「个税核对」页默认查上一年，对没有台账的年份显示空并有三条提示，属正常。

### 7.6 接口全部 500，日志有连接超时

原因：MySQL 容器停了或不可达。

处理：

```bash
docker ps -a --filter name=payroll-mysql
docker start payroll-mysql
docker logs --tail 100 payroll-mysql
```

确认端口：

```bash
nc -z 127.0.0.1 3307 && echo OK
```

应用 Hikari 连接超时 3 秒，数据库不可用时会快速返回 503「数据库繁忙」，而不是把 Tomcat 线程拖死。恢复数据库后应用一般无需重启，连接池会自动重连。

### 7.7 不存在的路径返回 500

原因：运行的是 404 修复前的旧 jar。

处理：

```bash
curl --noproxy '*' -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/api/v1/definitely-not-exist
```

当前版本应返回 `404`。如果返回 `500`，重新构建并替换 jar：

```bash
mvn -DskipTests clean package
sudo systemctl restart payroll
```

### 7.8 生成时所有员工失败：表不存在 / 列不存在

症状日志：

```text
计算失败：Table 'payroll.pay_ytd' doesn't exist
计算失败：Unknown column 'paid_months' in 'field list'
```

原因：升级脚本第 20/21 节没执行。

处理：

```sql
SHOW TABLES LIKE 'pay_ytd';
SHOW COLUMNS FROM pay_ytd LIKE 'paid_months';
```

缺表补执行第 20 节，缺列补执行第 21 节。执行后重新生成。

### 7.9 锁定期间失败

常见 409/400：

| 提示 | 原因 | 处理 |
|---|---|---|
| 上次生成有 N 人失败 | 有失败员工未处理 | 看生成进度失败明细，修复后重新生成 |
| 最近一次生成未成功 | 最近 run 是 FAILED/RUNNING | 等生成结束或重新生成 |
| 期间正在生成 | 租约未过期 | 等生成完成 |
| 锁定人不能是本期间的编制人 | 自己生成自己锁 | 换 `hr02` 或另一有 lock 权限的账号 |
| 期间尚未生成 | 状态还是 DRAFT | 先点生成 |

### 7.10 全新环境启动后没有表

原因：数据卷不是空的，MySQL 不会重复执行 `docker-entrypoint-initdb.d`。

处理（会清空数据，仅限全新环境）：

```bash
docker compose down -v
docker compose up -d
```

等待 healthy 后重新检查表数量。生产环境不要这样做，应手工导入 schema。

### 7.11 导入中文乱码

原因：导入时没带字符集。

处理：所有 `mysql` 导入命令都加 `--default-character-set=utf8mb4`。检查表字符集：

```sql
SELECT table_name, table_collation
  FROM information_schema.tables
 WHERE table_schema = 'payroll' AND table_collation NOT LIKE 'utf8mb4%';
```

应无输出。已有乱码数据需要重新导入，不能靠改字符集修复。

### 7.12 调薪保存报唯一键冲突

提示：`Duplicate entry ... for key 'uk_emp_effective'`

原因：升级第 17 节没执行，同一天第二次更正会撞键。

处理：

```sql
SHOW COLUMNS FROM emp_comp_profile LIKE 'active_key';
```

无输出则补执行第 17 节。执行后重试。

### 7.13 查看证件号 403 / 解锁 403 / 系统参数菜单不见

| 症状 | 缺失项 | 处理 |
|---|---|---|
| `hr01` 查看证件号 403 | `payroll:sensitive:view` | 执行升级第 19 节 |
| `hr02` 解锁 403 | `payroll:period:unlock` | 执行升级第 13 节 |
| `admin` 看不到系统参数 | `sys:config:view` | 执行 3.4 节的补充 SQL |
| 老环境没有管理员 | `SYS_ADMIN` 角色/权限 | 执行升级第 11 节 |

核对角色权限：

```sql
SELECT r.role_code, g.perm_code
  FROM sys_role r
  JOIN sys_role_grant g ON g.role_id = r.id
 WHERE r.role_code IN ('PAYROLL_CLERK','PAYROLL_REVIEWER','SYS_ADMIN')
 ORDER BY r.role_code, g.perm_code;
```

## 八、安全须知

### 8.1 谁能看工资：数据范围矩阵

数据范围挂在角色上，一个用户多角色时取最宽：

| 数据范围 | 含义 | 典型角色 | 能看到什么 |
|---|---|---|---|
| `ALL` | 集团全部主体 | 集团 HR、审计、薪酬专员/复核（种子角色） | 所有主体的工资 |
| `COMPANY` | 本公司全部部门 | 分公司 HR | 本主体全部工资 |
| `DEPT_SUB` | 本部门及下级 | 部门主管 | 本部门树内、且仅已锁定/归档期间 |
| `DEPT` | 本部门 | 部门负责人 | 本部门 |
| `SELF` | 仅本人 | 普通员工 | 自己的工资，且仅已锁定/归档期间 |

种子角色：

- `PAYROLL_CLERK`（hr01）：`ALL`，可编辑、导入、导出、查看敏感字段；
- `PAYROLL_REVIEWER`（hr02）：`ALL`，可查看、锁定、解锁、导出；
- `SYS_ADMIN`（admin）：`ALL`，但只有 `sys:*`，没有工资权限；
- `DEPT_MANAGER`：`DEPT_SUB`；
- `EMPLOYEE`：`SELF`。

非集团/公司范围的账号，期间列表只显示已锁定/已归档期间；期间合计按可见记录重算，不会回落到全公司合计。

### 8.2 敏感字段与审计

- 证件号、手机号在列表页只显示掩码（`****1234`、`138****8000`）。
- 查看完整值需要 `payroll:sensitive:view`，且每次调用 `GET /api/v1/employees/{id}/sensitive` 都写一条 `VIEW` 审计；界面会提示“本次查看已记入审计日志”。
- 数据库存的是 AES-256-GCM 密文 + HMAC 盲索引，不是明文；同一明文每次加密结果不同。
- 审计记录操作人、时间、IP、User-Agent、业务对象、字段、前后值（敏感值不写明文）。
- 解锁必须填写原因，原因写入 `pay_audit_log`；锁定/解锁/导出/改密/权限变更都留痕。
- 审计写失败会阻断业务操作，这是刻意的合规设计。

查询审计：

```sql
SELECT created_at, operator_name, biz_type, biz_id, action, field_name, old_value, new_value, ip
  FROM pay_audit_log
 ORDER BY id DESC
 LIMIT 100;
```

按人查：

```sql
SELECT * FROM pay_audit_log
 WHERE operator_name = '张三'
 ORDER BY id DESC;
```

当前没有审计日志查询界面，只能通过数据库只读账号查询。

### 8.3 内控规则（代码硬校验）

- 锁定人不能是本期间编制人；
- 有失败员工的期间不能锁定；
- 已锁定/已归档期间所有写接口返回 409；
- 已归档期间不可解锁（当前版本没有归档入口）；
- 低权管理员不能重置/停用/删除权限更高的账号；
- 不能停用/删除自己的账号；
- 不能删除最后一个系统管理员；
- 导出必须单独授权 `payroll:export`，且只允许已锁定期间。

### 8.4 部署层约束：数据库直连无留痕

这是应用层解决不了的问题，必须在部署层补：

- **只读账号**：运维/审计查询用 `payroll_ro`（仅 `SELECT`），不要用应用账号或 root。
- **网络隔离**：MySQL 只监听 `127.0.0.1:3307`，禁止办公网直连；需要远程连接时走 SSH 隧道 + 跳板机。
- **审计外发**：开启 MySQL 通用日志/审计插件，或通过网络侧数据库审计设备记录所有 SQL；日志单独存放，DBA 不可删改。
- **权限分离**：应用账号只有 DML；DDL 由 DBA 在变更窗口执行；备份账号单独。
- **备份加密**：备份文件含全量工资明文，必须加密、限权、异地保存。
- **密钥分离**：数据库口令、AES 密钥、盲索引密钥、token 密钥四者独立保管，不互相派生，不放进同一个备份包。

应用只能保证“通过应用做的操作有审计”；直接 `mysql` 客户端改一条 `pay_record.gross_amount` 不会产生任何 `pay_audit_log`。要满足财务审计要求，必须同时落地上述部署层措施。
