# 个税与社保公积金设计

> 状态：设计稿 ｜ 日期：2026-11-27
> 前置：当前系统「实发 = 应发 − 扣款」，没有个税社保。本设计补上，让「实发」名副其实。

## 一、为什么必须做

资深 HR 顾问的原话：

> 「实发里没有个税社保，财务真按这个数打款全公司都要多发。」

当前 1,874 人应发 36,520,605.92，实发也是 36,520,605.92。加上个税社保后，实发会显著低于应发——**这才是真实发放金额**。

## 二、口径（中国大陆，居民个人）

### 2.1 计算顺序

```
1. 应发合计       = Σ 增项（基本工资 + 津贴 + 绩效 + 奖金 + …）
2. 社保个人部分   = f(缴费基数, 参保城市参数)
3. 公积金个人部分 = f(缴费基数, 缴存比例)
4. 应税所得       = 应发 − 社保个人 − 公积金个人 − 专项附加扣除
5. 个人所得税     = 累计预扣法（见 2.3）
6. 实发           = 应发 − 社保个人 − 公积金个人 − 个税 − 其他扣款
```

### 2.2 社保公积金（个人部分）

| 险种 | 个人比例 | 说明 |
|---|---|---|
| 养老保险 | 8% | 基数上下限按城市 |
| 医疗保险 | 2% | 部分城市另有 3 元大病 |
| 失业保险 | 0.5% | 各地不同（0.2%–1%） |
| 住房公积金 | 5%–12% | 单位与个人同比例，由企业申报 |

缴费基数默认 = 员工上年月平均工资，限制在 `[城市下限, 城市上限]`。
**允许 HR 手工指定基数**（新入职、调薪、跨年基数调整的场景）。

### 2.3 个人所得税（累计预扣法）

居民个人工资薪金所得，按年累计预扣：

```
累计应纳税所得额 = 累计收入
                 − 累计减除费用（5,000 × 本年度已发月份数）
                 − 累计专项扣除（累计社保个人 + 累计公积金个人）
                 − 累计专项附加扣除
                 − 累计其他扣除

本期应预扣 = 累计应纳税所得额 × 预扣率 − 速算扣除数 − 累计已预扣预缴
```

预扣率表（工资薪金预扣率，与综合所得税率表同）：

| 累计应纳税所得额（元） | 预扣率 | 速算扣除数 |
|---|---|---|
| ≤ 36,000 | 3% | 0 |
| 36,000 – 144,000 | 10% | 2,520 |
| 144,000 – 300,000 | 20% | 16,920 |
| 300,000 – 420,000 | 25% | 31,920 |
| 420,000 – 660,000 | 30% | 52,920 |
| 660,000 – 960,000 | 35% | 85,920 |
| > 960,000 | 45% | 181,920 |

**关键点**：个税是**年度累计**属性，不是"当月收入 × 税率"。所以：
- 1–6 月税率低、7–12 月逐步进入高税率档
- 12 月的个税可能显著高于 1 月
- **必须依赖历史期间的累计数据**

### 2.4 专项附加扣除

| 项目 | 常见额度 |
|---|---|
| 子女教育 | 2,000 元/月/子女 |
| 3 岁以下婴幼儿照护 | 2,000 元/月/子女 |
| 继续教育 | 400 元/月（学历）或 3,600 元/年（职业资格） |
| 住房贷款利息 | 1,000 元/月 |
| 住房租金 | 800 / 1,100 / 1,500 元/月（按城市档） |
| 赡养老人 | 3,000 元/月（独生）或分摊 |
| 大病医疗 | 年度汇算时扣除，不按月预扣 |

## 三、数据模型

### 3.1 新增表

| 表 | 用途 |
|---|---|
| `pay_tax_bracket` | 预扣率表（可配置，年度生效） |
| `pay_insurance_param` | 城市 × 险种 × 比例 / 基数上下限（可配置） |
| `emp_social_insurance` | 员工参保信息：参保城市、缴费基数、公积金比例、生效区间 |
| `emp_special_deduction` | 员工专项附加扣除（按项、按月额、生效区间） |
| `pay_ytd` | 年度累计台账（累计收入/累计减除/累计扣除/累计已预扣），按员工×年度一行 |

### 3.2 新增工资项

| 编码 | 名称 | 类别 | 方向 |
|---|---|---|---|
| `SOCIAL_INS` | 社保个人 | COMPUTED | 扣款 |
| `HOUSING_FUND` | 公积金个人 | COMPUTED | 扣款 |
| `TAX` | 个人所得税 | COMPUTED | 扣款 |

### 3.3 现有表变更

- `emp_employee` 不需要加字段（参保信息放独立表，带生效区间）
- `pay_record` 的 `net_amount` 语义不变（= 应发 − 全部扣款），但现在扣款里真正包含社保/公积金/个税

## 四、关键设计决策

### D1 累计数据从哪来

**方案 A（推荐）**：`pay_ytd` 台账表，每期锁定时累加。
- 优点：查询快，不依赖历史期间是否还在
- 风险：解锁重算需要回滚累计

**方案 B**：每次计算时实时汇总已锁定期间的记录。
- 优点：无冗余
- 风险：2000 人 × 12 月，每期生成要扫历史，慢

**决策：方案 A**，解锁时按 `pay_ytd` 减去该期贡献值。

### D2 年度切换

- 每年 1 月自动把累计清零（新的 `pay_ytd` 行，year+1）
- 1 月发的是上一年 12 月的工资时，按**发放期间所属年度**归集

⚠️ **这条与「年度按归属期间归集」的既有口径冲突，需要业务确认**：
个税是按**发放月份**累计的（税法口径），而报表的年度归属是按**费用归属期间**。
两者可能不同。**建议：个税累计按发放期间，报表年度按归属期间，各自正确。**

### D3 社保基数

默认按上年月平均工资，但：
- 新入职员工无上年数据 → 按首月应发工资
- 每年 7 月社保基数调整 → 需要批量调整能力

**MVP 决策**：默认按「员工最近 12 个已锁定期间的平均应发」，无历史则用当月应发；允许 HR 手工覆盖。

### D4 年终奖（全年一次性奖金）

**本期不做**。单独计税政策是否延续、怎么计税，需业务确认。

## 五、与现有系统的衔接

| 环节 | 变更 |
|---|---|
| 工资项字典 | 新增 3 个 COMPUTED 扣款项 |
| 计算引擎 | `PayrollCalculator` 新增两项输入：社保公积金、个税；**个税依赖累计数据，不在纯函数里算**——由 Service 层算好传入 |
| 生成流程 | 生成时先算应发 → 查参保信息 → 算社保 → 查累计 → 算个税 → 落明细 |
| 锁定流程 | 锁定时把本期数据累加进 `pay_ytd` |
| 解锁流程 | 解锁时从 `pay_ytd` 减回 |
| 报表/导出 | 「实发」现在名副其实，但需注明「已扣个税社保，不含单位部分」 |
| 系统参数 | 新增个税起征点、社保参数的城市列表 |

## 六、边界与风险

| 风险 | 处理 |
|---|---|
| 累计预扣算错 → 员工多缴/少缴 | 必须有"年度汇算"核对报表；金额逐分可复算 |
| 社保基数跨年调整 | 提供批量调整入口，按生效月份 |
| 员工跨城市调动 | 参保城市变更需带生效区间 |
| 年中入职 | 累计减除费用从入职月起算，不是从 1 月 |
| 补发工资 | 补发计入发放月份的收入，影响当月累计 |
| 离职清算 | 最后一个月照常计算，之后不再累计 |

## 七、实施顺序

1. **参数表与配置**：`pay_tax_bracket`、`pay_insurance_param` 建表 + 系统参数页可维护
2. **员工参保信息**：`emp_social_insurance` + 人员档案页可维护
3. **专项附加扣除**：`emp_special_deduction` + 录入界面
4. **计算**：社保公积金 → 个税（累计）→ 实发
5. **累计台账**：`pay_ytd` + 锁定/解锁联动
6. **核对报表**：按人列出全年累计，可逐月核对

## 八、需要业务确认的三件事

| # | 问题 | 影响 |
|---|---|---|
| Q1 | 社保参保城市有哪几个？（决定要内置哪些城市的参数） | 中 |
| Q2 | 个税累计按「发放月份」还是「费用归属月份」？ | **高**（影响每个月扣多少） |
| Q3 | 专项附加扣除由 HR 录入还是员工申报？（员工不登录 → 只能 HR 录入） | 低（默认 HR 录入） |
